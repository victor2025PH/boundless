# 信用查机器人（TrustCheck Bot）— 多视角优化方案

> 基于三份需求文档的深度分析与整合，从全栈技术、UI/UX、数据库、功能、代码质量、安全、运维、测试、商业九大视角输出的统一优化方案（无代码，仅方案层）。

---

## 一、整合结论与统一取舍

### 1.1 文档冲突与统一决策

| 冲突点 | 文档A | 文档B | 文档C | 优化决策 |
|--------|--------|--------|--------|----------|
| 信用分刻度 | 等级（低/中/高） | 300–900 分 | 0–100 分 | **统一为 0–100 展示 + 内部 300–900 计算**：对外简单易懂，对内可扩展权重与模型 |
| 查询记录 | 保留最近 10 次 | 未明确 | 不存查询记录（隐私） | **匿名化存储 + 可选“我的最近查询”**：满足行为分析与合规，用户可选关闭 |
| 数据来源声明 | 可授权群 + 链上 | 127 部手机语料 | 匿名采集 | **统一口径**：仅“用户举报 + 可授权数据 + 公开链上”，不对外宣称未授权群/设备采集 |
| MVP 周期 | 2–3 周 | 分阶段 | 7–10 天 | **MVP 10–14 天**：7 天过紧，14 天可含基础测试与一次小迭代 |

### 1.2 产品定位（统一表述）

- **一句话**：面向 Telegram 的免费信用查询工具，输入对方 TG ID / @username / 钱包地址，返回风险等级、信用分与黑名单提示，一键防诈。
- **核心价值**：即时、可量化、可追溯；为后续 Mini App、担保/ Escrow 引流并积累数据。
- **目标区域**：菲律宾及东南亚（如 Quezon City 周边 USDT-PHP 等场景），兼顾全球 OTC/游戏账号/跨境场景。
- **原则**：简单优先、隐私合规、API 先行、Bot 与 Mini App 共享后端。

## 二、全栈技术总监视角（Architecture & Tech Lead）

### 2.1 系统边界与分层

- **表现层**：Telegram Bot（aiogram 3.x）、预留 Mini App（TMA SDK + React/Vue）。
- **网关/聚合层**：同一套 REST API（FastAPI），Bot 与 Mini App 共用，避免两套逻辑。
- **领域层**：查询服务、评分服务、举报服务、黑名单服务、订阅/提醒服务。
- **数据层**：PostgreSQL 主库 + Redis（缓存/限流/会话），SQLite 仅作本地开发。
- **外部依赖**：TG API（公开信息）、可选链上索引（TRC20/TON）、采集/语料管道（独立部署，与主服务解耦）。

### 2.2 技术栈统一建议

- **Bot**：Python 3.10+，aiogram（异步、Inline/卡片支持）。
- **后端**：FastAPI + Uvicorn；任务队列 Celery（Python）或 Bull（若 Node 介入）。
- **数据库**：SQLAlchemy 2.x + PostgreSQL；Redis 用于缓存 check 结果、限流、会话。
- **采集/语料**：独立进程（如 Telethon），与主服务网络/权限隔离，数据经脱敏后再入库。
- **Mini App**：Telegram Web App SDK + React 或 Vue，仅前端，调用同一 REST API。
- **部署**：单区域优先（如菲律宾/新加坡节点），保证 <3s P95 延迟；多 Bot Token 轮换由网关或 Bot 层配置。

### 2.3 接口统一与版本策略

- **基线路径**：`/v1/`，Bot 与 Mini App 均调用 `/v1/*`。
- **核心接口**：`GET /v1/check`（query 参数：tg_id / username / wallet）、`GET /v1/mycredit`、`POST /v1/report`、`GET /v1/mini-app/profile`（Mini App 专用，可返回更丰富结构）；管理端 `GET /v1/admin/stats`、黑名单/反馈管理用独立权限与路径（如 `/v1/admin/*`）。
- **响应**：统一 envelope（如 `{ data, meta, error }`），便于前端与 Bot 解析一致。

### 2.4 扩展与演进

- **Phase 1（MVP）**：Bot + 规则引擎评分 + 黑名单 + 基础举报。
- **Phase 2**：接入语料/风控模型（AI），规则与模型可配置切换。
- **Phase 3**：Mini App（信用名片、雷达图、担保跳转）。
- **Phase 4**：钱包绑定、链上履约、勋章/质押（如 TON），与合规同步设计。

## 三、UI/UX & Design 视角（交互与体验）

### 3.1 信息架构统一

- **主路径**：/start → 说明与“立即查询” → /check \<id|@user|wallet\> → 结果卡片 → 可选“举报/纠错”“用担保交易”（Mini App）。
- **辅助路径**：/mycredit（自查）、/help（FAQ + 举报入口）、/history（可选，最近 10 次查询，需隐私选项）。
- **结果卡片要素（Bot）**：风险等级（低/中/高/极高）+ 信用分（0–100）+ 3–5 条简短提示（如“新账号”“高危群活跃”“黑名单匹配”）+ 操作按钮（举报、纠错、订阅提醒、跳转 Mini App）。

### 3.2 多语言与可访问性

- **MVP**：英文 + Tagalog（菲律宾语），所有用户可见文案与按钮走 i18n，避免硬编码。
- **Mini App**：同一套多语言，支持后续扩展更多语种。
- **可访问性**：结果以文字为主、图为辅；Mini App 雷达图需配文字摘要，满足“仅读文字”也能理解风险。

### 3.3 信任与合规传达

- **首屏/帮助页**：明确写出“数据来源”（举报 + 可授权数据 + 公开链上）、用途（防诈）、是否存查询记录及用户可选策略。
- **结果页**：避免绝对断言（如“是骗子”），改为“风险较高，建议谨慎”“曾多次被举报”等可验证表述，并留纠错入口。

### 3.4 错误与边界状态

- **查无此人**：友好提示“未找到该 ID/地址的记录”，并说明“无记录不代表安全”。
- **限流/维护**：统一提示语与重试建议，Bot 与 Mini App 一致。
- **举报/反馈提交后**：明确“已收到，我们会核实”的反馈，并可选返回结果页或帮助页。

## 四、Database & Data Integrity 视角（数据库与数据一致性）

### 4.1 核心表与职责

- **users（或 entities）**：被查询主体。字段建议：`id (PK)`、`tg_id`（唯一）、`username`、`wallet_addresses`（JSON 或关联表）、`register_date`、`is_premium`、`risk_score`（0–100）、`risk_level`（enum）、`high_risk_group_count`、`blacklist`（bool）、`tips`（JSON）、`label`（商户/用户/高危）、`updated_at`。来源：采集管道写入或首次查询时补齐。
- **blacklist**：`tg_id (PK)`、`reason`、`evidence_refs`（链接或存储路径）、`source`（user_report/admin）、`status`（pending/confirmed/rejected）、`added_at`、`confirmed_at`。
- **reports（举报/维权）**：`id (PK)`、`reporter_tg_id`、`target_tg_id`、`evidence_data`（JSON：tx_hash、screenshot_url、description）、`status`（pending/verified/rejected）、`created_at`。同一 target 多笔 verified 可驱动自动升风险或入黑名单。
- **wallet_entity_graph（ID-钱包关联）**：`tg_id`、`wallet_address`、`chain`（TRC20/TON 等）、`first_seen`、`last_seen`。用于“换号不换地址”的关联分析。
- **query_log（若保留）**：匿名化设计。`id`、`query_hash`（如 hash(tg_id + day)）、`result_risk_level`、`created_at`。不存真实 tg_id，仅用于统计与行为分析；需在隐私政策中说明并支持“不记录”选项。
- **feedback（纠错/举报误报）**：`id`、`reporter_tg_id`、`target_tg_id`、`reason`、`evidence_refs`、`status`、`created_at`。
- **subscriptions（风险提醒）**：`id`、`subscriber_tg_id`、`target_tg_id`、`notify_on`（blacklist_change/risk_up）、`created_at`。

### 4.2 一致性策略

- **评分与等级**：由定时任务或事件驱动（新举报、黑名单更新）重算 `users.risk_score` / `risk_level` / `tips`，避免每次查询实时算导致不一致；查询时以表为准，必要时加短 TTL 缓存。
- **黑名单与 reports**：reports 核实后写入或更新 blacklist；blacklist 更新触发订阅通知与 users 表更新。
- **唯一与约束**：tg_id 在 users/blacklist 上唯一；reports 允许同一 (reporter, target) 多笔（不同证据）；wallet_entity_graph 使用 (tg_id, wallet_address, chain) 唯一。

### 4.3 审计与可追溯

- **敏感表**：blacklist、reports、feedback 的增删改记入 audit_log（who、when、what、old/new 关键字段），便于合规与纠纷处理。
- **数据保留**：明确 report/blacklist 的保留年限与匿名化策略，与隐私政策一致。

## 五、Functionality & Logic 视角（核心功能与逻辑）

### 5.1 查询逻辑（/check）

- **输入**：tg_id（数字）、@username、或钱包地址（TRC20/TON）；支持单一查询，后端解析并归一化为 tg_id 或 entity_id。
- **解析**：username → 调 TG API 解析为 tg_id（需处理未找到、隐私限制）；wallet → 查 wallet_entity_graph 反查 tg_id，若无则仅返回“该地址关联记录”或“无记录”。
- **输出**：风险等级（低/中/高/极高）、信用分（0–100）、tips 列表、是否在黑名单、可选“维权证据”摘要（不直接暴露截图 URL，可经后台审核后展示）。
- **性能**：读 users + blacklist + 缓存，目标 P95 <3s；复杂关联（如 graph）可异步或缓存 5–15 分钟。

### 5.2 评分与风险等级（规则引擎 MVP）

- **维度与权重（可配置）**：账号年龄、Premium、高危群数量、黑名单、被举报次数、链上履约（若有）、近期活跃。权重表存配置中心或 DB，便于 A/B 与后期模型替代。
- **等级划分**：0–100 分映射到低/中/高/极高；阈值可调（如 0–35 极高，36–55 高，56–75 中，76–100 低）。
- **tips 生成**：规则驱动（如“注册<3 个月”“高危群≥10”“已被 N 人举报”），每条 tip 带类型与置信度，便于后续 AI 替换为模型输出。

### 5.3 举报与黑名单

- **举报**：必填 target、reason、可选 tx_hash、截图 URL、描述。提交后 status=pending；多源同一 target 达阈值或管理员核实 → status=verified，并更新 users/blacklist。
- **黑名单**：仅由系统根据规则或管理员写入；展示时带“理由摘要”与“证据可查”说明，避免未核实即展示细节。
- **纠错**：结果页“信息有误”指向 feedback，与 report 区分；feedback 可驱动人工复核或模型再训练。

### 5.4 订阅提醒

- **维度**：按 target 订阅；事件类型：加入黑名单、风险等级上调。
- **实现**：blacklist/用户 risk 更新时扫 subscriptions 表，发 TG 消息（模板化）；限频（同一用户同一 target 24h 内不重复提醒）。

### 5.5 管理能力

- **命令或 API**：/stats 或 GET /v1/admin/stats（日/总查询量、用户数）；黑名单增删（/blacklist add|remove 或 REST）；举报/feedback 列表与状态更新。所有管理接口需强认证与审计。

## 六、Code Quality 视角（开发质量与可维护性）

### 6.1 分层与依赖

- **严格分层**：Bot 只调 API Client；API 层只调 Service；Service 调 Repository/外部；不跨层依赖。
- **配置外置**：环境变量 + 配置文件（评分权重、阈值、限流参数、TG Token），无硬编码密钥与业务参数。

### 6.2 可测试性

- **接口**：/v1/check、/v1/report 等具备明确入参/出参，便于契约测试与 Mock。
- **评分逻辑**：规则引擎纯函数化（输入用户特征 → 输出分数与 tips），单元测试覆盖边界（0 举报、大量举报、无群数据等）。
- **Bot**：命令与回调用 Handler 抽象，可单测逻辑；TG 请求用 Mock 或 Test Server。

### 6.3 文档与协作

- **API**：OpenAPI 3.0（FastAPI 自动生成），含请求/响应示例与错误码说明。
- **README**：本地启动、环境变量、迁移命令、测试命令；数据模型变更需在 CHANGELOG 或 ADR 中记录。

### 6.4 迭代与兼容

- **API 版本**：/v1 保持兼容；新增字段用可选；破坏性变更走 /v2 并公告。
- **数据库**：迁移脚本（如 Alembic）版本化，可回滚；大表变更需评估锁与备份。

## 七、Security 视角（安全与合规）

### 7.1 数据与隐私

- **最小化**：只存业务必需字段；不抓未授权群内容；语料采集与主服务隔离，脱敏后再入库。
- **查询日志**：若保留则匿名化（不可逆 hash 或聚合），且提供“不记录”选项并在产品内说明。
- **敏感字段**：钱包地址、截图 URL、举报描述等访问需权限控制与审计；展示时脱敏（如钱包只显示前后几位）。

### 7.2 访问控制

- **API**：Bot 用内部 Token 或服务间认证；Mini App 用 TG 校验 + 可选 session；管理端用独立 Token/角色，与普通用户隔离。
- **管理操作**：黑名单增删、举报核实、数据导出等需 RBAC + 操作日志。

### 7.3 防滥用与完整性

- **限流**：按 tg_id 或 IP 限制 /check、/report 频率（如每用户每分钟 N 次），Redis 实现。
- **举报**：防刷（同一 reporter 对同一 target 短时间大量提交需限制）；证据 URL 可做格式校验与安全扫描（避免恶意链接）。

### 7.4 合规表述

- **对外声明**：数据来源（举报 + 可授权 + 公开链上）、用途、保留期限、用户权利（查询、纠错、删除请求流程）；不宣称“未授权监控”或具体设备数量，避免法律与信任风险。

## 八、SRE & Performance 视角（运维与性能）

### 8.1 性能目标

- **查询**：P95 响应 <3s，支持日查询 1 万+（单机 + Redis 可满足 MVP）。
- **可用性**：目标 99% uptime；Bot 多 Token 轮换，前端可配置备用 Bot 或 Mini App 主入口以降低封号影响。

### 8.2 容量与扩展

- **缓存**：/check 结果按 (tg_id/username/wallet) 缓存 5–15 分钟，降低 DB 与评分计算压力。
- **DB**：users、reports、blacklist 建索引（tg_id、username、wallet、status、created_at）；大表分表策略预留（如 query_log 按月）。
- **水平扩展**：API 无状态，可多实例 + 负载均衡；任务队列单独扩容。

### 8.3 可观测与运维

- **日志**：结构化日志（请求 id、tg_id 脱敏、接口、耗时、错误码）；不记录完整证据内容。
- **监控**：接口延迟、错误率、限流触发次数、队列堆积；告警规则（如错误率>1%、P95>5s）。
- **部署**：一键部署脚本或 CI/CD；数据库迁移与回滚流程文档化；机密用 Secret 管理，不落代码库。

### 8.4 备份与恢复

- **DB**：定期快照与 WAL 归档；关键表（users、blacklist、reports）可做逻辑备份与恢复演练。
- **灾难恢复**：RTO/RPO 目标明确（如 RPO 1h）；恢复步骤文档化并定期演练。

## 九、QA & Edge Cases 视角（测试与边界）

### 9.1 功能测试

- **查询**：有效 tg_id、有效 @username、无效/不存在 ID、仅钱包、钱包无关联、黑名单用户、新用户（无记录）；权限/隐私导致的“无法解析 username”等。
- **举报**：正常提交、重复提交、缺少必填、非法 URL、超长文本；同一 target 多 reporter 触发自动升风险或入黑名单的规则验证。
- **订阅**：订阅/取消、黑名单与风险等级变更是否触发、限频是否生效。
- **管理**：stats 准确性、黑名单增删后查询结果是否更新、权限与未授权访问返回 403。

### 9.2 边界与异常

- **并发**：同一 target 多用户同时举报；同一用户高并发 /check 的限流与一致性。
- **数据**：tg_id 极大值、username 特殊字符、钱包地址多链格式；DB 无记录、部分字段为 null 时 API 与 Bot 的展示。
- **外部**：TG API 超时/限流/返回错误时的降级与提示；Redis/DB 短暂不可用时的重试与友好提示。

### 9.3 安全与合规测试

- **越权**：用普通用户 Token 调管理接口；用 A 的上下文调 /mycredit 返回 B。
- **注入**：username、reason、evidence URL 的校验与转义。
- **隐私**：确认日志与存储中无明文 tg_id 或敏感证据（按策略）。

### 9.4 性能与稳定性

- **压测**：/check 在 1w QPS 下的 P95、错误率；Redis 失效时 DB 压力与响应时间。
- **长时间**：7 天稳定运行、内存与连接数无泄漏。

## 十、Business Value 视角（商业与产品价值）

### 10.1 引流与留存

- **免费**：信用查 Bot 永久免费，作为担保/Escrow 与 Mini App 的流量入口。
- **粘性**：/mycredit 自查、订阅提醒、历史查询（可选）提升复访；结果页“用担保交易”直接导流到 Mini App 或担保下单。

### 10.2 数据与壁垒

- **数据**：举报与黑名单形成正向循环；若后续接入合规语料与风控模型，可形成“未举报先预警”的能力，与仅依赖事后举报的竞品差异化。
- **表述**：对外强调“用户举报 + 可授权数据”，不强调未授权采集，兼顾合规与竞争力。

### 10.3 变现预留

- **MVP 不收费**：核心查询、举报、基础提醒均免费。
- **后续可选**：高级报告（如详细背调、历史趋势）订阅制（如 0.5–1 USDT/次）；商户认证/勋章（如 TON 质押）与担保优先推荐结合；Mini App 内高级分析或 API 调用配额（B 端）。

### 10.4 风险与应对

- **Bot 封号**：多 Token 轮换 + Mini App 主入口，降低依赖单 Bot。
- **误报与纠纷**：纠错入口、申诉流程（后期可接 DAO 仲裁）、明确免责与“仅供参考”的文案。
- **合规**：隐私政策、数据保留与删除、地区法律（如菲律宾数据保护）在正式上线前完成合规审查。

## 十一、统一里程碑与交付物（推荐）

| 阶段 | 周期 | 核心交付 | 验收要点 |
|------|------|----------|----------|
| **MVP** | 10–14 天 | Bot（/start、/check、/mycredit、/help）+ 规则引擎评分 + 黑名单 + 举报 + 基础管理 + API + PostgreSQL + Redis | 查询 <3s、多输入类型、举报入库、黑名单展示、/stats |
| **V1.1** | +2–3 周 | 订阅提醒、纠错反馈、多语言（EN + Tagalog）、限流与安全加固、审计日志 | 提醒触发、反馈列表、无硬编码文案、限流生效 |
| **Mini App** | +2–4 周 | TMA 信用名片、雷达图、担保跳转、调用同一 /v1 API | 与 Bot 数据一致、移动端可用、跳转流程通 |
| **AI/风控** | +4–6 周 | 语料管道（脱敏）接入、风险模型训练与 A/B、规则与模型可切换 | 模型接口稳定、可回退规则、无 PII 泄露 |
| **扩展** | 后续 | 钱包绑定、链上履约、勋章/质押、高级报告与 B 端 API | 合规评审、合约与后端解耦 |

## 十二、文档体系建议（与开发配套）

- **FSD（功能需求）**：用户故事、功能列表、查询/举报/订阅流程图、数据字段定义、风险等级与评分算法说明、多语言与错误态。
- **TDD（技术设计）**：系统架构图、模块划分、数据流、DB ER 与迁移策略、API OpenAPI、AI/规则引擎接口、缓存与限流策略。
- **运维与发布**：环境变量与配置说明、部署步骤、监控与告警、备份与恢复、Bot 轮换与 Mini App 发布流程。
- **测试**：用例清单（功能/边界/安全/性能）、自动化范围、回归检查表。
- **合规与产品**：隐私政策、数据来源与用途声明、用户权利与申诉流程、版本与变更公告。
