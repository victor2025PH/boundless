# 信用查 — 功能总结与测试说明

## 一、功能总览

### 1.1 用户端（Bot）

| 功能 | 入口/触发 | 说明 |
|------|-----------|------|
| **欢迎与查询** | `/start`、主键盘「立即查询」 | 欢迎语、说明；点击后输入 ID/@用户名/钱包 即可查 |
| **信用查询** | `/check <id\|@user\|wallet>`、转发对方消息 | 解析后调 API，展示报告（风险、分数、tips、综合建议、下一步建议、标签、关联钱包/多账号、时间线*、免责） |
| **我的信用** | `/mycredit`、主键盘「我的信用」 | 本人报告 + 谁查过我（7 天被查次数、最近一次被查时间）+ 时间线 + 出示我的报告 / 我的申诉 按钮 |
| **帮助** | `/help`、主键盘「帮助」 | 结构化帮助：查询方式、邀请链接、我的信用与出示、对方不信我怎么办、举报与申诉、数据说明 |
| **举报/纠错** | 结果页「举报/纠错」按钮 | FSM 收集原因后提交，同步写入 Report + Feedback |
| **请对方出示报告** | 结果页按钮 | 说明：对方发 /mycredit 或点「我的信用」转发，或发邀请链接 |
| **转发报告** | 结果页按钮 | 将当前报告再发一条给用户，便于转发到其他聊天 |
| **出示我的报告** | 我的信用页「出示我的报告」 | 生成 24h 有效一次性链接，对方点开可看本人报告（用后即废） |
| **邀请链接** | `/invite`、主键盘「获取邀请链接」 | 生成 15 分钟有效链接，对方点开发消息后报告发回给当前用户 |
| **谁查过我** | 我的信用报告内区块 | 最近 7 天被查次数、最近一次被查时间 |
| **最近活动时间线** | 我的信用报告内区块 | 按日展示：被查 N 次、邀请打开 N 次、报告分享被查看 N 次（仅我的信用返回） |
| **最近查询** | 主键盘「最近查询」 | 最近查过的 N 个对象（去重），每项可「再查」 |
| **我的申诉** | 主键盘「我的申诉」、我的信用页按钮 | 本人发起的纠错/误报列表及状态（待处理/已处理/已驳回） |
| **我的订阅** | 主键盘「我的订阅」 | 风险变化提醒订阅列表，每项可再查或取消提醒 |
| **有变化时提醒我** | 结果页按钮（查别人时） | 订阅该用户的举报/拉黑动态，推送按用户语言（en/zh/tl） |
| **管理员统计** | `/stats`（仅 ADMIN_TG_IDS） | 今日查询、总用户、黑名单数、待处理举报 |

\* 时间线仅在「我的信用」中返回并展示；查别人不返回时间线。

### 1.2 API 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/v1/check` | 查询：user_id / username / wallet；可选 querier_tg_id（谁查过我）；返回报告 + 关联钱包/多 TG，无时间线 |
| GET | `/v1/mycredit` | 我的信用：tg_id；返回报告 + 谁查过我统计 + 时间线 |
| POST | `/v1/report` | 举报：reporter_tg_id, target_tg_id, reason, 可选 tx_hash/screenshot_url/description；同步写 Feedback，触发风险提醒入队 |
| GET | `/v1/admin/stats` | 管理统计（需 Admin Key） |
| GET | `/v1/admin/feedback` | 申诉列表，可选 status 筛选（需 Admin Key） |
| PATCH | `/v1/admin/feedback/{id}` | 更新申诉状态为 processed/rejected（需 Admin Key） |
| POST | `/v1/admin/blacklist` | 加黑名单，Body: tg_id, reason?, source?；触发 blacklist_added 提醒（需 Admin Key） |
| POST | `/v1/invite/create` | 生成邀请链接 |
| GET | `/v1/invite/consume` | 消费邀请 token（对方点链接后） |
| POST | `/v1/share/create` | 生成「出示我的报告」一次性链接 |
| GET | `/v1/share/view` | 消费分享 token，返回报告并标记已用 |
| GET | `/v1/my-recent-queries` | 最近查询列表 |
| GET | `/v1/my-feedback` | 我的申诉列表 |
| POST | `/v1/activity/log` | 记录活动（invite_clicked/share_viewed），Bot 用 |
| POST | `/v1/alert/subscribe` | 风险提醒订阅，可选 lang（en/zh/tl） |
| DELETE | `/v1/alert/subscribe` | 取消订阅 |
| GET | `/v1/alert/subscriptions` | 我的订阅列表 |
| GET | `/v1/alert/pending` | 待发提醒（Bot 轮询，需 Admin Key） |
| PATCH | `/v1/alert/pending/{id}` | 标记提醒已发送（Bot 用，需 Admin Key） |
| GET | `/health` | 健康检查 |

### 1.3 数据与业务逻辑

- **表**：users, blacklist, reports, wallet_entity_graph, feedback, query_log, pending_invites, check_log, report_share_tokens, activity_events, risk_alert_subscriptions, risk_alert_pending。
- **谁查过我**：每次 /check 且提供 querier_tg_id 时写 check_log；我的信用聚合 7 天次数与最近时间。
- **时间线**：check / invite 打开 / share 查看 时写 activity_events；仅 mycredit 返回 timeline。
- **风险提醒**：订阅表存 preferred_lang；举报/加黑时 enqueue_alerts_for_target，带去重+24h 限频；Bot 轮询 pending 按 subscriber_lang 推送后标记已发送。
- **举报**：写 Report + Feedback，并触发 new_report 提醒入队（排除举报人）。

## 二、测试方式

### 2.1 单元/集成测试（服务层 + API）

- 见项目根目录 `run_tests.py`：使用临时 SQLite 文件建表，依次调用核心 services 与 FastAPI TestClient 请求主要 API，校验无异常及必要字段存在。
- 运行：`python run_tests.py`（会强制覆盖 `DATABASE_URL`/`BOT_TOKEN`，无需启动 API/Bot，无需真实 .env）。
- **现有数据库（PostgreSQL / SQLite）**：若表结构早于当前代码，请运行一次 `python migrate_add_columns.py`，会按需补齐 `users.last_seen_at`、`users.query_count`、`reports.reason`，避免 500（如「字段 users.last_seen_at 不存在」）。

### 2.2 手动验证建议

1. **启动**：`python run_api.py`，再 `python run_bot.py`，确保 `.env` 中 `BOT_TOKEN`、`API_BASE_URL` 正确。
2. **查询与报告**：在 Bot 中 /check 一个 ID、点结果页举报并提交原因，检查「我的申诉」是否出现待处理。
3. **我的信用**：/mycredit，确认有谁查过我区块、时间线（若有活动）、出示我的报告与我的申诉按钮。
4. **邀请**：/invite 取链接，用另一账号或浏览器打开链接并发消息，确认原用户收到报告。
5. **出示报告**：我的信用 → 出示我的报告，用另一账号点链接，确认看到报告且再次点链接提示失效。
6. **最近查询**：主键盘「最近查询」，再查几人后确认列表与「再查」可用。
7. **风险提醒**：结果页「有变化时提醒我」订阅，用另一账号举报该 target 或管理端加黑，确认收到推送且语言正确；主键盘「我的订阅」可取消。
8. **管理**：设置 ADMIN_TG_IDS 与 API_INTERNAL_KEY，调用 `GET /v1/admin/stats`、`GET /v1/admin/feedback`、`POST /v1/admin/blacklist` 等验证鉴权与返回。

## 三、已知依赖与配置

- **API**：无 BOT_TOKEN 也可运行；username 解析需 BOT_TOKEN（在 config）时才会调 Telegram。
- **Bot**：需有效 BOT_TOKEN、API_BASE_URL；风险提醒轮询需 API_INTERNAL_KEY 与 API 同源。
- **数据库**：首次启动 API 时自动建表；若表已存在且缺少新列（如 preferred_lang、subscriber_lang），需按 `docs/风险变化提醒-方案与接口草案.md` 执行 ALTER。
