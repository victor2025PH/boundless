# 信用查 — 管理后台对接开发文档

> **用途**：本文档提供给开发方（如 AI Studio）实现「管理后台」前端；开发完成后交付物将与本项目（xyc2026）的现有 API 做对接。  
> **对接方**：本项目已提供全部管理接口，对接时只需配置「API 基础地址」与「管理密钥」即可。  
> **完整功能版**：若需**涵盖举报管理、举报人列表、交易列表、风险趋势及全部统计项**的对接方案，请以 **《管理后台UI-完整对接方案》**（`docs/管理后台UI-完整对接方案.md`）为准。

---

## 一、项目概述

### 1.1 目标

实现一个**仅面向内部管理员**的网页后台，用于：

- 查看运营统计（今日查询、总用户、黑名单数、待处理举报数）
- 查看并处理用户申诉（列表、按状态筛选、通过/驳回）
- 将用户加入黑名单（填写 tg_id、原因、来源）
- （可选）查看待发送的风险提醒队列（只读）

### 1.2 技术边界

- **后端**：不要求开发方实现新后端。所有数据与操作均通过**本项目已提供的 REST API** 完成。
- **鉴权**：所有管理接口需在请求头中携带 **Bearer Token**（即管理密钥 `API_INTERNAL_KEY`）。开发方只需实现「登录页输入密钥并保存」+ 后续请求自动带 Header。
- **对接方式**：开发方交付**可独立运行的前端工程**（如静态构建产物或带 dev 服务器的前端项目），由对接方配置 API 基础地址与密钥后挂载或反向代理。

### 1.3 对接方已提供

| 项 | 说明 |
|----|------|
| API 服务 | 本项目 `run_api.py` 启动的 FastAPI 服务，默认 `http://127.0.0.1:8001` |
| 管理密钥 | 与 `.env` 中 `API_INTERNAL_KEY` 一致；对接时由运营提供 |
| 接口文档 | 本文档第二节为完整接口约定；对接方也可提供 OpenAPI JSON（同源下 `/openapi.json`） |

## 二、接口规范（管理端）

**约定**：

- **Base URL**：由对接方配置，例如 `https://api.example.com` 或 `http://127.0.0.1:8001`。开发时可用占位符如 `VITE_ADMIN_API_BASE_URL`。
- **公共请求头**：所有下述请求必须携带  
  `Authorization: Bearer <API_INTERNAL_KEY>`  
  否则返回 `403 Forbidden`。
- **Content-Type**：请求体为 JSON 时使用 `Content-Type: application/json`。
- **响应**：成功为 `2xx`，业务错误为 `4xx`（如 400 参数错误、403 无权限、404 不存在），服务器错误为 `5xx`。

---

### 2.1 运营统计

**GET** `/v1/admin/stats`

- **Query**：无
- **Response 200**（JSON）：

```json
{
  "queries_today": 0,
  "total_users": 0,
  "blacklist_count": 0,
  "reports_pending": 0
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| queries_today | int | 今日查询次数 |
| total_users | int | 用户表总数 |
| blacklist_count | int | 黑名单条数 |
| reports_pending | int | 待处理举报/申诉数 |

---

### 2.2 申诉列表

**GET** `/v1/admin/feedback`

- **Query**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| status | string | 否 | 筛选：`pending` / `processed` / `rejected`；不传则全部 |
| limit | int | 否 | 条数，默认 100，范围 1–500 |

- **Response 200**（JSON）：

```json
{
  "items": [
    {
      "id": 1,
      "reporter_tg_id": 123456789,
      "target_tg_id": 987654321,
      "reason": "误报，已和解",
      "status": "pending",
      "created_at": "2025-02-16T12:00:00"
    }
  ]
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| items | array | 申诉列表 |
| items[].id | int | 申诉 ID，用于后续更新状态 |
| items[].reporter_tg_id | int | 举报人 Telegram ID |
| items[].target_tg_id | int | 被举报人 Telegram ID |
| items[].reason | string | 用户填写的理由 |
| items[].status | string | `pending` / `processed` / `rejected` |
| items[].created_at | string \| null | 创建时间，ISO 8601 |

---

### 2.3 更新申诉状态

**PATCH** `/v1/admin/feedback/{feedback_id}`

- **Path**：`feedback_id` 为申诉列表项中的 `id`（整数）。
- **Body**（JSON）：

```json
{
  "status": "processed"
}
```

- **status** 取值**仅允许**：`processed`（通过/已处理）、`rejected`（驳回）。
- **Response 200**（JSON）：

```json
{
  "ok": true,
  "message": "processed"
}
```

- **Response 404**：`feedback_id` 不存在，例如 `{"detail": "Feedback not found"}`。

---

### 2.4 加入黑名单

**POST** `/v1/admin/blacklist`

- **Body**（JSON）：

```json
{
  "tg_id": 987654321,
  "reason": "多次欺诈举报",
  "source": "admin"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| tg_id | int | 是 | 要拉黑的 Telegram 用户 ID |
| reason | string | 否 | 原因说明 |
| source | string | 否 | 来源，默认 `admin` |

- **Response 200**（JSON）：

```json
{
  "ok": true,
  "added": true
}
```

| 字段 | 说明 |
|------|------|
| added | `true` 表示本次新加入黑名单；`false` 表示该 tg_id 已在黑名单中（本次未重复插入） |

---

### 2.5 待发提醒列表（可选）

**GET** `/v1/alert/pending`

- **Query**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| limit | int | 否 | 条数，默认 50，范围 1–100 |

- **Response 200**（JSON）：

```json
{
  "items": [
    {
      "id": 1,
      "subscriber_tg_id": 111,
      "target_tg_id": 222,
      "event_type": "new_report",
      "subscriber_lang": "zh",
      "created_at": "2025-02-16T12:00:00"
    }
  ]
}
```

| 字段 | 说明 |
|------|------|
| items[].id | 待发记录 ID |
| items[].subscriber_tg_id | 订阅者 Telegram ID |
| items[].target_tg_id | 被关注目标 ID |
| items[].event_type | 如 `new_report`、`blacklist_added` |
| items[].subscriber_lang | 推送语言 |
| items[].created_at | 创建时间 |

此接口仅供后台**只读展示**；「标记已发送」由本项目的 Bot 进程调用，前端无需实现。

## 三、鉴权与「登录」流程

- 管理接口**无**用户名/密码登录接口；鉴权仅靠 **Bearer Token**（即 `API_INTERNAL_KEY`）。
- 开发方需实现：
  1. **登录页**：输入框填写「管理密钥」，提交后调用 `GET /v1/admin/stats`，若返回 200 则视为密钥有效，将密钥存入 **sessionStorage**（或内存），并跳转到后台首页。
  2. 若返回 403，提示「密钥无效或已失效」。
  3. 后续所有请求在 Header 中携带：`Authorization: Bearer <刚保存的密钥>`。
  4. 若某次请求返回 403，可清除本地密钥并跳回登录页。
- 密钥**不要**写入前端代码或公开仓库；对接时由运营在部署环境中配置。

## 四、页面与功能说明

### 4.1 登录页

- 输入：管理密钥（单行文本，可密文）。
- 操作：提交后调 `GET /v1/admin/stats`；成功则存密钥并进入总览；失败则提示错误。
- 无「注册」；无「忘记密码」（密钥由对接方线下提供）。

### 4.2 总览页（Dashboard）

- 调用 `GET /v1/admin/stats`，展示 4 个数字卡片：
  - 今日查询
  - 总用户数
  - 黑名单数
  - 待处理举报数
- 提供导航入口：申诉管理、黑名单管理；（可选）待发提醒。

### 4.3 申诉管理页

- 顶部可选 Tab 或下拉：全部 / 待处理(pending) / 已处理(processed) / 已驳回(rejected)。
- 列表字段：ID、举报人 tg_id、被举报人 tg_id、理由、状态、创建时间。
- 行内操作：
  - 状态为 `pending` 时显示「通过」「驳回」按钮；
  - 「通过」：`PATCH /v1/admin/feedback/{id}`，body `{"status":"processed"}`；
  - 「驳回」：`PATCH /v1/admin/feedback/{id}`，body `{"status":"rejected"}`。
- 操作前可二次确认（如「确认通过？」）；操作后刷新列表或仅更新该行状态。

### 4.4 黑名单管理页

- **当前 API 仅支持「新增」**，无列表接口。
- 页面内容：
  - 表单：tg_id（必填，数字）、reason（选填）、source（选填，默认 `admin`）；提交调用 `POST /v1/admin/blacklist`。
  - 成功且 `added: true` 提示「已加入黑名单」；`added: false` 提示「该用户已在黑名单中」。
- 若对接方后续提供「黑名单列表」接口，可再增加列表展示与分页（接口约定以对接方补充为准）。

### 4.5 待发提醒页（可选）

- 只读列表：调用 `GET /v1/alert/pending?limit=100`，展示 subscriber_tg_id、target_tg_id、event_type、subscriber_lang、created_at。
- 无需「标记已发送」等操作。

## 五、技术建议与约束（供开发方参考）

- **前端框架**：任选（如 Vue 3 / React / Svelte），建议 SPA；构建产物为静态 HTML/JS/CSS，便于对接方用 Nginx 或 FastAPI 挂载。
- **API 调用**：Base URL 通过环境变量或构建时配置注入（如 `import.meta.env.VITE_ADMIN_API_BASE_URL`），不要写死域名。
- **跨域**：若前后端不同源，对接方会在 API 侧配置 CORS 允许后台域名；开发时可用代理或同源部署避免跨域。
- **错误处理**：网络错误或 4xx/5xx 时，在页面或 Toast 中给出明确提示（如「密钥无效」「申诉不存在」「请稍后重试」）。

### 6.3 对接步骤（对接方执行）

1. 将前端构建产物放入本项目约定目录（如 `admin-dist/` 或由 Nginx 指向的路径），或单独部署到同一域名下子路径（如 `https://example.com/admin`）。
2. 配置前端运行时的 API Base URL 指向本项目 API（若为构建时注入，则重新构建并传入正确 Base URL）。
3. 在安全环境中将 `API_INTERNAL_KEY` 告知管理员，用于登录页输入。
4. 验证：登录 → 总览数据正确 → 申诉列表与通过/驳回 → 加黑表单提交成功。

## 七、附录：错误码与示例

| HTTP 状态 | 含义 | 典型处理 |
|-----------|------|----------|
| 200 | 成功 | 按 response 更新 UI |
| 400 | 参数错误（如缺少 tg_id） | 提示参数错误 |
| 403 | 未提供或错误的 Bearer Token | 清除密钥，跳转登录页 |
| 404 | 资源不存在（如 feedback_id 无效） | 提示不存在并刷新列表 |
| 500 | 服务器错误 | 提示稍后重试 |

**示例：校验密钥**

```http
GET /v1/admin/stats HTTP/1.1
Host: <API_BASE_URL>
Authorization: Bearer <API_INTERNAL_KEY>
```

- 200 + JSON body → 密钥有效。  
- 403 → 密钥无效或未配置。
