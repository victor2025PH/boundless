# 信用查（TrustCheck）— 产品功能与应用场景说明

> **用途**：本文档客观描述当前产品的功能、技术边界、用户角色与应用场景，**不包含市场或商业化结论**。供其他 AI 或团队在此基础上进行**市场分析**与**商业化分析**使用。

---

## 一、产品概览

| 项 | 说明 |
|----|------|
| **产品名称** | 信用查（中文）/ TrustCheck（英文） |
| **一句话定位** | 在 Telegram 上提供「交易/合作前查对方信用与风险」的机器人 + 后端服务；数据来自用户举报与公开信息，用于防诈与信任建立。 |
| **主要载体** | Telegram Bot（@xyc2026_bot）；REST API 供 Bot 与未来管理后台/第三方调用。 |
| **多语言** | 支持中文（简体）、英文、塔加洛语（Tagalog）。 |
| **当前商业模式** | 全部功能**免费**；无付费套餐、无内购、无广告；文档中明确「不新增收费」的优化方向。 |
| **目标地区/人群** | 文档与文案未限定地域；典型场景涉及 OTC、陌生人合作、加密货币相关交易与防诈，适用于依赖 Telegram 进行交易或沟通的用户。 |

## 二、核心功能清单（按用户动线）

### 2.1 查询与报告

| 功能 | 说明 | 入口/方式 |
|------|------|-----------|
| **信用/风险查询** | 按 Telegram 数字 ID、@用户名、或钱包地址（如 TRC20）查询；返回风险等级（低/中/高/极高）、信用分（0–100）、风险提示标签、举报与黑名单情况、综合建议与「下一步建议」。 | Bot：/check 或主菜单「立即查询」后输入 ID/用户名/钱包；或**转发对方一条消息**自动查。 |
| **我的信用** | 当前用户查看自己在系统中的信用报告（同查询结构）；含「谁查过我」统计（最近 7 天被查次数、最近一次被查时间）、本系统活动时间线（被查/邀请打开/分享被查看，按日聚合）。 | Bot：「我的信用」主菜单。 |
| **报告内容** | 报告编号、生成时间、被查人 ID/用户名/展示名、信用结论（风险+分数+提示）、综合建议与下一步建议、标签（如新账号）、关联钱包/多账号提示、举报与黑名单统计、首次记录与数据更新时间、本系统活动时间线、数据说明与免责。 | 查询/我的信用 结果页。 |
| **邀请链接查人** | 当对方隐藏来源时，查询方获取「邀请链接」发给对方；对方点开发送消息后，**报告自动发回给查询方**，无需对方主动配合查自己。 | Bot：「获取邀请链接」→ 将链接发给对方 → 对方点击并发消息 → 查询方收到报告。 |
| **出示我的报告** | 被查方主动生成**一次性链接**，发给对方点开即可查看自己的最新报告（只读），用于「对方不信我时我主动出示」建立信任。 | Bot：结果页「请对方出示报告」相关入口；我的信用页可生成分享链接。 |
| **转发报告** | 将当前报告正文再发一条给用户，便于转发到其他聊天或留底。 | Bot：结果页「转发报告」按钮。 |
| **最近查询** | 展示用户最近查过的若干对象（按被查人去重），点击可**一键再查**。 | Bot：「最近查询」主菜单。 |

### 2.2 举报与申诉

| 功能 | 说明 | 入口/方式 |
|------|------|-----------|
| **举报/纠错** | 对某 tg_id 发起举报或纠错，填写原因、可选 tx_hash/截图/描述；状态为待核实/已核实/已驳回。 | Bot：结果页「举报/纠错」→ 填写表单提交。 |
| **我的申诉** | 用户查看自己发起的纠错/误报反馈的**状态**（待处理/已处理/已驳回）。 | Bot：「我的申诉」主菜单。 |

### 2.3 订阅与提醒

| 功能 | 说明 | 入口/方式 |
|------|------|-----------|
| **风险变化订阅** | 用户对某 tg_id 订阅「有变化时提醒我」；当该用户**新增举报**或**被加入黑名单**时，Bot 向订阅者推送一条提醒。每人最多订阅 20 个目标；可区分订阅来源（直接查询/邀请报告/再查/转发等）用于统计。 | Bot：他人结果页「有变化时提醒我」；「我的订阅」列表可再查、按条取消。 |
| **上下线提醒（订阅）** | 用户可单独订阅某人的「上线/下线」提醒；数据来自**众包上报**（他人在 Bot 点「上报：TA 在线/离线」）或未来**专用监控端**上报。 | Bot：他人结果页「订阅上下线提醒」；「我的订阅」中展示类型（风险提醒 / 上下线）并支持按类型取消。 |
| **众包上报上下线** | 任意用户在看到他人报告时，可点「上报：TA 在线」或「上报：TA 离线」，将状态上报后台；若有人订阅了该目标的上下线，会收到推送。 | Bot：他人结果页「上报：TA 在线」「上报：TA 离线」按钮。 |

### 2.4 管理端（当前）

| 功能 | 说明 | 入口/方式 |
|------|------|-----------|
| **运营统计** | 今日查询数、总用户数、黑名单数、待处理举报数。 | API：GET /v1/admin/stats（需管理密钥）；Bot：/stats（仅配置的 Admin TG ID）。 |
| **申诉列表与处理** | 按状态筛选申诉列表；将某条申诉更新为「已处理」或「已驳回」。 | API：GET /v1/admin/feedback、PATCH /v1/admin/feedback/{id}（需管理密钥）。 |
| **加黑名单** | 将某 tg_id 加入黑名单（可选原因、来源）；触发后订阅了该目标「风险变化」的用户会收到拉黑提醒。 | API：POST /v1/admin/blacklist（需管理密钥）。 |
| **管理后台（规划）** | 网页后台：总览统计、申诉管理、黑名单管理、待发提醒只读等；对接文档已提供，由前端调用现有管理 API。 | 文档已就绪，前端可独立实现后配置 API 与密钥对接。 |
| **监控端管理（规划）** | 多监控账号通过 API/ID/接码在后台网站登录与绑定，向后台上报上下线等数据；方案文档已写，接口与表结构为概念层。 | 见《多监控端与后台管理-方案-接码登录》。 |

### 2.5 数据与风控逻辑

| 项 | 说明 |
|----|------|
| **信用分与风险等级** | 规则引擎计算 0–100 分及 low/medium/high/extreme；因子含：账号年龄、Premium、高危群数量、是否黑名单、举报次数等；输出综合建议与「下一步建议」（如小额试单、要求对方出示报告）。 |
| **数据来源** | 用户举报（含证据）、黑名单（管理端添加或确认）、钱包–TG 关联（wallet_entity_graph，用于「换号不换地址」提示）、本系统活动（被查、邀请点击、分享查看）、可选 Telegram 解析（用户名→tg_id）。 |
| **隐私与存储** | 文案声明「默认不存储您的查询记录」；匿名化查询日志可选；「谁查过我」为聚合统计（次数、最近时间），可脱敏。 |

## 三、用户角色与典型场景（客观描述）

| 角色 | 典型场景 | 产品中对应的能力 |
|------|----------|------------------|
| **准备交易/合作的人** | 大额转账、OTC、陌生人合作前想确认对方是否靠谱。 | 查询对方 ID/用户名/钱包；看报告与下一步建议；可要求对方出示报告或发邀请链接让对方配合出报告。 |
| **被查的人** | 对方要求先证明信用；希望主动出示报告或申诉误报。 | 出示我的报告（一次性链接）；我的信用；举报/纠错与「我的申诉」查状态。 |
| **商户/中介/高频查询者** | 每天查多人；需要快查、历史与风险变化提醒。 | 转发消息即查、最近查询一键再查、风险变化订阅与上下线订阅。 |
| **加密货币相关用户** | 关心 TG 或钱包是否靠谱、是否换号不换地址。 | 按钱包查、报告内关联钱包与多 TG 提示。 |
| **管理员/运营** | 处理申诉、加黑、看统计。 | 管理 API（统计、申诉、黑名单）；规划中的网页管理后台。 |

## 四、应用场景归纳（供市场与商业化参考）

- **OTC / 场外交易**：交易前查对方 TG 或钱包风险与举报记录，减少诈骗与纠纷。  
- **陌生人合作/兼职/租赁**：合作前查对方信用与黑名单，决定是否继续或要求担保。  
- **加密货币社区**：钱包–TG 关联与多账号提示，辅助识别「换号不换地址」等行为。  
- **群主/社区运营**：查成员是否在黑名单或高风险，辅助准入或提醒。  
- **持续关注某人动态**：通过「风险变化」与「上下线」订阅，在对方被举报、拉黑或上线/下线时收到提醒。  
- **信任建立与对质**：出示我的报告、邀请链接让对方配合出报告，用于对质与存证。  

以上场景均在文档或产品文案中有对应功能支撑；未对行业或地域做限定，可由分析方自行做市场细分与优先级判断。

## 五、技术边界与约束（客观事实）

| 类型 | 说明 |
|------|------|
| **平台依赖** | 主入口为 Telegram Bot；部分能力依赖 Telegram（如用户名解析、邀请链接、转发消息查人）；上下线数据依赖「其他账号」观测或众包上报（Telegram 不向 Bot 提供用户在线状态）。 |
| **数据边界** | 无链上深度分析、无社交图谱；举报与黑名单依赖用户与管理员输入；钱包关联需在系统内有过记录。 |
| **合规与条款** | 文档中提及需注意 Telegram 服务条款（如自动化、多账号）、隐私与知情同意、数据最小化；产品定位为防诈与信任建立，不承诺「能监控所有人」或「替代法律/合规」。 |
| **规模与性能** | 当前为单实例 API + Bot；订阅与待推送由 Bot 轮询拉取；未在文档中承诺 SLA 或并发规模。 |

## 六、已暴露的 API 与交付形态（供对接与生态分析）

- **对外/被 Bot 使用的 API**：检查（/v1/check）、我的信用（/v1/mycredit）、举报（/v1/report）、邀请创建与消费、出示报告创建与查看、最近查询、我的申诉、活动日志、订阅/取消/列表、待推送拉取与标记、监控事件上报（/v1/monitor/event）等；健康检查 /health。  
- **管理端 API**：统计、申诉列表与更新、加黑名单、待推送只读与标记（Bot 用）；规划中：监控账号 CRUD、接码相关。  
- **鉴权**：管理接口与监控上报需 Bearer Token（API_INTERNAL_KEY）；普通查询/举报/订阅等由 Bot 代用户调用，无用户级 API Key。  
- **交付形态**：Bot 即用；API 由本项目部署；管理后台与监控端管理为「文档 + 对接」形态，由第三方或后续迭代实现前端/客户端。
