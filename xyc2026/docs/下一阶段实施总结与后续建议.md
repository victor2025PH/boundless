# 下一阶段实施总结与后续建议

> 对应《P2实施总结与下一阶段建议》中「5.2 数据与策略优化」及 429/举报人列表等小优化。实施日期：2026-02-19。

---

## 一、本次实施内容

### 1.1 限流 429 响应增加 Retry-After 头

| 项 | 实现方式 |
|----|----------|
| **/check 限流 429** | 超限时计算剩余秒数 `remaining = max(1, int(RATE_WINDOW - (now - start)))`，在 `HTTPException(429, detail="rate_limit_check", headers={"Retry-After": str(remaining)})` 中返回。 |
| **/report 限流 429** | 同上，`detail="rate_limit_report"`，同样带 `Retry-After` 头。 |
| **效果** | 前端/Bot 可解析 `Retry-After` 展示「N 秒后重试」，或用于退避重试。 |

### 1.2 get_admin_reporters 优先使用 ReporterStats

| 项 | 实现方式 |
|----|----------|
| **原逻辑** | 从 Report 表按 reporter_tg_id 聚合：count、sum(verified)、max(created_at)。 |
| **新逻辑** | 直接从 ReporterStats 表 `order by total_reports desc limit limit`，返回 `reporter_tg_id`、`report_count`（= total_reports）、`verified_count`、`last_at`（= last_report_at）。 |
| **兼容** | 使用 `getattr(rs, "verified_count", 0)` 兼容旧库在加列前的 ReporterStats 行。 |
| **效果** | 减少对 Report 全表聚合，管理端举报人列表与 P2 举报人统计一致，且性能更稳定。 |

### 1.3 举报人权重可配置

| 项 | 实现方式 |
|----|----------|
| **配置** | 新增 `use_effective_report_count: bool = True`（环境变量 `USE_EFFECTIVE_REPORT_COUNT=1` 或 `0`）。 |
| **逻辑** | 在 `recompute_user_score` 中：若 `use_effective_report_count` 为 False，则传入 `effective=None`，scoring 退化为仅用 `report_count`；为 True 时行为与 P2 一致（按举报人可信度加权）。 |
| **.env.example** | 增加 `USE_EFFECTIVE_REPORT_COUNT=1` 及说明。 |

## 二、在方案基础上的优化与细化

### 2.1 Retry-After

- **剩余时间**：按当前窗口结束时间计算 `remaining`，最小为 1 秒，避免 0 或负数。
- **与 sync_flow 一致**：与现有 `sync_flow_rate_limit` 的 `Retry-After` 用法一致，便于前端统一处理。

### 2.2 举报人列表

- **单一数据源** | 举报人列表完全以 ReporterStats 为准，与 report_create/update_report_status 的写入一致，避免 Report 与 ReporterStats 口径不一致。
- **无 Report 回退** | 当前未做「无 ReporterStats 时从 Report 聚合」的回退；若存在仅出现在 Report 的举报人（如历史数据未回填），可后续加一次迁移或回填脚本，将 Report 中 reporter 聚合写入 ReporterStats。

### 2.3 权重开关

- **关闭即回退** | `use_effective_report_count=False` 时仅用 `report_count`，便于 A/B 或问题排查时快速关闭权重。
- **默认开启** | 保持与 P2 行为一致，新配置项仅作可选关闭。

## 五、后续实施建议（再下一阶段）

### 5.1 可选功能与架构（仍按需）

| 项 | 说明 |
|----|------|
| **Redis 限流/缓存** | 多实例或高并发时，将 check/report 限流迁至 Redis；可选对热点查询做短 TTL 缓存。 |
| **异常检测** | 同 IP/设备批量举报降权：需 Bot 或 API 上报 IP/设备标识后再实现。 |
| **独立 Worker** | 将风险提醒、被查通知等轮询从 Bot 拆出为独立进程。 |
| **管理后台前端** | 按《管理后台UI-完整对接方案》对接现有管理 API。 |

### 5.2 可做的进一步优化

- **ReporterStats 回填**：若存在仅有 Report 无 ReporterStats 的历史举报人，可编写一次性脚本：按 Report 聚合出 reporter_tg_id、total、verified、last_at，写入或更新 ReporterStats，再切回「仅从 ReporterStats 读」的列表逻辑。
- **权重公式可配置**：将「举报人可信度」公式（如 verified_count/total_reports 的上下限、或与 effective 的混合方式）做成配置或策略表，便于运营调参。
- **Bot 解析 Retry-After**：Bot 在收到 429 时读取 `Retry-After`，回复「请 N 秒后再试」或自动延迟重试。

## 六、小结

- **本阶段已完成**：429 限流响应增加 Retry-After 头；get_admin_reporters 改为优先（仅）使用 ReporterStats；举报人权重增加开关 `use_effective_report_count`。
- **在方案基础上的优化**：Retry-After 按窗口剩余时间计算、最小 1 秒；举报人列表单一数据源、兼容旧列；权重开关默认开启、关闭即回退为纯 report_count。
- **再下一阶段**：以可选架构（Redis、异常检测、Worker、管理后台前端）为主；可做 ReporterStats 回填、权重公式可配置、Bot 解析 Retry-After 等小优化。
