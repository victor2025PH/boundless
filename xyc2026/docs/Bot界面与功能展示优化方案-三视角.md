# 信用查 Bot — 界面与功能展示优化方案（三视角）

## 一、现状分析：功能在但「看不见」

### 1.1 已有功能与入口一览

| 功能 | 实现情况 | 当前暴露方式 | 问题 |
|------|----------|--------------|------|
| 立即查询 | ✅ | /start 内联按钮 + 主键盘 | 主键盘未在首屏展示 |
| 获取邀请链接 | ✅ | /start 内联按钮 + 主键盘 | 同上 |
| 帮助 | ✅ | 主键盘「❓ 帮助」+ /help | 主键盘首屏没有，新用户难发现 |
| 我的信用 | ✅ | 主键盘「我的信用」+ /mycredit | 首屏无主键盘 |
| 最近查询 | ✅ | 主键盘「最近查询」 | 首屏无 |
| 我的申诉 | ✅ | 主键盘 + 我的信用页内联 | 首屏无；无「申诉状态」独立入口感 |
| 我的订阅 | ✅ | 主键盘「我的订阅」 | 首屏无 |
| 举报/纠错 | ✅ | 结果页内联「📌 举报/纠错」 | 仅查完才有，无独立入口 |
| 请对方出示报告 | ✅ | 结果页内联 | 合理 |
| 转发报告 | ✅ | 结果页内联 | 合理 |
| 有变化时提醒我 | ✅ | 结果页内联 | 仅查完才有 |
| 出示我的报告 | ✅ | 我的信用页内联 | 需先进「我的信用」 |
| 管理员统计 | ✅ | /stats 命令 | 无按钮，仅命令 |

### 1.2 根因归纳

- **主键盘（ReplyKeyboard）只在「点击立即查询」后的回复里下发**，未在 `/start` 首屏下发。因此新用户或只打开一次 /start 的用户，**永远看不到**「帮助、我的信用、最近查询、我的申诉、我的订阅」等按钮，形成「功能都有但没按钮」的体感。
- **首屏仅有两个内联按钮**（立即查询、获取邀请链接），没有「帮助」「我的信用」「报告/申诉/订阅」等入口，发现路径单一。
- **无统一「状态/报告中心」**：「我的申诉」是状态管理的一部分，但入口名称偏业务（申诉），且与「我的订阅」「最近查询」分散，缺少「状态管理」或「我的动态」这类聚合入口的认知。
- **无独立「报告」一级入口**：报告分散在「查询结果」和「我的信用 → 出示我的报告」中，没有「我的报告」或「报告与链接」的顶层入口。

## 二、开发工程师视角：可维护性与一致性

### 2.1 UI/UX 优化

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **首屏即带主键盘** | /start（无参数或非 share/invite 流程）在欢迎语下方或紧接着一条消息中，附带 `reply_main`，使「立即查询、获取邀请链接、我的信用、帮助、最近查询、我的申诉、我的订阅」在首次进入即可见。 | 所有已实现功能从首屏就有按钮入口，减少「只有两个按钮」的错觉。 |
| **欢迎语与首屏结构统一** | 欢迎语 + 主键盘；或欢迎语 + 内联（立即查询 / 获取邀请链接）+ 主键盘同时出现，避免「先内联、主键盘延后」的分步逻辑。 | 交互路径清晰，后续扩展（如多语言、A/B）易维护。 |
| **结果页 / 我的信用页保留主键盘** | 在发送查询结果、我的信用、最近查询、我的申诉、我的订阅等回复时，若当前无主键盘或会话新建，可再次附带 `reply_main`，保证用户从任意入口返回后仍有一致的主菜单。 | 减少因 Telegram 客户端或会话状态导致主键盘丢失的问题。 |
| **内联与主键盘分工明确** | 主键盘：常驻主导航（查询、邀请、我的信用、帮助、最近查询、申诉、订阅）。内联：上下文动作（举报、转发、出示报告、提醒我、再查、取消订阅等）。 | 代码与文案职责清晰，便于 i18n 与后续改版。 |

### 2.2 功能与入口优化

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **「帮助」首屏可见** | 除主键盘外，可在欢迎语下方增加「❓ 帮助」内联按钮或短文案「点此查看使用说明」，与现有 help 内容打通。 | 降低新用户学习成本，减少重复咨询。 |
| **「状态 / 我的动态」聚合（可选）** | 新增主键盘或内联入口「状态 / 我的动态」，聚合：最近查询摘要、我的申诉条数/状态、我的订阅条数。点击后进入列表或短摘要 + 跳转（再查 / 我的申诉 / 我的订阅）。 | 满足「状态管理」的认知，又不破坏现有「我的申诉」「我的订阅」独立页。 |
| **报告相关入口统一** | 保持「出示我的报告」在「我的信用」内；在主键盘或帮助中明确写出「我的信用 → 出示我的报告」；可选增加主键盘「我的报告」指向我的信用（或直接复用「我的信用」文案）。 | 用户有「报告」心智时能找到入口，无需改底层 API。 |
| **管理员入口（可选）** | 对 ADMIN_TG_IDS 用户，在主键盘增加「📊 管理」或仅对管理员展示，点击等同 /stats 或打开简易管理菜单。 | 管理员不依赖记忆命令，便于运营。 |

### 2.3 数据与后端

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **首屏与键盘不增加新表** | 仅改变 Bot 下发键盘的时机与内容，不新增数据库表。 | 零迁移成本。 |
| **「状态聚合」若实现** | 复用现有 API：`/v1/my-recent-queries`、`/v1/my-feedback`、`/v1/alert/subscriptions`，Bot 层做聚合展示。可选在 API 层提供轻量 `/v1/my-summary`（最近 N 条、待处理申诉数、订阅数）减少请求次数。 | 前端体验更好，后端可渐进增强。 |
| **埋点与监控（可选）** | 对「主键盘展示」「帮助点击」「我的信用/申诉/订阅点击」做简单计数（现有或新增轻量日志表），便于验证改版效果。 | 数据驱动后续迭代。 |

## 三、市场经理视角：转化与品牌

### 3.1 UI/UX 优化

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **首屏即展示完整能力** | 新用户一眼看到「查询、邀请、我的信用、帮助、最近查询、申诉、订阅」，形成「功能多、可信、专业」的第一印象。 | 提升首留与继续使用意愿。 |
| **帮助前置** | 帮助入口首屏可见，减少「不会用就离开」；可在帮助内增加「邀请好友」「出示报告」等引导话术。 | 降低流失，提高邀请与报告分享率。 |
| **统一「我的」与「状态」** | 主键盘中「我的信用」「我的申诉」「我的订阅」并列，或增加「状态/我的动态」聚合，强化「我的数据我掌握」的品牌感。 | 提升信任与复访。 |
| **文案与图标统一** | 主键盘保持 ❓🔍 等图标与简短中文/多语言文案一致，便于对外宣传截图与素材统一。 | 品牌与传播一致。 |

### 3.2 功能与运营

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **可量化的「功能发现率」** | 在首屏主键盘上线后，通过「帮助点击率」「我的信用/申诉/订阅点击率」与历史对比，说明「按钮展示」带来的提升。 | 用数据支撑运营与推广话术。 |
| **邀请与报告分享话术** | 在帮助、欢迎语或结果页中，明确写出「把邀请链接/出示报告链接发给对方」，便于市场做素材与教程。 | 提高邀请与对质场景的使用率。 |
| **订阅与提醒的露出** | 首屏有「我的订阅」，结果页有「有变化时提醒我」，形成闭环认知。 | 提高风险提醒功能的渗透率。 |

### 3.3 数据与洞察

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **不新增敏感字段** | 优化仅涉及入口展示与点击，不改变用户隐私与数据范围。 | 合规、易对外说明。 |
| **可选统计看板** | 若已有或计划做简单管理后台，可增加「主键盘展示次数」「各主键盘按钮点击」等汇总，供市场看趋势。 | 支撑运营决策。 |

## 四、用户视角：易用与安心

### 4.1 UI/UX 优化

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **一进来就有完整菜单** | 打开 Bot 即看到底部或消息下方有「立即查询、获取邀请链接、我的信用、帮助、最近查询、我的申诉、我的订阅」，不用先点「立即查询」才能看到其它。 | 减少「不知道能做什么」的困惑。 |
| **帮助随时可见** | 首屏就有「帮助」，遇到问题可立刻点进去看查询方式、邀请、出示报告、对方不信我怎么办等。 | 自助解决，减少「不会用就放弃」。 |
| **「我的」集中** | 我的信用、我的申诉、我的订阅都在主菜单，需要查自己、看申诉进度、管理提醒时，不用回忆「上次是在哪点的」。 | 认知负担小，复访路径短。 |
| **结果页与我的信用页保持现有按钮** | 举报、转发、请对方出示、有变化时提醒我、出示我的报告、我的申诉等内联按钮保留，不减少能力。 | 在「发现」问题解决后，不损失现有操作效率。 |

### 4.2 功能与心智

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **「状态管理」可理解** | 若增加「状态/我的动态」入口，用户可理解为「看我最近查了谁、申诉到哪了、订阅了谁」，满足「想看看进度」的需求。 | 与「我的申诉」等形成互补，不替代原有入口。 |
| **报告与链接不迷路** | 通过帮助或主键盘文案，明确「我的信用 → 出示我的报告」或「我的报告」即我的信用页，减少「想发报告给对方却找不到」的情况。 | 提高对质、交易前出示报告的使用率。 |
| **订阅与提醒闭环** | 查完某人后有「有变化时提醒我」，主菜单有「我的订阅」可查看或取消，逻辑一致。 | 用户对「提醒」有掌控感。 |

### 4.3 数据与隐私

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **不增加新数据收集** | 本次优化不新增必填信息或敏感字段，仅优化入口与展示。 | 用户无新增隐私顾虑。 |
| **帮助中继续强调「默认不存查询记录」等** | 保持现有数据说明与免责，避免误解。 | 维持信任。 |

## 六、实施优先级建议（无代码，仅顺序）

1. **P0（必做）**  
   - 在 `/start` 首屏（普通欢迎流程）即下发主键盘 `reply_main`，使「帮助、我的信用、最近查询、我的申诉、我的订阅」与「立即查询、获取邀请链接」同时可见。  
   - 保证下发结果页、我的信用、最近查询、我的申诉、我的订阅等回复时，必要时再次附带主键盘，避免键盘丢失。

2. **P1（强建议）**  
   - 在欢迎语或首屏增加「❓ 帮助」入口（内联或主键盘已包含即可），并确认帮助内容包含：查询、邀请、我的信用与出示报告、对方不信我、举报与申诉、数据说明。  
   - 统一「结果页 / 我的信用页」的回复中主键盘的附带策略（何时带、何时不覆盖），保证体验一致。

3. **P2（可选）**  
   - 新增「状态 / 我的动态」聚合入口（主键盘或内联），聚合最近查询、申诉状态、订阅数量与快捷跳转。  
   - 为管理员增加「📊 管理」按钮（或仅对 ADMIN_TG_IDS 展示），对应 /stats 或简易管理菜单。  
   - 若产品需要，增加轻量「我的报告」主键盘入口，指向我的信用或出示报告流程。

4. **P3（可选）**  
   - 后端：`/v1/my-summary` 或等价聚合接口；简单按钮点击/展示埋点。  
   - 市场：基于埋点做「功能发现率」与宣传素材。

## 七、小结

- **问题本质**：功能已实现，但主键盘未在首屏展示，导致「订阅、帮助、状态管理、报告」等入口难以发现，形成「都没有按钮」的体感。  
- **开发**：首屏下发主键盘、明确内联与主键盘分工、可选状态聚合与管理员入口；数据库可零变更或仅轻量扩展。  
- **市场**：首屏即展示完整能力与帮助，利于转化与品牌；可配合埋点做数据化运营。  
- **用户**：一进来就有完整菜单与帮助，我的信用/申诉/订阅/报告路径清晰，易用且安心。  

按 P0 → P1 → P2 顺序落地即可在**不写业务新功能**的前提下，显著改善「所有功能都有按钮展示」的体验。

## 八、实施记录（已完成 P0 + P1）

- **P0**：/start 普通流程首屏下发 `reply_main`；share/invite 流程所有出口（成功/失败/过期）均带 `reply_main`。✅  
- **P1**：帮助回复、我的信用、最近查询、我的申诉、我的订阅、邀请链接、举报提交（成功/失败/空原因/会话过期）、再查结果与错误、出示我的报告（成功/失败）、订阅列表（含空与异常）均附带主键盘；带内联键盘的列表/结果后追加一条「👇 使用下方菜单继续」+ `reply_main`（i18n：`menu_hint`），保证主菜单不丢失。✅  
- **细化**：所有错误分支（check_error、mycredit_error、report 失败、recheck 失败等）回复均带 `reply_main`，避免出错后键盘消失。  
- **P2**（管理员按钮、状态聚合）暂未实施，可作下一阶段。
