## 一、本次实施内容

### 1.1 任务 1.6：举报人统计（仅落数据）

| 项 | 实现方式 |
|----|----------|
| **数据表** | 新增 `reporter_stats`：`reporter_tg_id`（PK）、`total_reports`、`last_report_at`。 |
| **写入时机** | 在 `report_create()` 内，在写入 Report 与 Feedback、并执行 `enqueue_alerts_for_target` 之后：按 `reporter_tg_id` 查询或新建 `ReporterStats`，`total_reports += 1`、`last_report_at = now`，同一事务内 flush。 |
| **迁移** | `migrate_add_columns.py` 增加 PG / SQLite 下 `reporter_stats` 表的创建；新建库由 API 启动时 `create_all` 自动建表。 |
| **管理接口** | `get_admin_reporters` 仍按 Report 表聚合（举报数、已核实数、最后时间），未改为读 `reporter_stats`，避免行为变化；`reporter_stats` 仅作数据沉淀，供后续 4.3 举报人权重接入 scoring 使用。 |

### 1.2 钱包变动推送触发

| 项 | 实现方式 |
|----|----------|
| **触发点** | 用户**成功绑定**一条新收款地址时：在 `bind_wallet()` 内，在 `session.add(w)` 且 `flush` 成功后，调用 `enqueue_wallet_change_for_target(session, tg_id)`。 |
| **效果** | 订阅了该用户「钱包变动」的订阅者会被写入 `risk_alert_pending`，由 Bot 轮询拉取后按现有逻辑推送「钱包变动」提醒。 |
| **范围** | 当前仅对「用户主动绑定」（UserBoundWallet）触发；若日后有写入 WalletEntityGraph 的入口（如系统发现关联），可在该处同样调用 `enqueue_wallet_change_for_target`。 |

## 二、在方案基础上的优化与细化

### 2.1 举报人统计

- **单表设计**：采用独立表 `reporter_stats` 而非仅依赖 Report 聚合，便于后续扩展 `verified_count`/`rejected_count` 及 scoring 权重，且与「仅落数据」不冲突。
- **事务一致**：举报人统计与 Report、Feedback、alert 入队放在同一事务，保证要么全成功要么全回滚。
- **迁移兼容**：PG 与 SQLite 均用「若表不存在则创建」，对已有库执行 `python migrate_add_columns.py` 即可，新建库由 create_all 处理。

### 2.2 钱包变动推送

- **仅绑定触发**：文档中「写入钱包关联」包含绑定与可能的系统关联；当前代码中仅 `bind_wallet` 会新增用户与地址的关联，故只在此处调用 enqueue，逻辑清晰、易排查。
- **不重复入队**：`enqueue_wallet_change_for_target` 内部已有时段去重与限频（`ALERT_RATE_LIMIT_HOURS`、`_alert_skip_set`），同一用户短时间多次绑定不会对同一订阅者重复刷屏。

### 2.3 未做但可后续做的

- **ReporterStats 与 get_admin_reporters**：管理端举报人列表仍从 Report 聚合，未改为读 `reporter_stats`，避免对现有管理行为做任何改变；若未来希望「举报人列表」与 scoring 共用同一数据源，可再让 `get_admin_reporters` 优先使用 `reporter_stats` 的 total / last_report_at。
- **update_report_status 时更新 ReporterStats**：任务 1.6 仅要求「report_create 时更新」。若后续在 ReporterStats 中增加 `verified_count`/`rejected_count`，可在 `update_report_status` 中根据 status 变更维护这两个字段。

## 五、下一阶段实施建议（P1 及可选 P2）

### 5.1 P1：体验与数据能力（建议顺序）

| 优先级 | 功能 | 实施要点 | 可做的优化 |
|--------|------|----------|------------|
| **高** | **本系统活动时间线** | 已有 `ActivityEvent` 表（target_tg_id, event_type, created_at）；在查询/邀请打开/分享被查看等时机写入事件；新增 GET 接口按用户返回最近 N 天或 N 条；Bot 在报告或「我的信用」中展示「本系统活动」区块（按日聚合文案）。 | 事件类型先做 queried / invite_clicked，再扩展 share_viewed；展示限制「最近 30 天」或最多 N 条，避免刷屏；文案明确「本系统可记录活动」，不涉及 Telegram 在线状态。 |
| **中** | **谁查过我（增强）** | 已有 CheckLog(querier_tg_id, target_tg_id, created_at)；若当前「我的信用」仅展示被查次数/最近时间，可增加「最近何人何时查过我」：需权限与隐私策略（仅本人可见、可选脱敏「某用户」+ 时间）。 | 首版可仅展示「最近 7 天被查次数」+「最近一次被查时间」，不暴露具体 querier，降低隐私与存储争议；若需「何人」，再上脱敏与合规策略。 |
| **中** | **报告复制/再次发送** | Bot 结果卡增加「复制报告」或「再次发送报告」按钮；再次发送 = 将当前报告正文以一条新消息发给用户，便于转发或自留。 | 先做「再次发送」成本低；「带 report_no 的链接」可后置，需设计链接格式与后端解析（如 start=report_xxx）。 |
| **低** | **帮助/FAQ 结构化** | 将帮助拆成多段（查询方式、邀请、我的信用、举报与纠错、数据说明），每段小标题 + 内容；仅 i18n 与 help_cmd 调整。 | 拆成 help_section_* 多个 key，便于多语言与后续单独维护。 |
