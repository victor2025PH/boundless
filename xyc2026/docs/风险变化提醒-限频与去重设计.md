# 风险变化提醒 — 限频与去重设计

## 一、目标

- **去重**：同一订阅者、同一被关注对象、同一事件类型，在「未发送」状态下只保留一条待发；避免同一 target 被多人连续举报时，对同一用户重复入队多条相同类型的提醒。
- **限频**：同一 (订阅者, 被关注对象, 事件类型) 在**最近 N 小时内**最多入队一次（不论是否已发送）；避免 24h 内对同一目标同一类型事件多次推送。

## 二、规则定义

| 维度 | 说明 |
|------|------|
| **去重** | 若已存在一条 `(subscriber_tg_id, target_tg_id, event_type)` 且 `sent_at IS NULL`，则本次**不再插入**。发送后该条被标记 `sent_at`，下次触发可再次入队。 |
| **限频** | 若已存在一条 `(subscriber_tg_id, target_tg_id, event_type)` 且 `created_at >= now - N 小时`（不论 `sent_at`），则本次**不再插入**。默认 N=24。 |

两者同时生效：**先满足去重，再满足限频**。即：若已有未发送则跳过（去重）；若 24h 内已有任意一条（含已发送）则也跳过（限频）。

## 三、实现位置与方式

- **位置**：`services.enqueue_alerts_for_target`，在「按订阅列表逐条插入 `RiskAlertPending`」之前，先算出一批「本次应跳过的 (subscriber_tg_id, target_tg_id, event_type)」。
- **方式**：  
  1. 查询 `risk_alert_pending` 中满足以下条件的**去重** `(subscriber_tg_id, target_tg_id, event_type)`：  
     `target_tg_id = ?` AND `event_type = ?` AND `sent_at IS NULL`。  
  2. 再查满足**限频**的**去重**三元组：  
     `target_tg_id = ?` AND `event_type = ?` AND `created_at >= now - N 小时`。  
  3. 合并两个集合得到「本次需跳过的 (sub, target, event_type)」；遍历订阅列表时，若当前项在该集合内则跳过插入，否则插入并带上 `subscriber_lang` 等字段。

为减少查询次数，可合并为**一条 SQL**：  
`SELECT DISTINCT subscriber_tg_id, target_tg_id, event_type FROM risk_alert_pending WHERE target_tg_id = ? AND event_type = ? AND (sent_at IS NULL OR created_at >= ?)`，其中 `?` 为 `now - N 小时`。  
将结果放入集合 `skip_set`，插入前判断 `(subscriber_tg_id, target_tg_id, event_type) in skip_set` 则跳过。

## 四、配置

- **限频窗口**：常量 `ALERT_RATE_LIMIT_HOURS = 24`（可后续改为配置项）。  
- **关闭限频**：将 `ALERT_RATE_LIMIT_HOURS` 设为 0 或负数，则仅做去重（只检查 `sent_at IS NULL`），不做时间窗口限制。

## 五、边界说明

- **新举报 vs 新拉黑**：`event_type` 不同（`new_report` / `blacklist_added`），因此同一 target 在同一天内可各收到一条「新举报」和「被拉黑」提醒，互不影响。
- **多 target**：不同 `target_tg_id` 独立计算，同一订阅者对 A、B 两个 target 的提醒互不干扰。
- **历史数据**：表中已有的旧待发记录会参与去重与限频判断；无需迁移。

## 六、与现有流程的衔接

- 在 `enqueue_alerts_for_target` 内：  
  1. 先执行上述「跳过集合」查询（一条 SQL，参数：`target_tg_id`, `event_type`, `now - N 小时`）。  
  2. 遍历订阅列表时，若 `(subscriber_tg_id, target_tg_id, event_type)` 在跳过集合中则 `continue`，否则 `session.add(RiskAlertPending(...))`。  
  3. 最后 `flush` 与现有逻辑一致。  

无需改表结构、无需新增 API、Bot 侧无改动。

- **已实现**  
  - `services._alert_skip_set(session, target_tg_id, event_type, since)`：查询满足「去重」或「限频」的 `(subscriber_tg_id, target_tg_id, event_type)` 集合（一条 `SELECT DISTINCT ... WHERE ...`）。  
  - `enqueue_alerts_for_target` 在插入前调用 `_alert_skip_set`（限频窗口 `ALERT_RATE_LIMIT_HOURS = 24`，若为 0 则仅按未发送去重）；若 `(sub, target, event_type)` 在集合内则跳过插入。
