# TrustCheck 升级方案对比与优化建议

> 对比「另一 AI 的硬核信用报告与用户自证系统」方案与**当前已实现功能**，并给出可落地的分阶段优化建议。

---

## 一、方案 vs 现状 对照表

| 方案项 | 方案描述 | 当前实现情况 | 差距说明 |
|--------|----------|--------------|----------|
| **报告唯一指纹** | 每份报告底部 8 位哈希（如 TX-78A2B9），可验真 | 有「报告编号」R+时间+2 随机字符，**非存库可验真** | 编号仅展示用，未入库、无 /verify |
| **/verify [指纹]** | 输入指纹返回「真实有效/篡改」 | 无 | 需 report_snapshots 表 + 生成时落库 |
| **多源数据标识** | [Official]/[Crowd]/[Network]/[On-Chain] 在字段前 | 无显式来源标签 | 数据实际来自 TG/举报/钱包，未在文案中标出 |
| **我的隐私设置** | /my_privacy，勾选：注册年/Premium/30天成交/保证金 | 仅有「被查通知」开关（我的信用内） | 无隐私矩阵、无保证金/成交展示控制 |
| **平台保证金 Trust Deposit** | TON 质押 5–10 TON，报告显示「已缴纳履约保证金」 | 无 | 需 TON 对接、托管/合约、合规与运营 |
| **资产验证 Asset Proof** | 绑定 TRC20/TON，RPC 校验余额，报告显示「已验证余额」 | 有 wallet_entity_graph 关联，**无余额查询** | 需 RPC 与展示逻辑；隐私与安全需设计 |
| **动态标签** | [高频更名]/[换号嫌疑]/[稳定商户] 等 | 有 tag（新账号、有举报、黑名单、Premium、商户） | 无「30天更名次数」「多封禁ID关联」「180天无争议」等数据源 |
| **四维度风险雷达** | 身份稳定性、资金实力、社区评价、关联风险 | 单一分数 + risk_level + tips | 无多维度拆解展示 |
| **转发隐私拦截** | 对方隐藏来源时，回复「专属诱导查询链接」 | **已实现**：`forward_sender_name` 时提示「对方开启隐私」+ **获取邀请链接** | 与方案一致，仅文案可再强化 |
| **报告防篡改** | content_hash 校验 | 无 | 需生成时存 content_hash，verify 时比对 |

---

## 二、结论摘要

- **已对齐或易对齐**：转发隐私 + 邀请链接、报告编号（扩展为可验真指纹 + /verify）、多源标识（文案层）、我的隐私（扩展为多开关）。
- **需新增数据或外部能力**：保证金（TON 集成）、余额校验（TRC20/TON RPC）、动态标签（更名/封禁关联/担保群 180 天等需埋点或第三方）。
- **方案中未明确实现路径的**：「127 部手机矩阵」监控、担保群内 180 天无争议等，当前仅有众包上报 + 可选监控端，可视为后续数据源扩展。

---

## 三、推荐分阶段优化方案（可落地）

在不改变「免费、不加复杂操作、不动核心动线」的前提下，按**可信度**与**自证能力**分步做。

---

### 阶段 A：报告防伪与多源标识（优先、无外部依赖）

**目标**：报告可验真、来源可辨识，提升「硬核」感。

| 项 | 内容 | 实现要点 |
|----|------|----------|
| 1. 报告指纹入库 | 报告生成时生成 8 位唯一码（如 `TC-78A2B9`），并写入 `report_snapshots`（report_hash, target_tg_id, content_hash, created_at） | 新增表 + 迁移；`format_result` 或 API 层在返回前生成 hash 与 content_hash（报告正文或关键字段的 hash），落库后把 report_hash 写入报告末尾 |
| 2. /verify 指令 | Bot 命令 `/verify TC-78A2B9`：查 report_snapshots，存在则返回「该报告真实有效，生成于 [时间]」；不存在则「警告：该报告指纹不存在或已失效」；可选：用 content_hash 校验用户粘贴内容是否与存档一致（进阶） | 新 handler；API 可提供 GET /v2/report/verify?hash= 供 Bot 调 |
| 3. 多源标识（文案） | 在报告各区块前加标识，不改数据结构：如「首次记录」→ [Official]（若来自 TG）、举报/黑名单 → [Crowd]、关联钱包 → [On-Chain]、高危群/监控 → [Network] | 在 `format_result` 里按字段加前缀；若某数据暂无来源则不加或标 [System] |

**产出**：报告底都有可验真指纹、支持 /verify、报告内可见 [Official]/[Crowd]/[On-Chain]/[Network]，无需新数据源。

**✅ 阶段 A 已实施完成（当前代码库）**

- **报告指纹**：`report_snapshots` 表 + 迁移；`format_result` 后由 `append_report_footer()` 对正文做 sha256、调用 `POST /v2/report/register` 取得 8 位验真码（TC-xxxxxx），追加至报告末尾；所有出报告入口（/check、转发、邀请、我的信用、最近查询再查）均已接好。
- **/verify**：新 handler `/verify <code>`，调用 `GET /v2/report/verify`，返回「真实有效 / 生成时间」或「不存在或已篡改」；中英塔三语 i18n。
- **多源标识**：在 `format_result` 中按区块加前缀——身份与首次记录 / Premium 标 [Official]，举报/黑名单/举报分类/近 7·30 天标 [Crowd]，风险来源占比内 high_risk_groups 标 [Network]、new_account 标 [Official]、wallet_anomaly 标 [On-Chain]，关联钱包与同钱包多账号标 [On-Chain]。

**实施中的优化（相对原方案）**

1. **验真码生成**：由 API 统一生成并落库，Bot 只传 `content_hash`，避免 Bot 与 API 重复逻辑；验真时仅校验「指纹是否存在 + 生成时间」，未做「用户粘贴正文与 content_hash 比对」的进阶防篡改（可后续在 /verify 支持「粘贴报告正文」时再做）。
2. **多源标识粒度**：风险来源占比中每个因子单独标 [Crowd]/[Network]/[Official]/[On-Chain]，便于一眼区分数据来源。
3. **测试**：新增 `test_api_report_register_and_verify` 与 `test_format_result_has_required_sections` 中对多源标识的断言，以及 i18n 键 `report_footer_verify`、`verify_*` 的覆盖。

---

### 阶段 B：我的隐私设置（多开关）

**目标**：用户自主控制「对查阅者展示什么」。

| 项 | 内容 | 实现要点 |
|----|------|----------|
| 1. 隐私设置存储 | users 表增加 `privacy_settings` JSONB，如 `{"show_register_year": true, "show_premium": true, "show_tx_30d": true}` | 迁移 + Model；默认全 true 以兼容现有 |
| 2. /my_privacy 交互 | Bot 内 /my_privacy 或「我的信用」下入口：Inline Keyboard 每项 ON/OFF（展示注册年份、展示 Premium、展示近 30 天成交笔数） | 同被查通知开关模式；API PATCH /v1/user/privacy 写入 |
| 3. 报告按隐私过滤 | check 与 report 生成时根据 target 的 privacy_settings 决定是否展示「首次记录」「Premium」「近 30 天交易笔数」 | 在 `check_by_tg_id` 或 format_result 中读 privacy，不返回或替换为「未公开」 |

**产出**：用户可开关「注册年/Premium/30 天成交」对查阅者的展示，报告尊重隐私设置。

**✅ 阶段 B 已实施完成（当前代码库）**

- **存储**：`users.privacy_settings` JSONB，默认 `{"show_register_year": true, "show_premium": true, "show_tx_30d": true}`；提供 `PATCH /v1/user/privacy`（或 `/v2/user/me/privacy`）写入；`check_by_tg_id` / 报告生成时读取被查人的 `privacy_settings`，决定是否在报告中展示「首次记录」「Premium」「近 30 天成交笔数」。
- **API**：`GET /v1/user/privacy?tg_id=`、`PATCH /v1/user/privacy`（部分更新）；遮蔽在 `check_by_tg_id` 内统一处理。
- **Bot**：`/my_privacy` 与「我的信用」内「🔒 隐私设置」；三项 Inline 一行一开关；中英塔三语。**优化**：PATCH 部分更新、默认兼容、交易项整块遮蔽、入口统一便于扩展「展示保证金状态」。

---

### 阶段 C：四维度风险雷达（展示层）

**目标**：不立刻改评分模型，先做「展示拆分」，为后续数据留口。

| 项 | 内容 | 实现要点 |
|----|------|----------|
| 1. 四维度展示 | 在报告中增加「风险维度」区块：身份稳定性（账号年龄、更名等，当前仅年龄）、资金实力（预留，暂无余额/保证金则显示「未验证」）、社区评价（举报/黑名单/交易确认）、关联风险（同钱包多号、高危群） | 用现有 tips/score/blacklist/report/transaction 数据映射到四维；文案如「身份稳定性：中」「资金实力：未验证」 |
| 2. 动态标签扩展 | 在现有 tag 基础上，若有数据再加：如「换号嫌疑」（同钱包关联过已封禁 ID 时）、「稳定商户」（需担保群活跃 180 天数据，暂无则可后补） | 先做「换号嫌疑」：同钱包下是否有 blacklist 或高风险；「高频更名」需 username 变更历史，当前多无此数据可暂缓 |

**产出**：报告中有四维度雷达式展示；标签在数据允许时逐步加，不强行依赖未有的数据源。

**✅ 阶段 C 已实施完成（当前代码库）**

- **四维度**：在 `check_by_tg_id` 中通过 `_compute_risk_dimensions()` 计算 identity/funds/community/association 四档（高/中/低/未验证/未知），写入 `risk_dimensions`；`format_result` 在「下一步建议」与「标签」之间增加「📊 风险维度」区块展示；资金实力固定「未验证」预留。
- **换号嫌疑**：`_linked_wallet_has_blacklist_or_high_risk()` 查询同钱包其他 ID 是否在黑名单或 risk_level 为 high/extreme；若存在则打标 `tag_same_wallet_risk`（i18n：换号嫌疑 / Same-wallet risk）。
- **数据**：结果中增加 `high_risk_group_count` 与 `risk_dimensions`，API 与 Bot 一致；社区评价维度结合举报数、黑名单与交易成功率判定档位。

**实施中的优化**：四维与总分/等级并存不替代；身份按首次记录月数划分档位；关联风险由 linked_tg_count + high_risk_group_count 映射；标签与维度共用 i18n（dim_* / tag_same_wallet_risk）。

---

### 阶段 D：资产验证与保证金（重、需合规与产品决策）

**目标**：仅做技术预留与最小可行，不承诺完整产品。

| 项 | 内容 | 实现要点 |
|----|------|----------|
| 1. 钱包余额校验（可选） | 用户绑定 TRC20/TON 后，后台通过公共 RPC 查余额；报告展示「已验证余额：>10,000 USDT」档位（区间即可，避免精确值） | 需 RPC 对接、频率与缓存策略、隐私（谁可看）；建议单独评审后再开发 |
| 2. 保证金（Trust Deposit） | 方案中的 TON 质押、赔付基金涉及资金与合规，建议**仅做产品与合规评审**；若要做，可先做「保证金状态」布尔 + 金额字段，展示「已缴纳平台履约保证金」由运营后台录入，不接链上 | 表字段可预留；链上集成与赔付规则后置 |

**下一阶段（阶段 D）实施要点与可做优化**

1. **表与展示预留**：`users` 可预留 `deposit_amount`、`wallet_balance_verified`（或单独「资产快照」表）；报告「资金实力」维当前为「未验证」，接入后改为按档位显示（如「已验证余额 >10k USDT」或「已缴保证金」）。
2. **钱包余额**：TRC20/TON 通过公共 RPC 查余额需频率与缓存策略、隐私策略（谁可看、是否需用户授权）；建议单独评审后再实现。
3. **保证金**：若仅运营录入「已缴保证金」状态，可只加布尔/金额字段与后台 API，不接链上；链上质押与赔付规则后置。

**建议**：阶段 D 不纳入首轮开发，仅保留文档与表结构预留；等有明确合规与运营方案再动。

---

## 四、实施优先级建议

1. **先做阶段 A**：报告指纹 + report_snapshots + /verify + 多源标识。成本低、无外部依赖、立刻提升「可验真」与「来源透明」。
2. **再做阶段 B**：/my_privacy 与隐私矩阵。与现有「被查通知」开关一致，用户心智易理解。
3. **然后阶段 C**：四维度 + 标签扩展。用现有数据即可做出雏形，后续有更多数据再增强。
4. **阶段 D**：仅预留与文档，不列入当前迭代。

---

## 五、与「另一 AI 方案」的取舍说明

| 方案原意 | 建议 |
|----------|------|
| 8 位哈希 + 验真 | ✅ 做，并入库 + /verify，增强防伪。 |
| 多源标识 [Official]/[Crowd]/[Network]/[On-Chain] | ✅ 做展示层，不改变现有数据结构。 |
| 我的隐私 + 多选项 | ✅ 做，与现有「被查通知」并列。 |
| 四维度风险雷达 | ✅ 先做展示层映射，再逐步补数据。 |
| 平台保证金 TON | ⚠️ 仅预留字段与产品讨论，不接链上。 |
| 资产验证 RPC 余额 | ⚠️ 单独评审隐私与安全后再做。 |
| 高频更名/换号嫌疑/稳定商户 | ⚠️ 有数据则加（如 username 历史、封禁关联、担保群活跃），无则延后。 |
| 转发隐私 + 专属链接 | ✅ 已实现，仅可优化文案。 |

按上述顺序落地，可在不引入重资产与合规风险的前提下，把 Bot 升级为「带防伪指纹、带来源标识、支持隐私自选、多维度展示」的信用报告与自证体验；保证金与链上验证作为后续阶段，有明确需求与合规后再接。
