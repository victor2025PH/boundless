# 风险变化提醒 — 订阅表设计与触发流程（方案与接口草案）

## 一、需求简述

用户对某 ID 订阅「**有变化时提醒我**」；当该用户**新增举报**或**被拉黑**时，向订阅者发送一条 Bot 消息。

## 二、表结构设计

### 2.1 订阅表 `risk_alert_subscriptions`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int PK | 自增主键 |
| subscriber_tg_id | bigint | 订阅者（要收提醒的用户） |
| target_tg_id | bigint | 被关注对象（有变化时通知订阅者） |
| created_at | datetime | 订阅时间 |

- **唯一约束**：`(subscriber_tg_id, target_tg_id)`，同一用户对同一对象只保留一条订阅。
- **限制**：单用户最多订阅 N 个 target（如 20），防止滥用。
- **索引**：`subscriber_tg_id`（查「我的订阅」）、`target_tg_id`（触发时查「谁订阅了该 target」）。

### 2.2 待发送提醒表 `risk_alert_pending`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int PK | 自增主键 |
| subscriber_tg_id | bigint | 接收人 |
| target_tg_id | bigint | 被关注对象 |
| event_type | varchar(32) | 事件：`new_report` / `blacklist_added` |
| created_at | datetime | 生成时间 |
| sent_at | datetime nullable | 发送成功时间（NULL=未发送） |

- **用途**：触发时按订阅关系写入待发记录；Bot 轮询或拉取未发送记录，发消息后更新 `sent_at`。
- **索引**：`(sent_at)` 或 `sent_at IS NULL` 的查询，便于 Bot 拉取待发列表。
- **清理**：可定时删除 `sent_at` 已设置且超过 7 天的记录，或保留做审计。

## 三、触发流程

### 3.1 触发点 1：新增举报

- **位置**：`services.report_create` 在成功写入 `Report`（及同步的 `Feedback`）之后。
- **动作**：根据 `target_tg_id` 查出所有订阅该 target 的 `subscriber_tg_id`，为每个订阅者插入一条 `risk_alert_pending`（`event_type='new_report'`）。
- **排除**：可选排除 `reporter_tg_id`，避免举报人自己收到「有人举报了 TA」的提醒（举报人已知情）。

### 3.2 触发点 2：被拉黑（预留）

- **位置**：未来若增加「加入黑名单」接口（如 `POST /v1/admin/blacklist` 或内部 `blacklist_add(session, tg_id, ...)`），在成功写入 `Blacklist` 之后。
- **动作**：同上，根据 `tg_id` 查订阅者，插入 `risk_alert_pending`（`event_type='blacklist_added'`）。
- **当前**：代码中暂无「加黑」写入口，可在实现管理端加黑时再接入。

### 3.3 流程小结

```
[用户/管理员操作] → Report 创建 或 Blacklist 新增
       ↓
enqueue_alerts_for_target(session, target_tg_id, event_type, exclude_tg_id=?)
       ↓
查询 risk_alert_subscriptions WHERE target_tg_id = ?
       ↓
对每个 subscriber（且 ≠ exclude_tg_id）INSERT risk_alert_pending
       ↓
Bot 拉取 sent_at IS NULL 的记录 → 发 Telegram 消息 → PATCH 标记 sent_at
```

## 四、接口草案

### 4.1 用户侧（Bot 代调）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/v1/alert/subscribe` | 订阅：`tg_id`（当前用户）, `target_tg_id`（被关注对象）。返回 201；已订阅则 409。超过订阅上限 400。 |
| DELETE | `/v1/alert/subscribe` | 取消订阅：`tg_id`, `target_tg_id`。返回 204 或 404。 |
| GET | `/v1/alert/subscriptions` | 我的订阅列表：`tg_id`。返回 `{ "items": [ { "target_tg_id", "created_at" }, ... ] }`。 |

### 4.2 Bot 消费待发（内网/鉴权）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/v1/alert/pending` | 拉取待发送提醒（如 `limit=50`）。需 **Admin Key**（与现有管理接口同源）。返回 `{ "items": [ { "id", "subscriber_tg_id", "target_tg_id", "event_type", "created_at" }, ... ] }`。 |
| PATCH | `/v1/alert/pending/{id}` | 标记已发送：Body `{ "sent": true }`，服务端设置 `sent_at=now()`。需 Admin Key。用于 Bot 发完消息后回调。 |

### 4.3 请求/响应示例（草案）

**POST /v1/alert/subscribe**

- Query: `tg_id=123`, `target_tg_id=456`
- 201: `{ "status": "subscribed", "target_tg_id": 456 }`
- 409: `{ "detail": "Already subscribed" }`
- 400: `{ "detail": "Subscription limit reached" }`

**GET /v1/alert/subscriptions?tg_id=123**

- 200: `{ "items": [ { "target_tg_id": 456, "created_at": "2025-02-16 12:00:00" } ] }`

**GET /v1/alert/pending?limit=50**（Header: Authorization: Bearer &lt;bot_key&gt;）

- 200: `{ "items": [ { "id": 1, "subscriber_tg_id": 123, "target_tg_id": 456, "event_type": "new_report", "created_at": "..." } ] }`

**PATCH /v1/alert/pending/1**（Body: `{ "sent": true }`）

- 200: `{ "ok": true }`

## 五、Bot 侧行为（草案）

1. **订阅入口**：在查询结果卡片的 inline 键盘增加「有变化时提醒我」按钮，`callback_data=alert_subscribe_{target_tg_id}`；已订阅则显示「已订阅提醒」或「取消提醒」。
2. **取消入口**：「我的订阅」列表（可从「我的信用」或设置进入）展示已关注 ID，每项提供「取消提醒」。
3. **发送逻辑**：Bot 进程内后台任务（如每 30s）调用 `GET /v1/alert/pending`，对每条记录向 `subscriber_tg_id` 发一条消息（文案见下），再调用 `PATCH /v1/alert/pending/{id}` 标记已发送。若发送失败可重试或保留记录下次再取。
4. **文案**（i18n）：  
   - `new_report`：您关注的 ID {target_tg_id} 收到新举报，建议重新查询其报告。  
   - `blacklist_added`：您关注的 ID {target_tg_id} 已被加入黑名单，请谨慎交易。

## 六、配置与安全

- **订阅上限**：每用户最多订阅数（如 20）写入配置或常量。
- **Bot 拉取鉴权**：`GET/PATCH /v1/alert/pending` 使用与 Admin 同源或单独的 Bot 密钥，避免暴露给普通用户。
- **频率**：可对同一 (subscriber, target, event_type) 在短时间（如 24h）内去重或限条数，避免同一事件重复提醒（当前草案为「每次举报一条待发」）。

## 七、与现有代码的衔接

- **models**：新增 `RiskAlertSubscription`、`RiskAlertPending`，在 `database.Base.metadata.create_all` 时一并建表。
- **services**：新增 `alert_subscribe`、`alert_unsubscribe`、`alert_list_subscriptions`、`enqueue_alerts_for_target`、`get_pending_alerts`、`mark_alert_sent`；在 `report_create` 末尾调用 `enqueue_alerts_for_target(session, target_tg_id, "new_report", exclude_tg_id=reporter_tg_id)`。
- **api/main.py**：注册上述路由；`/v1/alert/pending` 使用 `_require_admin` 或新增 `_require_bot_key`。
- **bot**：在结果页键盘增加订阅/取消按钮；新增后台任务拉取 pending 并发送；i18n 增加提醒文案与按钮文案。

  - 结果页「有变化时提醒我」按钮（`inline_result_actions`）与 callback `alert_subscribe_{target_tg_id}`；订阅/已订阅/上限文案。

- **数据库升级（若表已存在）**  
  - 新增列：`risk_alert_subscriptions.preferred_lang`（VARCHAR(8)）、`risk_alert_pending.subscriber_lang`（VARCHAR(8)）。若表为旧版创建，需执行：  
    `ALTER TABLE risk_alert_subscriptions ADD COLUMN preferred_lang VARCHAR(8);`  
    `ALTER TABLE risk_alert_pending ADD COLUMN subscriber_lang VARCHAR(8);`  
  - 新部署直接 `create_all` 即可。

- **已实现（推送语言 + 黑名单触发）**  
  - **推送按用户语言**：订阅表增加 `preferred_lang`（en/zh/tl），待发表增加 `subscriber_lang`；订阅时 Bot 传 `lang`，触发时写入 pending；Worker 按 `subscriber_lang` 调用 `t(..., lang=push_lang)` 发送。  
  - **黑名单触发**：`services.blacklist_add(session, tg_id, reason=..., source=...)` 在新增黑名单后调用 `enqueue_alerts_for_target(..., "blacklist_added")`；`POST /v1/admin/blacklist`（Admin Key）Body `{ "tg_id", "reason?", "source?" }`，返回 `{ "ok", "added" }`（added=true 表示本次新加入，false 表示已在黑名单未重复触发）。
