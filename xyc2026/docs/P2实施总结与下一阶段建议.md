## 一、本次实施内容

### 1.1 限流（P2-1）

| 项 | 实现方式 |
|----|----------|
| **/check 限流** | 按「调用方」每分钟限制次数：调用方 = `querier_tg_id`（若提供）或 `user_id`（自查场景）。限制值取自配置 `rate_limit_check_per_min`（默认 10）。超限返回 **429**，`detail="rate_limit_check"`。 |
| **/report 限流** | 按 `reporter_tg_id` 每分钟限制次数，限制值取自 `rate_limit_report_per_min`（默认 3）。超限返回 **429**，`detail="rate_limit_report"`。 |
| **实现方式** | 内存字典按 key（如 `check:{tg_id}`、`report:{tg_id}`）记录 (count, window_start)；每请求更新计数，超过 60 秒则重置窗口；字典超过 50000 条时清理过期 key，避免无限增长。**未接入 Redis**，满足当前单实例需求；后续可替换为 Redis 实现。 |
| **Bot 文案** | i18n 新增 `rate_limit_check`、`rate_limit_report`（中/英/塔加洛语），便于 Bot 在收到 429 时展示友好提示。 |

### 1.2 生产环境管理接口强制 Admin Key（P2-2）

| 项 | 实现方式 |
|----|----------|
| **配置** | 新增 `production: bool = False`（环境变量 `PRODUCTION=1` 或 `true` 时为 True）。 |
| **逻辑** | `_require_admin`：当 `production=True` 时，若 `API_INTERNAL_KEY` 未设置或为空，返回 **403**，`detail="Admin key not configured"`；若已设置，则要求请求头 `Authorization: Bearer <key>` 与配置一致，否则 403。当 `production=False` 时，保持原行为（key 未设置则不做校验）。 |
| **.env.example** | 增加 `PRODUCTION=0` 说明。 |

### 1.3 举报人权重接入 scoring（P2-3）

| 项 | 实现方式 |
|----|----------|
| **ReporterStats 扩展** | 表 `reporter_stats` 增加 `verified_count`、`rejected_count`（默认 0）。迁移脚本（PG/SQLite）支持新建表时包含两列，并对已有表执行 ADD COLUMN（若不存在）。 |
| **update_report_status** | 管理端将举报设为 verified 或 rejected 时：更新对应举报人的 ReporterStats（`verified_count` 或 `rejected_count` +1）；并同步被举报人的 `User.report_count`（verified 举报总数），保证与 Report 表一致。 |
| **有效举报数** | 新增 `_effective_report_count_for_target(session, target_tg_id)`：取该目标所有 status=verified 的举报的 reporter_tg_id，再查 ReporterStats，按「举报人可信度」加权求和。可信度 = `verified_count / max(total_reports, 1)`，限制在 0~1；无统计时权重 1.0。 |
| **scoring 接入** | `compute_score_and_tips` 增加可选参数 `effective_report_count`；若传入则用其参与报告因子计算，否则仍用 `report_count`。`recompute_user_score` 中先调用 `_effective_report_count_for_target`，将结果传入 scoring。 |
| **效果** | 举报来自「历史核实率高」的举报人时，对分数影响略大；来自「核实率低或新举报人」时影响略小，降低恶意举报权重。 |

## 二、在方案基础上的优化与细化

### 2.1 限流

- **不依赖 Redis**：采用与现有 flow 限流一致的内存结构，单实例下即可生效，部署简单；后续若有 Redis，可抽成统一限流接口再切换实现。
- **清理策略**：key 数超过 50000 时按窗口时间清理过期项，避免长期运行内存膨胀。
- **/check 调用方**：用 `querier_tg_id` 优先标识调用方（Bot 传参），无则用 `user_id`（自查场景），避免仅用 username/wallet 时无法限流。

### 2.2 生产环境 Admin Key

- **显式开关**：用 `production` 控制是否强制 key，开发/测试可不设，生产显式开启，避免误开严格校验。
- **未配置即 403**：生产下若未配置 `API_INTERNAL_KEY`，管理接口直接 403，促使上线前完成配置。

### 2.3 举报人权重

- **可信度公式**：`verified_count / total_reports`，除零用 `max(total_reports, 1)`；无 ReporterStats 时权重 1.0，兼容老数据。
- **同步 User.report_count**：在 `update_report_status` 中按 Report 表重新统计目标用户的 verified 数并写回 User，保证 `recompute_user_score` 使用的 `user.report_count` 与真实 verified 数一致。
- **tips 展示**：tips 仍使用「Reported by N user(s)」的原始 `report_count`，不展示加权值，便于用户理解「举报人数」。

### 2.4 未做但可后续做

- **Redis 限流**：需要时可实现基于 Redis 的限流（如 INCR + EXPIRE），并保留与当前配置（rate_limit_*_per_min）一致。
- **异常检测**：同 IP/设备批量举报降权需 IP 或设备数据源，暂未实现。
- **独立 Worker**：推送轮询仍由 Bot 进程承担，未拆出。

- 已执行 `python migrate_add_columns.py`（PG）：输出包含 `[ADD] reporter_stats.verified_count`、`reporter_stats.rejected_count`（或已存在）。
- 已执行 `python run_tests.py`：全部用例通过。
- **建议人工验证**：  
  1）连续多次 /check（同一 querier_tg_id）超过 10 次/分钟后应返回 429。  
  2）同一用户连续多次举报超过 3 次/分钟后应返回 429。  
  3）设置 `PRODUCTION=1` 且不设或错误设置 `API_INTERNAL_KEY` 时，调用管理接口应返回 403。  
  4）将某举报设为 verified 后，该举报人 ReporterStats.verified_count +1，被举报人 User.report_count 与 Report 表 verified 数一致；再次 recompute 后分数应反映举报人权重。

## 五、下一阶段实施建议（后续可选）

### 5.1 可选功能与架构

| 优先级 | 功能 | 说明 |
|--------|------|------|
| **低** | **Redis 限流/缓存** | 多实例或高并发时，将 check/report 限流改为 Redis；可选对热点查询做短 TTL 缓存。 |
| **低** | **异常检测** | 同 IP/设备批量举报降权：需 Bot 或 API 上报 IP/设备标识后再实现。 |
| **低** | **独立 Worker** | 将风险提醒、被查通知等轮询从 Bot 拆出为独立进程，便于扩展与运维。 |
| **按需** | **管理后台前端** | 按《管理后台UI-完整对接方案》对接现有管理 API。 |

### 5.2 数据与策略优化

- **ReporterStats 与 get_admin_reporters**：管理端举报人列表可优先展示 ReporterStats 的 total_reports、verified_count、last_report_at，减少对 Report 全表聚合。
- **权重公式可配置**：可将「举报人可信度」公式或 effective 与 report_count 的混合方式做成配置项，便于运营调参。
- **限流错误体**：429 响应可增加 `Retry-After` 头或 `detail` 中剩余时间，便于前端/Bot 展示「N 秒后重试」。

## 六、小结

- **P2 已完成**：/check、/report 按调用方/举报人限流（内存实现）；生产环境下管理接口强制 API_INTERNAL_KEY；ReporterStats 增加 verified/rejected 计数并在 update_report_status 中维护；scoring 接入举报人权重（effective_report_count）；同步目标 User.report_count。
- **在方案基础上的优化**：限流不依赖 Redis、带清理策略；production 显式开关；举报人权重与 User.report_count 同步、可信度公式与无统计兼容处理。
- **下一阶段**：以可选为主（Redis 限流、异常检测、独立 Worker、管理后台前端），按需推进；可做 429 的 Retry-After 与举报人列表使用 ReporterStats 等小优化。
