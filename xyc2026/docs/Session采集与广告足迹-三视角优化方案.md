# Session 采集与广告足迹追踪 — 三视角优化方案

> **核心目标**：通过 Telegram Session 文件登入群组/频道，采集用户在各渠道发布的广告信息，形成「广告足迹」数据，融入信用卡片展示与风险评分。

### 1.2 Session 管理模块

**核心技术选型**：Telethon（Python 异步 Telegram MTProto 客户端）

**数据库表：`session_account`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK | 自增 |
| phone | str | 绑定手机号（加密存储） |
| session_name | str | session 文件名标识 |
| session_data | blob/text | session 文件内容（加密存储，或存文件路径） |
| status | str | active / banned / cooldown / revoked |
| joined_channels | int | 已加入频道/群数量 |
| last_active_at | datetime | 最近一次采集时间 |
| daily_request_count | int | 今日请求数（防封控制） |
| created_at | datetime | 创建时间 |
| note | str | 备注 |

**关键设计要点**：
- Session 文件内容必须**加密存储**（AES-256），密钥从环境变量读取，不入库不入代码
- 一个 session 对应一个 Telegram 账号，不与 Bot 共用
- Session 有生命周期管理：active → cooldown（触发频率限制时）→ banned（被封时）
- 后台管理页面可上传 `.session` 文件、查看状态、手动切换状态

**防封策略**：
- 单个 session 每日请求上限（建议 ≤200 次 API 调用）
- 加群/频道间隔 ≥ 30 秒，随机抖动
- 消息抓取间隔 ≥ 2 秒/频道
- 多 session 轮换：3-5 个 session 轮流工作
- 冷却机制：触发 FloodWait 后自动进入 cooldown 状态，等待指定时间
- 定期检查 session 有效性（尝试 GetMe）

### 1.3 频道/群组管理模块

**数据库表：`monitored_channel`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK | 自增 |
| channel_id | bigint | Telegram chat_id（负数群组，正数频道） |
| channel_type | str | group / supergroup / channel |
| title | str | 频道/群名 |
| username | str | @username（若有） |
| member_count | int | 成员数（定期更新） |
| category | str | 频道分类：crypto_otc / gambling / investment / trading / mixed / unknown |
| risk_level | str | 频道本身风险等级：low / medium / high |
| status | str | monitoring / paused / removed |
| last_scraped_at | datetime | 最近一次采集时间 |
| scrape_interval_min | int | 采集间隔（分钟），默认 60 |
| joined_via_session_id | int | 通过哪个 session 加入 |
| created_at | datetime | 添加时间 |

**后台操作**：
- 管理员可通过后台添加需监控的频道/群（输入 @username 或 chat_id）
- Worker 使用可用 session 自动加入
- 支持设置采集频率、暂停/恢复监控
- 显示每个频道的消息总量、活跃用户数、最新采集时间

### 1.4 消息采集与广告识别

**数据库表：`channel_message`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK | 自增 |
| channel_id | bigint | 所属频道/群 |
| message_id | int | Telegram 消息 ID |
| sender_tg_id | bigint | 发送者 TG ID（群消息有，频道消息可能为空） |
| sender_username | str | 发送者用户名 |
| text | text | 消息文本（截取前 2000 字符） |
| has_media | bool | 是否含图片/视频/文件 |
| is_ad | bool | 是否被标记为广告 |
| ad_type | str | 广告类型（见分类体系） |
| ad_confidence | float | 分类置信度 0-1 |
| created_at | datetime | 消息发送时间 |
| scraped_at | datetime | 采集时间 |

**广告分类体系（`ad_type` 枚举）**：

| 分类 | 标识 | 典型关键词 |
|------|------|-----------|
| OTC 换汇 | otc_exchange | USDT、换U、收U、出U、汇率 |
| 赌博推广 | gambling | 彩票、棋牌、百家乐、赔率、盘口 |
| 投资理财 | investment | 理财、年化、保本、分红、跟单 |
| 贷款借款 | loan | 贷款、借款、放水、下款、利息 |
| 色情引流 | adult | 约炮、楼凤、外围、私聊有惊喜 |
| 仿盘/资金盘 | ponzi | 拆分盘、互助金、静态收益、动态收益 |
| 刷单跑分 | money_mule | 跑分、刷单、银行卡、收卡、过账 |
| 黑产工具 | black_tool | 接码平台、短信轰炸、钓鱼、ddos |
| 正常交易 | normal_trade | 正常商品/服务交易 |
| 其他 | other | 未匹配 |

**识别策略**（分层）：
1. **关键词规则引擎**（第一层，快速）：正则 + 关键词匹配，覆盖 80% 场景
2. **模式匹配**（第二层）：联系方式模式（频繁出现 @xxx、t.me/xxx）+ 金额模式（含数字+币种）
3. **预留 AI 接口**（第三层，未来）：接入 LLM 对模糊消息做分类

### 1.5 用户广告足迹聚合

**数据库表：`user_ad_footprint`**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK | 自增 |
| tg_id | bigint | 用户 Telegram ID（索引） |
| channel_id | bigint | 所在频道 |
| ad_type | str | 广告类型 |
| message_count | int | 该类型广告消息数 |
| first_seen_at | datetime | 最早一条时间 |
| last_seen_at | datetime | 最近一条时间 |
| sample_text | text | 示例消息文本（截取 200 字符） |
| updated_at | datetime | 最后更新时间 |

**联合唯一索引**：`(tg_id, channel_id, ad_type)`

**聚合逻辑**：
- Worker 每次采集后，按 sender_tg_id 聚合
- UPSERT：同一 (tg_id, channel_id, ad_type) 只更新计数和时间
- 定期任务：每日凌晨汇总，清理过期数据

### 1.6 与现有系统的集成

**信用卡片（Check API）增强**：
- `check_by_tg_id` 新增返回字段：
  ```
  ad_footprint_summary: {
    total_channels: int,        # 出现在多少个频道
    total_ad_messages: int,     # 广告消息总数
    ad_type_breakdown: {        # 按类型分布
      "otc_exchange": 15,
      "gambling": 3,
      ...
    },
    high_risk_ad_count: int,    # 高风险广告数（赌博+色情+黑产+资金盘）
    channels: [                 # 出现的频道列表
      { title, username, category, message_count, last_seen }
    ],
    first_ad_seen: str,         # 最早广告时间
    last_ad_seen: str,          # 最近广告时间
  }
  ```

**风险评分接入**：
- `scoring.py` 新增参数 `ad_risk_score`
- 计算方式：
  - 高风险广告类型（gambling, adult, ponzi, money_mule, black_tool）每条 -2 分
  - 出现在高风险频道每个 -3 分
  - 上限 -25 分
- 新增风险维度：`risk_dimensions.advertising` = high/medium/low/clean

### 1.7 Worker 架构

```
┌─────────────────────────────────────────┐
│              采集调度器 (Scheduler)        │
│  - 每分钟检查哪些频道需要采集              │
│  - 分配任务给可用 session                  │
│  - 监控 session 健康状态                   │
└─────────────┬───────────────────────────┘
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
 Session A  Session B  Session C
 (采集频道   (采集频道   (备用/冷却)
  1,2,3)     4,5,6)
    │         │
    ▼         ▼
 消息入库 → 广告识别 → 足迹聚合 → 分数更新
```

**运行方式**：独立进程 `run_collector.py`，可与 API 和 Bot 分别部署

## 二、市场经理视角

### 2.1 数据的商业价值

**广告足迹数据能回答的关键问题**：

1. **这个人可信吗？**
   - 一个在 10 个赌博群发广告的用户 vs 一个从未发过广告的用户 → 风险完全不同
   - 在 OTC 群活跃但从未被举报 → 可能是正常交易者

2. **这个人做什么的？**
   - 广告类型分布直接揭示用户的「职业画像」
   - 多类型混合发广告 → 可能是引流代理，风险更高

3. **趋势分析**
   - 某人突然在大量群组发广告 → 异常行为
   - 某频道突然涌入大量新广告 → 可能是新骗局

### 2.2 渠道风险分级

| 频道类别 | 风险等级 | 权重说明 |
|----------|---------|---------|
| 已知赌博/色情/黑产频道 | 🔴 高 | 在此活跃严重扣分 |
| OTC 交易群（无监管） | 🟠 中高 | 常规 OTC 扣分较少，但量大扣分 |
| 加密货币讨论群 | 🟡 中 | 正常讨论不扣分，发广告轻微扣分 |
| 正规商业频道 | 🟢 低 | 基本不影响信用 |
| 未分类 | ⚪ 待定 | 先不计分，人工或算法分类后生效 |

### 2.3 广告类型风险矩阵

| 广告类型 | 风险 | 对信用分影响 | 在卡片中的展示 |
|---------|------|------------|--------------|
| 赌博推广 | 🔴 极高 | -8 到 -15 | 红色警示标签「赌博广告活跃」 |
| 色情引流 | 🔴 极高 | -8 到 -15 | 红色标签「色情引流」 |
| 资金盘 | 🔴 极高 | -10 到 -20 | 红色标签「资金盘推广」 |
| 跑分刷单 | 🔴 高 | -6 到 -12 | 红色标签「跑分/刷单」 |
| 黑产工具 | 🔴 高 | -6 到 -12 | 红色标签「黑产工具」 |
| 贷款推广 | 🟠 中 | -3 到 -6 | 橙色标签 |
| 投资理财 | 🟡 中低 | -1 到 -3 | 黄色标签 |
| OTC 换汇 | 🟡 低 | 0 到 -2 | 中性标签 |
| 正常交易 | 🟢 无 | 0 | 不展示 |

### 2.4 关键指标（KPI）

- **频道覆盖率**：监控的高风险频道数 / 已知高风险频道总数
- **用户匹配率**：有广告足迹的用户数 / 总用户数
- **误判率**：被标记为广告但实际不是 / 总标记数（需定期抽检）
- **数据新鲜度**：各频道最新采集时间的平均延迟

### 2.5 合规与隐私边界

- 只采集**公开频道/群组**的消息，不采集私聊
- 不存储用户的个人信息（头像、简介等），只关联 tg_id
- 管理后台展示时，仅对管理员可见
- 信用卡片中只展示**聚合统计**（N个频道、N条广告），不展示原文
- 数据保留策略：消息原文 90 天后清理，聚合数据长期保留

## 五、实施优先级建议

### Phase 1（基础能力，1-2 周）
- Session 管理（数据库 + 后台页面 + 加密存储）
- 频道管理（数据库 + 后台页面 + 手动添加）
- 消息采集 Worker（Telethon + 基础采集 + 入库）

### Phase 2（广告识别，1-2 周）
- 关键词规则引擎（分类体系 + 正则匹配）
- 用户足迹聚合（定时任务 + UPSERT）
- 管理后台展示（频道消息列表 + 用户足迹页面）

### Phase 3（系统集成，1 周）
- Check API 增强（返回广告足迹摘要）
- 风险评分接入（ad_risk_score 参数）
- 信用卡片格式更新（新板块 + 新标签）
- 举报审核决策面板增加广告足迹

### Phase 4（优化与扩展）
- AI 辅助分类（接入 LLM）
- 频道自动发现（从已知频道的转发链挖掘新频道）
- 异常行为检测（广告突增告警）
- 数据清理策略（消息过期清理 + 聚合保留）

## 六、风险与注意事项

| 风险 | 等级 | 应对 |
|------|------|------|
| Session 被封 | 🟠 高 | 多 Session 轮换 + 频率控制 + 冷却机制 |
| Telegram ToS 合规 | 🔴 高 | 只采集公开频道，不骚扰用户，不发消息 |
| 误判（正常消息被标为广告）| 🟡 中 | 置信度阈值 + 人工抽检 + 管理员标注修正 |
| 数据量过大 | 🟡 中 | 消息 90 天清理 + 只存文本前 2000 字 + 聚合表分离 |
| Session 文件泄露 | 🔴 高 | AES 加密存储 + 环境变量密钥 + 最小权限原则 |
