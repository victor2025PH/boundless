|--------|----------|

## 二、在方案基础上的优化与细化

| 优化项 | 说明 |
|--------|------|
| **生成时间标注 UTC** | 生成时间后增加「(UTC)」，避免用户误以为本地时间，便于跨区沟通与存证时理解时间含义。 |
| **标签区始终展示** | 无标签时仍保留「🏷 标签 —」区块，报告结构固定，扫读时不会因「有时有、有时无」而错位；专业版面更一致。 |
| **帮助增加总标题** | 帮助页顶部增加「📌 帮助与说明」（及英/塔语），与报告分区风格统一，帮助入口更易识别。 |
| **报告编号可引用** | 编号用等宽字体展示（`report_no`），便于复制与口头引用，方便后续若有反馈/申诉时对应到某次报告。 |

## 四、下一阶段建议实施内容与可优化点

### 4.1 建议实施（按优先级）

| 优先级 | 功能 | 说明 | 依赖 |
|--------|------|------|------|
| **高** | **本系统活动时间线** | 在报告内或单独入口，免费展示「该用户在本系统内活动」时间线（被查、邀请打开等），按日/周聚合；命名与文案明确为「本系统可记录活动」，不涉及 Telegram 在线。 | 需后端：活动事件表（user_id, event_type, at）、写入时机（查询时、邀请打开时）、GET 接口；Bot 展示时间线文案或卡片。 |
| **中** | **我的信用 · 谁查过我** | 在「我的信用」中增加一块：最近何人何时查过我（可脱敏为「匿名用户」或「某用户」+ 时间）。 | 需后端：记录查询人 tg_id 与目标 tg_id、时间（或复用/扩展 query_log）；权限与隐私策略（仅本人可见）。 |
| **中** | **报告复制/分享** | 结果页增加「复制报告」或「分享」：复制为纯文本到剪贴板需 Mini App 或外部；Telegram 内可做「将报告以一条消息再次发送给用户」或「生成仅本人可用的报告链接」。 | Bot 侧：按钮 + 逻辑（如重发报告内容或生成带 report_no 的链接）；若做链接需后端短链或参数解析。 |
| **低** | **帮助/FAQ 结构化** | 帮助拆成多段（查询方式、邀请流程、我的信用、举报与纠错、数据说明），每段小标题 + 内容；可考虑分多条消息发送或折叠。 | 仅 i18n 与 help_cmd 拼接顺序，无新增接口。 |

### 4.2 下一阶段可做的优化改进

- **活动时间线**  
  - 事件类型先做「被查询」「邀请打开」两种即可，后续再加「举报相关」等。  
  - 展示格式：按「日期 + 事件类型」聚合，如「2026-02-16：被查询 3 次、邀请打开 1 次」，避免单条事件过多造成刷屏。  
  - 若单用户事件量很大，可限制「最近 30 天」或「最近 N 条」。

- **谁查过我**  
  - 首版可只展示「最近 7 天被查询次数」与「最近一次被查时间」，不展示具体查询人，降低隐私与存储压力；若需「何人」再考虑脱敏展示与合规。  
  - 需在查询接口或服务层写入「target_tg_id + querier_tg_id + at」；Bot 目前不向 API 传 querier，需在调用 check 时带上 querier_tg_id（或由 Bot 调新接口「记录查询」）。

- **报告分享**  
  - 先做「再次发送报告全文」按钮，用户可转发该消息给他人或自留，实现成本低。  
  - 「带 report_no 的链接」可后置，需设计链接格式与后端解析（如 t.me/bot?start=report_R202602161830-A1 需后端根据 report_no 取快照或提示「报告已过期」）。

- **帮助结构化**  
  - 将 help_body 拆成 help_section_query、help_section_invite、help_section_mycredit、help_section_report、help_section_data，在 help_cmd 中按顺序拼接并加小标题，便于后续单独维护与多语言。
