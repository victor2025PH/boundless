# 信用查 — 管理功能网页后台优化方案（多视角）

> 角色：全栈技术总监，UI/UX & Design，Database & Data Integrity，Functionality & Logic，Code Quality，Security，SRE & Performance，QA & Edge Cases，Business Value。  
> 目标：将现有「管理功能」从 Bot 命令/API 调用迁移为**网页后台**展示与操作，给出统一优化方案（不含代码实现）。

---

## 一、现状与范围

### 1.1 现有管理能力

| 能力 | 当前入口 | 数据/动作 |
|------|----------|-----------|
| 运营统计 | Bot `/stats`、API `GET /v1/admin/stats` | 今日查询数、总用户数、黑名单数、待处理举报数 |
| 申诉列表 | API `GET /v1/admin/feedback` | 按状态筛选，列表含 id / reporter_tg_id / target_tg_id / reason / status / created_at |
| 申诉处理 | API `PATCH /v1/admin/feedback/{id}` | 更新状态为 processed / rejected |
| 加黑名单 | API `POST /v1/admin/blacklist` | Body: tg_id, reason?, source?；触发 blacklist_added 提醒 |
| 待发提醒 | API `GET /v1/alert/pending`、`PATCH /v1/alert/pending/{id}` | Bot 轮询拉取、发送后标记；管理端仅间接依赖 |

### 1.2 鉴权方式

- 管理 API 统一依赖 **Header: Authorization: Bearer &lt;api_internal_key&gt;**（与 Bot 调用 API 共用 key）。
- 无单独「管理员账号/角色」表；无网页登录态。

### 1.3 待解决问题

- 管理员只能通过 curl/Postman 或 Bot `/stats` 看数字，**无可视化、无批量操作、无黑名单列表与审计**。
- 申诉处理需记 feedback_id 并调 PATCH，**效率低、易错**。
- 加黑仅 API，**无理由/来源留痕查看、无撤销或备注**。
- 无操作日志，**安全与合规审计不足**。

---

## 二、全栈技术总监视角：架构与边界

### 2.1 定位

- **网页后台**：仅面向内部管理员，用于「查看统计 + 处理申诉 + 管理黑名单 + 可选查看待发提醒/操作日志」。
- **与现有系统关系**：  
  - 复用现有 **FastAPI 管理 API**（/v1/admin/*），网页作为前端调用方。  
  - **不替代** Bot 的 /stats（可保留为快捷入口），不替代 Bot 对 /v1/alert/pending 的轮询与发送逻辑。
- **技术选型建议**：  
  - 前端：单页应用（SPA），可静态部署（如 Nginx/CDN），与 API 跨域调用。  
  - 后端：不新增业务后端服务，仅通过现有 FastAPI 暴露的管理接口；若需「网页登录态」再考虑在 API 层增加 Session/JWT（见安全视角）。

### 2.2 部署形态

- **同域**：网页与 API 同域（如 `/admin` 由同一 FastAPI 托管静态或反向代理），可减少 CORS 与 Cookie 域配置。  
- **分离**：网页单独域名/端口，API 显式配置 CORS 允许该源，Bearer Token 放在前端内存或短期 Cookie（见安全）。

### 2.3 接口策略

- **Phase 1**：网页直接调用现有 4 类管理 API（stats、feedback 列表/更新、blacklist 新增），不新增后端接口。  
- **Phase 2**：若需黑名单列表、操作日志、简单看板，再在 FastAPI 增加只读或小写入接口（见数据库与功能视角）。

---

## 三、UI/UX & Design 视角：交互与体验

### 3.1 信息架构

- **首页/总览**：单页展示 4 个统计卡片（今日查询、总用户、黑名单数、待处理举报），与现有 `AdminStatsResponse` 一致；可选「待发提醒数量」入口（仅数字或跳转列表）。  
- **申诉管理**：列表页，支持按状态 Tab 或下拉筛选（pending / processed / rejected）；行内展示 reporter_tg_id、target_tg_id、reason、created_at；行内操作：「通过」→ processed、「驳回」→ rejected；可选分页或「加载更多」。  
- **黑名单管理**：列表页（需后端新增列表接口）；行内展示 tg_id、reason、source、added_at；支持「新增」表单（tg_id 必填，reason/source 选填）；可选「移除黑名单」能力（需后端新增，见功能视角）。  
- **待发提醒（可选）**：只读列表，展示 pending 条目的 subscriber_tg_id、target_tg_id、event_type、created_at；用于排查 Bot 发送情况，不在此做「标记已发送」（仍由 Bot 调用）。

### 3.2 交互原则

- **先总后分**：总览 → 申诉/黑名单/提醒 分模块，每模块入口明确。  
- **关键操作二次确认**：加黑、驳回申诉 使用确认框或二次点击，避免误操作。  
- **即时反馈**：提交后 Toast/Inline 成功或失败，列表可自动刷新或保留当前筛选状态刷新。  
- **无账号时的登录**：若采用「仅 Bearer 固定 key」的 Phase 1，可做「一次输入 API Key 后存 sessionStorage/内存」的简易「登录」页，不落库；若 Phase 2 引入真实管理员账号，再做登录页与权限。

### 3.3 适配与可访问性

- 响应式：管理后台以桌面为主，平板可读；移动端可选只读总览。  
- 关键按钮与状态（如 pending/processed）具备足够对比度与可区分性（颜色+文案）。

## 四、Database & Data Integrity 视角：数据与一致性

### 4.1 现有表与读写

- **admin_stats**：来自聚合查询（query_log、users、blacklist、feedback），只读，无新增表。  
- **feedback**：已有 status；PATCH 仅更新 status，无历史版本表；若需「处理人/处理时间」可后续加字段（如 processed_at、processed_by）。  
- **blacklist**：当前仅插入（blacklist_add）；无列表 API 对应一条「黑名单列表」查询；无删除/撤销字段。

### 4.2 为网页后台建议的数据扩展（可选、按需）

- **黑名单列表**：  
  - 在现有 `Blacklist` 表上提供 **GET /v1/admin/blacklist**（分页、可选排序），无需新表。  
  - 若需「移除黑名单」：优先软删（如 status=removed 或 removed_at 非空），避免误删历史；业务层查黑名单时过滤 removed。
- **操作日志（审计）**：  
  - 新增 **admin_audit_log** 表（id, admin_id_or_key_ref, action, entity_type, entity_id, payload_snapshot, created_at）。  
  - 动作示例：feedback_processed, feedback_rejected, blacklist_add, blacklist_remove。  
  - 写入由 API 层在对应 PATCH/POST 成功后插入，网页只读展示（可选 Phase 2）。
- **feedback 扩展**：  
  - 可选字段：processed_at（DateTime）、processed_by（字符串，如 "web" 或 key 标识），便于「谁何时处理」追溯。

### 4.3 一致性

- 申诉状态更新、加黑、黑名单移除（若有）均在现有事务内完成；审计日志可在同一事务末尾插入，保证「操作成功则日志必存在」。

## 五、Functionality & Logic 视角：核心功能

### 5.1 必须支持（Phase 1，仅用现有 API）

- **总览**：调用 GET /v1/admin/stats，展示 4 项统计。  
- **申诉列表**：GET /v1/admin/feedback?status=…&limit=…，展示列表；行内「通过」「驳回」调用 PATCH /v1/admin/feedback/{id}，body 为 { "status": "processed" } 或 "rejected"。  
- **加黑**：表单提交 POST /v1/admin/blacklist，body { tg_id, reason?, source? }；返回 added: true/false 在页面上提示。

### 5.2 建议扩展（Phase 2，需少量后端）

- **黑名单列表**：GET /v1/admin/blacklist?limit=…&offset=…，返回黑名单条目列表（tg_id, reason, source, added_at）。  
- **黑名单移除**：POST /v1/admin/blacklist/remove 或 PATCH，body { tg_id }；后端软删或真删并写审计日志。  
- **待发提醒只读列表**：GET /v1/alert/pending 已有，网页只读展示；不在此做标记已发送（保留给 Bot）。  
- **操作日志只读**：若落地 admin_audit_log，则 GET /v1/admin/audit-log?limit=…&offset=… 供网页展示。

### 5.3 业务规则保持不变

- 加黑仍触发 `enqueue_alerts_for_target(..., "blacklist_added")`；申诉状态仅更新 Feedback，不自动改 Report（若未来要联动再单独设计）。  
- Bot 侧 /stats、alert 轮询与发送逻辑不改，网页仅「另一管理入口」。

## 六、Code Quality 视角：开发与可维护性

### 6.1 前端

- **单一入口**：管理后台路由统一前缀（如 /admin 或 /dashboard），与用户端完全分离。  
- **API 封装**：所有管理接口集中封装（如 adminApi.stats()、adminApi.feedbackList()、adminApi.feedbackUpdate()、adminApi.blacklistAdd()），便于替换为 Mock 或新接口。  
- **环境配置**：API Base URL 与是否启用「登录页」由环境变量或构建时配置，避免硬编码。  
- **类型**：对 AdminStatsResponse、AdminFeedbackItem、BlacklistAddBody 等做 TypeScript 类型定义，与 OpenAPI/Swagger 或手写保持一致，减少运行时错误。

### 6.2 后端（仅当新增接口时）

- 新增路由放在同一 `api/main.py` 的 admin 区段，或独立 `api/admin.py` 再挂载；复用 `_require_admin` 与现有 Session。  
- 黑名单列表、审计日志的查询使用参数化与 limit/offset，避免全表扫描与注入。

### 6.3 文档与契约

- 现有管理 API 已在 OpenAPI 中；新增接口补充 description 与 response_model；网页前端可按 OpenAPI 生成客户端或手写类型。

## 七、Security 视角：安全

### 7.1 鉴权

- **Phase 1（仅 Bearer Key）**：  
  - 网页在「登录」页输入 API Internal Key，校验方式可为前端调 GET /v1/admin/stats，根据 200/403 判断；通过后 Key 存 sessionStorage 或内存，后续请求 Header 带 Bearer。  
  - 风险：Key 暴露于前端，仅适用于内网或受控环境；生产建议 Key 不长期放在前端，或采用 Phase 2。  
- **Phase 2（推荐）**：  
  - 后端增加「管理员登录」：例如简单表 admin_user (id, username, password_hash, created_at)，登录接口返回 HttpOnly Cookie 或 JWT。  
  - 管理 API 改为校验 Cookie/JWT 中的 admin 身份，而非 Bearer api_internal_key；api_internal_key 仅用于 Bot↔API，不再用于网页。  
  - 网页不再接触 api_internal_key，降低泄露面。

### 7.2 访问控制与网络

- 管理后台仅允许**内网或 VPN** 访问（Nginx/防火墙限制 IP 或部署在内网域名）。  
- 若公网可访问，必须 HTTPS；并考虑限速、防暴力破解（登录失败次数限制）。

### 7.3 数据与操作

- 列表接口不返回敏感原文（如证据链接）时可做脱敏或权限控制；加黑、驳回等写操作仅允许已鉴权管理员。  
- 若落地审计日志，不记录完整 Key/密码，仅记录操作类型与实体 ID。

## 八、SRE & Performance 视角：运维与性能

### 8.1 可用性

- 网页为静态资源，可放 CDN；管理 API 与现有 run_api 同进程，无需单独进程。  
- 若管理请求量极低，无需为 admin 单独扩容；若未来管理 QPS 升高，可对 /v1/admin/* 做限流与独立熔断。

### 8.2 性能

- stats 与 feedback 列表均为单次查询或简单聚合，保持现有索引即可（如 feedback.status、blacklist.tg_id）。  
- 黑名单列表若新增，对 blacklist 表 added_at 或 tg_id 建索引，分页使用 limit/offset 或 cursor。

### 8.3 可观测性

- 管理 API 与普通 API 共用日志；建议为 admin 请求打 tag（如 request_path 含 admin），便于统计与告警。  
- 可选：管理操作失败（4xx/5xx）告警到运维通道。

## 九、QA & Edge Cases 视角：测试与边界

### 9.1 功能测试

- 总览：无 key → 403；正确 key → 200 且四类数字合理。  
- 申诉：列表空/非空；筛选 status；通过/驳回后列表与单条状态更新；无效 feedback_id → 404。  
- 加黑：重复 tg_id → added: false；首次 → added: true；无效 tg_id 或缺失必填 → 400。

### 9.2 边界与异常

- 网络超时：前端重试或提示「请稍后重试」。  
- 并发：同一 feedback 被两名管理员同时处理 → 以最后一次 PATCH 为准；可选乐观锁（version 字段）若需严格防覆盖。  
- 黑名单列表：无记录时返回空数组，不分页异常。

### 9.3 兼容性

- 保留现有 Bot /stats 与 API 调用方式，网页与 Bot 可同时使用管理 API；不破坏现有 run_tests 中的 admin 相关用例。

## 十、Business Value 视角：商业与价值

### 10.1 效率与成本

- 管理员从「记 ID、调接口」变为**点选、批量查看、一键通过/驳回**，处理申诉与黑名单的时间显著下降。  
- 统一入口便于后续扩展（如报表导出、数据看板），为运营决策提供基础。

### 10.2 风险与合规

- 操作可追溯（若落地审计日志），满足「谁在何时对谁做了什么」的合规与纠纷追溯。  
- 黑名单可列表、可备注理由与来源，减少误加与争议。

### 10.3 阶段交付

- **Phase 1**：仅前端 + 现有 4 类 API，快速上线「总览 + 申诉处理 + 加黑」，价值最大、成本最低。  
- **Phase 2**：黑名单列表/移除、待发提醒只读、审计日志与可选管理员登录，按需迭代。

## 十一、实施优先级与交付物建议

| 阶段 | 内容 | 依赖 |
|------|------|------|
| **Phase 1** | 网页：总览（stats）+ 申诉列表与通过/驳回 + 加黑表单；鉴权：Bearer Key 输入校验 | 无后端改动 |
| **Phase 2a** | 后端：GET /v1/admin/blacklist（列表）；网页：黑名单列表页 + 可选移除（后端软删） | 新增 1 个 GET、1 个 移除 接口 |
| **Phase 2b** | 后端：admin_audit_log 表 + 写日志 + GET /v1/admin/audit-log；网页：操作日志只读页 | 新表 + 2 处写日志 + 1 个 GET |
| **Phase 2c** | 后端：管理员账号/登录；API 鉴权从 Bearer Key 改为 Cookie/JWT；网页：登录页、不再存 Key | 新表 + 登录接口 + 鉴权中间件 |
| **可选** | 待发提醒只读页（调用现有 GET /v1/alert/pending）；feedback 表 processed_at/processed_by | 无或小表结构扩展 |

---

## 十二、小结

- **网页后台**作为管理功能的统一入口，复用现有管理 API，先实现**总览、申诉处理、加黑**（Phase 1），不写新后端即可交付。  
- 从**全栈、UI/UX、数据库、功能、代码质量、安全、SRE、QA、商业**各视角收敛为：同源/分离部署可选、数据与审计按需扩展、鉴权从 Key 过渡到管理员登录、保持与 Bot 及现有 API 兼容。  
- 按 Phase 1 → Phase 2a/2b/2c 分步实施，可在不破坏现有系统的前提下，提升管理效率与可审计性。
