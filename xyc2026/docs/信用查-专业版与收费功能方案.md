# 信用查 — 专业度提升、收费功能与多视角优化方案

> **说明**：产品已调整为**全部免费**，不再实施收费功能。专业度与版面以 **《全部免费-功能与专业版面方案》** 为准；本档保留仅供参考，其中「二、收费功能」及计费相关章节不再执行。  
> 原目标：提升专业度、增加 AI 智能分析 + 信息追踪两项收费功能，并从多视角对 UI/UX、功能与数据库做优化。

---

## 一、专业度提升：更详细的信息呈现

### 1.1 当前与目标对比

| 维度 | 当前 | 目标（专业版） |
|------|------|----------------|
| 身份信息 | 邀请报告中补全 ID/用户名/名称 | 所有查询结果统一展示「被查用户」区块（ID、用户名、名称、是否 Premium） |
| 时间维度 | 首次记录、数据更新于 | + 最近一次被查询时间、最近一次与机器人交互时间（若有） |
| 风险维度 | 分数 + 等级 + 综合建议 + 标签 | + 风险来源说明（哪几条规则触发）、历史分数变化趋势（可选） |
| 举报与黑名单 | 总数/待核实/已核实 | + 最近 N 条举报摘要（时间、类型、状态脱敏）、黑名单原因摘要（若为拉黑） |
| 数据来源与时效 | 文末一句隐私说明 | 单独「数据说明」区块：数据来源、更新频率、免责声明、合规提示 |

### 1.2 信息层级建议

- **第一屏**：被查用户标识 + 风险等级 + 信用分 + 综合建议（一眼结论）。
- **第二屏**：标签、提示、举报/黑名单/查询次数等关键指标。
- **第三屏**：详细信息（首次记录、举报明细、数据更新于、数据说明与免责）。

这样既保证「专业、信息足」，又避免信息过载，适合在 Telegram 里分段或折叠展示。

## 二、两项收费功能（按钮级）

### 2.1 功能一：AI 智能分析（付费）

- **入口**：查询结果卡片下方增加独立按钮「🤖 AI 智能分析」。
- **能力描述**：
  - 基于当前用户在本系统的全部可见数据（分数、举报、黑名单、标签、查询/被查记录等），由 AI 生成一段**自然语言信用分析报告**。
  - 内容可包含：风险解读、行为特征归纳、建议（是否建议交易/合作、需留意的点）、与同类用户对比（若做画像分层）。
- **收费与鉴权**：
  - 按次或按订阅（如每月 N 次）；需与支付（如 TON、内部积分）打通。
  - 仅对已付费/有额度的用户展示按钮并允许调用。
- **实现要点**：
  - 后端聚合「该被查用户」的可输出字段，构造 prompt，调用大模型 API，返回结构化/非结构化分析文案。
  - 结果可缓存（同一用户、同一数据快照可复用），降低成本与延迟。
  - 需明确标注「AI 生成，仅供参考」，并符合当地对自动化决策/征信的合规要求。

### 2.2 功能二：信息追踪 / 在线活跃度时间表（付费）

- **入口**：查询结果卡片下方增加独立按钮「📊 活跃度追踪」。
- **重要约束（Telegram 能力边界）**：
  - **Bot API**：机器人**无法**主动、周期性地获取任意用户的「最后在线 / 在线状态」。Telegram 仅在与用户发生交互等极少数场景下可能返回部分「last seen」类信息，且受隐私设置限制。
  - 因此，若严格理解为「用机器人每 2 分钟探测某用户是否在线」，在合规与接口能力上**不可行**。
- **可行替代方案（在合规与 API 允许范围内）**：

  **方案 A：本系统内「活动时间线」**  
  - 不依赖 Telegram 的在线状态，仅记录「该用户在本产品内的活动」：何时被谁查询、何时通过邀请链接打开机器人、何时触发过举报/被举报等。  
  - 用这些时间点生成「活跃度时间表」（按日/周聚合），体现「在本系统视角下的活跃程度」。  
  - 可配合「最近 7/30 天被查询次数」「最近一次在本系统出现时间」等指标，提升专业感与可解释性。

  **方案 B：用户主动上报 + 可选 Telegram 客户端能力**  
  - 若未来使用**用户自身账号**的客户端能力（如 MTProto/Client API）做「自己可见的在线状态」统计，需严格合规：仅限用户本人授权、仅用于本人查看，且不违反 Telegram 服务条款。  
  - 产品层面可先做成「用户授权后，展示其**本人**的在线/活动统计」，而不是「任意查别人实时在线」。

- **推荐产品表述**：
  - 按钮名称：「📊 活跃度时间表」或「📊 本系统活动时间线」。
  - 说明文案：基于本系统内**可记录的活动**（被查询、邀请打开、举报相关等）生成时间线，用于辅助判断该账号在「本平台视角下」的活跃情况；**不提供** Telegram 官方注册时间或实时在线状态。
- **收费与鉴权**：与 AI 分析类似，按次或按订阅，仅对已付费用户开放；可限制「同一被查用户」的追踪报告生成频率（如每日 1 次），避免滥用。

## 三、还可拓展的「更高级功能」（按角色视角归纳）

### 3.1 开发工程师视角（可维护性、扩展性、性能）

- **数据与模型**  
  - 用户维度：增加「风险快照表」或「分数历史表」，便于做趋势与回溯。  
  - 举报/黑名单：增加类型、来源、证据链 ID，便于审计与规则扩展。  
  - 日志与审计：关键操作（查询、举报、拉黑、付费）写审计日志，便于排查与合规。  
- **接口与架构**  
  - 查询/报告接口版本化（如 v1/v2），便于后续增加字段而不破坏旧客户端。  
  - 付费与限流：统一鉴权中间件、额度校验、限流（按用户/按 IP），为后续多付费档位做准备。  
  - 缓存：对「不变或低频变」的数据（如历史报告、聚合统计）做缓存，降低 DB 与 AI 调用压力。  
- **安全与合规**  
  - 敏感字段脱敏与访问控制（谁可看举报详情、谁可看完整时间线）。  
  - 数据保留策略（如 90 天后匿名化）、合规文档（隐私政策、数据使用说明）与工程师可落地的配置项。

### 3.2 市场经理视角（卖点、转化、留存）

- **分层产品**  
  - **免费版**：基础信用分 + 风险等级 + 简要提示 + 被查用户标识（ID/用户名/名称）；每日/每账号查询次数限制。  
  - **付费单次**：单次 AI 智能分析、单次活跃度时间表（本系统活动时间线）。  
  - **订阅制**：月度/季度「深度报告包」：含 AI 分析 + 活动时间线 + 历史趋势 + 举报摘要（脱敏）等，便于 B 端或高频用户。  
- **转化与运营**  
  - 在免费结果页明确标注「升级可解锁：AI 分析 / 活跃度时间表」，按钮置灰或带「付费」角标，点击后引导付费或订阅。  
  - 邀请/分享得额度、首单优惠、企业团购等，便于拉新与复购。  
- **信任与品牌**  
  - 报告页统一视觉：Logo、报告编号、生成时间、数据说明与免责。  
  - 可导出 PDF/长图（带水印），便于用户保存与传播，同时强化「专业、可信」感知。

### 3.3 用户视角（好用、好懂、可信）

- **查询与结果**  
  - 输入方式保持简单：ID / @用户名 / 钱包 / 转发消息；结果首屏即结论（等级 + 分 + 建议），再展开详情。  
  - 被查用户身份信息（ID、用户名、用户名称）始终可见，减少「查的是谁」的疑惑。  
- **付费功能理解成本**  
  - 用简短文案区分：  
    - 「AI 智能分析」= 用 AI 把数据解读成一段话，给建议。  
    - 「活跃度时间表」= 在本产品内该账号何时被查、何时有活动，形成时间线（不包含 Telegram 注册时间/实时在线）。  
  - 避免承诺「实时在线」「注册时间」等 Telegram 无法提供的能力，减少纠纷。  
- **透明与可控**  
  - 「我的信用」中可看到：谁在何时查过我（脱敏或匿名）、我有哪些举报记录与状态。  
  - 提供「误报/纠错」入口和进度查询，增强信任。

## 四、UI/UX 优化建议（不涉及具体代码）

### 4.1 信息架构

- **主导航**：保留 立即查询 / 获取邀请链接 / 我的信用 / 帮助；付费用户可在「我的信用」或设置中看到「已购服务」「额度」「订阅」。
- **查询结果页**：  
  - 第一块：被查用户（ID、用户名、名称、Premium）。  
  - 第二块：风险等级 + 信用分 + 综合建议 + 标签。  
  - 第三块：提示、举报/黑名单/查询次数、首次记录与数据说明。  
  - 第四块：操作按钮 — 举报/纠错、**AI 智能分析（付费）**、**活跃度时间表（付费）**。
- **付费能力**：未付费时，两个付费按钮可点击但跳转「开通/购买」说明与支付入口，而非直接调用。

### 4.2 视觉与一致性

- 统一使用「信用查」品牌色与图标；报告类长文使用分段、小标题、列表，便于扫读。
- 风险等级用颜色/图标区分（如绿/黄/橙/红），综合建议用一句话置顶。

### 4.3 多语言与无障碍

- 所有新增文案（含付费说明、数据说明、免责）进入 i18n，支持中/英/塔加洛语等。
- 关键数字与结论避免仅用颜色传达，配合文字或图标。

## 五、数据库与数据模型优化（方案级）

### 5.1 为「专业度」与「详情」服务

- **users**：已有 tg_id、username 等；可增加 `last_seen_at`（本系统内最后一次被查询或交互时间）、`first_query_at`（首次被查询时间），用于报告与时间线。
- **风险/分数历史**：新表 `user_risk_snapshots`（user_id, score, risk_level, tips, created_at），用于趋势与「历史分数」展示。
- **举报**：在现有 reports 上增加 `report_type`、`evidence_ref`、`admin_notes` 等，便于「举报明细摘要」与审计。

### 5.2 为「AI 分析」与「活跃度时间表」服务

- **AI 分析**：表 `ai_analysis_cache`（user_id, data_hash, analysis_text, model_id, created_at），按 user_id + 数据快照 hash 去重，避免重复调用。
- **活动时间线**：  
  - 已有 query_log 可部分支撑「被查询」时间点。  
  - 可新增 `user_activity_events`（user_id, event_type, at, meta），event_type 如：queried / invite_opened / report_created 等，用于生成「本系统活跃度时间表」。

### 5.3 为「付费」与「运营」服务

- **账户与权益**：`user_balances` 或 `subscriptions`（tg_id, plan, expires_at, ai_remaining, tracking_remaining 等），用于鉴权与扣减。
- **订单与审计**：`orders`（tg_id, product_type, amount, status, created_at）、`feature_usage_log`（tg_id, feature, target_user_id, at），便于对账与防刷。

## 六、实施优先级建议（仅顺序，非代码）

1. **阶段一（专业度）**：统一展示被查用户信息、完善数据说明与免责、首次记录与「注册时间」说明；必要时增加 last_seen_at / first_query_at 等字段与展示。  
2. **阶段二（付费基础设施）**：账户/额度/订单表设计、鉴权与限流、支付对接（如 TON 或内部积分）。  
3. **阶段三（两个收费按钮）**：  
   - 先上「AI 智能分析」：聚合数据 → 调用模型 → 缓存 → 展示；  
   - 再上「活跃度时间表」：基于本系统活动事件表生成时间线，不依赖 Telegram 在线状态。  
4. **阶段四（进阶）**：风险历史与趋势、举报摘要与脱敏、导出 PDF/长图、订阅制与运营活动。

## 七、总结表

| 方向 | 要点 |
|------|------|
| 专业度 | 被查用户信息完整、风险来源可解释、数据说明与免责清晰、信息分屏/分层展示。 |
| 收费功能 1 | AI 智能分析：基于本系统数据生成自然语言报告，按次/按订阅，标注 AI 生成与仅供参考。 |
| 收费功能 2 | 活跃度时间表：基于**本系统内可记录的活动**生成时间线；不承诺 Telegram 注册时间或实时在线，避免违规与用户误解。 |
| 工程师 | 数据模型扩展、审计与日志、接口版本化、缓存与限流、合规与安全配置。 |
| 市场 | 免费/单次/订阅分层、转化入口与运营玩法、报告导出与品牌统一。 |
| 用户 | 首屏结论、身份清晰、付费能力说明简单、透明与纠错入口。 |
| 数据库 | 用户活动与快照、AI 缓存、活动事件表、账户/订单/使用日志。 |

本方案保持与 Telegram 能力边界一致，避免承诺「实时在线」「注册时间」等 Bot API 无法提供的能力，同时通过「本系统活动时间线」和「AI 分析」提升专业度与付费空间。后续若需某一块的接口设计或表结构细化，可单独拆文档或迭代到实现阶段再落代码。
