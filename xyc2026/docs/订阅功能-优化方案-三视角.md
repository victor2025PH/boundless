# 信用查 — 订阅功能优化方案（三视角）

> **背景**：帮助文案已写明「在查询结果上点「有变化时提醒我」即可订阅」，但部分场景下查询结果未展示该按钮，或入口不统一，导致用户体感「订阅功能不完善」。  
> **角色**：开发工程师、市场经理、用户。**输出**：UI/UX、功能、数据库的优化方案，不含代码。

---

## 一、现状与问题

### 1.1 订阅能力（已有）

| 能力 | 说明 |
|------|------|
| 订阅入口 | 查询结果页内联按钮「有变化时提醒我」（callback_data=alert_subscribe_{target_tg_id}） |
| 订阅逻辑 | 调用 API POST /v1/alert/subscribe，存 risk_alert_subscriptions，限频/去重已有 |
| 我的订阅 | 主键盘「我的订阅」→ 列表，每项可再查、取消订阅 |
| 推送 | Bot 轮询 pending，按 subscriber_lang 推送；举报/加黑触发入队 |

### 1.2 问题归纳

- **邀请链接触达的报告没有按钮**：对方点击邀请链接并发消息后，**发给查询方的那条报告消息没有附带任何内联键盘**（无「有变化时提醒我」「举报」「转发」等）。因此从「邀请」场景进入的用户看不到订阅按钮，与帮助说明不一致。
- **查自己时仍显示订阅按钮**：当前用户查询自己（输入自己 ID 或 @自己）时，结果页仍展示「有变化时提醒我」。点击会提示已订阅/不能订阅自己，造成困惑；应在此场景隐藏该按钮或改为「查看我的信用」等。
- **结果页按钮依赖 tg_id**：当 API 未返回 tg_id（如用户名未找到、钱包无记录）时，整条结果仅展示「邀请」按钮，无订阅入口，符合逻辑；但需保证**所有「有 tg_id 且非本人」的结果**都统一带订阅按钮。
- **发现路径单一**：订阅仅存在于「某次查询结果下方」；若用户从未成功查到一个具体用户（只看了帮助或点了「我的订阅」空状态），会只看到「暂无订阅，在查询结果上点…」，缺少在结果页的强感知。

## 二、开发工程师视角：逻辑与一致性

### 2.1 功能与展示规则

| 场景 | 当前 | 建议 |
|------|------|------|
| 直接查询他人（有 tg_id，且 tg_id ≠ 当前用户） | 有「有变化时提醒我」 | **保持**，且保证该行始终存在、不折叠 |
| 直接查询自己（tg_id = 当前用户） | 有「有变化时提醒我」 | **隐藏**该按钮，或改为「查看我的信用」跳转我的信用页，避免无效点击 |
| 邀请流程：对方点链接后发给查询方的报告 | **无内联键盘** | **补充**与结果页一致的内联键盘（举报、请对方出示、转发、**有变化时提醒我**），使该条消息可订阅 |
| 再查（从最近查询/我的订阅点「再查」） | 有订阅按钮 | 保持 |
| 转发报告 | 有订阅按钮 | 保持 |
| 我的信用页 | 无订阅按钮（本人） | 保持，不给自己订阅自己 |

### 2.2 键盘与回调约定

- **统一「结果键盘」**：凡展示「他人」信用报告的消息（含邀请流程里发给查询方的那条），均使用同一套内联键盘：举报、请对方出示报告、转发报告、**有变化时提醒我**。  
- **本人结果键盘**：当且仅当「被查人 = 当前用户」时，使用另一套键盘：不含「有变化时提醒我」，可含「查看我的信用」「我的申诉」等（与我的信用页入口一致即可）。  
- **callback_data**：继续使用 `alert_subscribe_{target_tg_id}`；服务端已做「自己订阅自己」与「已订阅」校验，前端只需在「本人结果」不展示该按钮即可减少无效请求。

### 2.3 数据库与接口

- **无需改表**：订阅逻辑、限频、去重、推送语言均已在现有表与 API 中实现。  
- **可选扩展（非必须）**：若后续要做「订阅来源」统计（如来自邀请报告 vs 直接查询），可在 risk_alert_subscriptions 增加 source 字段（如 invite_result / query_result）；当前阶段可不做。  
- **接口**：保持现有 POST /v1/alert/subscribe、GET /v1/alert/subscriptions、DELETE /v1/alert/subscribe；无需新接口。

### 2.4 边界与异常

- 邀请流程中，若 report_data 无 tg_id（理论上不应出现），则不发键盘或仅发「转发」等安全按钮。  
- 订阅成功/已订阅/限流/自己 等文案已存在，保持即可；若需要可在结果页下方增加一行短提示：「订阅后该用户有新举报或拉黑会通知您」（可选，避免结果页过长可不做）。

## 三、市场经理视角：转化与认知

### 3.1 UI/UX 优化

- **所有「他人报告」入口统一带订阅按钮**：用户无论通过「直接查询」「邀请链接收到报告」「再查」「转发报告」看到他人报告时，都应看到「有变化时提醒我」，形成一致认知：「看到报告就能订阅」。  
- **减少无效入口**：查自己时不展示「有变化时提醒我」，避免「点了没反应/提示不能订阅自己」的负面体验。  
- **帮助与空状态一致**：帮助中「在查询结果上点「有变化时提醒我」」与「我的订阅」空状态文案已一致；确保**实际所有结果卡片都带该按钮**后，用户按说明操作即可完成首次订阅，降低流失。

### 3.2 传播与话术

- 对外说明可统一为：「在任意一条对方信用报告下方点击「有变化时提醒我」，即可在该用户被举报或拉黑时收到通知。」  
- 邀请场景是高频路径：对方点链接后，查询方收到的报告若带订阅按钮，可顺势引导「关注此人动态」，提高订阅渗透率。

### 3.3 可量化

- 若后续有简单埋点，可区分「订阅来自邀请报告 vs 直接查询 vs 再查」，用于评估邀请流程对订阅的贡献；当前阶段以「全场景展示按钮」为主即可。

---

## 四、用户视角：易用与预期

### 4.1 预期与一致性

- 用户看到帮助里「在查询结果上点「有变化时提醒我」」后，会认为**每一条查询结果**（只要是自己查别人得到的报告）都应有点击入口。  
- **邀请链接**是常见场景：把链接发给对方，对方点开发消息，自己收到一条报告。若这条报告没有「有变化时提醒我」，用户会认为功能缺失或 Bug。  
- 查自己时，用户预期是「看自己的信用」，而不是「订阅自己」；不展示订阅按钮更符合心智。

### 4.2 操作路径

- 理想路径：查某人 → 看到报告 + 下方「有变化时提醒我」→ 点击 → 提示已订阅 → 之后在「我的订阅」中可管理。  
- 当前断点：邀请流程下收到的报告没有按钮，路径中断。  
- 优化后：邀请报告与直接查询报告在按钮上一致，路径完整。

### 4.3 文案与反馈

- 订阅成功后的提示（如「已订阅。该用户有新举报或拉黑时会通知您。」）已清晰；无需改。  
- 「我的订阅」为空时的说明「在查询结果上点「有变化时提醒我」即可订阅」与优化后的实际界面一致，用户按图操作即可。

## 六、实施要点（无代码，仅清单）

1. **邀请流程**：对方通过邀请链接发消息后，**发给查询方的那条报告消息**附加与「查询结果页」相同的内联键盘（举报、请对方出示、转发、**有变化时提醒我**）；被查人 tg_id 即邀请点击者的 tg_id。  
2. **本人结果**：当「被查人 tg_id = 当前用户 tg_id」时（直接查自己、或理论上从某入口看到自己的报告），该条消息**不展示「有变化时提醒我」**；可展示「查看我的信用」「我的申诉」等，与我的信用页一致。  
3. **其余场景**：直接查询他人、再查、转发报告已带订阅按钮，逻辑保持不变，仅确认展示无误。  
4. **帮助与空状态**：无需改文案；确保实现与「在查询结果上点「有变化时提醒我」」一致即可。

---

## 七、小结

- **根因**：邀请流程下发给查询方的报告未带内联键盘；查自己时仍展示订阅按钮，造成困惑。  
- **开发**：邀请报告补全键盘；本人结果隐藏订阅按钮或替换为「我的信用」入口；其余场景保持，无新接口与改表。  
- **市场**：所有他人报告入口统一带订阅按钮，便于话术与转化；邀请场景订阅入口补全有利于渗透率。  
- **用户**：与帮助说明一致，「任意他人报告」都能点「有变化时提醒我」；查自己时不出现无效订阅按钮，体验更清晰。

按上述要点落地后，订阅功能的 UI/UX 与功能闭环即可与文档和帮助说明对齐。

## 八、实施记录（已完成）

- **邀请流程**：`start.py` 中对方点邀请链接后，发给查询方的报告消息增加 `reply_markup=inline_result_actions(target_id, locale)`，查询方收到报告即可看到「有变化时提醒我」「举报」「转发」等按钮。✅  
- **查自己**：`check.py` 的 `_do_check_and_reply` 中，当 `querier_tg_id is not None and tg_id == querier_tg_id` 时使用 `inline_mycredit_actions`（出示我的报告、我的申诉，无订阅按钮），否则使用 `inline_result_actions`。✅  
- **转发报告**：`check.py` 的 `cb_forward_report` 中，若 `target_tg_id == cb.from_user.id` 使用 `inline_mycredit_actions`，否则 `inline_result_actions`，并统一为转发结果附带键盘（原逻辑无键盘，已补全）。✅  
- **再查**：`history.py` 的 `cb_recheck` 中，若 `target_tg_id == cb.from_user.id` 使用 `inline_mycredit_actions`，否则 `inline_result_actions`。✅  
- **转发消息查人**：`forward.py` 中，当转发消息查到的 `tg_id` 等于当前用户时使用 `inline_mycredit_actions`，否则 `inline_result_actions`。✅  
- **细化**：转发报告回调原先未附带任何键盘，本次一并补上与结果页一致的键盘（本人用我的信用键盘、他人用带订阅的结果键盘），与方案中「所有他人报告入口统一带订阅按钮」一致。

## 九、下一阶段实施记录（体验与来源统计）

- **我的订阅空状态**：在「暂无订阅。在查询结果上点「有变化时提醒我」即可订阅。」后增加一句 i18n（`alert_my_subscriptions_empty_invite_hint`）：「通过邀请链接收到的报告下方也有该按钮。」（中/英/塔加洛语）。✅  
- **他人结果页订阅提示**：在展示「他人」报告时（直接查询、转发报告、再查、邀请报告、转发消息查人），正文末尾增加一行 `result_alert_tip`：「订阅后该用户有新举报或拉黑会通知您。」；本人结果不追加。✅  
- **订阅来源 source**：表 `risk_alert_subscriptions` 增加可选列 `source`（VARCHAR(32)）；API `POST /v1/alert/subscribe` 增加可选 query 参数 `source`；服务层 `alert_subscribe(..., source=None)` 写入该字段；Bot 调用时传 `source="bot"`；迁移脚本 `migrate_add_columns.py` 增加对 `risk_alert_subscriptions.source` 的补齐。✅  
- **Bot 细分 source（query / invite / recheck / forward）**：✅  
  - `inline_result_actions(..., source=...)` 支持可选 `source`，写入 callback_data 为 `alert_subscribe_{target_tg_id}_{source}`（无 source 时保持 `alert_subscribe_{target_tg_id}` 兼容）。  
  - `alerts.py` 中 `_parse_alert_subscribe_callback` 解析 callback_data，将合法 source（query/invite/recheck/forward）传给 API，否则传 "bot"。  
  - 调用处：直接查询结果 → `source="query"`；邀请链接收到的报告 → `source="invite"`；历史「再查」结果 → `source="recheck"`；转发报告/转发消息查人结果 → `source="forward"`。  
  - 便于后续按来源做订阅转化与留存分析。

## 十、结果页订阅区优化与扩展方向（含订阅提示与多类型追踪）

> **诉求**：在「有变化时提醒我」按钮处强化「订阅」认知，并预留「上线/下线提醒」「更多追踪」等扩展；从开发、市场、用户三视角对**本页** UI/UX、功能与数据库给出方案，**不含代码**。

### 10.1 当前页面与问题简述

- **现状**：结果页底部有文案「订阅后该用户有新举报或拉黑会通知您。」+ 内联按钮「有变化时提醒我」。用户容易把按钮理解为「单次提醒」而非「订阅能力」；也不清楚订阅还能扩展为上线/下线或更多追踪。
- **目标**：让用户一眼理解「有变化时提醒我」= 订阅功能；在 UI/UX 上为「更多提醒类型」（如上线/下线、活动动态）留出认知与入口空间；库表与接口能支撑后续多类型订阅。

---

### 10.2 开发工程师视角：逻辑、数据与库表

#### 10.2.1 本页 UI/UX（结果页订阅区）

| 项目 | 建议 | 说明 |
|------|------|------|
| **订阅区标题/副标题** | 在「有变化时提醒我」按钮**上方**增加一行短标题或副文案（可 i18n） | 例如：「订阅提醒」或「关注此人动态」，让该区域明确是「订阅」功能区，而不是孤立的按钮。 |
| **订阅提示与按钮关系** | 保持现有「订阅后该用户有新举报或拉黑会通知您」在正文末尾；可考虑在该句与按钮之间增加一条极短说明 | 例如：「点击下方按钮即订阅」或「下方为订阅按钮」，减少「点了会怎样」的疑惑。 |
| **按钮文案** | 可保持「有变化时提醒我」；若产品希望更突出「订阅」，可改为「订阅：有变化时提醒我」或保留主文案、用副文案补充 | 需兼顾按钮长度（Telegram 内联按钮不宜过长）与多语言。 |
| **扩展入口** | 若后续支持多种提醒类型，可在同一区域增加「更多提醒类型」或「管理订阅」入口（如内联按钮或「我的订阅」引导） | 当前阶段可仅在文案中预留「如上线/下线、活动动态等（即将推出）」类说明，不增加复杂控件。 |

#### 10.2.2 功能范围与数据可行性

| 能力 | 当前 | 扩展方向 | 数据/实现要点 |
|------|------|----------|----------------|
| **风险变化提醒** | 已实现：新举报、拉黑时推送 | 保持为默认/主能力 | 现有 `risk_alert_subscriptions` + 举报/黑名单触发即可。 |
| **上线/下线提醒** | 未实现 | 可选扩展 | **限制**：Telegram 不向机器人提供用户「最后在线」「上线/下线」状态，无法做「真实 Telegram 上下线」提醒。**可行替代**：（1）用「本系统」数据做「活动提醒」——例如该用户再次被任何人查询、或点击邀请链接等有记录时通知订阅者；（2）**由其他账号监控目标上下线并上报后台、Bot 再推送给订阅用户**——详见独立方案《上下线与动态监控-方案-监控账号与后台》。若对外说「上线/下线」，需明确数据来源（本系统活动 vs 监控端观测）。 |
| **更多追踪** | 无 | 可选 | 如：该用户关联新钱包、新账号被关联、风险等级变更、标签变更等；均可基于现有或扩展后的业务表 + 推送队列实现，无 Telegram API 限制。 |

#### 10.2.3 数据库与接口（扩展多类型订阅时）

| 类型 | 建议 | 说明 |
|------|------|------|
| **表结构** | 若支持多种提醒类型，建议在订阅表增加「提醒类型」或「订阅偏好」 | 例如：`risk_alert_subscriptions` 增加 `alert_types`（如 JSON 或枚举：`risk_change`, `activity`, `online_related` 等），或单表多行：每行 (subscriber_tg_id, target_tg_id, alert_type)。现有逻辑等价于仅 `risk_change` 一种类型。 |
| **兼容** | 旧数据视为「仅风险变化」订阅 | 新字段默认值或迁移时写为当前唯一类型，不影响现有推送逻辑。 |
| **接口** | 订阅/取消接口支持可选「类型」参数 | 例如 POST /v1/alert/subscribe 增加 `alert_types[]` 或 `type=risk_change|activity`；未传则沿用当前行为。 |
| **推送** | 不同事件触发不同订阅类型 | 举报/拉黑 → 只通知 `risk_change` 订阅者；「本系统活动」→ 只通知开通了 `activity` 的订阅者，避免骚扰。 |

### 10.3 市场经理视角：话术、转化与差异化

| 维度 | 建议 |
|------|------|
| **订阅认知** | 统一话术：「有变化时提醒我」= 订阅该用户的**风险变化**（新举报/拉黑）；在结果页用一句「订阅提醒」或「关注此人动态」强化该区域即「订阅」入口，提升首次点击率。 |
| **预期管理** | 若上线「活动/动态」类提醒，对外可称「有新动态时提醒」（本系统内有新查询/互动等），避免承诺「Telegram 上线/下线」以免无法兑现；可留口「更多提醒类型陆续开放」。 |
| **转化** | 在结果页订阅区增加「点击即订阅」类短句，降低理解成本；「我的订阅」空状态与帮助中继续强调「在任意他人报告下方点击订阅按钮」，与本页一致。 |
| **差异化** | 「风险变化 + 后续活动/动态」组合可做成产品亮点；需在文案中明确数据范围（本系统数据、不含 Telegram 真实在线状态），建立信任。 |

---

### 10.4 用户视角：易用、预期与价值

| 维度 | 建议 |
|------|------|
| **一眼看懂** | 结果页底部不只有一句说明 + 一个按钮，而是有明确的「订阅」区域感（小标题或副文案），用户能立刻理解「这里就是订阅」。 |
| **点击预期** | 用户点击「有变化时提醒我」前应知道：这是订阅，会持续生效直到取消；会收到的是「新举报或拉黑」类通知。可在按钮上方或订阅区用一行短句写清。 |
| **扩展预期** | 若产品后续提供「有新动态时提醒」等，应在 UI 或帮助中提前铺垫（如「后续将支持更多提醒类型」），避免用户误以为已有「上线/下线」而投诉。数据说明中已写明「Telegram 不提供最后在线」，与本页订阅说明一致，可减少误解。 |
| **价值感** | 当前订阅解决「不想反复查、又怕对方出事」的需求；若增加「本系统内活动」提醒，可满足「想知道对方是否还有在系统里出现」的衍生需求，价值描述要清晰、不夸大。 |

### 10.5 小结与实施优先级（本页 + 扩展）

- **仅本页 UI/UX（不改表、不扩功能）**  
  - 在「有变化时提醒我」按钮上方增加「订阅提醒」或「关注此人动态」类标题/副文案；可选在订阅提示与按钮之间增加「点击下方按钮即订阅」类短句。  
  - 开发：文案 i18n、结果页排版微调。市场：话术统一为「结果页订阅区」。用户：订阅区域更清晰、点击预期更明确。

- **扩展多类型订阅（含「活动/动态」、未来「上线/下线」表述）**  
  - 功能：明确「上线/下线」仅能基于本系统活动（如被查询、邀请点击等），产品命名建议用「有新动态时提醒」。  
  - 数据库：订阅表增加提醒类型或偏好字段；接口支持按类型订阅与推送。  
  - 市场：对外统一「风险变化 + 新动态」等表述，不承诺 Telegram 真实在线。用户：帮助与结果页写清每种提醒的触发条件与数据范围。

以上方案先落地「本页订阅区 UI/UX 强化」，再按需迭代多类型订阅与库表扩展。
