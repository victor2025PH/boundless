## 二、在方案基础上的优化与细化

### 2.1 活动时间线

- **独立接口**：新增 `GET /v1/activity/timeline`，不仅依赖「我的信用」接口，便于前端或 Mini App 单独调用；days 参数范围 1-30，默认 7。
- **数据完整性**：确认所有写入点（queried/invite_clicked/share_viewed）均已覆盖；Bot 端邀请流程调用 `activity_log` 作为双重保险（即使服务层未写入也有记录）。
- **展示限制**：时间线限制为最近 7 天，避免单用户事件过多造成刷屏；若需扩展，可在接口层增加 limit 参数。

### 2.2 报告再次发送

- **明确用途**：按钮文案「再次发送报告给我」明确发送给用户自己，与「转发报告」（可能发给他人）区分；发送后提示「可保存或转发」，引导用户使用场景。
- **数据一致性**：再次发送时重新查询并合并 breakdown（风险来源占比、举报分类等），保证报告内容为最新。

### 2.3 帮助结构化

- **无需改动**：当前实现已满足需求，6 个 section 覆盖主要功能点；每个 section 有独立标题与正文，便于后续扩展与多语言维护。

### 2.4 未做但可后续做的

- **谁查过我具体列表**：当前仅展示统计（7 天次数 + 最近时间），未展示具体查询人；若未来需要，可在 `get_mycredit_queried_stats` 中增加脱敏列表（如「某用户」+ 时间），并需隐私策略与合规审查。
- **时间线事件类型扩展**：当前仅 queried/invite_clicked/share_viewed；可扩展为「举报相关」「交易确认」等，需在对应写入点增加 `_activity_insert`。

## 五、下一阶段实施建议（P2 及可选）

### 5.1 P2：安全与架构（按需）

| 优先级 | 功能 | 实施要点 | 可做的优化 |
|--------|------|----------|------------|
| **高** | **Redis 限流** | 对 `/check`、`/report` 按 tg_id 限流（如每分钟 N 次）；生产环境管理接口强制 `API_INTERNAL_KEY`（未设置时返回 403）。 | 限流策略可配置（如按功能不同限流阈值）；限流错误返回 429 与重试提示。 |
| **中** | **举报人权重接入 scoring** | 在 ReporterStats 中增加 `verified_count`（或在 `update_report_status` 时维护）；scoring 中按举报人历史核实率等对举报影响加权。 | 权重公式可配置（如 verified_rate > 0.8 则权重 1.2，< 0.5 则权重 0.8）；权重仅影响举报因子，不影响其他因子。 |
| **低** | **异常检测** | 同 IP/设备批量举报降权：需有 IP/设备数据源后再做（如 Bot 上报 IP、API 请求头 X-Forwarded-For）。 | 降权策略可配置（如 24h 内同 IP 超过 N 次举报则降权）；降权仅影响该批举报，不影响举报人历史统计。 |
| **低** | **独立 Worker** | 将风险提醒、被查通知等轮询从 Bot 进程拆出为独立 Worker，便于扩展与运维。 | Worker 支持多实例与负载均衡；推送失败重试机制（如 3 次重试，失败后标记为 failed 供人工处理）。 |

### 5.2 可选功能扩展

| 项 | 说明 |
|----|------|
| **谁查过我具体列表** | 在「我的信用」中增加「最近查询人列表」（脱敏「某用户」+ 时间），需隐私策略与合规审查。 |
| **时间线事件类型扩展** | 增加「举报相关」「交易确认」等事件类型，需在对应写入点增加 `_activity_insert`。 |
| **报告分享链接** | 「带 report_no 的链接」功能（如 `t.me/bot?start=report_R202602161830-A1`），需设计链接格式与后端解析（根据 report_no 取快照或提示「报告已过期」）。 |
| **管理后台前端** | 按《管理后台UI-完整对接方案》独立实现前端，对接现有管理 API；与 P2 后端可并行。 |

### 5.3 数据与性能优化

- **ReporterStats 扩展**：增加 `verified_count`/`rejected_count`，在 `update_report_status` 时维护；`get_admin_reporters` 可优先使用 ReporterStats 的 total/last_report_at，避免全表扫描。
- **时间线聚合优化**：若单用户事件量很大，可在 `get_timeline` 中增加 limit 参数（如最多返回最近 N 条），或按周聚合而非按日。

## 六、小结

- **P1 已完成**：本系统活动时间线（独立接口 + Bot 展示）、谁查过我增强（统计展示）、报告再次发送、帮助结构化（已存在无需改动）；在方案基础上做了独立接口、明确用途、数据一致性等细化。
- **下一阶段**：优先 P2「Redis 限流」与「举报人权重接入 scoring」，再视需要做异常检测与独立 Worker；可选功能扩展（谁查过我列表、时间线事件扩展、报告分享链接）按产品决策推进。
- **原则**：v1 接口保持兼容；不增加收费与复杂操作；核心动线不变；数据与推送逻辑与现有限频/去重一致。
