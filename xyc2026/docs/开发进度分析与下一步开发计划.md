# TrustCheck（信用查）— 开发进度分析与下一步开发计划

> 基于当前代码库与文档的整理结果；用于明确**已完成功能**、**待办/可选项**及**建议的下一步开发顺序**。  
> 生成日期：2026-02-19。

---

## 一、项目概况

- **产品**：TrustCheck Bot（信用查）— Telegram 内信用/风险查询与信任积累机器人 [@xyc2026_bot](https://t.me/xyc2026_bot)
- **技术栈**：Python 3.10+、FastAPI（API）、aiogram（Bot）、SQLAlchemy + SQLite/PostgreSQL
- **运行方式**：`python run_api.py`（API，默认 8001）+ `python run_bot.py`（Bot），Bot 通过 HTTP 调 API，无直连 DB

| 邀请与分享 | 获取邀请链接、出示我的报告、邀请报告展示 | 转发隐私时引导专属链接 |
| 帮助 | /help、主菜单「帮助」 | 带总标题与多语言 |

### 3.2 API（v1 / v2）

- **查询与报告**：GET /v1/check、GET /v1/mycredit、GET /v2/report/breakdown、GET /v2/report/sharecard、GET /v2/report/register、GET /v2/report/verify
- **举报**：POST /v1/report（含 category）
- **交易**：POST /v2/transaction/confirm、respond；GET /v2/transaction/pending
- **用户设置**：GET/PATCH /v1/user/notify_on_checked、GET/PATCH /v1/user/privacy
- **被查通知**：GET /v2/notify_checked/pending、PATCH mark sent
- **收款与流水**：GET/POST/DELETE/PATCH /v2/user/me/wallets、flow、sync-flow、from_db、stats_30d；GET /v2/report/can_view_flow、/v2/report/flow（含 from_db）
- **群**：POST /v2/group/scan
- **管理**：GET /v1/admin/stats、feedback、reporters、reports、transactions、stats/risk_trend；PATCH feedback、reports；POST blacklist
- **邀请/分享/活动/订阅**：invite create/consume、share create/view、my-recent-queries、my-feedback、activity/log、**activity/timeline（P1）**、alert subscribe/delete/subscriptions、alert/pending 拉取与 mark sent
- **监控**：POST /v1/monitor/event
- **健康**：GET /health

### 3.3 数据与评分

- **模型**：User、Blacklist、Report（含 category）、Transaction、WalletEntityGraph、Feedback、QueryLog、CheckLog、RiskAlertSubscription、RiskAlertPending、NotifyCheckedPending、GroupScanLog、绑定与流水相关表等
- **评分**：规则引擎 0–100 分、四档风险、tips、risk_factor_breakdown；每次查询重算并与 blacklist 一致
- **迁移**：migrate_add_columns.py 支持 PG/SQLite；rebuild_db.py 可重建库

## 六、下一步开发计划建议

### 6.1 原则

- 与现有文档一致：v1 接口保持兼容、不增加收费与复杂操作、核心动线不变。
- 优先补齐「已设计但未完成」的小项，再按产品价值做功能扩展。
- 管理后台 UI 为独立前端工程，可与后端并行或外包对接。

### 6.2 建议优先级与任务拆解

#### P0：补齐待办与闭环（约 1–2 周）

1. **举报人统计（任务 1.6）**
   - 新增 reporter_stats 表或按 Report 聚合统计（举报数、已核实数、最后举报时间等）；在 report_create 时更新。
   - scoring 暂不接入权重，仅落数据，为后续 4.3 举报人权重预留。

2. **钱包变动推送触发**
   - 在「写入钱包关联」或绑定/解绑/流水同步等关键写入处，调用已有的 enqueue_wallet_change_for_target，使「钱包变动」订阅者有实际推送。
   - 确认文档中约定的写入点与限频/去重一致。

3. **管理后台前端（可选但建议）**
   - 以《管理后台UI-完整对接方案》为准，实现独立前端（总览、举报管理、申诉、黑名单、举报人列表、交易列表、风险趋势）；鉴权使用 API_INTERNAL_KEY。
   - 不要求改后端，仅对接现有管理 API。

#### P1：体验与数据能力（✅ 已完成）

4. **本系统活动时间线** ✅
   - 数据：已有 `ActivityEvent` 表；`check_log_insert` 写入 "queried"；`share_consume` 写入 "share_viewed"；Bot 端邀请流程调用 `activity_log("invite_clicked")`。
   - API：新增 `GET /v1/activity/timeline?tg_id=xxx&days=7`（days 范围 1-30）；Bot 在「我的信用」中展示（明确标注「本系统可记录活动」）。

5. **谁查过我（增强）** ✅
   - 当前实现：已有 `CheckLog` 表；`get_mycredit_queried_stats` 返回 `recent_7d_query_count` 与 `last_queried_at`；在「我的信用」中展示统计。
   - 状态：已完成基础增强（统计展示）；具体查询人列表留待后续产品决策后再做（需隐私策略与合规审查）。

6. **报告复制/再次发送** ✅
   - Bot 新增「再次发送报告给我」按钮（`btn_resend_report`），重新查询并发送给用户自己，便于保存或转发；与「转发报告」区分（转发可能发给他人）。

7. **帮助/FAQ 结构化** ✅
   - 帮助已结构化：`help_cmd.py` 中 `HELP_SECTIONS` 包含 6 个 section（查询、邀请、我的信用、对方不信我、举报与申诉、数据说明），每个 section 有标题与正文。

#### P2：安全与架构（✅ 已完成）

8. **限流（4.4 部分）** ✅
   - /check 按 querier_tg_id 或 user_id 每分钟限流（rate_limit_check_per_min，默认 10）；/report 按 reporter_tg_id 每分钟限流（rate_limit_report_per_min，默认 3）。内存实现，超限 429。

9. **生产环境管理接口强制 API_INTERNAL_KEY** ✅
   - 配置 `production=True`（PRODUCTION=1）时，管理接口必须配置并校验 Bearer key；未配置返回 403。

10. **举报人权重接入 scoring（4.3 部分）** ✅
    - ReporterStats 增加 verified_count、rejected_count；update_report_status 时更新并同步目标 User.report_count；scoring 使用 effective_report_count（按举报人可信度加权）。

11. **异常检测（4.3）** — 未做
    - 同 IP/设备批量举报降权：需有数据源后再做。

12. **独立 Worker** — 按需
    - 推送轮询仍在 Bot 进程；可按负载再拆出。

### 6.3 不建议本阶段做的（与文档一致）

- **收费与计费**：当前为「全部免费」方案，付费基础设施、AI 分析、活跃度时间表可保留为后续产品决策后再做。
- **真实 Telegram 上下线**：Telegram 不向 Bot 提供用户在线状态；现有「上下线提醒」依赖监控端上报（/v1/monitor/event），不扩展监控端则不做「真实在线」承诺。
- **破坏性变更**：v1 接口保持兼容；报告格式与核心动线不大改。

### 6.4 实施与复盘建议

- 每完成 P0 中 1–2 项或 P1 中 1 项，更新《V2.0-分阶段开发任务清单》中对应「状态」及文档中的「实施记录」。
- 管理后台若为独立交付物，可在对接前用 Postman/curl 按《V2.0-功能测试清单》第三节验证管理 API，再交前端对接。
- 若需调整优先级（例如先做活动时间线再做举报人统计），可在本计划基础上只做顺序调整，不改变上述任务范围。
