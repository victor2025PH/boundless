# 信用查 — 网站管理后台：多视角优化方案

> **定位**：基于当前程序全部功能与既有管理端 API，给出**仅前端交付**的网站管理后台优化方案（无代码，仅方案与规范）。  
> **视角**：全栈技术总监、UI/UX、数据库与数据一致性、功能与逻辑、代码质量、安全、运维与性能、测试与边界、商业价值。

---

## 一、全栈技术总监视角（架构与交付）

### 1.1 边界与原则

- **后端零开发**：所有数据与操作仅通过现有 REST API（Base URL + Bearer 鉴权）；不新增后端接口、不直连数据库。
- **鉴权唯一**：管理后台仅支持「管理密钥」登录（即 `API_INTERNAL_KEY`）；无账号体系、无注册/找回密码。
- **交付物**：独立前端工程（源码 + 可构建产物），通过环境变量配置 API Base URL 与密钥后即可对接；支持静态部署或与现有 API 同域反向代理。

### 1.2 技术选型建议

- **框架**：任选主流 SPA（如 React/Vue/Svelte + TypeScript），便于类型安全对接接口字段与后续维护。
- **请求层**：统一封装 HTTP 客户端，Base URL 来自环境变量（如 `VITE_ADMIN_API_BASE_URL`），所有请求自动附加 `Authorization: Bearer <密钥>`；401/403 统一跳转登录并清空本地密钥。
- **状态**：密钥仅存 sessionStorage（或内存），不落 localStorage，减少泄露面；总览/列表等数据按页请求，可不做全局状态库，以简化首版。
- **构建与部署**：构建产物为静态资源；部署时通过 Nginx/反向代理挂载，或与 API 同域下独立 path（如 `/admin`），避免跨域；生产环境关闭 source map。

### 1.3 与现有程序功能的对应关系

| 程序能力 | 管理后台体现 |
|----------|--------------|
| 运营统计（admin/stats） | 总览页 8 项指标卡片 |
| 举报列表与审核（reports + PATCH） | 举报管理页：列表、筛选、分页、设为已核实/驳回 |
| 申诉列表与处理（feedback + PATCH） | 申诉管理页：列表、Tab 筛选、通过/驳回 |
| 黑名单（POST blacklist） | 黑名单页：表单加黑（tg_id + 原因 + 来源） |
| 举报人信誉（reporters，来自 ReporterStats） | 举报人列表页：举报数、已核实数、最后举报时间 |
| 交易确认列表（transactions） | 交易列表页：按状态筛选、只读展示 |
| 风险趋势（stats/risk_trend） | 风险趋势页：按日风险分布图表 |
| 待发提醒（alert/pending，只读） | 可选：待发提醒页只读列表 |

## 二、UI/UX & Design（交互与体验）

### 2.1 信息架构与导航

- **单层主导航**：总览、举报管理、申诉管理、黑名单、举报人列表、交易列表、风险趋势、（可选）待发提醒；当前页高亮，支持键盘可聚焦与快捷键（如 Alt+数字）以提升效率。
- **总览优先**：登录后默认进入总览；总览页用 8 张卡片呈现运营统计，并突出「待处理举报数」「待确认交易数」，引导管理员优先处理待办。
- **列表页统一范式**：顶部筛选（状态/Tab）+ 表格 + 分页（或「加载更多」）；行内操作（审核/通过/驳回）带二次确认，成功后有 Toast 或行内状态更新，避免整页强刷。

### 2.2 交互细节

- **登录页**：单输入框（管理密钥），类型 password；提交后仅一次 GET /v1/admin/stats 校验；失败提示「密钥无效或已失效」，不泄露是否存在该密钥。
- **举报/申诉表格**：reason、evidence_data 等长文本可截断 + 悬停或点击展开/弹窗，避免表格过宽；时间统一格式（如 YYYY-MM-DD HH:mm），时区建议标注为 UTC 或与后端一致。
- **风险趋势图**：横轴日期、纵轴数量，多系列（low/medium/high/extreme）用不同颜色或堆叠柱状图；支持 7/14/30 天切换（对应 API 的 days 参数）；无数据时展示空状态文案。
- **加黑表单**：tg_id 必填、reason 与 source 选填；提交前校验 tg_id 为数字；提交后根据返回 added true/false 提示「已加入黑名单」或「该用户已在黑名单中」。

### 2.3 无障碍与兼容

- **焦点与键盘**：所有可操作元素可键盘聚焦；列表内操作支持 Tab 与 Enter。
- **响应式**：最小支持 1024px 宽度（管理后台以桌面为主）；表格在小宽度下可横向滚动或列隐藏次要字段。
- **文案**：按钮与状态使用一致术语（如「设为已核实」「已驳回」），与 API 与现有文档一致，便于协作与排查。

## 三、Database & Data Integrity（数据库视角）

### 3.1 只读与写入边界

- **只读**：总览统计、举报人列表、交易列表、风险趋势、待发提醒；前端不直接访问数据库，仅通过 API 读取，数据一致性由后端与 DB 保证。
- **写入**：举报审核（PATCH reports）、申诉处理（PATCH feedback）、加黑（POST blacklist）；所有写操作由后端事务完成，前端仅发起请求并展示结果。

### 3.2 数据一致性理解

- **举报审核**：PATCH 设为 verified/rejected 后，后端会更新 ReporterStats（verified_count/rejected_count）、目标 User.report_count；前端只需刷新列表或更新该行状态，无需关心库表细节。
- **举报人列表**：数据来自 ReporterStats（total_reports、verified_count、last_report_at），与当前程序实现一致；若某举报人仅有历史 Report 无 ReporterStats（极端情况），列表可能不展示，可后续由后端回填解决。
- **分页与刷新**：列表使用 limit/offset 或单次 limit；审核/处理后建议刷新当前页或仅更新该行，避免跨页状态不一致。

### 3.3 错误与边界

- **404/400**：举报或申诉 ID 不存在、参数错误时，后端返回 4xx；前端统一提示「操作失败，请刷新后重试」或展示后端 detail，不猜测业务逻辑。
- **列表为空**：各列表无数据时展示「暂无数据」与说明（如「待处理举报为空表示当前无待审核举报」），避免空白页令人困惑。

## 四、Functionality & Logic（核心功能视角）

### 4.1 功能清单与优先级

| 优先级 | 功能 | 接口 | 说明 |
|--------|------|------|------|
| P0 | 登录（密钥校验） | GET /v1/admin/stats | 200=成功并跳转总览，403=失败 |
| P0 | 总览 | GET /v1/admin/stats | 8 项统计卡片 + 导航入口 |
| P0 | 举报管理 | GET /v1/admin/reports，PATCH /v1/admin/reports/{id} | 列表、status 筛选、分页、设为已核实/驳回 |
| P0 | 申诉管理 | GET /v1/admin/feedback，PATCH /v1/admin/feedback/{id} | 列表、status 筛选、通过/驳回 |
| P0 | 加黑名单 | POST /v1/admin/blacklist | tg_id + reason + source |
| P1 | 举报人列表 | GET /v1/admin/reporters | 只读，举报数/已核实数/最后时间 |
| P1 | 交易列表 | GET /v1/admin/transactions | 只读，按状态筛选 |
| P1 | 风险趋势 | GET /v1/admin/stats/risk_trend | 图表，days 可选 |
| P2 | 待发提醒 | GET /v1/alert/pending | 只读，可选页 |

### 4.2 状态与错误处理

- **登录态**：以「本地是否存有密钥 + 请求是否 403」为准；403 时清空密钥并跳转登录。
- **请求错误**：网络错误或 5xx 提示「服务暂时不可用，请稍后重试」；4xx 根据 detail 或 code 展示（如「该举报不存在」）；429 可展示「操作过于频繁」并可选展示 Retry-After。
- **乐观更新**：审核/驳回后可直接更新该行状态并 Toast 成功，失败再恢复并提示；或采用保守策略：先请求再刷新列表。

### 4.3 与现有程序功能对齐

- **举报分类**：列表与详情中展示 category（scam/run_order/lost_contact/other），与 Bot 举报类型一致。
- **交易状态**：pending/confirmed/rejected 与 Bot 侧「待我确认」及同意/拒绝一致，后台仅查看不操作。
- **风险趋势**：数据来源于 QueryLog 的 result_risk_level，与用户端报告风险等级一致。

## 五、Code Quality（开发视角）

### 5.1 项目结构建议

- **按模块划分**：如 `auth`（登录、鉴权）、`dashboard`（总览）、`reports`、`feedback`、`blacklist`、`reporters`、`transactions`、`risk-trend`、`pending-alerts`（可选）；每模块含列表/表单/请求封装。
- **请求层集中**：所有 admin API 调用集中在一个 api 或 services 层，Base URL 与 Header 统一注入，便于切换环境与 Mock。
- **类型与接口**：为每个 API 的请求/响应定义 TypeScript 类型（或从 OpenAPI 生成），减少字段拼写错误与变更遗漏。

### 5.2 可维护性

- **环境变量**：仅使用 `API_BASE_URL`（或项目约定命名）与密钥输入；不在代码中写死域名或密钥。
- **文档**：README 中说明「如何配置 Base URL」「如何登录（管理密钥由运营提供）」「如何构建与部署」；与《管理后台UI-完整对接方案》接口清单对齐。
- **版本与变更**：前端版本号或构建时间可展示在页脚；接口变更时由后端保证兼容或提供过渡期，前端按文档升级字段。

### 5.3 与后端约定

- **接口文档**：以现有 `docs/管理后台UI-完整对接方案.md` 及 API 的 `/openapi.json` 为准；新增管理接口由后端迭代，前端按版本对接。
- **错误格式**：后端 4xx 返回 `detail`（或 `message`）；前端统一解析并展示，不依赖具体文案做分支逻辑。

## 六、Security（安全视角）

### 6.1 鉴权与密钥

- **密钥不落代码**：管理密钥仅通过登录页输入或部署环境注入，不写入前端代码或公开仓库。
- **传输**：生产环境必须 HTTPS；Bearer Token 仅放在请求头，不放在 URL 或 Cookie（若用 Cookie 需 HttpOnly+Secure，当前方案以 Header 为主即可）。
- **存储**：密钥存 sessionStorage，关闭标签页即失效；避免 localStorage 长期留存；不打印、不提交到日志。

### 6.2 生产环境行为

- **后端 production 模式**：当后端设置 `PRODUCTION=1` 时，未配置或错误的 `API_INTERNAL_KEY` 将导致 403；前端在 403 时统一视为未授权并跳转登录。
- **登出**：提供「退出」入口，清除本地密钥并跳转登录页；避免共用设备时密钥残留。

### 6.3 前端安全

- **XSS**：所有后端返回的文本在展示时做转义或使用框架默认转义；避免 `dangerouslySetInnerHTML` 或等效方式直接插入用户/API 内容。
- **CSP**：若部署方支持，可配置 Content-Security-Policy，限制脚本与请求来源。
- **敏感信息**：列表与详情中展示的 tg_id、reason 等仅限管理员可见；不对外暴露管理后台 URL 或密钥获取方式。

## 七、SRE & Performance（运维与性能）

### 7.1 部署方式

- **静态托管**：构建产物可部署至任意静态托管（如 Nginx、OSS+CDN）；仅需配置 Base URL 为当前 API 地址。
- **同域部署**：推荐与 API 同域（如 `https://api.example.com/admin`），由 Nginx 将 `/admin` 指向前端静态资源，避免跨域与 CORS 配置。
- **健康与可用性**：管理后台可用性依赖 API；API 健康检查已有 `/health`，运维可监控该接口；前端可 periodic 调用 GET /v1/admin/stats 或轻量接口以检测「登录态是否仍有效」。

### 7.2 性能

- **首屏**：登录后总览页优先加载；总览仅一次 GET /v1/admin/stats，数据量小，首屏可控制在单次 RTT 内。
- **列表**：举报/申诉/交易等列表使用 limit（如 20/50）+ offset 分页，避免单次拉取过多；表格支持虚拟滚动或分页即可。
- **风险趋势**：按需请求 risk_trend（如默认 7 天）；图表库选型时注意数据量（最多 90 天），避免重绘卡顿。

### 7.3 可观测

- **前端错误**：关键操作（登录、审核、加黑）失败时可上报前端错误（如 Sentry），不携带密钥；便于排查网络或接口问题。
- **审计**：所有写操作（举报审核、申诉处理、加黑）由后端落库与日志；前端不负责审计日志，但可考虑在操作成功后在 UI 记录「谁在何时做了什么」（若后端未来提供操作人标识可对接）。

## 八、QA & Edge Cases（测试视角）

### 8.1 测试策略

- **单元/集成**：请求层与 API 契约可单测（Mock 响应）；列表渲染、筛选、分页可组件测试。
- **E2E**：登录 → 总览 → 举报列表 → 审核一条 → 返回列表校验状态；申诉、加黑同理；使用测试环境与专用测试密钥。
- **兼容**：浏览器支持 Chrome/Firefox/Edge 最新两版；移动端仅保证「可打开、可登录」，复杂表格可次要支持。

### 8.2 边界与异常

- **无数据**：各列表为空、风险趋势无数据时，有明确空状态与说明。
- **网络超时/断开**：请求超时或失败时提示重试或检查网络，不静默失败。
- **403**：任何接口返回 403 时，统一清空密钥并跳转登录，避免在无权限状态下继续操作。
- **大文本**：reason、evidence_data 过长时，表格内截断 + 展开/弹窗，避免布局错乱或性能问题。
- **分页边界**：offset 超出时后端可能返回空列表；前端不展示「上一页」当 offset=0，不展示「下一页」当返回条数 < limit。

### 8.3 与后端联调

- **环境**：开发阶段使用与后端约定好的 Base URL（如本地或测试环境）；密钥使用测试用 API_INTERNAL_KEY。
- **接口契约**：以 OpenAPI 或《管理后台UI-完整对接方案》为准；字段新增时后端兼容旧字段，前端按需升级展示。

## 九、Business Value（商业视角）

### 9.1 业务价值

- **运营效率**：总览集中呈现待处理举报与待确认交易，便于优先处理；举报/申诉审核与加黑在一处完成，减少切换与遗漏。
- **风控与合规**：举报人列表（信誉聚合）支持识别高频或高核实率举报人；风险趋势支持观察产品健康度；黑名单与审核动作为后续合规留痕提供基础。
- **可扩展**：当前不包含「用户列表」「敏感数据导出」等，避免首版范围过大；后续若需可单独规划并与后端新增接口对接。

### 9.2 迭代建议

- **第一期**：登录、总览、举报管理、申诉管理、加黑名单（P0），保证日常运营闭环。
- **第二期**：举报人列表、交易列表、风险趋势（P1），增强风控与数据可见性。
- **第三期**：待发提醒只读（P2）、前端错误上报、可选「操作记录」展示（若后端提供）。

### 9.3 成功指标

- **使用**：管理员能在一分钟内完成登录并看到总览；单条举报/申诉审核在三次点击内完成（列表 → 操作 → 确认）。
- **稳定**：与 API 契约一致，无因前端错误导致的误操作（如误点驳回后可有二次确认补救）；403/网络错误有明确提示。
- **交付**：交付物可直接通过配置 Base URL 与密钥对接现有 API，无需后端改动即可上线使用。

## 十、方案小结（优化要点汇总）

| 视角 | 优化要点 |
|------|----------|
| **全栈** | 后端零开发、Bearer 唯一鉴权、环境变量配置 Base URL 与密钥、静态部署或同域 /admin。 |
| **UI/UX** | 单层导航、总览优先、列表统一范式（筛选+表格+分页）、长文本截断+展开、风险趋势图多系列、键盘与无障碍。 |
| **数据库** | 前端不直连 DB；理解举报审核会联动 ReporterStats 与 User.report_count；列表以 API 为准，空与错误由后端定义。 |
| **功能** | P0 登录/总览/举报/申诉/黑名单，P1 举报人/交易/风险趋势，P2 待发提醒；状态与错误统一处理，与 Bot/API 语义一致。 |
| **代码质量** | 按模块划分、请求层集中、TypeScript 类型与接口文档对齐、README 与部署说明完整。 |
| **安全** | 密钥不落代码与仓库、sessionStorage、HTTPS、403 统一登出、XSS 转义、不暴露后台 URL/密钥获取方式。 |
| **SRE** | 静态托管或同域部署、列表分页控量、图表按需请求、前端错误上报（不携密钥）、审计依赖后端。 |
| **QA** | 请求层与契约单测、E2E 覆盖登录与核心审核流程、空/403/超时/大文本/分页边界有明确处理。 |
| **商业** | 首期 P0 闭环、二期风控与数据可见、三期可选能力；成功指标为 1 分钟登录、3 次点击内完成单条审核、交付即可对接。 |

以上方案在现有《管理后台UI-完整对接方案》与《管理后台-对接开发文档》基础上，从九大视角做了收敛与优化，可直接作为管理后台前端设计、开发与验收的规范依据，且不涉及后端代码变更。
