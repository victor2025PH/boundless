# 阶段一实施总结与下一阶段计划

## 一、阶段一完成内容（专业度提升）

### 1.1 已实现项（按方案）

| 方案项 | 实现方式 |
|--------|----------|
| 统一展示「被查用户」 | 所有查询结果（含普通查询、转发、邀请报告）均在报告顶部展示 **被查用户** 区块：用户ID、用户名、用户名称（有则显示）、是否 Premium。 |
| 时间维度增强 | **首次记录** 保留并带说明「本系统首次记录；Telegram 不提供注册时间」；新增 **最近活动（本系统）**：`last_seen_at`，每次被查询时更新。 |
| 风险来源说明 | 在综合建议后增加一句 **风险依据**：上述提示、举报与黑名单数据综合计算。 |
| 单独「数据说明」区块 | 报告末尾增加 **📌 数据说明** 标题 + 原有隐私说明文案，形成独立区块。 |
| API 与数据层 | `User.last_seen_at` 字段；`check_by_tg_id` 返回 `last_seen_at`；CheckResponse / MyCreditResponse 增加 `last_seen_at`。 |

### 1.2 实施中的优化与细化（在方案基础上的改进）

1. **身份块与展示逻辑统一**
   - 方案只要求「所有查询结果统一展示被查用户」。实现时把身份块集中到 **一处**：`format_check_result()`，通过可选参数 `display_name` 支持邀请场景的「用户名称」。
   - **优化**：邀请流程不再在 start.py 里重复拼身份块，改为调用 `format_check_result(data, locale, display_name=...)`，避免两处维护、格式不一致。
   - **细化**：转发查询时若有 `forward_from`，从 `first_name`/`last_name` 拼出 `display_name` 传入，普通 /check ID 或 @用户名 时无 display_name 仅显示 ID/用户名。

2. **Markdown 安全**
   - 身份块中的用户名、用户名称可能含 `_`/`*`，会破坏 Telegram Markdown 解析。增加 **`_md_esc()`**，对用户提供文案做转义，避免 "can't parse entities" 类错误。

3. **Premium 展示位置**
   - 方案要求「被查用户区块含是否 Premium」。实现时把 Premium 放在身份块正下方（单独一行），与 ID/用户名/名称同属「被查人信息」区域，详情区不再重复展示 Premium。

4. **last_seen_at 的兼容**
   - 使用 `hasattr(user, "last_seen_at")` 与 `getattr(..., None)`，保证未迁移的旧库或缺少该列时不会报错，仅不展示「最近活动」一项。

5. **i18n 与多语言**
   - 新增 `detail_last_seen`、`data_disclaimer_header`、`risk_basis` 的中/英/塔加洛语文案，与现有多语言策略一致。

## 二、涉及文件与变更摘要

- **models.py**：`User` 增加 `last_seen_at: DateTime | None`。
- **services.py**：`check_by_tg_id` 中更新并返回 `last_seen_at`，兼容无该列情况。
- **api/schemas.py**：`CheckResponse`、`MyCreditResponse` 增加 `last_seen_at: str | None`。
- **bot/format_result.py**：  
  - 新增 `_md_esc()`；  
  - `format_check_result(data, locale, display_name=None)`：顶部身份块（ID/用户名/用户名称/Premium）、综合建议后风险依据、详情区 last_seen_at、单独数据说明区块。
- **bot/i18n.py**：`detail_last_seen`、`data_disclaimer_header`、`risk_basis`。
- **bot/handlers/start.py**：邀请报告改为 `format_check_result(report_data, locale, display_name=...)`，删除重复身份块与本地 `_md_esc`。
- **bot/handlers/forward.py**：转发查询时拼 `display_name` 并传入 `format_check_result(..., display_name=...)`。
- **bot/handlers/check.py**：无改动（仍调用 `format_check_result(data, locale)`，无 display_name）。

## 三、数据库与部署说明

- 新建库：直接 `python run_api.py`，表结构会包含 `last_seen_at`。
- 已有库（测试可重建）：执行 `python rebuild_db.py` 后重启 API 即可。
- 若需保留数据：对现有 PostgreSQL 执行 `ALTER TABLE users ADD COLUMN last_seen_at TIMESTAMP;`。

## 四、下一阶段建议：付费基础设施 + 两个收费按钮

### 4.1 阶段二目标（建议实施顺序）

1. **付费基础设施（不涉及具体支付渠道）**
   - **数据模型**：  
     - `user_balances` 或 `subscriptions`：tg_id、方案/类型、到期时间、AI 分析剩余次数、活跃度时间表剩余次数等。  
     - `orders`：tg_id、产品类型、金额、状态、创建时间（便于对账与审计）。  
     - `feature_usage_log`：tg_id、功能名、被查用户 id、时间（防刷与限频）。
   - **鉴权与限流**：  
     - 查询结果页是否展示「AI 智能分析」「活跃度时间表」按钮，由「是否有对应额度」决定；无额度时点击跳转「开通/购买」说明。  
     - 调用 AI 分析 / 生成时间表时先扣减额度并写 `feature_usage_log`，失败或异常时考虑回滚额度。
   - **接口**：  
     - 可选：`GET /v1/me/balance` 或 `GET /v1/me/subscription` 返回当前用户额度与到期日；Bot 据此决定是否展示/允许使用付费功能。

2. **收费功能一：AI 智能分析**
   - 查询结果页增加按钮「🤖 AI 智能分析」（仅对有额度用户展示或对所有人展示但点击时鉴权）。
   - 后端：聚合该被查用户在本系统的可输出字段，构造 prompt，调用大模型 API，返回一段自然语言分析；结果可缓存（如按 user_id + 数据快照 hash）。
   - 表：`ai_analysis_cache`（user_id, data_hash, analysis_text, model_id, created_at）。
   - 文案：明确标注「AI 生成，仅供参考」，并考虑合规。

3. **收费功能二：活跃度时间表（本系统活动时间线）**
   - 查询结果页增加按钮「📊 活跃度时间表」（仅对有额度用户展示或点击时鉴权）。
   - **不依赖 Telegram 在线状态**：仅使用本系统内可记录的活动（被查询、邀请打开、举报相关等）。
   - 数据层：  
     - 方案 A（最小实现）：复用现有 `query_log` 与用户 `last_seen_at`，按被查用户聚合「最近 N 次被查询时间」等，生成简单时间线文案。  
     - 方案 B（可扩展）：新增 `user_activity_events`（user_id, event_type, at, meta），在每次查询/邀请打开/举报时写入，再按日/周聚合生成时间表。
   - 限频：同一被查用户可限制「每日最多生成 1 次」等，写入 `feature_usage_log`。

### 4.2 建议的优化与改进（相对原方案）

- **先做「展示 + 占位」**：在阶段二可先实现「两个按钮始终展示」，未付费用户点击后收到「该功能为付费功能，即将上线」或引导至支付/订阅页，再逐步接入真实扣费与 AI/时间表逻辑，降低首期开发量。
- **AI 分析缓存 key**：除 user_id 外，用「关键字段的 hash」（如 score、risk、report_count、updated_at 等）作为缓存 key，数据未变时直接返回缓存，减少调用与延迟。
- **活动时间线表述**：产品文案与 Bot 内说明统一为「本系统活动时间线」「基于本系统内可记录的活动」，避免出现「实时在线」「Telegram 注册时间」等无法实现的说法，减少客诉与合规风险。
- **额度与订阅分离**：若未来同时支持「单次购买」和「订阅包」，建议数据模型上区分「次数包」与「订阅状态」，便于运营配置不同档位（如 3 次 AI + 1 次时间表 打包价）。
