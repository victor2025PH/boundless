## 实施与复盘

### 第 1 阶段实施记录与优化（已完成 1.1–1.5）

- **实施要点**
  - 迁移：`migrate_add_columns.py` 增加 `reports.category`；`models.py` 增加 `REPORT_CATEGORIES` 与 `Report.category`。
  - 服务层：`report_create(..., category=)`、`get_report_stats_for_target`、`get_report_breakdown`、`check_by_tg_id` 返回 `linked_tg_ids` / `linked_wallet_count` / `linked_tg_count`；`scoring.compute_risk_factor_breakdown` 提供占比。
  - API：`ReportCreate.category` 可选；`GET /v2/report/breakdown?user_id=|username=|wallet=` 返回 `ReportBreakdownResponse`；v1 check 保持兼容，`CheckResponse` 增加 `linked_wallet_count`、`linked_tg_count`。
  - Bot：举报先选类型（诈骗/跑单/失联/其他）再填原因，提交时带 `category`；查询结果用 v1/check + 再请求 v2/report/breakdown 合并展示「举报分类」「近 7/30 天举报」「风险来源占比」；i18n 已加对应 key。
- **优化**
  - 查询展示：不改为“只调 v2”，而是 v1/check（保留 谁查过我/check_log）后再用已解析的 `tg_id` 调 v2/report/breakdown 做展示合并，避免重复传参且保证日志正确。
  - 举报入口：`report_` 与 `report_cat_` 用过滤器区分，避免选类型时误触其他 callback。

### 第 2 阶段实施记录与优化（已完成 2.1–2.5）

- **实施要点**
  - 数据库：`Transaction` 模型（initiator_tg_id, counterparty_tg_id, amount, currency, memo, status, created_at, confirmed_at）；`migrate_add_columns.py` 中 PG/SQLite 增加 `transactions` 表创建。
  - 服务层：`transaction_confirm_create`（自刷拦截：initiator≠counterparty；同对限频：每对最多 5 笔 pending）、`transaction_respond`、`get_user_transaction_stats`（成功笔数、成功率、累计确认金额）、`get_pending_transactions_for_counterparty`；`check_by_tg_id` 返回中合并 `tx_*` 统计。
  - API：`POST /v2/transaction/confirm`、`POST /v2/transaction/respond`、`GET /v2/transaction/pending?counterparty_tg_id=`；`TransactionRejectError` 统一 400 + code/detail。
  - 报告与展示：`CheckResponse`/`MyCreditResponse` 增加 `tx_success_count`、`tx_total_count`、`tx_success_rate`、`tx_total_amount`；`format_result` 在「详细信息」前有数据时展示「交易确认」区块（成功笔数/成功率/累计金额）；i18n 已加。
  - Bot：结果卡增加「请求对方确认交易」→ 输入金额（可选备注）→ 调用 confirm → 向对方私发一条消息带 [同意]/[拒绝]；主菜单增加「待我确认」+ `/pending` 列出待处理并 Inline 同意/拒绝；同意/拒绝后编辑原消息为「已同意」/「已拒绝」。
- **优化**
  - 同对限频用「每对 5 笔 pending」而非「每日 N 笔」，减少互刷的同时避免正常用户被误伤。
  - 发起确认后 Bot 主动给 counterparty 发一条带 Inline 的消息，对方无需先点「待我确认」即可在通知里操作。
  - API 400 返回 `code`（如 self_trade、too_many_pending），Bot 用 `httpx.HTTPStatusError` 解析后展示对应 i18n 文案。

### 第 3 阶段实施记录与优化（已完成 3.1–3.4）

- **实施要点**
  - 数据库：User 增加 `notify_on_checked`（Boolean 默认 True）；新增表 `notify_checked_pending`（target_tg_id, querier_tg_id, sent_at）、`group_scan_log`（group_id, requester_tg_id, created_at）；迁移脚本已支持 PG/SQLite。
  - 被查通知：`check_log_insert` 后若被查人 `notify_on_checked` 为 True 则写入 `notify_checked_pending`；Bot 轮询与风险提醒共用 worker，拉取 `GET /v2/notify_checked/pending` 后向 target 发送「有人查了你的信用」并 `mark_sent`；「我的信用」页增加「被查通知：开/关」Inline 开关（GET/PATCH /v1/user/notify_on_checked）；我的信用 API 返回 `notify_on_checked` 供 Bot 展示状态。
  - 信用卡片：`get_sharecard_data(session, tg_id)` 返回简要风险/分数/标签/交易统计；`GET /v2/report/sharecard?user_id=`；Bot `/sharecard` 及「我的信用」内「分享卡片」按钮，格式化为文案（未做 PNG）。
  - 群扫描：`group_scan(session, group_id, requester_tg_id)` 按群+当日限 1 次；`POST /v2/group/scan`；Bot `/scan_group` 仅在群组内响应，`get_chat_administrators` 校验管理员后调 API，回复「已记录」或「今日已扫描」。
- **优化**
  - 被查通知与风险提醒共用同一 worker 轮询，先处理 risk alerts 再处理 notify_checked，减少重复 sleep 与代码。
  - 被查通知默认开启（notify_on_checked=True），用户可在「我的信用」一键关闭，无需单独设置页。
  - 信用卡片先做 JSON + 文案展示，PNG 留作后续扩展，避免引入图片依赖。
  - 群扫描仅记录「本群今日已扫」并限频，不做成员列表拉取（Telegram 不提供），后续可扩展为「管理员提交成员 ID 列表再扫」。

### 第 4 阶段实施记录与优化（已完成 4.1–4.2）

- **实施要点**
  - 4.1 订阅类型：`_normalize_alert_type` 支持 `report_spike`、`wallet_change`；`enqueue_alerts_for_target` 在 `new_report` 时除 risk_change 外再为 report_spike 订阅者入队（event_type=report_spike）；新增 `enqueue_wallet_change_for_target`（在钱包关联写入处可调用，当前未接）；Bot worker 对 `report_spike`、`wallet_change` 使用新 i18n 推送；结果卡增加「举报动态」「钱包变动」订阅按钮；「我的订阅」列表与取消支持上述类型。
  - 4.2 管理后台：`admin_stats` 增加 `transactions_pending`；新增 `get_admin_reporters`（按举报人聚合举报数/已核实数）、`get_admin_transactions`（按状态筛选）、`get_admin_risk_trend`（按日 query_log 风险分布）；API 新增 `GET /v1/admin/reporters`、`GET /v1/admin/transactions`、`GET /v1/admin/stats/risk_trend`（需 Admin Key）。
- **优化**
  - report_spike 与 new_report 共用同一触发点（新举报），仅订阅类型与推送文案区分，避免重复入队逻辑。
  - 风险趋势基于现有 QueryLog（result_risk_level + created_at），不新增表即可出图数据。
  - 管理端统计与列表均需 Admin Key，与现有管理接口一致。

### 任务 1.6 与钱包变动推送实施记录（P0）

- **1.6 举报人统计**：新增表 `reporter_stats`（reporter_tg_id PK, total_reports, last_report_at）；在 `report_create` 内同一事务中 upsert 更新；`get_admin_reporters` 仍按 Report 聚合，未改行为；表数据供后续 4.3 举报人权重接入 scoring。
- **钱包变动推送触发**：在 `bind_wallet` 成功写入 UserBoundWallet 后调用 `enqueue_wallet_change_for_target(session, tg_id)`，订阅了该用户「钱包变动」的用户会收到 Bot 推送；若日后有写入 WalletEntityGraph 的入口，可同样调用 enqueue。
- 详见 `docs/P0实施总结与下一阶段建议.md`。

### 后续可选（4.3、4.4）

- 4.3 异常检测：待有 IP/设备等数据源后再做举报降权；举报人权重接入 scoring 可沿用 1.6 的 ReporterStats 数据。
- 4.4 架构：Redis 限流/缓存、独立 Worker 按需引入，当前轮询与内存状态可继续支撑。

- 每阶段完成后：更新上表「状态」、在方案文档中记录「实施记录与优化点」、给出下一阶段实施建议与可改进项。
- 原则：不增加收费、不增加复杂操作、不改变核心动线；v1 接口保持兼容。
