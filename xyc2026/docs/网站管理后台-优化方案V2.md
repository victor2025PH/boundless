# 信用查 — 网站管理后台：优化方案 V2

> **与 V1 方案的区别**：V1 是对现有对接文档的九视角收敛；本 V2 是在此基础上重新思考「管理员真正的操作场景与痛点」，加入**上下文决策辅助**、**批量操作**、**用户画像嵌入**、**实时感知**、**操作安全网**等原创设计，并拉齐九大视角。  
> **仍然不写代码**，仅方案。

---

## 一、核心设计理念（V2 新增）

### 1.1 从「管理后台」到「运营工作台」

V1 将每个页面视为独立模块。V2 的核心转变是：**管理员不是来浏览数据的，而是来做决策的**。每一条举报、每一条申诉，管理员需要的是**决策上下文**而不是跳转多个页面拼凑信息。

**设计原则**：
- **零跳转决策**：审核一条举报时，所有决策所需信息（被举报人风险画像、该举报人历史信誉、相关举报列表）都在同一视野内呈现，无需打开新页面。
- **待办驱动**：总览不只是数字卡片，而是一个「待办清单」——管理员登录后直接看到需要处理的举报和申诉，一键进入处理流程。
- **操作安全网**：所有不可逆操作（加黑、审核）都有「确认 → 5 秒可撤回」的缓冲机制，而不仅是二次确认弹窗。

### 1.2 信息密度的平衡

管理后台的用户是内部运营，不是普通用户：
- **高信息密度**：表格优先、卡片辅助，不做大面积留白与装饰性动画。
- **快速扫描**：颜色编码一致（🟢低风险 / 🟡中 / 🟠高 / 🔴极高），状态用色块标签而非纯文字；关键数字（待处理数）用强调色。
- **但不拥挤**：通过合理的行高、列宽和可折叠区域避免信息过载。

## 二、页面重设计（V2 新增与优化）

### 2.1 登录页

- 单输入框（密钥，password 类型），回车即可提交。
- 校验方式不变（GET /v1/admin/stats，200=成功，403=失败）。
- **V2 新增**：
  - 登录失败时做 **2 秒延迟**再提示，防止暴力枚举。
  - 连续 5 次失败后前端锁定 60 秒，展示倒计时（纯前端限制，非后端依赖）。
  - 页面不出现「信用查」「TrustCheck」等产品名，仅显示「管理面板」与输入框，减少攻击面。

### 2.2 总览页（工作台模式）

**V1 方案**：8 张统计卡片 + 导航入口。

**V2 优化**：分为三个区域。

**区域 A：待办摘要（页面上方 1/3）**
- 两张突出卡片：「待处理举报 N 条」「待处理申诉 N 条」，附带**「立即处理」按钮**，一键跳转对应列表且 status 自动筛选为 pending。
- 若 N > 0，卡片用橙色/红色背景强调；若 N = 0，显示绿色「全部处理完毕」。

**区域 B：运营指标（页面中间）**
- 其余 6 张指标卡片（今日查询、总用户、黑名单、待确认交易、绑定地址、流水快照），每张带一个小趋势箭头（若后端日后提供昨日对比数据可对接；首版可不展示箭头，仅数字）。

**区域 C：最近 7 天风险趋势迷你图（页面下方 1/3）**
- 直接嵌入 risk_trend（days=7）的小折线图，无需跳转风险趋势页就能一眼感知。
- 图下方链接「查看详细趋势 →」跳转完整风险趋势页。

**V2 新增**：
- 页面右上角「数据刷新于 HH:MM:SS」+ 手动刷新按钮。
- 可选：30 秒自动轮询 stats，仅更新数字（不整页重渲染），配合淡入动画使数字变化可感知。

### 2.3 举报管理页（决策工作台模式）

**V1 方案**：列表 + 行内按钮。

**V2 核心优化**：**主从布局（Master-Detail）**

- **左侧 60%：举报列表**
  - 顶部：状态筛选 Tab（全部 / 待处理 / 已核实 / 已驳回）；分类筛选下拉（全部 / 诈骗 / 跑单 / 失联 / 其他）。
  - 列表行：ID、被举报人 tg_id、分类（色块标签）、状态（色块标签）、时间。行内不放操作按钮——**点击某行展开右侧面板**。
  - 分页：底部 offset/limit 翻页。

- **右侧 40%：决策面板（选中某行后展开）**
  - **举报详情**：举报人 tg_id、被举报人 tg_id、分类、理由全文、证据（可展开 JSON/图片链接）、时间。
  - **被举报人画像**（调用 GET /v1/check?user_id=xxx）：风险等级（色块）、信用分、标签、举报次数（pending/verified）、是否黑名单。
  - **举报人信誉**（从举报人列表已有数据或缓存中展示）：该举报人历史举报数、核实数、核实率 %。
  - **操作区**：底部两个按钮「设为已核实」「设为驳回」，按钮旁有小字提示（如「核实后将影响被举报人信用分」）；点击后进入 5 秒倒计时撤回状态（见 2.8 操作安全网）。

**效果**：管理员在一个页面内完成「看列表 → 看详情 → 看被举报人 → 看举报人信誉 → 做决策」全流程，零跳转。

### 2.4 申诉管理页

- 布局与举报管理类似（主从），但决策面板更简：申诉详情 + 被申诉人简要画像 + 操作按钮。
- Tab：全部 / 待处理 / 已处理 / 已驳回。

### 2.5 黑名单页（增强）

**V1 方案**：仅加黑表单。

**V2 优化**：

- **上方：加黑表单**——tg_id、reason、source（下拉：admin / verified_reports / other），提交前校验 tg_id 为数字。
- **下方：最近加黑记录**——虽然后端当前无黑名单列表接口，但可以在前端本地维护一个「本次会话内加黑记录」的临时列表（存 sessionStorage），让管理员知道「本次操作了哪些」，避免重复加黑。
- **加黑确认**：输入 tg_id 后先调用 GET /v1/check?user_id=xxx 展示该用户当前信用画像（风险等级、信用分、举报数），让管理员在加黑前确认「目标是否正确」。

### 2.6 举报人列表页

- 表格：举报人 tg_id、举报总数、已核实数、核实率（前端计算 verified/total）、最后举报时间。
- **V2 新增**：核实率列用进度条或色块——核实率 > 80% 绿色、50-80% 黄色、< 50% 红色——一眼识别高信誉举报人。
- 点击某行可展开：该举报人最近的举报列表（调用 GET /v1/admin/reports?reporter_tg_id=...），但当前 API 不支持按 reporter 筛选，故首版可不做，仅预留 UI 位置。

### 2.7 交易列表页

- Tab 筛选 + 表格，只读。
- **V2 新增**：金额列右对齐并高亮大额交易（如 > 1000 USDT 加粗或标色），便于管理员关注异常交易。

### 2.8 操作安全网（V2 新增）

**所有写操作**（审核举报、处理申诉、加黑名单）的交互流程：

1. 管理员点击操作按钮。
2. 按钮变为「✅ 已提交，5 秒内可撤回」倒计时状态。
3. **5 秒内**：管理员可点击「撤回」，前端取消请求（若请求已发出则不可撤回，按钮变灰并提示「已生效，无法撤回」）。
4. **5 秒后**：自动发送 PATCH/POST 请求；成功则 Toast + 更新行状态；失败则提示错误。

**实现方式**：前端 setTimeout + AbortController（若使用 fetch）；真实请求在 5 秒倒计时结束后才发出。

**好处**：比弹窗式二次确认更快（不打断操作流），且给管理员真正的反悔窗口。

### 2.9 风险趋势页（增强）

- 图表选择器：7 / 14 / 30 / 90 天。
- **V2 新增**：
  - 堆叠面积图（默认）+ 可切换为折线图。
  - 图表下方展示该周期内的**汇总**：总查询数、各等级占比 %、high+extreme 占比（一个百分比数字加红/绿色）。
  - 鼠标悬停某天时，展示该天的具体数值（Tooltip）。

## 三、全局交互与视觉系统（V2 新增）

### 3.1 颜色系统

| 语义 | 颜色 | 使用场景 |
|------|------|----------|
| 低风险 / 成功 / 正常 | 🟢 绿 `#22c55e` | 风险等级 low、状态 confirmed/processed、核实率高 |
| 中等风险 / 注意 | 🟡 黄 `#eab308` | 风险等级 medium、待处理 pending |
| 高风险 / 警告 | 🟠 橙 `#f97316` | 风险等级 high、驳回 rejected |
| 极高风险 / 危险 | 🔴 红 `#ef4444` | 风险等级 extreme、黑名单、核实率极低 |
| 中性 / 信息 | 蓝 `#3b82f6` | 链接、按钮、信息提示 |
| 背景 | `#f8fafc` / `#0f172a`（暗色） | 默认/暗色模式 |

所有风险等级、状态标签、数字强调统一使用该色系，管理员形成条件反射。

### 3.2 暗色模式

管理后台可能在夜间或长时间使用，提供暗色模式切换（右上角 icon）；暗色下文字与背景对比度符合 WCAG AA。

### 3.3 全局快捷键

| 快捷键 | 功能 |
|--------|------|
| `G D` | 跳转总览（Dashboard） |
| `G R` | 跳转举报管理（Reports） |
| `G F` | 跳转申诉管理（Feedback） |
| `G B` | 跳转黑名单（Blacklist） |
| `/` | 聚焦搜索框（若有） |
| `Esc` | 关闭弹窗/侧面板 |

页面右下角有 `?` 图标，点击展示快捷键列表。

### 3.4 导航栏徽标数

- 左侧导航「举报管理」旁显示待处理数（红色圆点 + 数字）。
- 「申诉管理」旁同理。
- 数字来自 stats 接口，与总览页一致；30 秒轮询或页面切换时刷新。

### 3.5 全局 Toast 系统

- 所有写操作成功/失败用 Toast 提示（右上角，3 秒自动消失）。
- 错误 Toast 用红色边框，成功用绿色。
- 429 限流时 Toast 展示「操作过于频繁，请 N 秒后重试」（N 来自 Retry-After 头）。

## 四、技术架构（V2 细化）

### 4.1 前端架构

```
src/
├── api/              # 请求层：所有 admin API 封装，统一 BaseURL + Auth
│   ├── client.ts     # axios/fetch 实例，拦截器处理 403 → 登出
│   ├── admin.ts      # stats, reports, feedback, blacklist, reporters, transactions, risk_trend, pending_alerts
│   └── check.ts      # /v1/check（用于决策面板中的用户画像）
├── auth/             # 登录页、密钥管理（sessionStorage）
├── layout/           # 主布局：侧导航 + 顶栏 + 内容区
├── pages/
│   ├── dashboard/    # 总览（工作台模式）
│   ├── reports/      # 举报管理（主从布局 + 决策面板）
│   ├── feedback/     # 申诉管理
│   ├── blacklist/    # 黑名单（表单 + 本地记录）
│   ├── reporters/    # 举报人列表
│   ├── transactions/ # 交易列表
│   ├── risk-trend/   # 风险趋势
│   └── alerts/       # 待发提醒（可选）
├── components/       # 通用组件：Table, StatusBadge, RiskBadge, Toast, ConfirmCountdown, MiniChart
├── hooks/            # useAuth, usePoll, useKeyboardShortcut
├── styles/           # 颜色系统、暗色模式变量
└── types/            # 对接 API 的 TypeScript 类型（与 OpenAPI 一致）
```

### 4.2 请求层设计

- **拦截器**：请求前注入 `Authorization: Bearer <key>`；响应 403 → 清除密钥 → 跳转登录。
- **错误归一化**：4xx 返回 `{ code, message }`（解析自后端 detail/message）；5xx 返回固定 message；网络错误返回「网络不可用」。
- **429 处理**：解析 `Retry-After` 头，返回给调用方以供 Toast 展示。
- **缓存**：不做全局缓存；决策面板中调用 /v1/check 时可做 5 分钟内存缓存（同一 tg_id 不重复请求）。

### 4.3 状态管理

- **极简原则**：首版不引入 Redux/Pinia 等全局状态库。
- **页面级状态**：每个页面管理自己的列表数据、筛选条件、分页。
- **全局状态仅两项**：密钥（sessionStorage + 内存引用）、stats 数据（供导航徽标数使用，30 秒轮询）。

## 五、安全增强（V2 新增）

### 5.1 会话超时

- 密钥存入 sessionStorage 时记录时间戳。
- 每次请求前检查：若距上次活跃超过 **30 分钟**，自动清除密钥并跳转登录，提示「会话已过期，请重新登录」。
- 任何用户交互（点击、键入）重置活跃时间戳。

### 5.2 操作确认增强

- 加黑名单：除了 5 秒撤回机制外，输入 tg_id 后先展示该用户画像（调用 /v1/check），管理员确认目标无误后再加黑。
- 举报审核为 verified：面板中展示「此操作将影响被举报人信用分」提示。
- 举报审核为 rejected：面板中展示「此操作将计入举报人 rejected_count」提示。

### 5.3 防重复提交

- 所有写操作按钮在请求 pending 期间（或 5 秒撤回期间）设为 disabled，避免连点。
- POST /v1/admin/blacklist 提交后，前端在本地记录该 tg_id，再次提交同一 tg_id 时前端先提示「该用户本次会话内已操作」。

## 八、验收标准（V2 量化）

| 维度 | 标准 |
|------|------|
| **效率** | 管理员从登录到完成首条举报审核 ≤ 90 秒 |
| **效率** | 单条审核操作（列表点击 → 决策面板 → 操作 → 生效）≤ 15 秒 |
| **安全** | 密钥不出现在 URL / localStorage / 控制台日志 / source map |
| **安全** | 连续 5 次登录失败后前端锁定 60 秒 |
| **稳定** | 403 → 1 秒内跳转登录；网络错误 → 3 秒内展示 Toast |
| **兼容** | Chrome/Firefox/Edge 最新两版 100% 功能可用 |
| **构建** | `npm run build` 产出静态资源 ≤ 500KB（gzip），首屏 ≤ 1 秒（同域部署） |
| **对接** | 配置 1 个环境变量（API Base URL）+ 输入密钥即可使用，零后端改动 |

## 九、与 V1 方案的对比

| 维度 | V1 方案 | V2 优化方案 |
|------|---------|-------------|
| **总览** | 8 张数字卡片 | 待办摘要 + 指标卡片 + 迷你趋势图，待办驱动 |
| **举报审核** | 列表 + 行内按钮 | 主从布局 + 决策面板（被举报人画像 + 举报人信誉），零跳转决策 |
| **操作确认** | 二次确认弹窗 | 5 秒可撤回倒计时（更快更安全） |
| **加黑** | 纯表单 | 表单 + 加黑前预览用户画像 + 本地操作记录 |
| **视觉** | 无统一色系 | 颜色系统 + 暗色模式 + 状态标签 + 分类图标 |
| **导航** | 静态导航 | 导航徽标数（待处理数）+ 全局快捷键 |
| **安全** | sessionStorage + XSS | 增加会话超时、登录失败延迟与锁定、防重复提交 |
| **性能** | 无定义 | 构建产物 ≤ 500KB(gzip)、首屏 ≤ 1 秒、决策面板用户画像 5 分钟缓存 |
| **趋势** | 独立页 | 总览内嵌迷你图 + 独立页可切换与汇总 |
| **举报人** | 仅表格 | 核实率进度条/色块，一眼识别高信誉举报人 |

## 十、小结

V2 方案的核心改进不在于功能数量的增加，而在于**信息组织方式**的根本转变：

1. **决策面板**：把管理员审核所需的全部上下文（被举报人画像、举报人信誉、举报详情）集中在一个视野内。
2. **待办驱动的总览**：总览不再是被动的数据展板，而是主动引导管理员去处理待办。
3. **操作安全网**：用 5 秒可撤回替代弹窗确认，兼顾速度与安全。
4. **视觉系统**：统一颜色、图标与状态标签，让管理员形成条件反射式扫描。
5. **会话安全**：超时登出、登录锁定、防重复提交，覆盖管理后台常见安全场景。

以上均在**后端零改动**的约束下实现（决策面板的用户画像复用 `/v1/check`，举报人信誉复用 `/v1/admin/reporters`）。
