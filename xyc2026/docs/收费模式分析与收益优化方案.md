# 信用查 — 收费模式分析与收益优化方案

## 一、当前收费模式简述

- **免费**：基础信用分、风险等级、提示、被查用户标识；可加每日查询次数上限。
- **付费**：  
  - **AI 智能分析**：按次或订阅（如每月 N 次），生成自然语言信用解读。  
  - **活跃度时间表**：按次或订阅，基于本系统活动生成时间线。  
- **可选**：月度/季度「深度报告包」订阅，面向 B 端或高频用户。

---

## 二、可行性分析

### 2.1 有利因素

| 维度 | 说明 |
|------|------|
| 需求真实 | 交易/合作前查对方信用是刚需，尤其在加密货币、跨境、陌生人合作场景；用户已有「查一查」心智。 |
| 差异化 | 免费结果已给结论，付费卖的是「深度解读」和「行为时间线」，和基础查询不重叠，便于讲清价值。 |
| 边际成本可控 | AI 分析可缓存（同用户+同数据快照复用）；活动时间线基于自有数据，无按次外部 API 高成本。 |
| 与 Telegram 契合 | 用户已在 TG 内，支付可用 TON、Stars 或第三方，无需跳转复杂流程即可完成小额付费。 |
| 可扩展 | 先做按次，再做订阅、B 端包，定价可逐步试错。 |

### 2.2 风险与限制

| 维度 | 说明 |
|------|------|
| 付费意愿不确定 | C 端用户对「查人」类工具有免费替代（群内问、手动查），需强场景（如大额交易前）才愿付费；若免费能力已够用，两个付费点可能点的人少。 |
| 活跃度时间表感知价值有限 | 当前方案是「本系统内活动」时间线，不是「Telegram 在线状态」；若用户误以为是「实时在线/最后上线」，易失望；若理解正确，又可能觉得「只是被查了几次」价值一般。 |
| AI 分析同质化 | 若仅是把分数+标签用 LLM 重写一遍，用户可能觉得「和免费结论差不多」；需在 prompt 和展示上做出「决策建议、风险拆解、对比」等明显增量。 |
| 冷启动 | 新用户少时，举报/黑名单数据少，免费报告已显薄，付费报告更难卖出；需要运营或合作带来首批场景与案例。 |
| 合规与表述 | 涉及「信用」「风险建议」时，需注意当地金融/征信相关表述，避免被认定为征信或投资建议；AI 需明确「仅供参考」。 |

### 2.3 结论（当前模式）

- **可行**：方向正确，有真实需求，且实现与成本可控。  
- **但**：若仅靠「AI 分析 + 活动时间表」两个按次/订阅，在 C 端容易遇到付费率低、LTV 有限的问题；**需要搭配其他收益与增长手段，并优化定价与价值呈现**。

## 三、收益模式优化方案（在现有基础上做加减法）

### 3.1 保留并强化的部分

- **保留「AI 智能分析」付费**  
  - 定位为「决策解读」而非「把分数再说一遍」：强调「风险拆解 + 建议动作 + 注意事项」，可加「与同类用户对比」或简单情景建议（如「小额可试，大额建议再核实」）。  
  - 定价：建议**先按次**（如 1–3 元/次或等值 TON），再根据数据做「N 次包」「月包」；单次门槛低，便于首次转化。  
- **保留「活跃度时间表」付费，但改名与说清价值**  
  - 名称建议：「本系统活动时间线」或「查询与活动记录」，避免「在线」「活跃」引发「实时在线」联想。  
  - 文案明确：基于「被查次数、邀请打开、举报相关」等本系统可记录行为，用于判断**该账号在本平台的暴露度/被关注度**，而不是 Telegram 在线状态。  
  - 可捆绑：与 AI 分析一起做成「单次深度包」（1 次 AI + 1 次时间线）略低于分开买，拉高客单价。

### 3.2 建议新增或强化的收益方式

| 方式 | 说明 | 优先级 |
|------|------|--------|
| **查询次数包 / 月卡** | 免费版每日 3–5 次查询，超出需用「次数包」或「月卡」解锁更多次；高频用户（中介、商户）付费意愿更明确。 | 高 |
| **B 端 / 群主 / 商户套餐** | 按群或按组织：群内成员共享一定查询额度、或白名单内免费查；适合社区、换汇群、电商群，客单价高、续费稳定。 | 高 |
| **「被查提醒」订阅** | 用户订阅「谁查了我」提醒（脱敏或匿名展示），按周/月付费；增强安全感与粘性，适合在意隐私的用户。 | 中 |
| **举报/申诉加急或优先处理** | 免费为普通排队，付费可加急或优先审核（若后续有人工/半人工审核）；面向被误伤或急于澄清的用户。 | 中 |
| **导出与存证** | 报告导出 PDF/长图（带水印、报告编号、时间），免费限次数或仅最近一条，更多次或历史导出付费；便于存证与传播，适合 B 端。 | 中 |
| **邀请返额 / 邀请分成** | 邀请新用户注册或首次查询，奖励查询次数或小额抵扣券；拉新同时为「次数包」培养习惯。 | 高（增长） |
| **品牌/合规展示** | 在报告页或 Bot 内适度展示「合作机构」「数据来源」「合规声明」，提升信任，为日后 toB 或合作背书。 | 中（品牌） |

### 3.3 建议弱化或延后的部分

- **纯「活跃度时间表」单独大力推**：价值需用文案和案例教育用户，建议先作为「深度包」一部分或与 AI 捆绑，观察点击与复购再决定是否单独主推。  
- **过早推长周期订阅**：在没有稳定日活和付费习惯前，月付/季付转化难；可先做「按次 + 次数包」，再根据数据加月卡/季卡。  
- **过度承诺**：任何地方都不出现「实时在线」「Telegram 注册时间」「官方征信」等无法实现或易违规的表述。

## 四、定价与节奏建议（可落地的优化）

### 4.1 阶段划分

- **第一阶段（验证）**  
  - 免费：每日 5 次查询（可调），基础报告完整展示。  
  - 付费：仅「AI 智能分析」按次（低价试水，如 1 次 ≈ 1–2 元或等值），不急于上订阅。  
  - 目标：验证「有人愿意为深度解读付费」及大致付费率。  

- **第二阶段（扩品类）**  
  - 上「活动时间线」（命名与文案按 3.2 收敛）。  
  - 上「查询次数包」（如 10 次/30 次/月卡），满足高频用户。  
  - 推出「单次深度包」（1 次 AI + 1 次时间线）略低于分开买。  
  - 目标：提高 ARPU、观察哪个 SKU 转化最好。  

- **第三阶段（规模化）**  
  - 根据数据上 B 端/群主套餐、被查提醒订阅、导出与加急等；订阅制可作为「月卡/季卡」形式与次数包并存。  

### 4.2 定价原则（建议）

- **单次单价**：低于用户「懒得折腾」的阈值（如一杯奶茶的 1/5–1/3），便于冲动尝试。  
- **包比单次便宜**：例如 3 次包单价 < 单次 ×3，引导多买。  
- **月卡与次数包二选一或并存**：月卡适合「天天查」用户，次数包适合「偶尔深度查」用户；可先上一种，再补另一种。  
- **B 端单独报价**：按群/按年谈，不直接对标 C 端单价。

## 五、综合结论与落地顺序

### 5.1 当前收费模式是否可行？

- **可行**：AI 分析 + 活动时间线 作为付费点，在逻辑和实现上成立，且与免费层有清晰边界。  
- **不足**：若只靠这两项，C 端付费率与 LTV 可能有限；需要**加入「查询次数/月卡」和「B 端或群主套餐」**，并配合邀请与运营，收益和可持续性会更好。

### 5.2 优化后的收益结构（建议）

1. **免费层**：基础信用报告 + 每日查询次数上限（如 5 次）。  
2. **核心付费**：  
   - 查询次数包 / 月卡（高频刚需）；  
   - AI 智能分析（按次或包）；  
   - 活动时间线（与 AI 打包或单独，命名与文案按 3.2）。  
3. **扩展付费**：B 端/群主套餐、被查提醒、导出/加急等，按阶段上。  
4. **增长与留存**：邀请返额/分成、首单优惠、报告导出与水印（提升传播与信任）。

### 5.3 落地顺序（建议）

1. 先做**免费次数限制 + 单次 AI 分析付费**，验证意愿与转化。  
2. 再上**查询次数包/月卡**和**活动时间线**（含命名与文案优化），并做「深度包」捆绑。  
3. 根据数据再开 B 端套餐、被查提醒、导出与加急等，并逐步完善订阅与长期套餐。

按上述方式，在**不推翻现有两项收费设计**的前提下，用「次数/月卡 + B 端 + 运营手段」做增强，整体收费模式会更可行、收益更稳。若需要，我可以把本方案拆成「产品需求要点」或「接口/计费设计要点」便于开发对接。
