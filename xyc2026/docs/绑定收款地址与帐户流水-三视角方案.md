# 绑定 USDT/TON 收款地址与展示帐户流水 — 三视角优化方案

> 功能概述：用户可绑定 USDT（如 TRC20/ERC20）与 TON 等收款地址；系统通过调用链上/索引服务展示交易记录，使查阅方可查看被查人的「帐户流水」，增强交易前信任。  
> 本文从**开发工程师**、**市场经理**、**用户**三个角度对 UI/UX、功能与数据库给出优化方案，**不涉及具体代码**。

---

## 一、开发工程师视角（功能与数据架构）

### 1.1 现状与缺口

| 现状 | 缺口 |
|------|------|
| `wallet_entity_graph` 存 tg_id–钱包–chain，用于「换号不换地址」关联分析 | 无「用户主动绑定收款地址」的语义与权限控制；链上数据仅用于关联，未用于展示流水 |
| `transactions` 表为**站内交易确认**（发起方/对方确认），非链上交易 | 无「链上交易记录」的拉取、存储与展示 |
| 报告/信用卡片已有「交易确认 X 笔、成功率 Y%」 | 无「对方帐户流水」入口与数据源 |

因此需要：**绑定关系与展示策略**、**链上/索引交易数据的获取与存储**、**流水展示的 API 与鉴权**。

### 1.2 数据库优化建议

- **绑定关系（与现有表的关系）**
  - **方案 A**：复用 `wallet_entity_graph`，增加字段区分「系统发现」与「用户主动绑定」，并增加「是否对查阅者展示流水」等控制项。
  - **方案 B**：新建 `user_bound_wallets`（或 `payment_addresses`）表，仅存用户主动绑定的收款地址；`wallet_entity_graph` 继续只做关联分析。绑定表字段建议：
    - `id`, `tg_id`, `chain`（如 TRC20/ERC20/TON）, `address`, `label`（可选，如「主收款」）, `show_flow_to_public`（是否对查报告的人展示流水）, `created_at`, `verified_at`（可选：是否做过签名/所有权校验）。
  - **推荐**：方案 B。职责清晰，绑定 = 用户声明收款地址 + 展示策略；关联图 = 风控与换号追踪。若同一地址既被绑定又被查询过，可在应用层关联，不必混在一张表。

- **链上交易记录（流水数据）**
  - **方案 A**：不落库，每次「查看流水」时实时调链/索引 API，结果缓存短 TTL（如 1–5 分钟）。
  - **方案 B**：落库「流水快照」表，如 `wallet_transaction_snapshots`：`id`, `bound_wallet_id`（或 tg_id+address+chain）, `tx_hash`, `chain`, `direction`（in/out）, `amount`, `currency`, `counterparty_address_masked`（可选脱敏）, `block_time`/`created_at`，定期或按需从索引同步；展示时查库 + 必要时补拉最近 N 条。
  - **推荐**：先方案 A（实时+缓存），降低存储与合规压力；待产品验证后再考虑方案 B（便于统计、去重、分页与离线展示）。若采用 B，需明确数据保留周期与删除策略（如仅保留近 90 天、用户解绑即删）。

- **隐私与权限**
  - 在绑定表或 `users.privacy_settings` 中增加「是否对查阅者展示流水」开关（可与「展示近 30 天成交」并列）；报告/流水接口根据被查人的该开关决定是否返回流水或仅返回汇总（如「近 30 笔」笔数、总流入/流出区间）。

### 1.3 功能与接口设计要点

- **绑定流程**
  - 入口：Bot 内「我的」/「设置」下的「收款地址」或 `/bind_wallet`；可支持多链多地址（如 1 个 TRC20 + 1 个 TON），上限建议 2–5 个，防滥用。
  - 校验：地址格式校验（按 chain）；可选「所有权验证」（如签名或小额转入），提升可信度，但非必须 MVP。
  - 解绑：支持删除某条绑定；解绑后该地址的流水不再对任何人展示，历史缓存可清理。

- **交易记录获取**
  - 数据源：TRC20/USDT 用 TronGrid 或同类 API；TON 用 TON API / 官方索引；ERC20 可选 Etherscan 等。统一封装「按地址+链拉取最近 N 笔」的适配层，便于换链或换供应商。
  - 频率与限流：按「查看流水」请求限流（如每用户/每被查对象 1 分钟 1 次）；对链/索引侧做请求合并与缓存，避免爆量。

- **展示与鉴权**
  - 仅当「被查人」已绑定地址且开启「对查阅者展示流水」时，查阅方才能看到流水入口（报告内或单独「查看对方流水」按钮）。
  - 流水内容：建议脱敏（如对方地址仅显示前 4 后 4）；金额、方向、时间、链可展示；是否展示 tx_hash 需权衡（可验真 vs 隐私），建议可选或仅「在报告内不展示，验真时再提供」。

### 1.4 UI/UX 对实现的影响

- **报告内**：若展示流水，建议「折叠」或「摘要 + 点击展开」，避免报告过长；摘要可为「近 30 笔 / 近 7 天流入约 XXX USDT」等。
- **独立流水页/消息**：分页（如每页 10 条）、按链筛选、按时间排序，接口需支持 `limit/offset` 或游标。
- **无绑定/未开放**：报告不出现「流水」区块；或仅提示「对方未绑定收款地址」/「对方未开放流水」，不暴露是否绑定。

### 1.5 安全与合规

- 绑定与流水接口需鉴权（当前用户 = 绑定者，或当前用户 = 查阅者且被查人开放流水）。
- 链上数据公开，但「谁绑定了哪个地址」属于敏感信息，需访问控制与日志脱敏。
- 数据保留与删除：遵守隐私政策；用户解绑或注销后，绑定与流水快照的删除/匿名化策略需明确。

## 二、市场经理视角（价值、叙事与风险）

### 2.1 价值主张与差异化

- **对用户**：「先看对方流水再打款」—— 绑定自己的收款地址并开放流水，相当于出示「可验证的收款与履约记录」，适合 C2C、兼职结薪、小商户收款等场景，与「仅靠举报与黑名单」形成互补。
- **对产品**：与「交易确认笔数/成功率」结合，形成「站内确认 + 链上流水」双重证明，提升报告可信度与分享转化。
- **叙事话术建议**：强调「自主绑定、自主选择是否展示」「链上可验、数据来源透明」「仅展示汇总或脱敏流水，保护隐私」。

### 2.2 用户旅程与触点

- **绑定方（希望被信任的人）**
  - 触点：我的信用 / 设置 / 新入口「收款地址」→ 添加 TRC20 或 TON 地址 → 可选「对查我的人展示最近流水」开关 → 保存。
  - 激励：在报告/信用卡片中展示「已绑定收款地址」「近 30 笔流水可查」等徽章或一句说明，引导对方「查看流水」。
- **查阅方（想核实对方的人）**
  - 触点：查报告或信用卡片后，若对方开放流水，出现「查看对方流水」按钮 → 进入流水摘要或列表（分页）→ 理解对方收款/付款习惯后再决策是否交易。
  - 若对方未绑定或未开放：不出现入口，或仅提示「对方未开放流水」，避免误导。

### 2.3 市场与运营注意点

- **合规**：不同地区对「展示他人支付/流水信息」有不同要求；建议文案中明确「仅用于交易前参考、不构成投资或法律建议」，并保留「用户主动授权展示」的记录。
- **教育**：首次绑定与首次开放流水时，用简短说明解释「展示后，查你的人可以看到你该地址的近期交易笔数/金额方向」，避免事后纠纷。
- **节奏**：可先上线「绑定 + 仅自己看汇总」，再开放「对查阅者展示流水」；或先支持 TRC20，再扩展 TON/ERC20，降低实现与运维成本。

### 2.4 风险与应对

| 风险 | 应对 |
|------|------|
| 用户绑定他人地址「挂羊头卖狗肉」 | 可选所有权验证（签名/小额转入）；报告中标明「已验证/未验证」；举报与风控可对异常绑定做处理 |
| 流水暴露过度导致隐私投诉 | 默认「不展示」或「仅展示笔数/汇总」；脱敏与保留期限明确写进隐私政策 |
| 链上 API 不稳定或限流 | 降级策略：无法拉取时提示「暂不可用，请稍后再试」，不展示错误详情 |

## 三、用户视角（体验与心理）

### 3.1 为什么要绑定？

- **希望被信任**：在交易前主动出示「我的收款地址有真实流水」，减少对方顾虑。
- **与报告一体化**：绑定后，报告/信用卡片可显示「已绑定 USDT/TON 收款地址」，并可选「近 30 笔流水可查」，形成完整信用画像。

### 3.2 为什么要开放流水给查阅方？

- **自愿与可控**：仅当用户打开「对查阅者展示流水」时才展示；可随时关闭或解绑。
- **预期**：查阅方更容易建立信任，促成交易；绑定方获得「可验证商户/靠谱收款方」的标签。

### 3.3 查阅方看什么？

- **摘要优先**：先看到「近 7 天/30 天笔数、流入/流出大致区间」，再决定是否点开详细列表。
- **详细列表**：时间、方向（入/出）、金额、链；对方地址脱敏（前 4 后 4 或仅「外部地址」）；不强制展示 tx_hash，避免信息过载。
- **无流水时**：明确提示「该用户未绑定收款地址」或「未开放流水」，避免误以为「没有记录 = 不安全」（与「无记录不代表安全」一致）。

### 3.4 UI/UX 优化建议（用户感受）

- **绑定流程**：步骤少（选链 → 粘贴地址 → 可选标签 → 是否展示流水 → 完成）；错误时给出可操作提示（如「该地址格式不正确，请检查 TRC20 地址」）。
- **报告内展示**：流水区块与「交易确认笔数」区分开；用「链上流水」与「站内确认」两个小标题，避免混淆。
- **隐私安心**：在绑定页与开关旁简短说明「谁可以看到」「看到什么」「可随时关闭」；流水列表注明「数据来源：链上公开，本产品仅做展示」。
- **多语言**：绑定、流水、错误与说明文案均走 i18n（中/英/塔等），与现有 Bot 一致。

### 3.5 边界与预期管理

- **延迟**：链上数据可能有几分钟延迟，可在流水页注明「数据约延迟 X 分钟」。
- **链/币种**：仅展示已支持的链（如 TRC20-USDT、TON）；其他链或代币可后续扩展，避免承诺「所有链」。
- **不替代人工判断**：文案中强调「流水仅供参考，交易前请自行核实身份与合同」，与报告免责一致。

## 四、综合：推荐落地方案摘要

### 4.1 数据库

- **新增**：`user_bound_wallets`（或等价名）表，存用户主动绑定的收款地址、链、是否对查阅者展示流水、创建时间；可选 `verified_at`。
- **流水数据**：MVP 以「实时调用链/索引 API + 短 TTL 缓存」为主；可选后续增加 `wallet_transaction_snapshots` 与同步任务，并约定保留期与解绑清理。
- **隐私**：绑定表或 `privacy_settings` 中「展示流水」开关；报告与流水接口统一根据该开关与绑定状态决定是否返回流水或摘要。

### 4.2 功能与 UI/UX

- **绑定**：Bot「收款地址」入口；多链多地址（上限 2–5）；地址格式校验；可选「对查阅者展示流水」；解绑即停展示并清理相关缓存。
- **展示**：仅当被查人绑定且开放时，报告/卡片中出现「查看对方流水」；流水先摘要后列表，脱敏与分页；无绑定/未开放时仅提示「未开放流水」。
- **调用**：统一适配层拉取 TRC20/TON（及可选 ERC20）交易记录；限流与缓存；失败时友好降级。

### 4.3 分阶段建议

1. **Phase 1**：绑定表 + Bot 绑定/解绑/列表；仅自己可见「我的收款地址」与「我的流水摘要」（不对外开放），验证链上拉通与体验。
2. **Phase 2**：开放「对查阅者展示流水」开关；报告/卡片中「查看对方流水」入口与摘要 + 列表；i18n 与隐私说明补齐。
3. **Phase 3**：可选所有权验证、更多链/币种、流水快照落库与统计增强（如「近 90 天总流入」），按产品与合规再定。

## 五、与现有方案的衔接

- 与 **阶段 D（资产验证/保证金）** 的关系：绑定收款地址是本方案核心；「余额校验」可在此基础上增加 RPC 查余额并展示档位；保证金为独立字段，可并行。
- 与 **wallet_entity_graph** 的关系：绑定表存「用户声明的收款地址」；`wallet_entity_graph` 仍用于查询时解析钱包→tg_id 及换号分析；若某地址既被绑定又曾在查询中出现，可在风控或展示上做关联，但不混表。
- 与 **transactions（站内确认）** 的关系：站内确认继续提供「成功笔数/成功率」；链上流水提供「该地址的真实收支记录」；在报告/卡片中两者并列展示，互为补充。

以上为绑定 USDT/TON 收款地址与展示帐户流水的三视角优化方案，便于后续评审与分阶段实施；具体表结构、接口定义与实现可在确定方案后再细化到代码层面。

## 六、实施完成记录与优化

### 已实现（按方案 Phase 1 + Phase 2）

- **数据库**：新增 `user_bound_wallets` 表（id, tg_id, chain, address, label, show_flow_to_public, created_at, verified_at），唯一约束 (tg_id, address, chain)；`migrate_add_columns.py` 已增加 PostgreSQL 建表逻辑，启动时 `create_all` 也会创建。
- **链上流水**：`chain_flow.py` 模块，TRC20 使用 TronGrid `v1/accounts/{address}/transactions/trc20`（USDT 合约过滤），地址校验与对方脱敏（前 6 后 4）；内存缓存 TTL 2 分钟；TON 暂返回空，可后续接 TON API。
- **服务层**：`list_bound_wallets`、`bind_wallet`（格式与上限校验）、`unbind_wallet`、`update_wallet_show_flow`、`can_view_flow`、`get_flow_for_target`；`get_sharecard_data` 增加 `has_flow_visible`。
- **API**：`GET/POST/DELETE/PATCH /v2/user/me/wallets`、`GET /v2/user/me/wallets/flow`（我的流水）、`GET /v2/report/flow?target_user_id=`（对方流水，仅当对方开放时有效）。
- **Bot**：我的信用 → 收款地址 → 列表/添加/解绑/开关「展示流水」/我的流水；绑定流程：选链（TRC20/TON）→ 粘贴地址（FSM）；查报告结果页增加「查看对方流水」按钮，点击拉取对方流水或提示「对方未开放流水」；i18n 中英塔补齐。

### 相对方案的细化与优化

1. **入口**：收款地址放在「我的信用」内联按钮中，不占主菜单一行，减少主菜单拥挤。
2. **查看对方流水**：报告结果区始终显示「查看对方流水」按钮，点击时再请求 API；若对方未开放则提示「对方未开放流水」，避免在结果中依赖 `has_flow_visible` 的额外请求。
3. **错误处理**：绑定失败时按 API 状态码返回「地址格式错误」「已达上限」「已绑定过」等明确文案。
4. **解绑后刷新**：解绑后直接 `edit_text` 更新当前消息为最新列表与键盘，无需再发一条新消息。

### 下一阶段建议

- **TON 流水**：在 `chain_flow.py` 中对接 TON API / TON Center，实现 `fetch_ton_flow`，与 TRC20 一致返回 direction/amount/counterparty_masked/time。
- **可选所有权验证**：绑定时可要求签名或小额转入验证，表中 `verified_at` 已预留；报告/卡片可展示「已验证/未验证」。
- **仅当对方开放时显示按钮**：若希望不暴露「对方未绑定」，可在查报告时请求 sharecard 或 `can_view_flow`，仅当为 true 时显示「查看对方流水」按钮（当前为始终显示、点击后再判断）。
- **流水限流**：对 `GET /v2/report/flow` 与 `GET /v2/user/me/wallets/flow` 按 user_id 做 1 分钟 1 次限流，防止滥用链上 API。

## 七、下一阶段实施完成记录与再优化

### 已实现（按「下一阶段建议」）

- **TON 流水**：`chain_flow.fetch_ton_flow` 对接 TON Center API v2 `getTransactions`，解析 `in_msg` / `out_msgs` 的 value（nanoton→TON）、direction、counterparty 脱敏、time；与 TRC20 同结构返回，支持缓存与可选 api_key。
- **已验证/未验证展示**：`list_bound_wallets` 返回 `verified_at`；API `BoundWalletItem` 增加 `verified_at`；Bot 收款地址列表与解绑后列表中每条展示「· 已验证」或「· 未验证」；i18n `wallet_verified` / `wallet_unverified`。暂未实现自动或手动「设置 verified_at」逻辑，仅展示字段。
- **仅当对方开放时显示按钮**：新增 API `GET /v2/report/can_view_flow?target_user_id=` 返回 `{ can_view_flow: bool }`；Bot 在查报告、转发、邀请、最近查询再查等所有出「结果键盘」处调用 `can_view_flow_get(target_tg_id)`，仅当为 true 时在 `inline_result_actions` 中加入「查看对方流水」按钮，避免暴露对方是否绑定。
- **流水限流**：两个流水接口增加依赖 `flow_rate_limit`，按 `X-Telegram-User-Id`（Bot 请求时传入）或 IP 60 秒 1 次；超限返回 429；Bot 调用时传 `X-Telegram-User-Id`，并在 429 时展示 `flow_rate_limit` 文案。

### 相对方案的再优化

1. **TON 与 TRC20 统一**：共用同一 `api_key` 配置（当前 `trongrid_api_key`）；若后续 TON 单独限流可增加 `toncenter_api_key`。
2. **限流 key**：优先使用 Header `X-Telegram-User-Id`（Bot 传 caller），无则退化为 IP，避免未带 header 时同一 IP 多用户共用一个配额。
