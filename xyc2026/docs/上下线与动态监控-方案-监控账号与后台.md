# 上下线与更多动态监控方案：监控账号 → 后台 → 机器人推送

> **背景**：Telegram 不向机器人提供用户「最后在线」「上线/下线」状态。本方案通过**其他账号**（监控端）观测目标账号的上下线等信息，将数据上报后台，再由机器人根据订阅关系向订阅用户推送。  
> **输出**：整体架构、数据流、后台与 Bot 设计要点、合规与风险说明；不含具体代码。

---

## 一、整体思路

- **监控端**：使用「别的帐号」——可以是**真人用户**或**专用监控账号**（User 账号，非 Bot）——在能观测到目标用户在线状态的环境下（如互为联系人、同群、同频道等）获取上下线或其它动态。
- **后台**：接收并存储监控端上报的**状态/事件**（如上线、下线、最后在线时间等），并支持按「目标 tg_id」查询最新状态、按「订阅关系」判定需要通知的订阅者。
- **机器人**：用户通过 Bot 订阅「某人的上下线/动态」；Bot 调用后台接口获取订阅列表与待推送事件，向订阅用户发送通知（如「TA 刚刚上线」「TA 已下线」及更多信息）。

这样，**数据来源**从「Bot API 无法提供的在线状态」变为「监控端观测 + 后台汇总」，Bot 只做订阅管理与推送展示。

---

## 二、角色与数据流（概览）

```
┌─────────────────┐     上报状态/事件      ┌─────────────────┐     查询订阅 & 拉取事件      ┌─────────────────┐
│  监控端（一个    │ ──────────────────►  │     后台服务      │ ◄──────────────────────────  │   信用查 Bot     │
│  或多个账号）   │   (API / 队列)        │  存储 + 推送逻辑   │   (API：订阅、事件、推送)     │  订阅与推送      │
└─────────────────┘                      └────────┬──────────┘                              └────────┬──────────┘
        │                                                │                                                │
        │ 观测目标                                       │ 按 target_tg_id 存                              │ 按 subscriber 推
        │ 的上下线等                                     │ 按 subscriber 查                                │ 送消息给用户
        ▼                                                ▼                                                ▼
  目标用户 (tg_id)                              订阅表 + 状态/事件表                              订阅用户 (tg_id)
```

- **监控端**：对「目标用户」有可见性（联系人/同群等），能获知其在线状态或其它动态；将**目标 tg_id + 事件类型 + 时间戳**（及可选更多字段）上报后台。
- **后台**：落库「目标维度的状态/事件」；维护「谁订阅了谁的哪种提醒」；在 Bot 拉取或事件到达时，解析出需要通知的订阅者，可写入推送队列供 Bot 消费。
- **Bot**：用户侧只和 Bot 交互（订阅/取消、查看「我的订阅」）；Bot 定时拉取「待推送事件」或接收后台回调，向订阅用户发送一条消息（如「用户 XXX 刚刚上线」及更多信息）。

## 三、监控端形态（「别的帐号」如何工作）

| 形态 | 说明 | 数据如何到后台 | 可行性简述 |
|------|------|----------------|------------|
| **A. 专用监控账号（User 客户端）** | 使用 Telegram **用户账号**（非 Bot）登录 MTProto 客户端，通过 Telegram Client API 获取指定联系人的 online/offline、last_seen 等；监控端程序**定时轮询**被监控帐号的在线状态（建议**每 2 分钟检查一次**），仅在状态变化时上报后台，即可实现上下线提醒。 | 监控端 → HTTP/内部 API 上报「target_tg_id, event_type, ts, [last_seen]」等 | 技术上可行；需注意 Telegram 对自动化与多账号的 ToS 与风控（见第五节）。 |
| **B. 众包 / 用户主动上报** | 订阅者本人（或其它已授权用户）在与目标同群/同聊时，在 Bot 里点「上报：TA 当前在线/离线」；Bot 将上报结果发往后台，后台按 target 汇总。 | Bot 收到用户点击 → 调用后台「上报状态」接口（带 reporter_tg_id, target_tg_id, status） | 不依赖自动化客户端，合规风险低；覆盖范围取决于「谁愿意上报」、且可能延迟或不连续。 |
| **C. 混合** | 部分目标由专用监控账号覆盖，部分依赖用户上报；后台统一事件模型，Bot 推送格式一致。 | 同上，两路写入同一套「状态/事件」表或队列 | 可逐步扩展监控面；需在后台区分来源（monitor_id / reporter_tg_id）便于审计与限流。 |

**建议**：先明确产品是「仅众包」还是「允许专用监控账号」；若允许 A，需在合规与风控上单独评估（见第五节）。下面以「后台统一接收事件、Bot 统一推送」为前提，兼容 A/B/C。

#### 3.1 专用监控端轮询策略：每 2 分钟检查一次即可实现

- **实现方式**：监控帐号（专用 User 客户端）对**每个被分配到的被监控帐号**，每隔 **2 分钟** 向 Telegram 查询一次其在线状态（online / offline / last_seen）；与上一轮结果对比，若有变化则上报后台（如 `event_type=online` 或 `offline`，带时间戳）。
- **优点**：逻辑简单、实现成本低；2 分钟间隔在「及时性」与「请求频率」之间较均衡，便于控制对 Telegram 的请求量；仅在上报「状态变化」时写库与推送，避免重复推送与存储膨胀。
- **注意**：若单监控帐号负责的目标数量较多，可将目标分批、错峰轮询（如每 2 分钟轮一批），或按目标数量适当拉长单目标间隔（如 3–5 分钟），以兼顾限流与体验；具体间隔可在实施时按负载与策略微调。

## 四、后台设计要点

### 4.1 数据模型（概念）

- **监控/上报来源**（可选单独表或字段）  
  - 若用专用监控账号：可存 `monitor_tg_id` 或 `monitor_client_id`，便于限流与审计。  
  - 若用众包上报：存 `reporter_tg_id`（谁点的「上报」）。

- **目标维度状态/事件**（核心）  
  - 建议至少：`target_tg_id`、`event_type`（如 `online` / `offline` / `last_seen`）、`at_ts`（发生时间）、`payload`（可选 JSON：如 last_seen_platform, 扩展信息）。  
  - 可做成「事件流」表（按 target + time 写入），再在展示层做「当前状态」聚合（如每个 target 一条最新状态）；或只存「最新状态」表，每次上报覆盖并写一条「变更事件」到事件表供推送。

- **订阅关系**（与现有订阅表扩展或新表）  
  - 当前已有「风险变化」订阅（如 `risk_alert_subscriptions`）；可在此表增加 `alert_type`（如 `risk_change` | `online_offline` | `activity`），或单独建表 `online_alert_subscriptions (subscriber_tg_id, target_tg_id, created_at)`。  
  - 支持「某人订阅某目标的上下线提醒」与「某人订阅某目标的风险变化」并存；推送时按 `alert_type` 过滤。

- **待推送队列**（可选但推荐）  
  - 事件写入后，由后台根据订阅表生成「待推送记录」（subscriber_tg_id, target_tg_id, event_type, message_payload, created_at）；Bot 轮询或后台回调 Bot 时只消费该队列，避免 Bot 直接查订阅表+事件表做复杂关联。

### 4.2 接口（建议）

| 用途 | 方向 | 说明 |
|------|------|------|
| 监控端上报 | 监控端 → 后台 | 如 `POST /internal/status` 或 `/v1/monitor/event`：body 含 `target_tg_id, event_type, ts, [reporter_tg_id|monitor_id], [payload]`；鉴权用 API Key 或内部 Token（仅监控端/服务端持有）。 |
| Bot 拉取待推送 | Bot → 后台 | 如 `GET /v1/alert/pending` 或 `POST /v1/alert/poll`：返回当前待推送给该 Bot 的列表（或按 subscriber 分批）；消费后标记已发送，避免重复推送。 |
| 用户订阅/取消 | Bot → 后台 | 复用或扩展现有订阅接口，如 `POST /v1/alert/subscribe` 增加 `type=online_offline`；`DELETE` 取消时带 type。 |
| 查询某目标最新状态（可选） | Bot → 后台 | 如 `GET /v1/status/{target_tg_id}`：Bot 在用户「查看 TA 当前状态」时展示最近一次上线/下线时间等。 |

（上述路径与命名可按现有 API 风格统一调整。）

### 4.3 推送逻辑（后台侧）

- 监控端上报一条「目标 A 上线」→ 后台写入事件表/状态表；根据订阅表查出「订阅了 A 的上下线提醒」的所有 subscriber；为每人写一条待推送记录（或直接写推送队列）。  
- Bot 定时（如每 10–30 秒）拉取待推送列表，按 subscriber 分组发送消息；发送成功后调用后台「标记已推送」接口，避免重复。  
- 「更多信息」可在 `payload` 中扩展（如设备类型、last_seen 时间等），后台原样或稍作加工写入待推送内容，Bot 按模板组文案即可。

## 五、机器人（Bot）侧要点

- **订阅入口**：在现有「有变化时提醒我」旁或「我的订阅」内，增加「上线/下线提醒」选项（或单独订阅类型）；用户选择目标后，可勾选「风险变化」「上下线」等，Bot 调用后台订阅接口写入对应 type。
- **推送内容**：从后台拉取的待推送项中取 `event_type`、`target_tg_id`、`payload` 等，组文案如「用户 123456 刚刚上线」「用户 123456 已下线（最后在线 2 分钟前）」；若 payload 中有「更多信息」（如平台、备注），可一并展示。
- **限频与去重**：同一目标在短时间内的多次上下线，可由后台做合并或节流（如 5 分钟内只推一条「上线」），避免刷屏；Bot 侧按后台返回的条数逐条发即可。
- **语言**：待推送记录中可带 `subscriber_lang`（或 Bot 按用户设置取语言），推送时用对应 i18n 模板。

## 六、合规、隐私与风险（必读）

| 维度 | 说明与建议 |
|------|------------|
| **Telegram 服务条款** | 使用**用户账号**做自动化监控（形态 A）可能触及 ToS 中关于自动化、多账号、爬取等条款；需法务/合规评估。众包上报（形态 B）为用户主动操作，风险相对较小。 |
| **隐私与知情** | 被监控目标的「上下线」属于敏感信息；若产品对外提供该能力，建议在隐私政策与产品文案中明确：数据来源（由其他用户或系统观测）、用途、保留期限；对监控端账号的授权与数据使用范围也需说明。 |
| **滥用与风控** | 防止「监控端」被滥用（如批量监控、恶意上报）；后台对 reporter/monitor 做限流、黑名单与审计；订阅数量限制（如每人最多订阅 N 个目标的上下线）可沿用现有订阅上限逻辑。 |
| **数据最小化** | 仅存储实现「上下线提醒」与「更多信息」所必需字段；可配置事件与状态数据的保留时长（如仅保留最近 7 天状态变化），到期清理。 |

## 七、扩展「更多信息」

在「上下线」基础上，同一套「监控端 → 后台 → Bot」可扩展更多维度，只要监控端能观测并上报：

| 类型 | 说明 | 数据来源 |
|------|------|----------|
| 上线 / 下线 / 最后在线时间 | 如上 | 监控端（User API 或众包上报） |
| 在线状态变更（如 last_seen 从「2 分钟前」变为「刚刚」） | 可视为一次「动态」事件 | 同上 |
| 平台/设备（手机/桌面/网页） | 若监控端能拿到 | 写入 payload，推送时展示 |
| 头像/昵称变更 | 若监控端能检测并上报 | 可作为「动态」的一种，推送「TA 换了头像/昵称」 |
| 加入/离开某群（若监控端在该群） | 事件类型扩展 | 监控端在群内检测并上报 |

后台只需统一「事件类型」枚举与 payload 结构，Bot 按类型选用不同推送模板即可。

## 八、实施顺序建议（无代码，仅顺序）

1. **后台**：定稿「状态/事件」表与订阅扩展（含 `online_offline` 类型）；实现监控端上报 API、待推送队列与 Bot 拉取/标记已推送 API；内部用脚本或测试账号模拟上报，验证「订阅 → 事件 → 待推送 → 拉取」全链路。  
2. **Bot**：扩展订阅类型（上下线）、「我的订阅」展示与取消；实现拉取待推送与发送消息（含 i18n）；在结果页或订阅管理页增加「订阅上线/下线提醒」入口。  
3. **监控端**：先做众包形态（用户点击「上报：TA 在线/离线」）对接后台上报 API，快速验证端到端；若需形态 A，再单独开发监控客户端并严格做合规与风控。  
4. **合规与文案**：上线前完成隐私政策与产品说明更新（数据来源、用途、保留期）；对「由其他账号观测」做明确提示。

## 九、小结

- **思路**：用「别的帐号」（监控端）观测目标上下线等信息 → 上报后台 → 后台按订阅关系生成待推送 → 机器人拉取并发给订阅用户；可扩展更多动态类型。  
- **后台**：事件/状态存储、订阅表扩展、待推送队列、监控端上报 API、Bot 拉取与标记 API。  
- **Bot**：订阅类型扩展、推送文案与限频、i18n。  
- **监控端**：可选专用 User 客户端（注意 ToS）或众包上报；建议先众包再视需求上专用端。  
- **合规**：明确数据来源与用途、隐私与 ToS 评估、风控与数据保留策略。

按上述方案可实现「由其他账号监控 → 后台汇总 → 机器人向订阅用户推送上下线及更多信息」的完整链路；具体表结构、接口路径与监控端实现可再按现有项目风格细化。

## 十、三角色关系与逻辑流程（深度）

### 10.1 三种角色定义

| 角色 | 定义 | 与系统的关系 |
|------|------|----------------|
| **监控帐号 (Monitor)** | 能够「看到」某目标在 Telegram 上的在线/最后在线等状态的**用户账号**（User 账号，非 Bot）。通过我们的监控客户端或 Bot 上报该目标的状态到后台。 | 在后台注册为「监控端」；需完成登录/会话管理；对「被监控帐号」具备 Telegram 层面的可见性。 |
| **订阅帐号 (Subscriber)** | 希望收到「某人的上下线/动态」提醒的**用户**。通过 Bot 发起「监控需求」（订阅某目标），不要求自己能看见目标。 | 仅与 Bot 交互：订阅、取消、查看「我的订阅」；不参与观测，只接收推送。 |
| **被监控帐号 (Target)** | 被观测在线状态或其它动态的**目标用户**。 | 在 Telegram 侧通过**隐私设置**决定谁能看到自己的「最后在线」；在本产品侧可选「是否允许被本系统监控」（见下）。 |

核心约束：**谁能看到目标的在线状态，由 Telegram 的可见性规则决定**（目标的隐私设置 + 与观察者的关系），与「订阅帐号」是否 Premium、与「监控帐号」是否 Premium 均无直接关系（见 10.6）。

---

### 10.2 监控帐号：注册与登录管理

目标：让「监控帐号」被后台识别、鉴权，并能稳定上报其能观测到的目标状态。

#### 10.2.1 注册与身份绑定

- **入口**：在 Bot 内提供「成为监控员」或「开通监控端」入口（或独立监控端管理页）。
- **流程**：用户用其 Telegram 账号与 Bot 交互 → Bot 获取其 `tg_id` → 调用后台「注册监控账号」接口，后台写入 `monitors` 表（如 `monitor_tg_id, status=active, created_at`）；可选要求用户同意「监控员协议」后再激活。
- **结果**：该 Telegram 账号在系统中拥有「监控身份」，可用于上报与配额管理。

#### 10.2.2 登录/会话管理（专用监控客户端时）

当监控端为**专用 User 客户端**（形态 A）时，该客户端需以「监控帐号」的 Telegram 用户身份登录，才能从 Telegram 获取联系人的 online/last_seen。此时涉及「登录管理」：

| 环节 | 说明 |
|------|------|
| **会话来源** | 用户在该监控客户端内使用「用 Telegram 登录」或「扫码/输入手机号」完成 Telegram 登录，客户端获得该账号的 **MTProto 会话**（session）。会话仅存在于该客户端设备，后台不存储会话本身。 |
| **与后台的关联** | 登录成功后，客户端将「本机标识 + monitor_tg_id」上报后台（或带一次性 token），后台将「该 monitor_tg_id」与「此客户端实例」绑定，并下发 **API Token**（或刷新 token）供客户端后续上报事件时鉴权。即：**后台只管理「哪个 tg_id 是监控员、其上报用的 token」**，不管理 Telegram 登录会话；会话由监控客户端本地管理。 |
| **多设备** | 同一 Telegram 账号可在多台设备登录 Telegram；若多台设备都跑我们的监控客户端，可视为同一监控帐号的多个「上报源」，后台可按 monitor_tg_id 去重或做负载分配（见 10.4）。 |
| **登出/失效** | 用户在 Telegram 侧登出或改密，会导致该设备上的会话失效；监控客户端检测到会话失效后应停止上报，并可选在 Bot 内提示「监控端已断开，请重新登录客户端」。后台侧可将该 monitor 标记为「未连接」或保留身份待重连。 |

若为**众包形态**（形态 B）：无独立「监控客户端」，监控帐号即「在 Bot 里点上报」的普通用户，无需单独「登录监控端」，仅用其 Telegram 与 Bot 的对话身份即可；后台用 `reporter_tg_id` 标识上报来源。

#### 10.2.3 监控帐号能观测谁（可见性约束）

- 监控帐号**只能**上报其**在 Telegram 上能看到的**目标的状态。
- Telegram 规则大致为：目标设置的「谁可以看到我的最后在线」为「所有人」时，任何账号都能看到；为「联系人」时，仅目标通讯录中的账号能看到；为「没有人」时，任何人看不到精确时间（仅模糊如「最近」）；还可「自定义」白名单/黑名单。
- 因此：**同一监控帐号不能观测所有用户**；只能观测与其有「可见关系」的目标（如在其联系人列表、或同群且目标未限制等）。  
- **开通 Telegram 会员（Premium）并不能让监控帐号看到所有人的在线状态**；可见性仍由**被查看者（目标）的隐私设置**决定（详见 10.6）。

---

### 10.3 订阅帐号：如何发送「监控需求」

订阅帐号不参与观测，只表达「我想收到谁的上线/下线提醒」。

#### 10.3.1 发起订阅（发送监控需求）

- **入口**：Bot 内，例如在「查询结果页」或「我的订阅」中增加「订阅 TA 的上下线提醒」。
- **输入**：订阅帐号选定「目标」（通常为刚查过的 tg_id，或从历史/转发中选的用户）。
- **请求**：Bot 调用后台 `POST /v1/alert/subscribe`，参数含 `subscriber_tg_id`（当前用户）、`target_tg_id`、`type=online_offline`（及可选 source 等）。
- **后台处理**：  
  - 校验订阅数量上限、是否重复订阅等；  
  - 写入订阅表（如 `subscriber_tg_id, target_tg_id, alert_type=online_offline`）；  
  - **分配/匹配监控源**（见 10.4）：若当前无任何监控源能覆盖该目标，可标记该订阅为「待覆盖」或提示用户「暂无可用监控，将在他人在线可见时尝试开通」。

#### 10.3.2 关系要点

- 订阅帐号与目标**不必**互为联系人、不必同群；订阅帐号只需在 Bot 里选目标并确认订阅。
- **谁能真正观测到目标**，由「监控帐号」与目标在 Telegram 的可见性决定；订阅帐号只消费推送结果。

---

### 10.4 被监控帐号：如何「让」监控帐号去监控

分两层理解：「Telegram 层」与「本产品层」。

#### 10.4.1 Telegram 层（谁能看到我）

- **决定权在目标**：目标在 Telegram 设置中选择「谁可以看我的最后在线」：所有人 / 联系人 / 没有人 / 自定义。
- 只要某监控帐号在目标的「可见范围」内（如被列为联系人、或设为「始终对某人可见」等），该监控帐号**无需目标额外操作**即可在 Telegram 上看到其在线状态；目标「允许」的方式就是**没有把该观察者排除在隐私设置之外**。
- 若目标设为「没有人」或把某账号加入「从不分享」，则**没有任何账号**（包括 Premium）能看到其精确最后在线，我们的监控端也无法上报精确上下线。

#### 10.4.2 本产品层（是否允许被本系统监控）

- **可选策略**：在 Bot 或产品内提供「不允许被信用查监控我的上下线」开关。  
  - 若目标用户开启该选项，后台将该 `tg_id` 加入「监控排除名单」或标记 `opt_out_online_monitor=true`；  
  - 后台逻辑：不接受针对该目标的新增上下线订阅（或拒绝写入）；已有订阅可保留但**不再推送**该目标的上下线事件（或推送时注明「目标已关闭监控」）。  
- 这样「被监控帐号让监控帐号去监控」在产品侧可理解为：**默认允许**（未 opt-out 即允许）；目标若不愿意，可主动 opt-out，系统不再为其生成/推送上下线提醒。

#### 10.4.3 小结

- **让监控帐号能监控到**：由目标在 **Telegram 隐私设置** 决定（不屏蔽即可能被能看到他的人观测到）。  
- **让本系统是否推送**：由目标在本产品内的 **opt-out 开关**（若实现）决定。

---

### 10.5 监控需求与监控源的匹配（分配逻辑）

订阅帐号发起「订阅目标 T 的上下线」后，后台需有**至少一个能观测到 T 的监控源**才会产生有效推送。

#### 10.5.1 监控源从哪来

| 来源 | 说明 |
|------|------|
| **专用监控账号池** | 已注册的监控帐号，运行监控客户端，客户端定期上报其「能看到的」目标列表或状态。后台维护「monitor_id → 能观测的 target_tg_id 集合」（可从上报历史或客户端声明中推断）。 |
| **订阅者即监控者（众包）** | 订阅者本人若与目标同群/互为联系人，可邀请其「同时作为上报者」：在 Bot 内提供「您可以看到 TA 的在线状态，是否愿意上报？」；同意后，该订阅者的上报即作为该目标的监控源。 |
| **其他众包用户** | 任意用户在与目标同场景下，在 Bot 内点「上报：TA 在线/离线」，后台用该次上报作为事件源；不要求该用户事先是「订阅者」。 |

#### 10.5.2 分配/匹配流程（逻辑）

1. **订阅创建时**：后台收到「订阅者 S 订阅目标 T 的上下线」。
2. **查是否有现成监控源**：  
   - 若存在「已注册监控帐号 M，且 M 曾上报过 T 或 M 声明能观测 T」→ 可为该订阅分配 monitor_id=M（或仅记录「当前由 M 覆盖」）；  
   - 若为众包模式：暂不分配，等有任意用户对 T 上报时，再将该事件与「订阅了 T 的 S」匹配并推送。
3. **若无现成监控源**：  
   - 可将该订阅记为「待覆盖」；  
   - 若 S 本人可能是观测者（如同群），Bot 可提示「若您能看到 TA 的在线状态，可点击「我来上报」成为该目标的监控源」；  
   - 或提示「暂无监控源覆盖该用户，待有数据时将通知您」。
4. **上报到达时**：任意监控源上报「T 上线/下线」→ 后台写事件表 → 查订阅表「所有订阅了 T 的 online_offline 的 S」→ 写待推送 → Bot 拉取后发给 S。

（具体表结构可为：订阅表含 `subscriber_tg_id, target_tg_id, alert_type`；可选 `assigned_monitor_id`；事件表含 `target_tg_id, event_type, monitor_id/reporter_tg_id`。）

---

### 10.6 监控帐号开通 Telegram 会员能否监控所有帐号？

**结论：不能。**

- **谁能看到某人的「最后在线」**，由**被查看者（目标）的 Telegram 隐私设置**决定，与查看者是否 Premium 无关。  
  - 目标设为「所有人」→ 任何账号都能看到；  
  - 目标设为「联系人」→ 仅其通讯录能看到；  
  - 目标设为「没有人」→ 所有人都只能看到模糊状态（如「最近」「一周内」等），**任何账号（含 Premium）都无法获得精确时间**。  
- Telegram 官方说明：即使用户隐藏了自己的最后在线时间，他人（包括 Premium 用户）也无法绕过该限制看到精确时间；Premium 不提供「查看所有人在线状态」的能力。  
- 因此：**监控帐号即使用 Telegram 会员，也仅能监控「在 Telegram 上对其可见」的那部分帐号**；无法仅凭 Premium 监控「所有帐号」。

---

### 10.7 逻辑流程总览（文字 + 示意）

#### 流程 1：监控帐号注册与登录（专用客户端时）

```
[用户] 在 Bot 内点击「成为监控员」 → [Bot] 取 tg_id，调后台注册
    → [后台] 写入 monitors(monitor_tg_id)，下发 API Token（或链接）
    → [用户] 在监控客户端用 Telegram 登录（获得本地 MTProto 会话）
    → [客户端] 用 Token + monitor_tg_id 与后台握手，后台标记「已连接」
    → [客户端] 每 2 分钟轮询其负责的被监控帐号的 online/last_seen，有变化时上报后台
    → [后台] 写入事件表，按订阅表生成待推送
```

（众包形态无「监控客户端登录」；用户直接在 Bot 里点「上报」即可。）

#### 流程 2：订阅帐号发送监控需求

```
[订阅者 S] 在 Bot 选择目标 T，点「订阅上下线提醒」
    → [Bot] POST /v1/alert/subscribe (S, T, type=online_offline)
    → [后台] 校验上限、去重；写订阅表；执行「匹配监控源」（见 10.5）
    → [后台] 若有监控源覆盖 T：返回成功；若无：返回「待覆盖」或提示 S 可自愿成为上报者
    → [Bot] 向 S 展示「已订阅」或「等待监控源覆盖」
```

#### 流程 3：被监控帐号对「是否被监控」的影响

```
[目标 T] 在 Telegram：设置「谁可以看我的最后在线」 → 决定哪些账号（含我们的监控帐号）能在 TG 侧看到
[目标 T] 在本产品（若实现）：打开「不允许信用查监控我的上下线」 → [Bot] 调后台 opt-out
    → [后台] 标记 T 为不可监控 / 停止对 T 的订阅推送
```

#### 流程 4：从上报到订阅者收到推送

```
[监控源 M] 观测到目标 T 上线 → [客户端/Bot] 上报 (target_tg_id=T, event_type=online, ts)
    → [后台] 写事件表；查订阅表得「订阅了 T 上下线的 S 列表」；写待推送队列
    → [Bot] 轮询拉取待推送 → 按条给 S 发消息「用户 T 刚刚上线」
    → [Bot] 调后台标记已推送
```

---

### 10.8 三角色关系小结表

| 关系 | 说明 |
|------|------|
| **监控帐号 ↔ 后台** | 监控帐号注册、登录（客户端会话本地，后台只认 token + monitor_tg_id）；上报事件时带鉴权，后台按 monitor 限流与审计。 |
| **监控帐号 ↔ 被监控帐号** | 仅当目标在 Telegram 上对监控帐号「可见」时，监控帐号才能观测并上报；目标可通过 TG 隐私或本产品 opt-out 限制/关闭。 |
| **订阅帐号 ↔ 后台** | 通过 Bot 发起订阅/取消；后台维护订阅表与待推送队列，Bot 拉取后推送给订阅帐号。 |
| **订阅帐号 ↔ 被监控帐号** | 无直接 Telegram 关系；订阅帐号仅表达「我想收到谁的提醒」，不参与观测。 |
| **订阅帐号 ↔ 监控帐号** | 通常无直接关系；仅在「订阅者即上报者」的众包场景下，同一人兼具两角。 |

---

### 10.9 实施时可落地的策略建议

- **监控帐号管理**：在 Bot 内做「监控员注册」与状态展示；专用客户端用 Token 鉴权上报，不存 TG 会话于后台。  
- **订阅需求**：Bot 统一走「订阅目标 + type=online_offline」；后台实现「匹配监控源」与「待覆盖」状态，必要时引导订阅者成为上报者。  
- **被监控帐号**：产品文案写清「数据来自对您可见的账号的观测」；可选提供 opt-out，并尊重 Telegram 隐私（不承诺能监控所有人）。  
- **Premium**：对外统一说明「开通 Telegram 会员不能查看所有人的在线状态，可见性由对方隐私设置决定」，避免误导。

### 11.1 已实现

- **数据与迁移**
  - `RiskAlertSubscription` 增加 `alert_type`（risk_change | online_offline），唯一约束改为 (subscriber_tg_id, target_tg_id, alert_type)。
  - 新表 `OnlineStatusEvent`：target_tg_id, event_type, reporter_tg_id, monitor_tg_id, at_ts, created_at, payload。
  - 迁移脚本 `migrate_add_columns.py`：增加 alert_type 列、PG 更新唯一约束、新建 online_status_events；SQLite 在首次迁移时重建 risk_alert_subscriptions 并建 online_status_events。

- **后台**
  - `alert_subscribe(..., alert_type)`、`alert_unsubscribe(..., alert_type)`、`alert_list_subscriptions` 返回每项 `alert_type`。
  - `enqueue_alerts_for_target` 仅对 `alert_type=risk_change`（或 NULL 兼容旧数据）入队。
  - 新增 `monitor_report_status(session, target_tg_id, event_type, reporter_tg_id, ...)`：写 OnlineStatusEvent、5 分钟去重、为 online_offline 订阅者入队 RiskAlertPending(event_type=online|offline)。

- **API**
  - `POST /v1/alert/subscribe` 增加 query 参数 `type=risk_change|online_offline`，默认 risk_change。
  - `DELETE /v1/alert/subscribe` 增加可选 `type`，未传则取消该 target 下全部类型。
  - `POST /v1/monitor/event`（需 Admin Key）：body 含 target_tg_id, event_type(online|offline), reporter_tg_id 等；供 Bot 众包或专用监控端上报。

- **Bot**
  - 结果页（他人报告）键盘：在「有变化时提醒我」下增加「订阅上下线提醒」「上报：TA 在线」「上报：TA 离线」。
  - 订阅回调：解析 `alert_subscribe_online_{id}` 为 type=online_offline；调用 API 时传 alert_type；成功提示用 msg_alert_subscribed_online。
  - 取消订阅：callback_data 含 alert_type（alert_unsubscribe_{target}_{alert_type}），按类型取消。
  - 「我的订阅」列表展示每项 type_label（风险提醒/上下线），并带 type 的取消按钮。
  - 众包上报：`report_status_online_` / `report_status_offline_` 回调 → 调 `POST /v1/monitor/event`（Admin Key），提示「已上报」。
  - 轮询 worker：对 event_type=online/offline 用 alert_push_online / alert_push_offline 推送。

- **i18n**：alert_push_online/offline、btn_subscribe_online_offline、btn_report_online/offline、msg_alert_subscribed_online、alert_type_risk/online、msg_status_reported；alert_my_subscriptions_item 增加 type_label 占位。

### 11.2 实施中的优化（相对原方案）

- **复用待推送表**：上下线与风险变化共用 `RiskAlertPending`，通过 event_type 区分（new_report / blacklist_added / online / offline），Bot 轮询与标记逻辑一致，无需单独队列。
- **去重窗口**：监控上报采用 5 分钟同 target 同 event_type 去重，减少重复推送与存储。
- **我的订阅展示**：列表按 (target, alert_type) 分行展示并支持按类型取消，同一目标可同时保留「风险提醒」与「上下线」两种订阅。
- **SQLite 迁移**：用 `_migration_markers` 表保证「重建 risk_alert_subscriptions 以更新唯一约束」只执行一次，避免重复重建。

### 11.3 下一阶段建议

- **专用监控客户端**：实现「每 2 分钟轮询被监控帐号在线状态」的 User 端客户端，使用同一 `POST /v1/monitor/event`（Bearer Token 或 body 中 monitor_tg_id），后台已支持。
- **监控员注册与 Token**：若启用专用端，在 Bot 内增加「成为监控员」入口，后台下发 API Token 供客户端鉴权。
- **可选**：GET /v1/status/{target_tg_id} 查询某目标最新上下线状态（从 OnlineStatusEvent 取最近一条）；管理后台展示监控事件与订阅统计。
