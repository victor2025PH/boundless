# 信用查 — 产品需求要点 & 计费/接口设计要点清单

> 基于《收费模式分析与收益优化方案》整理，便于产品评审与开发对接。  
> **产品需求要点** 供产品/运营使用；**计费/接口设计要点** 供后端/前端/Bot 开发使用。

---

## 第一部分：产品需求要点

### 1. 功能范围与层级

| 层级 | 内容 | 说明 |
|------|------|------|
| **免费** | 基础信用报告 | 被查用户标识、风险等级、信用分、综合建议、标签、提示、详情（首次记录、举报、黑名单、被查询次数、数据更新于、最近活动）、数据说明与免责。 |
| **免费限制** | 每日查询次数上限 | 如每日 5 次（可配置）；超出后提示升级或购买次数包/月卡。 |
| **付费-单次** | AI 智能分析 | 基于当前报告数据生成自然语言「决策解读」：风险拆解、建议动作、注意事项；可含与同类对比或情景建议。 |
| **付费-单次** | 活动时间线 | 基于本系统内可记录活动（被查、邀请打开、举报相关）生成时间线；**命名**用「本系统活动时间线」或「查询与活动记录」，**不承诺** Telegram 在线/注册时间。 |
| **付费-包/卡** | 查询次数包 | 如 10 次 / 30 次 等，购买后增加可用查询次数（可与每日上限叠加或单独计）。 |
| **付费-包/卡** | 月卡 | 在有效期内放宽或取消每日查询次数限制（如每日 20 次或不限）。 |
| **付费-包** | 单次深度包 | 1 次 AI 分析 + 1 次活动时间线，定价略低于两项单独购买之和。 |
| **扩展（后置）** | B 端/群主套餐、被查提醒、导出/加急等 | 按阶段上线，见下方阶段表。 |

### 2. 用户故事（可验收）

| ID | 角色 | 故事 | 验收标准 |
|----|------|------|----------|
| P1 | 普通用户 | 每日免费查几人，看到完整基础报告 | 每日前 N 次查询正常返回报告；第 N+1 次提示「今日次数已用尽」及购买入口。 |
| P2 | 普通用户 | 对某次查询结果想得到「AI 解读」 | 在结果页点击「AI 智能分析」，若有余额则生成并展示分析文案；若不足则引导购买。 |
| P3 | 普通用户 | 想看对方在本平台的「活动时间线」 | 在结果页点击「活动时间线」，若有余额则展示基于本系统活动的时间线；若不足则引导购买。 |
| P4 | 高频用户 | 免费次数不够用 | 可购买「次数包」或「月卡」，购买后额度到账/生效。 |
| P5 | 被查用户 | 不想被误以为「官方征信」 | 所有报告与 AI 分析处有「仅供参考」「非官方征信」等明确表述；AI 分析有「AI 生成，仅供参考」。 |

### 3. 文案与合规（必达）

| 项 | 要求 |
|----|------|
| **活动时间线** | 名称与说明中不得出现「实时在线」「最后上线」「Telegram 在线状态」「注册时间」等；统一为「本系统内可记录的活动」「暴露度/被关注度」。 |
| **AI 分析** | 必须带「AI 生成，仅供参考」或等价表述；不得构成投资建议或官方征信承诺。 |
| **报告页** | 数据说明/免责区块保留；可加「数据来源」「合规声明」等以增强信任。 |
| **付费入口** | 未付费时点击付费功能，提示清晰（如「该功能为付费功能」+ 价格或「开通/购买」引导），不静默失败。 |

### 4. 阶段与优先级（产品侧）

| 阶段 | 产品范围 | 目标 |
|------|----------|------|
| **一** | 免费次数上限 + 仅「AI 智能分析」按次付费 | 验证付费意愿与转化率。 |
| **二** | 活动时间线（命名/文案按上）+ 查询次数包/月卡 + 单次深度包 | 拉高 ARPU、观察 SKU 表现。 |
| **三** | B 端/群主套餐、被查提醒、导出/加急、长周期订阅等 | 规模化与差异化。 |

### 5. 定价与运营（参考，非接口约束）

- 单次 AI：建议低价试水（如 1–2 元/次或等值 TON）。
- 次数包：包单价 < 单次 × 次数；月卡与次数包可二选一或并存。
- 深度包：1 次 AI + 1 次时间线，略低于分开买。
- B 端：单独报价，按群/按年。

## 第二部分：计费/接口设计要点

### 1. 概念与名词

| 名词 | 含义 |
|------|------|
| **查询人** | 发起查询的 Telegram 用户（tg_id），即「谁在查」。 |
| **被查人** | 被查询的 target（tg_id / username / 钱包对应实体）。 |
| **额度** | 某查询人在某产品上的剩余可用次数或权益（如查询次数、AI 次数、时间线次数）。 |
| **产品/商品** | 计费单位：如 `query_pack_10`、`ai_analysis_once`、`activity_timeline_once`、`deep_pack_once`、`monthly_pass` 等。 |

### 2. 数据模型要点（库表/实体）

| 实体/表 | 用途 | 关键字段建议 |
|----------|------|-----------------------------|
| **用户额度/订阅** | 某 tg_id 的权益与有效期 | tg_id, product_type, balance（剩余次数）, expires_at, 可选 plan_id。 |
| **订单** | 支付与对账 | tg_id, order_id, product_type, amount, currency, status, paid_at, 可选 payment_channel。 |
| **功能使用日志** | 扣减、限频、防刷 | tg_id, feature（query/ai_analysis/activity_timeline）, target_id（被查人）, at；可选 idempotency_key。 |
| **AI 分析缓存** | 同用户同数据快照复用 | user_id（被查人）, data_hash, analysis_text, model_id, created_at。 |
| **活动事件（时间线用）** | 本系统活动流水 | user_id, event_type（queried/invite_opened/report_*）, at, 可选 meta。 |

- **查询次数**：可按「查询人 + 自然日」统计已用次数，与「每日上限」和「次数包/月卡余额」配合判断是否允许本次查询。
- **扣减顺序建议**：先扣「次数包」再扣「月卡」再扣「免费每日额度」（或按产品策略定）。

### 3. API 设计要点

| 能力 | 建议方式 | 说明 |
|------|----------|------|
| **查额度** | `GET /v1/me/balance` 或 `GET /v1/me/subscription` | 入参：tg_id（或由 Bot 从 session 带）；返回：每日剩余免费次数、各付费产品剩余次数、月卡/订阅到期时间等。Bot 据此决定是否展示付费按钮、是否允许调用付费能力。 |
| **查询（现有）** | `GET /v1/check` | 在逻辑内增加：先校验「查询人」是否超每日免费上限、是否有次数包/月卡可用；通过则扣减（免费或包/卡），再执行现有 check 逻辑；超限返回 4xx + 明确 code（如 `QUOTA_EXCEEDED`）及 message，Bot 展示「今日次数已用尽」等。 |
| **AI 分析** | `POST /v1/ai/analyze` 或 `GET /v1/ai/analyze?target_user_id=xxx` | 入参：查询人 tg_id（鉴权）、被查人 target_user_id（或 tg_id）；先鉴权并扣减「AI 分析」额度，再查缓存（被查人 + 当前数据 hash），有则返回缓存，无则调模型写入缓存后返回；失败/余额不足返回 4xx。 |
| **活动时间线** | `GET /v1/activity/timeline?target_user_id=xxx` | 入参：查询人 tg_id、被查人 target_user_id；先鉴权并扣减「活动时间线」额度；限频（如同一被查人每日最多生成 1 次）；返回按日/周聚合的时间线数据或文案。 |
| **下单/支付** | 视支付渠道而定 | 若自建：可 `POST /v1/orders` 创建订单，返回支付链接或参数；支付回调后更新订单状态并给对应 tg_id 加额度。若用 TON/Stars 等，需对接其 Webhook 与入账逻辑。 |

### 4. 鉴权与限流

| 项 | 要点 |
|----|------|
| **鉴权** | 所有计费相关接口需明确「查询人」身份（tg_id）；Bot 侧从 Telegram 消息取 from_user.id，API 可用 Header（如 X-Telegram-User-Id）或 Query 传递，并校验与 session/token 一致（若用 token）。 |
| **免费次数限制** | 按「查询人 tg_id + 自然日」统计当日已用查询次数；未付费用户每日上限配置化（如 5）；超限即拒绝并返回明确错误。 |
| **付费功能限频** | 活动时间线可按「被查人 + 自然日」限制同一被查人每日最多生成 1 次（防刷）；AI 分析可按「查询人 + 被查人 + 数据 hash」做缓存，避免重复扣费。 |
| **幂等** | 扣减额度时建议带 idempotency_key（如 client 生成 UUID），防止重复点击导致多次扣减。 |

### 5. 配置项（建议可配置，便于运营）

| 配置项 | 含义 | 示例 |
|--------|------|------|
| 每日免费查询次数上限 | 未购买包/卡时，每 tg_id 每日可查询次数 | 5 |
| 单次 AI 分析价格（展示用） | 前端/Bot 展示 | 2 元/次 或 等值 TON |
| 活动时间线单次价格 | 同上 | 1 元/次 |
| 深度包价格 | 1 次 AI + 1 次时间线 | 2.5 元 |
| 次数包规格与价 | 如 10 次 / 30 次 | 配置化列表 |
| 月卡有效期与权益 | 如 30 天内每日 20 次 | 30 天、每日 20 次 |
| 同一被查人时间线生成间隔 | 限频 | 24 小时 |

### 6. Bot 侧要点（与计费联动）

| 项 | 要点 |
|----|------|
| 结果页按钮 | 根据「查额度」接口决定是否展示「AI 智能分析」「活动时间线」按钮；或始终展示，点击时再鉴权，无额度则跳转购买/开通说明。 |
| 错误处理 | 查询超限、付费能力余额不足时，展示统一文案（如「今日免费次数已用尽」「AI 分析次数不足，请购买」）并带购买/开通入口。 |
| 支付闭环 | 用户完成支付后，可通过 Bot 内菜单或链接查询「我的额度」「我的订单」；支付回调后可选推送「购买成功，额度已到账」类消息。 |

### 7. 落地顺序（开发侧）

1. **阶段一**：实现「每日免费次数上限」+ 额度查询接口（可先硬编码「无付费额度」）；实现「AI 分析」单次扣减与调用逻辑；Bot 展示 AI 按钮并在无额度时引导。
2. **阶段二**：实现次数包/月卡的数据模型与扣减顺序；查询接口与额度接口联动；实现活动时间线接口与限频；单次深度包（一次扣减两种权益）。
3. **阶段三**：订单与支付回调、B 端套餐、被查提醒、导出/加急等按产品排期接入。
