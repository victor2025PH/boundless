# 升级安装自愈（104 事故）—— 交接说明

> 2026-07-31。**结论先说**：同一安装包在「旧数据目录 + 新程序」下，四平台扫码 +
> 账号常驻 + 产品基线功能现已全部自愈，并有四道门禁（三层源码 + 一层冻结产物）钉住。
> 冻结产物级证据：`cd desktop && npm run smoke:upgrade` → 全绿。

## 一、事故与根因

104 实机（幻颜节点，装 0.2.11）打不开 LINE / WhatsApp / Messenger 的扫码登录，而
**同一个安装包**在 198 与其他笔记本上四平台全可用。

- **不是网络/机器问题**：104 装的是打包版，自带并拉起本机后端（`backend.exe`，
  127.0.0.1:18799），不连 117 生产实例；扫码能否用完全取决于它**本机后端的配置**。
- **根因＝种子只播一次**：`ConfigManager._ensure_seeded` 仅在 config 文件**不存在**时
  把 `config/config.desktop.min.yaml` 拷进用户数据区。而「产品该默认点亮哪些功能」这个
  **产品决策**当时写在种子里 → **升级安装**（旧 config 快照）永远拿不到后加的开关。
  104 在 7/29 装过旧版，7/30 装 0.2.11 只换了 Program Files，`%APPDATA%` 里的旧 config
  原地保留 → 那几个开关仍是关的。
- **重装不修**：数据目录在 `%APPDATA%`，覆盖安装/卸载重装都不动它。用户最自然的自救
  动作（重装）在这类问题上必然无效 → 每一例都会变成远程排查工单。
- 同类先例：`licensing.trial`（首启体验档）踩过同一个坑并已在 `local_trial.
  configure_local_trial` 里用「桌面态 + 配置从未写过 → 按桌面默认开」修过。本次是第二次。

## 二、两套自愈机制（并存，分工明确）

| 机制 | 实现 | 适用 | 是否写用户配置 |
|---|---|---|---|
| **读时解析** | `platform_login.resolve_login_switch` + `_DESKTOP_LOGIN_DEFAULT_ON` | 接入开关（4 平台 + orchestrator） | 否 |
| **启动补齐** | `feature_registry` A 类 + `ConfigManager._ensure_baseline` | 其余基线功能（goals / deep_persona / bubbles） | 是（写 overlay） |

三态语义（两套共用）：**配置显式写过 → 完全以配置为准（含 `false`）；从未写过 →
桌面态按代码默认开、服务器部署保持默认关**。服务器部署（无 `AITR_DESKTOP_MODE`）
行为零变化；运营显式关闭永远被尊重。

### 两个关键设计边界（勿顺手「统一」掉）

1. **诊断类刻意仍读字面值**：`config_check` / `companion_preflight` /
   `protocol_diagnostics` 回答的是「配置里到底写没写」（运维审计视角），与「实际会不会
   生效」正交；统一成有效值会让审计视角失真。该边界由 `_orchestrator_on` 处代码注释 +
   `test_platform_login_defaults` 的白名单防过期断言共同固化。
2. **`read_from_store` 选「对齐代码默认」而非「进 A 类回填」**：① 它是内部读路径开关，
   不是面向客户的功能，进 `feature_registry` 会让它出现在功能总览 UI 里（语义错位）；
   ② `config.example.yaml` 与生产实例都**显式 `true`**，故改默认对生产**可证明是 no-op**，
   只影响该键出现之前装的陈旧配置——正是要修的人群。

## 四、四道门禁（各守一层，缺一层就有盲区）

| 门禁 | 层次 | 守什么 |
|---|---|---|
| `tests/test_platform_login_defaults.py` | 读取函数 | 默认表 ↔ 种子双向；四平台读取函数**集合相等**覆盖性；三态语义；**字面直读旁路守卫**（全 `src/` 扫描，白名单仅 3 个诊断模块 + 防过期） |
| `tests/test_platform_login_upgrade.py` | 诊断判定 | 用 104 真实陈旧配置形态验 `diagnose_mode`（弹窗真正消费的那层）；配服务器态自证 |
| `tests/test_seed_switch_upgrade_coverage.py` | 类别级 | 种子里为 `true` 的每个开关必须被两套机制之一覆盖，或落在带**核实到代码位置**的豁免表；覆盖集从机制数据结构**派生**（不手抄） |
| `desktop/build/smoke_upgrade.py` | 冻结产物 | 陈旧数据目录起打包后端，一次验两套机制（modes 端点 + features 端点） |

前三道已注册进 `scripts/gate_sweep.ps1`（26 文件 478 passed）。第四道走
`npm run smoke:upgrade`（**刻意未链进** `build:backend`——那是别人的发布门禁）。

### 为什么门禁要「派生 / 扫描」而不是手写清单

`messenger` 与 `telegram` **两次**都是同一形态：键进了默认表、读取函数却漏接（表项对
该平台等于死的）。而第一版门禁里那条读取接线断言本身就是一份**手写清单**，telegram
正是从它漏过去的——同一失效模式的第三次重演。故改为：表↔读取函数**集合相等** +
源码级旁路扫描，以后加平台或有人写新的字面直读，门禁自己会红。
