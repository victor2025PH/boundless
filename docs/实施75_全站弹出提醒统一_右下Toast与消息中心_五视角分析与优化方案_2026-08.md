# 实施75：全站弹出提醒统一（右下 Toast + 消息中心）——五视角分析与优化方案

> 2026-08-27。触发：老板截图顶部蓝条「服务刚完成重启，约 2 分钟内若偶发加载失败属正常……（系统冷却保护中，连环重启已自动抑制）」，问「为什么一直存在、没有关闭的地方」，并拍板：**以后不再用顶部状态条这种形式，全站弹出统一为「右下角弹出消息 + 消息栏（消息中心）提醒」两种形态**。
> 本文档为方案（未改代码）。范围：engines/chengjie web 全站（工作台壳 + 经典后台 + 收件箱 + RPA 页）+ ChatX 桌面壳。

---

## 0. 蓝条之谜：为什么它「一直在、关不掉」

**机制**（都是既有设计，不是 bug）：

- 这条是 `workspace_base.html` 的 `ws-restartcool` 横幅，数据链：重启脚本写冷却账本（`D:\chengjie-instances\.ops\restart_cooldown\last_restart_zhiliao.json`，`cooldown_min=10`）→ `src/utils/instance_restart_status.py::seat_restart_banner` 算 `cooldown_active/cooldown_left_min` → `/api/workspace/ai-runtime-status` 60s（冷却期 30s）轮询 → 点亮横幅。**每次重启后整整点亮 10 分钟**，文案里「约 N 分钟」就是剩余冷却倒计时。
- **刻意没做关闭按钮**（注释原文：「冷却窗内温和预期管理，勿催坐席狂刷」）。同族的红色通道条 `ws-chandown` 今天（08-27）刚被并行线加上 × 和 24h 暂缓，蓝条没有同步跟进——关闭语义在横幅家族内部就不一致。
- **为什么感觉常驻**：重启事件账本显示今天 0:00–12:09 已重启 **14 次**——凌晨看门狗自愈 8 次（00:08/00:13/03:43/03:48/03:58/04:43/04:48/05:28，实例反复宕机）+ 06:18 事故恢复（日志轮转死锁弄死 web 监听）+ 白天开发批次 5 次（07:15/09:07/09:39/10:24/12:09）。每次重启 = 停机窗（红/蓝连接条）+ 10 分钟蓝条，累计横幅在屏时间约 2.5~3 小时，占上午时段 ~25%；03:43–05:38 那段几乎连续。截图里的「约 2 分钟」正是 12:09 批次的冷却尾巴。
- **附带事实**：这条横幅不只是视觉——它同步驱动 `__wsRestartCool.quiet` 功能信号（收件箱轮询降速、abort 拉长、conn-banner 转蓝色维护语义）。**统一改造时视觉可以撤，信号链必须原样保留。**

**两个正交结论**：① 蓝条是诚实的，病根之一是重启频率本身（凌晨崩溃风暴 + 白天 5 个开发批次，其中 09:07/09:39/10:24 三次在三窗口纪律之外）——这属值守/稳定性治理，本方案不展开；② 但 UI 把「被动告知、用户无法行动」的信息用了**最高打断等级（常驻通栏横幅）且不可关闭**，这是形态错配，本方案解决的是这个。

## 2. 五视角问题清单

### 2.1 开发工程师

1. **同一需求实现了 7 次**：「给用户说句话」有 7 套 toast，位置/时长/样式/去重各自为政；新人不知道该调哪个，于是第 8 套只是时间问题（额度墙私有 toast 就是这么长出来的）。
2. **每个新状态发明一种新形态**：13 条顶部横幅是逐个需求各自长出来的，wsBanner 优先级是手工魔法数字（100/90/80/70/60/40/35/30/20/18/16/15/15），加一条要人肉排位。
3. **视觉与功能信号耦合**：`ws-restartcool` 同时承载 `quiet_poll` 轮询降速信号；`conn-banner` 承载重连语义。动视觉必须先剥离信号，否则改一条横幅可能弄坏收件箱自适应轮询。
4. **同一事件多路投递、去重规则不同源**：toast（无去重）、铃铛（8s 会话+预览窗）、SSE 缓冲（4s）、watchdog 告警（6h 去抖）——排查「为什么弹了三次/为什么没弹」要读四处代码。
5. **原生 alert/confirm 188+131 处**：阻塞 JS 线程、在桌面壳里是系统弹窗观感、绕过 i18n/主题/审计，还会打断 SSE 处理。
6. **热更新直上生产 + 哑按钮风险**：横幅内按钮必须挂 window，本区一天内两次实锤（`_uiBeacon`/`_closeFtabMore`）；形态越多，这类雷越多。
7. **测试面碎片化**：每条横幅/每套 toast 要单独的 verify_* 浏览器门禁；形态不收敛，门禁只能逐个补，漏一个就是生产哑按钮。
8. **壳与 web 双体系**：更新提示、公告、通知权限在壳（`update-notify.js`/`shell.notify`）与 web（`__wsNotify`）各一套，i18n 键也两套。

### 2.2 市场经理

1. **顶部通栏 = 广告位，现在登的是事故**：每次演示/截图/录屏，最显眼的位置写着「服务刚完成重启」「AI 暂时无法自动回复」——等于把系统不稳定打在品牌门脸上。今天客户看到的首屏就是这样。
2. **运维黑话直达客户**：「连环重启已自动抑制」「系统冷却保护中」「熔断」「兜底」——用户不懂，只会不安；这类词一条都不该出现在客户可见面。
3. **营销与事故同一形态**：试用引导（aitrial）、新手引导（aiguide）与事故横幅（delivblock）都在同一根横幅槽里轮播，营销信息被事故语境污染，转化场景反而被吓退。
4. **行业观感落后**：成熟 SaaS（Slack/Intercom/飞书/钉钉）清一色右下 toast + 通知中心；顶部通栏事故横幅是内部运维工具的形态，对外显得半成品。
5. **客服成本**：「这条蓝的是什么/怎么关」本身就在制造报障工单（实施51 刚做了报障入口，第一批进来的就会是这类咨询）；不可关闭的条子还会训练用户忽略一切横幅——真正需要行动的红条也会被无视。
6. **白标风险**：横幅样式/文案硬编码运维语气，白标客户拿到的还是同一套事故语言，无法按品牌调性收口。

### 2.3 用户（坐席/老板）

1. **关不掉、不知道多久消失、不知道要不要做什么**（本次投诉原文）。同样是条子：红色通道条有 ×、蓝条没有——规律无法学习。
2. **占地方**：405px 桌面壳下一条横幅挤掉整整一行会话；收件箱首屏密度主线刚从 6-7 行救回 9 行，横幅一出又吃回去。
3. **重复轰炸**：同一件事 toast 弹一次、铃铛响一声、桌面通知再来一次、横幅还常驻——信息只有一条，打扰有四次。
4. **分不清「要我行动」和「只是告知」**：蓝条其实什么都不用做，红条有时要点「重新登录」，但形态权重一样，只能逐条读完才知道。
5. **位置不可预期**：提示可能从顶部、右上、右下、底中、屏中央任何方位出现，眼睛要扫全屏找反馈（点了发送，确认在右下；点了归档，撤销条在底中；会话被拦，横幅在顶部）。
6. **刷新/重开无记忆**：横幅每次刷新页面重新出现，「我已经知道了」不被记住（chandown 今天刚有暂缓，其余都没有）。
7. **消息中心存在感低**：铃铛面板功能齐全，但事件也同时以横幅/toast 出现，用户从未被训练成「找历史去铃铛」，出了事还是往顶上看。

### 2.4 美术设计

1. **色彩体系割裂**：横幅是深色渐变通栏（蓝 `#1e3a5f→#1e40af`、琥珀 `#78350f→#92400e`、红 `#7f1d1d→#991b1b`），toast 是黑底白字圆角卡，铃铛面板是白底硬编码 `#fff`（暗色主题下发白块）——同一产品三种材质语言。
2. **同一语义多种表达**：「错误」有红渐变横幅、红 toast、红 dead-click 条、原生 alert 四种视觉；「信息」有蓝横幅与蓝 toast 两种。
3. **图标混用**：emoji（⚠⛔⏳🎙🔴）与 `data-ui-icon` 单色线性图标同屏混排，颗粒度和风格都不统一。
4. **形状/圆角/阴影/字号不成体系**：toast 10px 圆角浮层、横幅 0 圆角通栏、通知面板 12px 圆角、原生弹窗系统样式；字号 11/12/12.5/13px 散布。
5. **渐变通栏视觉重量过大**：状态信息做成了营销 banner 的视觉等级，页面层级失衡；蓝色渐变还与品牌主色打架。
6. **动效无规范**：各 toast 自写 transform/opacity/时长（0.2s/0.3s/1.4s/2.8s/6s/8s），没有统一缓动与节奏。
7. **z-index 竞技场**：99999/99998/99900/9999/8900 手工数字，新浮层只能「比最大再 +1」。

### 2.5 UI/UX 设计专家

1. **打断等级与信息价值错配**（核心病）：按「紧急×重要×可行动」矩阵，重启冷却属「低紧急/低可行动/纯告知」，应该用最低打断等级（瞬态 toast + 留痕），现在却占最高等级（常驻通栏且不可关）；反过来，真正需要行动的「通道掉线」历史上只靠轮询变横幅，曾长期没有直达操作。
2. **没有通知分类学**：全站没有 transient（瞬态反馈）/ ongoing（持续状态）/ blocking（需决策）三类的定义，每个开发者临场自选形态，13 条横幅就是这么积出来的。
3. **关闭/暂缓语义不一致**：chandown 有 ×+24h 暂缓+签名重弹，restartcool/expiry/uibuild 无 ×，aiguide/aitrial 有各自 dismissed 存储——用户建立不起任何心智模型。
4. **无频控与聚合**：14 次重启 = 14 轮横幅，没有「今天已维护 N 次」的合并表达；toast 无同屏上限、无 dedupKey。
5. **可达性缺失**：toast 无 `aria-live`（读屏不播报）、横幅依赖颜色传义、Esc/键盘关闭不统一、`pointer-events:none` 的 toast 无法被辅助技术聚焦。
6. **位置心理学被破坏**：顶部是导航/身份区，被事故信息侵占；右下是行业公认的瞬态反馈位，却只有一部分 toast 在那里。注意力训练完全失败。
7. **消息中心不具备「唯一留痕地」资格**：内存 200 条、刷新丢、无服务端持久、无「进行中状态」分组——横幅之所以不敢撤，正是因为撤了就没有任何地方能看到这些状态。
8. **偏好颗粒度不足**：只有声音/弹窗开关，没有类别级订阅（营销类/运维类/协作类分别控制）。

## 3. 统一方案（按优先级）

### 3.0 目标形态（老板拍板项，全方案的锚）

全站用户可见提醒收敛为 **两个家族 + 一个例外**：

| 家族 | 形态 | 承载 |
|---|---|---|
| **右下角 Toast 栈** | 屏幕右下、卡片式、自动消失、可点关、同屏 ≤3 条超出合并 | 瞬态反馈（操作结果、一次性事件通报） |
| **消息中心（铃铛）** | 右上面板升级：新增置顶「进行中」分组 + 服务端留痕 | 全部事件留痕 + 持续状态的常驻表达（替代横幅的「常驻性」） |
| 例外：阻断层 | 中央确认弹层（统一 confirm）/ 壳强制升级 | 需用户决策才能继续的事（危机安全、强制升级、不可逆操作确认） |

**顶部区域从此只放导航与身份，不再承载任何状态条**（唯一保留：`_boot_error_guard` 这类「页面 JS 已整体崩坏时的最后自愈红条」，因为那时 toast 基建本身可能已死；可顺带把它也移到右下，实现上是自包含的，无依赖）。

**持续状态怎么办**（横幅的存在理由）：右下 toast 栈顶部放一枚**系统状态胶囊**——一行小 chip（如 `🔧 维护预热中 · 剩 6 分钟`、`📴 1 个通道离线`），多状态折叠成一枚计数胶囊，点开即消息中心「进行中」分组看明细与操作按钮。它常驻但极小（一行高、不通栏、不推挤内容、可折叠成小圆点），这是「用户要能看到状态」与「不占广告位」的平衡点。

### 3.1 P0 —— 止血（本周内，改动最小，蓝条问题即刻消失）

1. **`ws-restartcool` 蓝条降级**：重启冷却改为「右下 toast 一次（8s，文案带预计恢复时间）+ 消息中心留痕 + 状态胶囊倒计时」；**同一冷却窗口只提示一次**（复用 chandown 刚落地的签名+暂缓机制，sessionStorage 记冷却窗签名）。`__wsRestartCool.quiet` 信号链**原样不动**（纯视觉迁移，收件箱轮询降速照旧）。
2. **文案人话化双语**：去掉全部运维黑话。`ws.restartcool.text` 改为「系统刚完成维护，正在预热，约 {n} 分钟内恢复最佳状态」；hint 整句删除（「连环重启已自动抑制」是写给运维的，进 ops 卡即可）。全横幅族文案按「用户能做什么」重写（红条句式=「发生了什么 + 点这里做什么」；告知类句式=「发生了什么 + 无需操作」）。
3. **关闭语义补齐**：迁移完成前的过渡期，所有仍在顶部的横幅一律补 ×（暂缓语义与 chandown 对齐：24h 或状态签名变化前不再弹）。
4. **壳/web 双顶栏去重**：桌面壳 `#shell-notice` 的「公告」类下沉进 web 消息中心；壳只保留「更新就绪/强制升级」两种（前者也可改右下 toast + 菜单徽标，后者保留阻断）。

### 3.2 P1 —— 统一通知总线（一到两周，新基建 + 首批迁移）

1. **单一入口 API**（新共享组件 `static/workspace/notify-bus.js`，双树镜像进桌面壳）：

```js
AITRNotify.notify({
  severity: 'info|success|warn|error|critical',
  category: 'ops|conversation|billing|marketing|collab',  // 偏好订阅粒度
  text, detail, actions: [{label, onClick|href}],
  dedupKey,            // 同键冷却窗内合并计数「(×N)」
  ttlMs,               // 瞬态时长；0 = 仅入消息中心
  ongoing: {id, until} // 持续状态：注册/更新/撤销状态胶囊 + 消息中心「进行中」
})
```

   渲染面只有三个：右下 toast 栈（收编 `CRMW.toast` 为唯一实现并升级：队列、同屏 ≤3、`aria-live`、可带 action/undo）、消息中心写入、状态胶囊区。声音/桌面通知仍走 `__wsNotify` 既有偏好，不新增开关。
2. **7 套 toast 收编为薄壳**：base.html `showToast`、RPA `rpa.toast`、收件箱 `_toast` 回落、额度墙私有、`_win_unique` 兜底全部改为一行委托 `AITRNotify.notify()`；`_undoToast` 的撤销能力并入 actions。调用方 300+ 处**零改动**（旧函数名保留为 alias），风险集中在一个文件。
3. **13 条顶部横幅逐条迁移**（附录 A 迁移表）：告知类→toast 一次+胶囊；需行动类→toast（带按钮）+胶囊+消息中心置顶；营销/引导类→退出通知体系，改页内卡片或消息中心任务项。迁移完成后 `wsBanner.register` 白名单清空（保留仲裁器代码一个版本以便回滚）。
4. **消息中心升格为唯一事实源**：新增「进行中」置顶分组（消费 ongoing 状态）；事件服务端留痕（新表或复用 ops_events，保 7 天，登录即可回看，解决「刷新即丢」）；徽标 = 未读数 + 进行中数。
5. **频控预算**：同 dedupKey 60s 冷却合并；同屏 toast ≤3 超出折叠「+N」；重启类事件按「窗口签名」聚合（一天 14 次重启 = 胶囊里一条「今日已维护 14 次」而不是 14 轮弹条）。

### 3.3 P2 —— 长尾收编（两到四周，分批）

1. **原生对话框收编**：`alert` 188 处→`AITRNotify.notify(error/info)`；`confirm` 131 处→统一 `AITRNotify.confirm()`（合并 `_wsConfirm`/`_appConfirm` 两套为一套，保留 checkbox/三键能力）；`prompt` 27 处→表单弹层。按页面分批，ratchet 门禁天花板只降不升。
2. **桌面壳合流**：`#cp-toast`（底中）收编进右下栈；壳 `shell.notify` 与 web `__wsNotify` 打通为一个偏好；海报第 2/3 次曝光的右下角卡直接复用统一 toast 容器（视觉已对齐）。
3. **会话内嵌条刻意保留**（budget/acct/send-gate/claim/hist-view）：它们是「当前会话上下文」的就地信息，不是全局通知，搬走反而降低可用性——但样式统一走 `--tk-*` token、句式按 P0 规范重写。
4. **dead-click/boot 兜底红条**：视觉迁到右下（保持自包含零依赖实现），语义不变。

### 3.4 P3 —— 治理与防回潮（长期）

1. **门禁三件套**：① 禁新增顶部横幅（`wsBanner.register` 调用点白名单钉死、只减不增）；② 禁新建 toast 实现（静态扫描 `position:fixed` + 通知类特征，白名单只有 notify-bus）；③ 原生 alert/confirm/prompt 计数 ratchet（非增天花板，与既有 CJK ratchet 同款机制）。
2. **设计 token 化**：通知色/圆角/阴影/动效时长/z-index 全部进 `--tk-notify-*` token 表；图标统一 `data-ui-icon` 线性族，emoji 只留品牌允许清单。
3. **a11y**：severity→`aria-live`（info/success=polite，warn/error=assertive）；Esc 关最新 toast；胶囊与消息中心键盘可达。
4. **偏好中心**：类别级订阅（营销类可整类关闭；运维类管理员默认开、坐席默认收敛）。
5. **验收指标**（上线后两周复盘）：顶部横幅出现时长/天 → 0；toast 峰值频率 ≤3 条/分钟；「这条是什么/怎么关」类报障 → 0；消息中心打开率、「进行中」点击率作为采用度读数；坐席首屏会话行数不再被横幅挤占。

### 3.5 风险与刻意不做

- **功能信号零改动**：`quiet_poll`/`__wsRestartCool`/conn 重连语义/SSE 事件源/后端 API 全部不动，本方案只动渲染层。这是最大的回归风险点，迁移顺序必须「先立新渲染面 → 再断旧横幅」，每一步热更新自洽（共享树纪律）。
- **强制升级与危机安全保留阻断等级**：壳强制升级、危机安全网相关提示不降级——安全线高于形态统一。
- **连接中断的弱网可见性**：API 全挂时消息中心拉不到数据——状态胶囊与 toast 是纯客户端渲染，不受影响；收件箱列表区的 conn 条保留为上下文条。此点在迁移表中单列验证场景。
- **不做「一次大爆炸」**：7 套 toast 先收编为 alias（调用方零改动），13 条横幅分三批迁（告知类→行动类→营销类），每批带浏览器门禁；期间新旧并存但用户可见形态已统一。
- **重启频率是另一个病**：本方案不解决「一天 14 次重启」，那属值守纪律与凌晨崩溃风暴（log-rotation 死锁已由值守线处置）的治理范畴；但统一后的聚合表达能把 14 次重启的打扰从 14 轮横幅压成 1 枚胶囊。
- **与并行线的边界**：`workspace_base.html`/chandown 生命周期/「状态中心 v2」角标是另一条线本周的活跃区（意向板在案）——P0 动工前必须 `agent_probe -Intent` 登记并与该线合流（其 chandown 暂缓机制正是 P0 要复用的件），避免两线各造一套。
