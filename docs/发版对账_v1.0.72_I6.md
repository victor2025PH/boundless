## 结论 A：61 单为什么从没被冲刷（F1①）

三层叠加，缺一层都不会躺 5 天：

1. **「标 fixed → 自动回访」只在处置台 UI 路由成立。** 回访发送只挂在 `POST /api/admin/bug-intake/{id}/status`（`bug_intake_routes.py` L255-264）。修复线按实施91/92 派工单的写法「修完标 fixed + fix_note → 自动按钮回访」，实际用的是 CLI（`duty_reply.py --status fixed` → `/reply` 路由 L316-322 直接 `set_ticket_status`，**不调** `_send_group_notify`）或脚本直接 `set_ticket_status()`。证据：61/61 `notify_note` 为空（路由路径失败会留 note）；`updated_ts` 落在 10 个批次分钟（08-31 22:35 一分钟 17 单）；60/61 的 body 里没有 fix_note 文本（＝标 fixed 时也没发任何群消息）。
2. **冲刷工具存在但没人调用。** `tools/duty_notify_pending.py --flush`（实施81 P0-3b）没有任何计划任务；唯一自动钩子 `push_chatx_hotpatch.ps1` 只打印一行提示、`-NotifyPending` 是 opt-in。值守 SOP §G「回访前先核报障人版本」把回访刻意推到发版后——1.0.71（09-03 05:51）发版后走的是**群公告 mid=1098 + 手工回访**，没有 `mark_notified`，台账不知道；最后一次真冲刷是 09-02 12:18（6 单，1.0.71 之前）。
3. **没有积压告警。** DutyGroupWatchdog 只盯「群里提问没人答」，BugIntakeWeekly 一周一报，ops 卡 `pending_notify` 要有人看。积压从 08-30 22:29 第一批到 09-04 人肉对账才被发现。且 `/notify-pending` 每次最多 20 单、一单一条消息——对 61 单本来就不可用（轰炸）。

补洞落点：`98323a00`（--alert + 6h 计划任务，只报不发）+ `duty_notify_summary.py`（按人汇总记账）。**仍是业务侧缺口**（不在 I-6 边界、已写进结束报告）：`/reply` 路由带 `status=fixed` 时应同步走 `_send_group_notify` 或至少把 `notify_note` 记成 `not_attempted:cli`，让「标了没通知」在台账里可见。

## 结论 B：verify_no 误归属（F3② 发现）

`pending_verify_ticket` 按「该报障人最新一条 fixed 且 notify_ts>0 的单」归属确认/否认，`detect_verify_intent` 不解析文中 `#N`。09-01 01:19/01:23 钧说「LINE还是不能收发图片语音视频」（LINE 媒体，#145②），系统把它挂到了 #67（相册）和 #63（按账号接管）上并转回 confirmed——两单被冤枉。汇总回访后同一报障人有 47 单同时处于「已回访待验证」，任何一句「还是不行」都会打到最大 id 那单（skuio→#151）。文案里已要求「一次一项、带 #号」，但代码不认号——**这是业务缺口**，建议：`detect_verify_intent` 命中且文中有 `#N` 且 N 属该报障人 fixed+notified 单 → 归属 N；否则维持现状。归属：`src/ops/bug_intake.py`（I-6 文件边界内，但属业务逻辑，等老板拍）。
