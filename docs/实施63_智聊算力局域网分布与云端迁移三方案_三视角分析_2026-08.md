## 0. 结论速览（TL;DR）

1. **智聊现状＝混合架构**：主对话 LLM 已在云端（DeepSeek deepseek-v4-flash，老板锁定），
   其余 9 类算力消费全部在局域网 4 台 GPU 机上。
2. **局域网算力紧张点只有一处但很致命：176（5090 32G）**——快照实测 vram_free
   仅 **0.98G/34.2G**，hub GPU 管家已把 5 个服务「泊车」、11 个「挂起」；8-21/8-22
   两起生产事故（探针 122 轮连败、客服链 45s 超时三连静默）根因都在这台卡的显存挤兑。
3. **140（4070 12G）三役并载**（嵌入+克隆TTS真身+Whisper STT）约 10.4G/12G，是第二紧张点；
   **173（5090）反而有 ~10G 富余**（vLLM 27B 驻留 ~20G，Ollama 空载）；117/198 无近忧。
4. 交付三套可执行方案：**A 全云**（应急/SaaS 档，10 类能力逐项给云替代与代价清单）、
   **B 混合**（推荐，现状收敛 + 「能力级整体切云」的单向 spill 预案包）、
   **C 全本地**（技术已就绪：173 vLLM chatx 27B 实测 81 tok/s，但被老板锁封存，作为
   数据主权档与断云容灾档保留）。
5. 最优先动作（P0，全部免重启）：**填 key 池（现为空！云主链单 key 单厂商是当前最大单点）**、
   备好 4 份「能力级切云」overlay 补丁落库、给 176 的 gpu_watermark 告警接外发通道。

## 3. 为什么「把对应算力全部移到云端」是对的止血方向

1. LAN 无冗余可腾挪：176 的七项负载彼此挤兑，140 已满，173 被主链候补+中枢契约占用，
   跨机搬模型（如 MT 迁 173）历史上引发过「抢卡杀 vLLM」事故——**LAN 内部腾挪的
   边际收益低、事故率高**。
2. 智聊消费的 LLM/MT/VLM/ASR 四类都是**无状态请求**，云上有成熟的 OpenAI 兼容
   替代，本仓的配置契约（`openai_compatible` provider、`base_url`+`api_key`）
  **天然支持指向云端点，多数键热重载 ~30s 生效免重启**。
3. 真正移不动的只有三样（见 §4.1 代价表）：**克隆声实时合成、PuLID 锁脸出图、SER**
  ——它们要么是品牌资产（声纹/人设脸），要么无成熟云替代。这三样恰好有现成的
  软着陆（预渲染命中层/相册备货/CPU 回落），紧张期可降档不致穿帮。

### 4.1 方案 A：全云（cloud_full）——应急整切 + SaaS 商品档

**定位**：两个用途。① 本集群灾难态（176 大故障/机房断电/搬迁）的整机止血；
② 对外交付的零 GPU 档（`config/profiles/cloud_light.yaml` 已存在，本方案即其
生产化超集）。

**逐能力切法与代价**（overlay 键 → 目标值；除注明外全部热重载生效）：

| 能力 | overlay 改法 | 代价/风险 |
|---|---|---|
| 主链 LLM | 已在云。补 `ai.key_pool.keys: [{api_key: <备用DeepSeek>}, {base_url: <他厂兼容端点>, model: …, api_key: …}]` | 云内容策略 vs 亲密陪聊定位（本地无审查 27B 的存在理由）；缓解=多厂商池+提示词工程，残余风险如实接受 |
| 工具/改写 LLM | `ai.fallback.{base_url: https://api.deepseek.com/v1, model: deepseek-v4-flash, api_key: <同主链>}`；`avatar_voice.colloquial.llm_endpoints[0]` 同改，`timeout_sec` 保持 8 | 改写延迟 1-2s 云内可达；费用小（短文本）。fail-closed 语义保留 |
| 翻译 | `translation.engines.order: [ai]`（可选再挂 deepl/google key） | 质量口径变化（hy-mt2 评测语义分 0.93+，DeepSeek ai 引擎 0.92+，可接受）；成本从 0 → 按 token |
| 视觉 | `vision.{base_url: <云VLM>/v1, api_key: <NEW_KEY>, model: <云型号>, no_cloud_fallback: false}` | 需新采购 key（旧智谱 key 已 401 失效）；识图内容出网 |
| ASR | `voice_recognition.{base_url: <云whisper>/v1, api_key: …}`；`audio_pipeline` 同步 | 客户语音出网（隐私敏感度最高的一项，需老板知情）；按分钟计费 |
| SER | `speech_emotion.enabled: false`（或留 CPU 回落） | 语音情绪信号丢失（软损失，影响拟人细节） |
| 嵌入 | `ai.embedding_base_url(s)` → 兼容云端点；或 `memory.vector.enabled: false` | 前者小钱；后者记忆召回退关键词（-20% 召回，评测口径） |
| TTS | 短期：预渲染命中层照常（本地文件零 GPU）+ `policy.no_edge_fallback: false` + `telegram.voice_reply.backend: edge_tts` | **丢克隆声身份**＝对客户是「换人了」级破绽（实施60 主线结论）；必须配套坐席可见警示，且只作应急态 |
| TTS（长期选项） | 商用克隆 API 适配器（fish.audio/MiniMax 类，fish_speech 本就同源） | 新开发项；声纹上云的合规/合同问题；按字符计费吃毛利——**默认不做，P2 评估** |
| 出图 | `companion.selfie.provider.enabled: false`（相册照发，生成停）；补货停 | 无货场景回「诚实文字」（既有语义）；锁脸生成无云等价物，不硬找替代 |
| 唱歌 | `companion.singing.enabled: false` 或 cap→0 | 功能暂停 |
| 运维探针 | `ops.gpu_watermark.enabled: false` 等（照 cloud_light） | 免看板恒 unknown 噪声 |

**成本模型**（参数化，用现成读数校准，不拍数字）：
`月成本 ≈ Σ(日均tokens_主链+工具+翻译)×单价 + ASR分钟×单价 + VLM次数×单价 (+ 克隆TTS字符×单价)`。
现成读数：`/api/setup/cloud-credentials.usage`（出话分布/费用 tier）、`llm_cost`、
`token_ledger`（P5a 已在观测克隆语音/翻译/配图记账）、DeepSeek 余额探针。
**先跑 7 天混合态读数再定价全云档**，避免拍脑袋。

**A 方案回滚**：所有补丁均为 overlay 层，逐能力反向恢复即可；主链 key 原位不动。

### 4.2 方案 B：混合（推荐）——现状收敛 + 「能力级整切云」预案包

**定位**：日常生产态。承认现状已是最优基线（云管对话、LAN 管媒体与向量），
把 8-21/8-22 两次「临场手改配置」的应激操作，升级为**预先审计过的补丁包 + 单向门
纪律**。这正是把「当局域网算力紧张就把对应算力全部移云」制度化。

**B-1 常备四补丁**（落库 `deploy/compute/spill/`，dry-run diff 过目后 `--apply`；
全部热重载免重启）：

1. `spill_translation.yaml`：`translation.engines.order: [ai]`
   ——触发：176 Ollama 挤兑/hy-mt2 连续超时。**立省 176 显存 5.0G**（keep_alive 24h 到期后）。
2. `spill_vision.yaml`：vision 指云 + `no_cloud_fallback: false`
   ——触发：qwen3-vl 被泊车或 176 高水位。**立省 5.5G**。前置：先采购云 VLM key（P0）。
3. `spill_asr.yaml`：voice_recognition + audio_pipeline 指云 whisper
   ——触发：176:8765 挂/超时激增。前置：云 ASR 供应商选型（隐私条款老板过目）。
4. `spill_tool_llm.yaml`：ai.fallback + colloquial 指回云
   ——触发：173 被编码模式/中枢征用或 Ollama 异常。
   （嵌入不做常备补丁：140 无挤兑史、bge-m3 仅 664MB；真出事走 `memory.vector.enabled: false` 软降级即可。）

**B-2 单向门纪律**（沿用 `ai.primary_lock` 哲学）：
- 切云：值班可即时执行（贴 diff + 审计行进 `logs/ai_primary_audit.jsonl` 同款台账，
  `via=compute_spill`）；ops 卡与坐席端必须可见（复用 ai-runtime-status 降级条模式，
  杜绝「静默换路」——0821 翻回事故的教训就是切换无审计无展示）。
- 切回 LAN：只在每日三窗（04:00/12:30/22:30）人工执行，且先看 gpu_watermark 连续
  30min 绿再回。
- 每次 spill 后 24h 内复盘：若同一能力 30 天内 spill ≥3 次 → 升级为「该能力常驻云/
  扩容」的产品决策，不再反复横跳。

**B-3 LAN 侧减压（不动架构的三个小动作）**：
- `translation.engines.ollama_mt.keep_alive: 24h → 4h`：翻译低峰时段自动让出 5G，
  代价=低峰首译多 ~10s 冷载（翻译链有 25s timeout 兜得住）。先看翻译时段分布再定。
- 预渲染备货加密度（台词库扩容）：TTS 命中率每 +10%，176/140 的实时合成压力等比降。
- 唱歌 cap 期间性降 0（当前 hub 已把 singing hold，名义开着实际不可用——配置与实况
  对齐，避免客户点了没反应）。

**B-4 云侧前置补强（P0）**：key 池至少 1 个备用 key（异厂商更佳）；采购云 VLM key
（作为休眠补丁，不开 fallback，不违无兜底纪律）；选型云 ASR（隐私条款先行）。

### 4.3 方案 C：全本地（local_full）——数据主权档/断云容灾档

**技术就绪度（实测）**：173 vLLM `chatx`（Qwen3.6-27B-abliterated AWQ）此刻在线，
64k ctx，81.5 tok/s，历史切流实录 10h 65 次真实客户 completion 无一失败；
其余能力本就全 LAN。即：**全本地不是待建能力，是被治理决定封存的现成能力**。

**⛔ 治理边界（本方案不可自行执行）**：
- 2026-08-22 老板锁：`ai.primary_lock: cloud`，`compute_mode.py` 已删 local/local_only
  档。历史事故：自动化把主链翻回 local_only → 客服链三条消息全部 45s 超时静默。
- 启用唯一路径：老板拍板 → 改 `ai.primary_lock` → 治理接口切换（全程审计）。

**启用前置清单**（把 8-22 事故的根因逐条对掉）：
1. 翻回锁已在（lock+audit+装载点强制），自动翻转通道已死——满足。
2. 173 保活链健康：中枢 `AvatarHubVllmKeepwarm` + WslPinOnly 在位；切换前
   `verify_vllm.ps1 -MinTokS 50` 过线。
3. 真实组包形状验收（多 system/语言钉子/注入块）——8-15 换代已建题库，重跑即可。
4. 观察期 SLA：reply_latency p95 + true_probe 零连败 48h 才转 local_only。
5. 断云语义向老板书面确认：local_only 下 vLLM 失败=canned，**不回云**。

**C 方案的商业面**（不只是容灾）：「用户内容零出网」是可卖的私有化旗舰档
（合规/出海敏感客户），与 A 档（零 GPU SaaS）构成价格带两端；见 §5 市场视角。

## 5. 三视角分析与优化

### 5.1 开发工程师视角

**现状强项**（保持，别推倒重来）：
- 观测面完整：gpu_watermark 四主机、hub parked/held、avatar-status、llm_cost/token_ledger、
  reply_latency SLO——「紧张」是可量化的，不靠感觉。
- 治理成熟：overlay 单源+ruamel 保注释、`ai.primary_lock`+全程审计、单向门哲学、
  无兜底纪律（宁可如实失败不静默顶包）——两次事故换来的机制别绕过。
- 降级语义处处软着陆：嵌入退关键词、改写 fail-closed、TTS strict 不发错声、
  出图相册优先——移云/降档不会引发穿帮式次生事故。

**结构性弱点（本次要修的）**：
1. **云侧单点**：主链单 key 单厂商、key 池空——LAN 再稳，DeepSeek 一抖全站 canned。
   这是比 176 更「便宜就能修」的单点。
2. **176 单机七役**：视觉/翻译/ASR/SER/TTS质量轨/出图/中枢 同卡，vram_free 3%。
   任何一项流量尖峰都通过「hub 泊车」传导成其他项的故障（8-21 实录）。
3. **应急操作手工化**：紧张时改哪些键、改成什么值，散落在事故记忆里——0821/0822
   的「临场手改+无审计」正是翻车温床。
4. 死键与实况漂移：唱歌开着但 hub 已 hold；198 qwen3:8b 重新 pull 了但智聊配置
   已摘（谁在用待确认）——配置≠实况的缝要定期对。

**优化（工程 P0/P1/P2）**：
- **P0（本周，全免重启）**：① key 池填 1-2 个备用（含异厂商）；② 四份 spill 补丁
  落库 + 本文档 §4.2 作为 runbook；③ 采购云 VLM key（休眠）；④ gpu_watermark/hub
  parked 告警接外发通道（先查 `/api/admin/alert-link-status` verdict）。
- **P1（下周）**：① `compute_mode.py` 加 `spill` 子命令（复用其 dry-run/diff/备份/
  审计骨架，~100 行）；② spill 状态进 ops 卡 + 坐席降级条（复用 ai-runtime-status
  模式）；③ MT keep_alive 24h→4h 试点（看翻译时段分布数据）；④ 唱歌配置与 hub
  实况对齐。
- **P2（本月）**：① 云克隆 TTS 适配器可行性评估（fish.audio/MiniMax：合同/隐私/
  字符单价三关，任一不过就书面放弃）；② `private_full_local` 部署 profile（照
  cloud_light 反向做一份，为 C 档商品化铺路）；③ 176 减负架构评审（视觉迁 173 的
  可行性需中枢线会签——「抢卡杀 vLLM」有前科，不擅动）。

### 5.2 市场经理视角

**核心洞察：三套算力方案天然就是三个价格档**，不是运维内部事务，而是产品矩阵：

| 商品档 | 对应方案 | 卖点 | 目标客户 | 现成度 |
|---|---|---|---|---|
| SaaS 云起步档 | A（cloud_light+hosted gateway） | 零 GPU 零运维，装完即用；语音/识图走官网网关 | 中小卖家、试用转化 | **已在售**（cloud_light 播种+托管网关已上线） |
| 旗舰混合档 | B | 克隆声/锁脸/相册在私有 GPU＝**别家抄不走的拟人护城河**；对话走云快且稳 | 现主力客户 | 即现状，需把 spill 预案打磨成 SLA 承诺 |
| 主权全本地档 | C | 用户内容零出网、无审查模型、断网可用 | 合规敏感/出海/大客户 | 技术就绪，商务未包装 |

**优化建议**：
1. **把「算力弹性」写进售卖话术**：「LAN 紧张自动溢出云端、云端故障本地兜底」
   是稳定性卖点，竞品少有；配 ops 看板截图讲故事。
2. **token_ledger 是现成的计费桥**（P5a 已记 AI 回复/克隆语音/翻译/配图）：
   全云档的云成本直接映射成 token 定价，enforce 模式（耗尽→降免费路径）与 spill
   的降档语义同构——**一套账本同时管成本与收费**，别再建第二套。
3. **克隆声坚持自有 GPU**：云克隆 API 按字符计费会吃穿语音重度用户的毛利，且声纹
   出网有合同风险；「独家克隆声」作为旗舰档专属卖点反而更值钱。
4. **全云档如实标注能力差异**（克隆声→标准声、生成图→相册图）：卖点是「随处可用」，
   不是「无差异」；虚标会反噬口碑（内测反馈线的教训）。
5. 风险直视：亲密陪聊场景 vs 云厂商内容政策是 A 档天花板——A 档面向客服/获客场景
   售卖，陪伴场景引导到 B/C 档，销售培训要讲清楚。

### 5.3 用户视角（坐席 + 终端客户）

**坐席（直接用户）**：
- 已经做对的：降级可见（蓝条维护窗/红条断连/ai 降级条）、诚实失败（识图失败报错
  而非瞎编）、strict 语音（不发错声）。
- 痛点与优化：
  1. **切换必须可见**：spill 生效时坐席端出一条「翻译已临时切云端引擎」类 toast +
     ops 卡状态行——0821 的「静默翻回」对坐席是最大信任杀手。
  2. 长静默后首条语音「没润色」（173 冷载 9.8s > 8s 超时是设计内跳过）：接受现状
     或加 3.5h 保活 ping（keep_alive 4h 内续期，成本≈0）——建议后者，P1 顺手。
  3. 唱歌功能开关与实况对齐（点了没反应比灰掉更伤）。
- 终端客户（间接用户）：
  1. 全云应急态下克隆声降级为通用声——按实施60「克隆音色身份可信链」结论，宁可
     **文字+预渲染语音顶住**，也不要突然换声；edge 兜底只用于新会话（无声纹预期的
     客户），老会话保持 strict。把这条写进 A 档 runbook。
  2. 时延感知：云 VLM/ASR 往返比 LAN 慢 0.5-2s，但慢速拟人 v3 本就在节奏里注入
     停顿——**移云对终端客户几乎无感**，这是敢做 spill 的底气。
  3. 断云态（C 档意义）：DeepSeek 故障时今天的表现是 canned 句——对客户是明显
     的「变笨」；key 池（P0-①）把这个概率再砍一个数量级，受益最直接的是客户体验。

### C.4 结论与规模化拐点

1. **当前流量下，全云对智聊便宜一个数量级**：新增云支出 ≈ ¥6-10/月（其余全躺免费档），
   含主链合计 ≈ ¥25-55/月，vs 智聊分摊的 LAN 成本 ¥600-1,200/月。原因很直白：
   日均 155 条消息的流量太小，撑不满任何一张 GPU。
2. **规模化外推**（LLM 项线性增长，其余项长期贴地）：
   ×5 流量（~450 出站/日）≈ ¥120-250/月；×20（~1,800 出站/日，companion_send_gate
   150/日 × 12 账号的满负荷）≈ ¥450-950/月——仍与机队电费同量级。
   **纯算成本账，云在可预见规模内都不输**；LAN 机队的真正理由是且只是：
   克隆声/锁脸无云等价物、无审查模型余量、数据主权卖点、LiveX 实时链路。
3. **峰谷红利（顺手优化）**：DeepSeek 峰时=北京工作日 9-12/14-18。主动触达（689 条/月）
   的择时本就有 quiet hours 机制，规划器再避开峰时窗口即可全按半价出话——现在省的是
   零钱，×20 规模时是每月几百元。
4. **风险成本（钱以外的账）**：ASR 切 Groq＝客户语音出境（美国，SOC2/GDPR），需老板
   书面知情；主链云端内容政策 vs 亲密陪聊定位的摩擦是持续税（本地 27B 因此存在）；
   fish.audio 克隆＝声纹上云，三关（合同/隐私/单价）中单价关已过（C.2#7），前两关待过。
