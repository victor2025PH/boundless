## 0. 结论速览（TL;DR）

| # | 报障 | 一句话根因 | 定性 |
|---|---|---|---|
| 1 | Messenger 点重登无响应 | Facebook cookie 已在 FB 侧失效（≥8/26 15:31），**必须人工重输账密**；而重登窗只会弹在 117 服务器屏幕上，坐席端「看起来没反应」。叠加：收件箱按钮超时 10s < 后端 60s；worker 在跑代码是旧版（`code_stale:true`，实施68 的 PIN/中继修复没装载） | 一半是**待办运维动作**（人工登录），一半是**反馈契约缺陷** |
| 2 | 阿龙下方「需人工」 | 「需人工」＝系统标签 `HANDOFF_TAG`：AI 自动回复链失败时**自动打标**（空回复/发送失败/配额/熔断/营业外/高风险），坐席人工发消息才自动清。阿龙 7 月底有多次 `empty_reply` 打标记录；**当前库里标签已清空**（01:15 有过出站）。产品缺陷＝打标**无溯源**，用户看不到「谁打的、为什么」 | 机制正常，**可解释性缺失** |
| 3 | 生图「算力紧张」 | 不是失败、不是云端：是打开生图工具箱时探测 **176 ComfyUI 空闲显存 <14G** 的知情预警（实测 11.6G/31.8G，正好触发）。出图**全在本地 LAN**（176:8188），云端只有主对话 LLM。兜底链已有 5 层（详见 §1.3） | 文案吓人 + 算力真相需要一页说清 |
| 4 | 标签被悬浮菜单遮挡 / 右键无删标签 | hover 快捷条 `.conv-quick`（absolute + z-index:3）盖住同角落的行内标签 chips——**布局重叠**；「弹出的菜单」是行级工具条不是标签菜单。删标签功能**其实存在**（「打标签」弹层内可加可摘、会话头 chip 有 ×），但右键菜单没有直达入口 | 纯前端 UX 缺陷（热更可修） |

**共同病根（开发视角一句话）**：四件事没有一件是「链路断了」，全是「**机制在、表达断**」——
状态不可见（cookie 失效没人知道该去哪登录）、反馈不闭环（超时文案误导）、行为无溯源（打标不留原因）、层级无让位（工具条压标签）。

## 1. 逐题取证与根因

### 1.1 Messenger「已离线 + 重登无响应」

**实测证据链**（2026-08-27 01:20 取证）：

- worker 活着：`:8791` LISTENING（PID 15356，00:12 起）；`GET /accounts` 返回
  `{"accounts":[], "worker":{"code_fp":"8ac7d862...", "code_stale":true}}` —— **内存 0 个已授权账号**。
- `logs/messenger-web-20260827.log`：00:13 开机恢复 → 注入 cookie 快照 →
  `restore: not auto-authorized after 10s (cookies expired/invalidated) → MANUAL RE-LOGIN likely required`
  → 10 分钟观察窗结束 `status=expired`。**8/26 15:31 / 19:05 / 23:54 三次重启全部同样收场**：
  Facebook 侧已经把这套 cookie 作废了，重启多少次都救不回，**只能人工重输账密（可能含 2FA）**。
- 今日日志里**没有任何 relogin 请求到达 worker**——「点重新登录」的请求根本没打到 Node，或打到了引擎但被
  权限（`manage_ops` → 403）/前端超时截断。
- `code_stale:true`：实施68 的 E2EE PIN 二次输入窗、表单中继（`login_relay.js` 契约层已落盘）都
  **还没被在跑进程装载**——磁盘代码新于进程启动。

**「点了无响应」的三个确定性成因**（按概率排序）：

1. **成功即无响应（UX 设计缺陷）**：relogin 成功的效果＝在 **117 服务器屏幕**弹一个 headed Chromium
   登录窗（30 分钟有效），坐席/老板屏幕上只有一条 toast「请到运行 Messenger 的机器窗口内完成登录」。
   人在坐席机 → 什么都看不到 → 「无响应」。
2. **超时契约分裂**：收件箱账号卡的 `reloginMessengerAcct` 走 `_acctFetch` 默认 **10s** 超时，而后端打
   Node 是 **60s**（关旧浏览器+起新窗常超 10s）→ 前端先报「请求超时」，观感＝没反应（ops 卡 120s、
   工作台红条 65s 都对齐了，唯独收件箱这处没对齐）。
3. **权限 403**：端点要求 `manage_ops` 写权限，普通坐席账号点了只会得到一条容易错过的无权限 toast。

**修复方向**（P0/P1 见 §3）：运维侧先重启 worker 装载新代码 + 在 117 完成一次人工 FB 登录；
产品侧把「重登」从「去服务器找窗口」升级为「坐席端原生分步表单」（表单中继 `login_relay` 契约已备好，
feature-flag 默认关，需灰度验证 FB 风控面）。

### 1.2 「需人工」标签溯源

**机制全貌**（代码实证）：

- 字面「需人工」在会话行上＝**系统标签** `HANDOFF_TAG`（`protocol_autoreply.py:618`）渲染的红 chip；
  另有两处同字样：筛选栏「需人工」chip（＝标签 ∪ 72h 内 SLA crit，同口径 `_isAttnConv`）、
  左侧账号 dock 悬停面板「需人工 N」。
- **自动打标唯一写口**：协议自动回复链失败且属 `HANDOFF_REASONS` →
  `high_risk / empty_reply / generate_error / send_error / quota_hour / quota_day / circuit_open / off_hours`
  （`protocol_autoreply.py:78-81, 1190-1192`）。语义＝「AI 这条没接住，请人来」。
- **手动打标**：坐席标签编辑器 / 批量打标。
- **清除**：坐席在该会话**人工发出消息**自动摘标（`unified_inbox_send_routes.py:636-639`）；
  或标签编辑器摘除；或驾驶舱「已处理」。**标签不自动过期**（人打的/系统打的都等人处理）。
  注意：**autosend 自动发送成功不清标**——这是刻意的（AI 恢复 ≠ 人看过）。

**阿龙实证**（只读库 + 审计）：

- 全部「阿龙」会话（WhatsApp `阿龙🐉` + Telegram ×5）当前 `conv_tags = []`——**取证时刻标签已不在**。
- `autoreply_audit`：WhatsApp 阿龙会话 7/22-7/26 有 **4 次 `empty_reply` 跳过**（该原因会打标）——
  历史上确实被系统打过「需人工」。
- 该会话 01:15:07 刚有一轮 autosend 出站（msg_count 68，CSAT 3.4）。结论二选一：
  ① 用户看到的是**残留至今的老标签**，在 01:15 前后被某次人工发送顺手清掉；
  ② 用户悬停的是**账号 dock 的「需人工 N」聚合 chip**（那是账号级计数，不是这条会话的）。
- **产品缺陷**：打标时不存原因、不存时间、不存来源（系统/人）——用户只能来问「为什么」。
  这正是本报障的真正待修点：**标签要能自解释**。

### 1.3 生图「算力紧张」与算力真相

**这句话是什么**：`cp.image.vram_low_warn`＝「⚠ 算力紧张（显存剩 {g}G）：本次生成需先腾挪显存，
耗时更长，且可能让翻译短暂变慢」。触发条件＝打开「AI 生成图片」工具箱时 `GET /api/image/config`
探测 176 ComfyUI `/system_stats`，`vram_free_gb < 14` 就显示（`cp-image.js:307-315`）。
**知情不拦**：生成按钮照常可点。取证时刻实测 `vram_free = 11.6G / 31.8G` ——正好在预警区。

**算力现状直答**（实施63 实测口径，8/23 快照 + 本次复核）：

| 问题 | 答案 |
|---|---|
| 全云端了吗 | **没有**。云端只有：主对话 LLM（DeepSeek，8/22 老板锁 `ai.primary_lock: cloud`）+ 小智问答 + 新闻/天气公网源 |
| 还在用本地算力吗 | **在，而且是大头**：出图（176 ComfyUI）、翻译 MT（176）、识图 VLM（176）、ASR/SER（176:8765）、克隆声 TTS（140:7852）、质量轨 TTS（176 hub）、嵌入（140）全在局域网 4 台 GPU 机上 |
| 为什么紧张 | 结构性单点：**七类负载压同一台 176（5090 32G）**。不是「全网算力不够」，是这张卡挤 |
| 出图会不会失败 | 预警 ≠ 失败。真失败有对症错误码：`vram_insufficient`（腾挪后仍不够）/ `lock_busy`（排队）/ `gen_timeout`（超时） |

**现有兜底链**（5 层，代码实证）：

1. 生成前：**相册存货直发**（`/api/image/album-stock`，零 GPU 秒发）；
2. 生成时：跨进程互斥锁串行化（防显存峰值叠加）+ `ensure_vram` 主动腾挪（先 `/free` 再卸同卡 Ollama）；
3. 生成后：VLM 体检不合格**换种子重试**（`generate_with_gate`）；
4. 坐席手动链失败：**如实报错**（刻意禁止相册顶包——坐席要的是现生成）；
5. 自动聊天链失败：相册回落（场景硬匹配，无货诚实文字），绝不静默顶包。
6. 预留：`backend: openai` 云端出图通道已有配置契约（未启用；PuLID 锁脸无云替代，切云=放弃锁脸，
   属实施63 §4.1 已知代价，需老板拍板）。

### 1.4 标签悬浮遮挡 + 右键无删除

**遮挡根因**（CSS 实证）：hover 快捷条 `.conv-quick{position:absolute; right:8px; bottom:6px; z-index:3}`
钉在行右下角，而标签 chips（`.conv-tag-chip`）正好也在第二行右侧（`.conv-line2-chips`，max-width 52%，
无 z-index）——**同占右下 + 工具条更高层级 = 必然盖住**（`unified-inbox.css:821-822` + 模板 5514-5531）。
用户说「移到标签上弹出菜单」——实际弹的是**整行 hover 工具条**（`.conv-item:hover .conv-quick{display:flex}`），
不是标签专属菜单；因为鼠标必须经过标签所在区域，体感就是「碰标签就弹菜单挡住标签」。

**删标签现状**：功能**存在但入口深**——
- 「打标签」（行 🏷 / 右键菜单）打开的编辑弹层里，已有标签带 ×（`_tageRemove`）可摘；
- 会话头的标签 chip 也带 × 直删；
- 行内标签 chip 点击即开编辑器（但没有任何视觉暗示可点）。
右键菜单 9 项里**没有**「移除标签」直达项——用户在右键菜单里找删除，找不到，结论就是「没有这功能」。

## 2. 三视角深度分析

### 2.1 开发工程师视角

**这批报障的工程学共性**：四件事全部属于「**状态机正确、观测/表达层断**」——

1. **反馈契约不统一**：同一个 relogin 动作三处入口三种超时（10s/65s/120s），三种成败表达
   （toast/红条内文字/alert）。缺一条「**超时必须 ≥ 后端预算 + 成败必须显式且驻留**」的前端纪律。
   （类似问题此前在语音发送修过一轮：`voice_send_tracker` 的「前端超时 ≠ 发送失败」三态对账——
   同一个模式应当平移到 relogin。）
2. **状态无出处**：`需人工` 标签、`已离线` 状态都是「裸结论」，不带 why/when/who。库表
   `conv_tags` 是纯字符串数组，没有 sidecar 元数据——溯源要靠翻审计库，用户不可能自助。
3. **半部署常态化**：`code_stale:true` 是本仓自建的优秀观测（实施68 沉淀），但**只自报不告警**——
   磁盘代码与在跑进程分叉 27 小时无人知（Python 实例重启 ≠ Node worker 重启，两个动作极易只做前者）。
4. **层级冲突无门禁**：hover 工具条与行内 chips 的遮挡属「可见但被盖」，现有密度门禁
   （`verify_inbox_density.py` 有「可见但空」扫描）**扫不到「可见但被盖」**——缺一个 hover 态的
   元素遮挡断言。

**工程债定级**：无新架构必要，全部是收口活。P0 三项都可热更（模板/CSS/i18n 免重启），
Messenger 侧要一次 worker 重启（≠ 引擎实例重启，无 30 分钟冷却约束，但需与 messenger 线协调——
实施68 代码正等这次重启装载）。

### 2.2 市场经理视角

**内测客户感知 = 产品口碑的放大器**。这四条报障在客户嘴里会变成什么：

| 报障 | 客户传播语 | 实际 | 商业风险 |
|---|---|---|---|
| 重登无响应 | 「Messenger 掉了修不好」 | 修得好，窗口在服务器上 | **部署顾问成本**：每次掉线都要远程协助=人力不可规模化；SaaS 化卖点「多平台聚合」被单平台掉线体验拖累 |
| 需人工不知因 | 「AI 乱打标签」 | AI 失败时的**负责任让位** | 这本来是**卖点**（自动转人工=兜底承诺），因为不可解释反而变成扣分项 |
| 算力紧张 | 「他们服务器不行」 | 显存预警，生成照常 | 「算力紧张」四个字对客户＝能力不足自白；同样的信息说成「出图约需 40-60 秒」就是中性排期 |
| 标签遮挡/找不到删除 | 「界面糙」 | 功能全在，入口深 | 首因效应：内测期 UI 毛刺直接折损转化 |

**市场侧三个动作**：
1. **话术资产化**：把 §1.3 的算力真相表做成一页「算力架构说明」（哪些云/哪些本地/为什么），
   给销售当 FAQ——「本地 GPU 出图=你的照片不出内网」反而是隐私卖点。
2. **失败文案人话化**是转化率工程：所有面向坐席的系统提示按「现状 + 影响 + 你现在能做什么」三段式改写。
3. **可解释的自动化**做成差异化主张：「AI 每次让位都告诉你为什么」——竞品普遍做不到。

### 2.3 用户（坐席/老板）视角

用户旅程逐条走查，每个断点问两个问题：「我知道发生了什么吗？我知道下一步做什么吗？」

1. **Messenger 掉线**：现状「已离线 → 点重登 → 没动静」两问全不及格。期望：点重登后就地告诉我
   「登录窗在服务器 117 上/或直接在我屏幕出现输入框」，登录成功后主动 toast「已恢复收发」。
2. **需人工**：现状「凭空出现四个字」。期望：悬停即见「8/26 23:14 AI 回复发送失败，自动转人工」，
   旁边一个「我已处理」按钮；我回一条消息它自己消失（这条其实已实现，但用户不知道）。
3. **算力紧张**：现状「像故障警报」。期望：「当前出图约需 1 分钟（显卡忙），可先发相册照片」——
   把决策选项递到手边。
4. **标签**：现状「想看标签被按钮挡、想删标签找不到」。期望：悬停按钮别压内容；右键有「标签」
   一项点开就能勾选/摘除。

## 3. 优化方案（P0/P1/P2）

### P0 — 止血（当天，全部可热更或运维动作，零重启风险）

| # | 事项 | 做法 | 验收 |
|---|---|---|---|
| P0-1 | **Messenger 恢复收发**（运维） | ① 重启 messenger-web worker（顺带装载实施68 PIN 窗代码，消 `code_stale`）；② 在 117 屏幕上点一次重登、人工完成 FB 账密+2FA 登录（**需要运营提供凭据，代码侧无法自造**）。与 messenger 线协调执行 | `GET :8791/accounts` 出现 authorized 账号且 `code_stale:false`；收件箱账号转在线 |
| P0-2 | **relogin 反馈契约收口**（前端热更） | 收件箱 `reloginMessengerAcct` 超时 10s→65s 对齐；成功 toast 升级为驻留式横幅：「登录窗已在服务器(117)打开，请在 30 分钟内到该机完成登录」；403/502 文案带下一步指引 | 三入口超时全 ≥65s；点击后 100% 有可见反馈 |
| P0-3 | **hover 工具条让位**（CSS 热更） | `.conv-item:hover .conv-line2-chips{padding-right/位移}` 给 chips 让位，或工具条上移半行错开；加 ~150ms hover 显示延迟（路过不弹）；bump `?v=` + ui-build 双戳 | 悬停时标签 chips 完整可见；`verify_inbox_density` 补「hover 遮挡」断言 |
| P0-4 | **「算力紧张」文案人话化**（i18n 热更） | 改为「🕐 当前出图较忙（显存剩 {g}G）：预计更慢约 1 分钟，期间翻译可能略慢。可先发相册存货📁」并在预警条内挂「查看相册存货」按钮（组件已有 album-stock 接口） | 预警不再出现「算力紧张」字样；预警条可直达相册 |

### P1 — 本周（低风险增量，多数热更；.py 改动攒批进重启窗）

| # | 事项 | 做法 |
|---|---|---|
