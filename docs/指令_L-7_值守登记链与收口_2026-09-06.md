## 2. A —— 报告到达即登记（根治漏立单）

**现状**：`duty_watch_loop.py --once` 从 VPS `uploads.jsonl` 拉新报告到 `tmp_diag/<码>/` 就结束；立单靠值守对话手写 `duty_split_*.py`。

**先看清两条渠道的关系（09-06 08:4x 三方映射，`tmp/overlap_0906.py`）**：#164–#213 共 50 单里 **25 单两渠道都有、21 单只来自 Cursor 报告、3 单只来自群消息**——报告是更富的证据源（09-05 拆单的根因几乎全来自报告），群是更快的人话源。09-05 那 28 份漏立单的报告**全部是「只发了报告、没在群里贴」的**；他 09-06 凌晨在群里补贴的 20 张截图里 14 张就是这 28 份的主题；03:17–04:17 的 16 份「复验」报告又把同一批题做了第三遍。**同一批问题走了三遍，根子是我们对报告渠道零回音。** 所以登记链的规则是：**工单是主键；群消息和报告是同一张单的两种附件；先挂后立；每条回执带单号。**

**09-06 09:5x 老板新规（总账 D-L9）改变了本项的性质**：内测人的 bug **只走 Cursor 报告、不贴群**——群不再是 skuio 的立单入口，所以「报告到达自动立单/挂单」从应做变成**必做、且是本条第一优先**。已经落地的部分不要重做：`tools/duty_channel_reminder.py`（随 `duty_watch_tick.ps1` 第二步每 2 分钟跑）已负责 ① 他在群里提交时自动提醒走 Cursor（6h 一次）② 新报告到达自动回「收到 <码>（主题）」回执。**本项只补「挂单/立单 + 回单号」**，把回单号接进同一个回执链（回执文案已承诺「立单/挂单后回单号」）；建议直接在 `duty_channel_reminder.check_new_reports` 之后加 `auto_ticket(code)`，或新建 `tools/duty_auto_ticket.py` 由同一 tick 调用，勿在 `duty_watch_loop.py` 里发消息（它的契约是只读）。

**修法**（`tools/duty_channel_reminder.py` / 新 `tools/duty_auto_ticket.py` + `deploy/duty/**`）：
1. 拉到 `field-agent:*:report` 后自动解析 `note:`，**挂单优先**（按顺序命中即停）：① 文中含 `#N` → 挂 #N；② 以 `【复现` / `【复验` / `复验 <码>` / `补证` / `关联 <码>` 开头或含已知报告码 → 挂该码所在单；③ 同一报障人 **30 分钟内**群里有截图/文字且主题词重叠（note 前 40 字 vs 群消息 + 图片摘要）→ 挂那条群消息的单；④ 都不命中 → **自动新立单**（`record_bug_ticket`，标题取 note 首句 ≤80 字，body 全文，`reporter_version` 取 `app:`，事件 `auto_split`）。无论挂单还是新立，**群里发一条受理回执**「收到 <码>，已挂/已立 #N」（`duty_reply --receipt`，同一分钟内多份合并成一条）。`field-agent:*:verify` 不立单只更新版本；`【汇总` 类总表不立单，推值守人工处理。
2. 反向同理：群里的截图/文字若 30 分钟内已有同主题报告立了单 → 挂到那张单（bot 现有 30 分钟 collect 窗只会把截图堆进**最近一单**——mid 1206–1223 全被堆进 #194 就是这个毛病——改成按主题词匹配，匹配不到才进最近一单）。
3. 每份报告在 `tmp_diag/<码>/` 落 `ticket.txt` 记归属，`duty_reports_index` 读它。
4. 回访时**明确告诉两位内测人**（按 D-L9）：bug 一律让 Cursor 提交报告，不要贴群，群只用来回答值守追问；报告里带上单号 `#N` 我们就能自动挂对；1.0.7x 的复验请对着我们发的验收清单做，不必逐项证明「未修」。

**验收**：`tests/test_duty_watch_autoticket.py`：三类 note → 挂单 / 新单 / 只更新版本；真机：下一份 skuio 报告 2 分钟内有单号回执。
