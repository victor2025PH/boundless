## 2. A —— 关怀真发止血（#214 #218，P1）

**事实**（WN4JXJ / XZFA3S / M2SHYA / 9YYD44）：① 用户在「补一条关怀」填的是**要发的话**，系统按「TA 说过的事」交 LLM 改写，未注入客户档案（菲律宾本地人、相识一年），生成「How are you finding life in the Philippines? Is the food there as good as what I cook?」并真发；② 启动行 `proactive_care 派发循环 dry_run=True`，而 1.0.75 新 `care_dispatcher` 已真发——两处状态不一致，用户 12:43 看到「到点了，下轮巡检就处理」、点「立即发」无执行，14:03 又真发了；③ care 生成零上下文日志。

**修法**（D-M2）：
1. 表单默认档改为 **verbatim（到点发这句）**，「让 AI 润色」为可选勾选；勾了必须先出预览（「我理解为：… 将于 X 发出：…」）并确认才入队；`care_dispatcher.py` L629 路径已在，不重写。
2. LLM 档强制：注入客户档案（国籍 / 居住地 / 相识时长 / 语言）与近 20 条对话；出稿过 `fabrication_guard`（L-1 C）扩一条「与档案矛盾（把本地人当外国人 / 把老客当新客）」；含地名 / 人名 / 首次对该客户真发 → 强制预览。
3. **状态统一**：`dry_run` 只留一个真值源（`companion_proactive` 启动行 / 面板「模拟中」/ `care_dispatcher` 三处同读）；面板「到点了，下轮巡检就处理」改为真实状态（模拟中 / 排队中 / 已发 / 失败原因）；「立即发」在 dry_run 时明确提示「当前为模拟运行，不会真发」。
4. care 生成落日志：输入原文 / 注入字段 / 输出 / 走了哪档，`[care-gen]` INFO 一行。

**验收**：`tests/test_care_verbatim_default_218.py`：默认档不经 LLM 原文入队；LLM 档无预览确认不入队；档案矛盾句被拦。skuio 机再补一条「问候早上好」→ 到点原文发出。

## 3. B —— 出站语言闸（#234，P1）

**事实**（8DVDVC / U5Y7TX / GSYXQ8）：Messenger 客户发 "Hi"，15:44 AI 自动投递中文「Hey! 好久不见了，这么晚还没睡呀?」。链路：AutosendWorker 中文起草再译；账号数据清除后会话语言记忆清零、单句 "Hi" 判不出 en → 目标语言落空；输入框「收→中·发→英」是手动发送设置，自动投递不读；15:43 六条 `[xlate] provider=none ok=0 err=ai:target_lang_mismatch` 校验失败后**兜底发原文**。现有 `translate_hold`（L885 / L1178）只盖住 provider 不可用。

**修法**（D-M3）：
1. 目标语言决策单一函数 `resolve_outbound_lang(conv)`，优先级：会话级手动翻译设置 > 客户档案语言 > 客户消息文字系统（单句按字符集判：拉丁→en 默认由人设对外语言兜底、假名→ja、谚文→ko、泰文→th）> 人设 / 账号对外默认语言 > **全无 → 返回 None**。
2. None → 草稿转半自动（L1，reason=lang_unknown，接 M-2 E 的 reason 字段），**禁止自动投递**；`target_lang_mismatch` / 任何校验失败 → 同 `translate_hold` 口径拦下标「翻译失败待确认」，**不得发原文**；任何路径不得落到操作员界面语言 zh。
3. 表情 / 单字符 / 纯标点不进翻译器（避免 `src_len=1 mismatch` 刷屏，也避免被判失败）。
4. `[xlate]` 日志加 `decided_by=` 字段（哪一级定的目标语言）。

**验收**：`tests/test_outbound_lang_gate_234.py`：清空语言记忆 + 客户 "Hi" → 不投递、L1 reason=lang_unknown；mismatch → hold 不发原文；表情不进翻译。

## 4. C —— 己方删除消息同步（#219，P2）

**事实**（4NHEYW / J64GVX）：steven 号 14:03 发出的关怀消息 mid=88808 被用户在 Telegram 原生端删除，工作台重载仍显 ✓；后端零删除事件。`telegram_client._on_deleted`（L1131–1145）与 `protocol_bridge.report_deleted_messages` 只处理对方删除（peer_delete：情景记忆按 source_quote 反查删 + 上下文剔除）。风险：已删消息留在 AI 上下文与记忆源，AI 下一轮接着聊。

**修法**：`UpdateDeleteMessages` 只带裸 id → 按 `platform_msg_id` 全账号反查时**不再只匹配入站行**：命中出站行 → 标 `revoked=1`（`messages.revoked` 列已存在）+ 气泡灰显「你撤回了一条消息」+ 从 `_conversation_history` / 记忆源剔除（复用 peer_delete_purge 的两步）；启动 / 刷新时与服务端近 N 条历史对账兜底（拉近 50 条 id 集合，本地多出的标 revoked）；删除事件落 INFO；WhatsApp / LINE 同路径复查（落点表写结论，不一定改）。

**验收**：`tests/test_own_delete_sync_219.py`：出站行收到 delete 更新 → revoked=1 + 上下文剔除。
