## 2. 设计决策（为什么这样做）

### 2.1 五步全部「串既有能力」，新增写面只有两个

- **① 授权**：页面 JS 读 `GET /api/admin/license`（state/plan/quota 含体验档剩余小时），
  粘贴激活复用 `POST /api/admin/license/activate`（`apply_license_token` 唯一实现，
  含「激活即关体验档」反白嫖规则）；缺授权给 `licensing.trial.site_url`（回落
  `shop_url`）官网深链。
- **② 渠道**：读 `GET /api/setup/channels` 渲染就绪度；接入动作**深链**
  `/workspace/setup?channel=<id>`（渠道向导页原生支持该参数），不内嵌不重写。
- **③ 人设**：整件复用 `persona_create_wizard.js`（5 个内置模板：陪聊/商务/客服/
  导师/导购——恰是规格要的客服型/陪伴型/销售型超集）。该组件设计上防御式引用宿主
  全局（`window.loadProfileList`/`openNewProfile`/`_toast`/`_allProfiles`），welcome
  宿主定义这四个钩子：创建成功 → 刷新计数 + 自动标记本步完成；`_allProfiles` 喂
  `/api/personas/profiles` 真列表让组件的 ID 查重护栏在 welcome 上同样生效。保存走
  Studio 同一端点 `PUT /api/personas/profiles/{id}`（retired_facts 冲突检测/审计/
  乐观锁全数生效）——符合 chengjie-persona-discipline「勿直写 YAML」。
- **④ 自动化档位**：新端点 `POST /api/onboarding/automation-tier`，三档映射：
  - `manual` → `inbox.auto_draft.automation_mode=manual` + `l2_autosend_deliver=off`；
  - `review` → `automation_mode=review` + `deliver=off`；
  - `auto_ai` → `automation_mode=auto_ai` + `l2_autosend_worker=on` + `deliver=on`。
  capability 键逐条过 `capability_toggle.check_toggle`（与 `/api/companion/
  capabilities/toggle` 同一护栏），档位键走 `cm.set_overlay_flag`（ruamel 保注释）。
  被拦如实回 `blocked` 明细，**绝不静默半应用装成功**。`manual/review` 刻意不动
  worker（无 auto_ai 会话时 worker 本就无事可做，关它反而给「先人审后全自动」多埋
  一步）；`auto_ai` 不必写 bootstrap 开关（`bootstrap_enabled_from_config` 默认
  「全局 auto_ai 即 bootstrap」）。
- **⑤ 测试消息**：页面 JS 复用 `POST /api/unified-inbox/send`，载荷钉死
  `chat_key='me'`（账号自己的收藏消息，与 live_multiwin_drill 同一安全语义）+
  `client_msg_id='onb-*'` 幂等键。可发账号清单由 status 端点从 account_registry
  只读推导（telegram 协议号、剔 default/official，在线优先）。

新增的写面只有：进度 JSON（数据根）与档位 overlay 写（护栏路径）——授权/渠道/
人设/发送四类真实动作全部落在既有端点上，零口径分叉。

### 2.2 flag 语义：关 = 「无此页」

`onboarding.enabled` 基线 false。关闭时页面与全部 `/api/onboarding/*` 返回 **404**
（对齐 `/workspace/workflows` 运营关闭档的语义）——对老实例，本功能与不存在时零差异。
登录侧半边同理：`welcome_pending` 在 flag 关 / 已完成 / 任何异常时恒 False，
`_role_default_dest` 行为与向导前逐字节一致（有门禁钉住）。

### 2.3 桌面播种 = 搭 WP-1 的车

不给 desktop 加任何新代码：`cloud_light.yaml` 增加 `onboarding.enabled: true`，
经 WP-1 的 `_ensure_deploy_profile`（AITR_DEPLOY_PROFILE + fresh seed 双闸）在**桌面
全新安装**时播种进 overlay。升级安装/既有配置永不被应用——「生产老实例不受打扰，
新装客户默认见到向导」由同一机制保证，无第二条播种路径可漂移。

### 2.4 入口：登录直达而非导航项

不加 nav 入口（首启页用完即走，常驻侧栏是噪音）。发现路径 = 非坐席登录且向导未完成
→ post-login 默认落地 `/welcome`；交付串的显式 `?next=` 深链维持最高优先级（托管
首登直达自检看板的语义不被向导劫持，有门禁）。完成向导后登录恢复角色默认落地；
页面本身仍可直达（完成态显示「已完成过」提示 + 完成页）。
运维令牌直登（`auth_token`）刻意不改：其 role_default 硬编码 `/`（应急排查肌肉记忆）。

### 2.5 speech_prints 指纹：刻意不做运行时自动补条目（对规格的一处显式偏离）

规格技术要点写「模板安装时自动补占位条目并提示」。实施判定**不写**，理由：
1. `platform/spoken_style/data/speech_prints.json` 是 git 跟踪的共享代码根文件，
   运行时写它 = 弄脏共享树（global_rules 正是为同一问题才 overlay 化的，教训在案）；
   打包态该目录在安装区，可写性不保证。
2. 指纹键 = 人设**口称名**，而向导模板创建时名字由**客户自定**——占位条目无法
   开发期预置，运行时写又踩 1。
3. 缺条目的降级是**软的且正确**：spoken_style 桥接对无指纹人设走全局 `ai_name`
   条目 + 通用口语层（规则原文：「漏了＝该人设只剩通用口语层没有指纹」）；且
   `ai.spoken_style` 在 example 基线与 cloud_light 档都是**关**——新装客户全程
   不消费指纹。
「提示」半边保留语义：需要指纹的部署（开了 spoken_style 的运营实例）属 AvatarHub/
运营内容线，按既有流程在 Studio 侧补条目。若后续 spoken_style 支持数据根 overlay
加载，再回补自动占位（登记为 WP-6 顺带项）。

### 2.6 全局规则组合：向导不改全局规则

规格「模板=persona 档案 + 默认全局规则组合」实施为：模板人设 + **出厂默认全局规则**
即为组合——出厂 `global_rules.yaml` 自带 13 条硬约束（含「不要自称AI」），对模板
人设天然生效。首启向导**不写** `/api/persona/global-rules`：全局规则影响所有人设，
让一个首启向导静默重写它，破坏面大于收益（该端点带乐观锁正是因为误覆盖代价高）。
运营要细调走 Studio 全局规则卡（有备份槽位）。

## 5. 运营/后续要点

- **生产两实例**：flag 基线关，不播种、不重启也无行为变化；本批 `.py`
  （welcome_routes/onboarding_state/admin 注册/登录落地钩子）随下个重启窗装载，
  装载前 `/welcome` 404（与 flag 关同语义，无中间态破绽）。
- **桌面发版**：下次打包自动带上（profiles 目录 WP-1 已进 DATAS；本批只改了该
  YAML 内容与模板/JS——模板在 backend sidecar 内随包）。
- **想在某台老实例开向导**：overlay 加 `onboarding: {enabled: true}` 热重载即可
  （页面/i18n 免重启；登录直达钩子在 `.py`，要等重启窗）。
- WP-6（人设备货）接棒点：向导人设步的「之后在人设工作室细调」提示 + speech_prints
  自动占位（若届时支持数据根 overlay）。
