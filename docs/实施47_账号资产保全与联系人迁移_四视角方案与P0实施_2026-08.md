## 2. 三个关键判断（方案骨架）

1. **卖点本质是「业务连续性」不是「存储」**：数据早就落库，缺的是「资产可见 → 可验证 →
   可导出 → 可迁移」四级信任阶梯，每级都要有页面承载。
2. **「转移联系人」协议层不存在无缝转移，诚实分三层**：数据层（CRM `Contact/
   ChannelIdentity` 系统内重绑，100% 可控；**不改写历史消息 account_id**，用继任关系聚合）
   / 触达层（按 username/phone 生成重建联清单，新号分批加回，吃 warmup+日配额护栏，
   成功率<100% 必须显式呈现）/ 预防层（高价值客户提前绑第二锚点，封号从灾难降级为切换）。
3. **封号是高压情绪时刻**：UX 目标「3 分钟从惊慌到行动」——封号瞬间自动快照 + rail 红徽
   + 横幅三按钮（查看资产/导出/开始迁移）。

## 3. 四视角分析要点

- **开发**：媒体根不在数据根=备份带不走（已修）；`meta.banned` 没贯穿到前端状态口径；
  三套「联系人」（protocol_contacts / CRM Contact / 会话列表）必须以 **Contact 为人、
  ChannelIdentity 为绑定边**，别造第四套；迁移编排是**状态机不是脚本**（可中断可重跑、
  逐行落库、配额记账）；快照 hook 挂 `ban_signal.apply_action` ban 分支后必须全异步。
- **市场**：定位「客户资产保险箱 + 业务连续性」，可进官网合规能力页（实施45 系）；话术
  诚实边界=卖「资产可携带」不卖「封号无敌」，对外指标用「可加回句柄覆盖率」；需要 3 分钟
  Demo 剧本；资产中心「已保全资产总量」大数字=沉没价值可视化=续费理由。
- **用户（坐席）**：封号被当掉线反复重连是最大痛点；要「接手感」（新号继续聊自动带出
  历史/备注/上次聊到哪）；批量但不失控（排好序的清单+每日安全额度）；老板要回收率报表。
- **UI/UX**：状态色板缺「封禁」语义档（最严重状态反而没表达）；「历史」ghost 样式像垃圾箱
  不像保险箱；405px 桌面壳窄屏是一等公民；全部走 `--tk-*` token 双主题；危险色克制
  （红只给徽章和横幅边，不整屏泛红）。

## 5. 迁移包 Schema v1（P0 契约，向导的输入）

zip 流式下载，命名 `chatx-migration_{platform}_{account}_{yyyymmdd-HHMM}.zip`（对齐既有
`chatx-history_*`）。结构：

```
manifest.json          # schema_version:1, generated_at, platform/account_id/label,
                       # ban{reason,banned_at}(取 registry meta), counts{conversations,
                       # messages,contacts,media_files,media_bytes,media_missing},
                       # integrity{各文件 sha256}, generator{app 版本}
contacts.jsonl         # 「人」清单，三源合并（见下）
contacts.csv           # 运营友好投影（UTF-8 BOM，Excel 直开）
conversations.jsonl    # 逐字复用 export-history schema=1 白名单（_CONV_FIELDS/_MSG_FIELDS）
media/                 # 可选（默认不打包，勾选才捞）
media_index.jsonl      # message_id → 包内相对路径/size/sha256/missing
README.txt             # 人话说明书 zh/en
```

contacts.jsonl 每行：并集基表（`chat_key/display_name(通讯录备注名优先)/notify_name/
in_book/has_conversation/never_spoke/last_ts/unread`）+ conversations 身份列（`username/
phone/avatar_url/first_seen`）+ CRM best-effort（`contact_id/funnel_stage/intimacy_score/
tags/notes/follow_up_at`，contacts 子系统未启用则留空）+ 派生 `reachability`
（both/username/phone/none——「可加回覆盖率」唯一口径）。

端点 `GET /api/accounts/{p}/{id}/export-migration`：权限与 export-history 同闸
（`_require_account_manager`），审计 `ops_events: account_export_migration`（只记行数）。
counts 与逐行数据必须对账一致（导出完整率指标的数据源）。

## 6. 迁移向导数据与交互规格

**数据模型**（新库 `config/migration.db`，服务层跨库组装、不 SQL attach）：
`migration_tasks(task_id, src_platform, src_account_id, dst_account_id, status:
draft→inventory→ready→running→paused→done/cancelled, policy_json, counts_json,
created_by, ts…)` + `migration_items(item_id, task_id, chat_key, contact_id?, reachability,
value_score, batch_no, state: pending→staged→invited→reconnected|failed|skipped|
unreachable, attempts, last_err, reconnected_cid, ts…)`。同 src 同时只许一个非终态任务
（重复发起 409）；items 幂等按 chat_key。

**自动认领**：新号入站首条 → `phone 精确 > username 精确 > name+语言+时区模糊` 三级，
前两级直接 reconnected + CRM 挂接（复用 MergeService/link-channel），模糊级进
`merge_review_queue`；命中推事件流+收件箱 toast。契约测试：非清单渠道回来不误挂、
reconnected 不重复计数。

**边界情况**（每条进门禁）：新号中途被封→任务 paused+告警+可换 dst 续跑；每日额度耗尽→
批次顺延不弹错；客户新号已有会话→盘点即标 reconnected 跳过邀请；旧号解封→可 cancel、
双 identity 保留合法；跨平台迁移 v1 不支持（UI 置灰指路既有 handoff 引流）；句柄失效→
重试 3 次转 unreachable 如实入统计；迁移中导出允许（只读）。

**API 面**：`POST /api/migrations`、`GET /api/migrations[/{id}]`、`POST .../inventory`、
`PATCH .../{id}`、`POST .../start|pause|cancel`、`POST .../items/{item}/mark`；前端轮询；
权限 `_require_account_manager`；动作全进 `ops_events`（`migration_*` 家族）。
