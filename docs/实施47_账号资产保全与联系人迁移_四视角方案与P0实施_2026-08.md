## 2. 三个关键判断（方案骨架）

1. **卖点本质是「业务连续性」不是「存储」**：数据早就落库，缺的是「资产可见 → 可验证 →
   可导出 → 可迁移」四级信任阶梯，每级都要有页面承载。
2. **「转移联系人」协议层不存在无缝转移，诚实分三层**：数据层（CRM `Contact/
   ChannelIdentity` 系统内重绑，100% 可控；**不改写历史消息 account_id**，用继任关系聚合）
   / 触达层（按 username/phone 生成重建联清单，新号分批加回，吃 warmup+日配额护栏，
   成功率<100% 必须显式呈现）/ 预防层（高价值客户提前绑第二锚点，封号从灾难降级为切换）。
3. **封号是高压情绪时刻**：UX 目标「3 分钟从惊慌到行动」——封号瞬间自动快照 + rail 红徽
   + 横幅三按钮（查看资产/导出/开始迁移）。

## 3. 四视角分析要点

- **开发**：媒体根不在数据根=备份带不走（已修）；`meta.banned` 没贯穿到前端状态口径；
  三套「联系人」（protocol_contacts / CRM Contact / 会话列表）必须以 **Contact 为人、
  ChannelIdentity 为绑定边**，别造第四套；迁移编排是**状态机不是脚本**（可中断可重跑、
  逐行落库、配额记账）；快照 hook 挂 `ban_signal.apply_action` ban 分支后必须全异步。
- **市场**：定位「客户资产保险箱 + 业务连续性」，可进官网合规能力页（实施45 系）；话术
  诚实边界=卖「资产可携带」不卖「封号无敌」，对外指标用「可加回句柄覆盖率」；需要 3 分钟
  Demo 剧本；资产中心「已保全资产总量」大数字=沉没价值可视化=续费理由。
- **用户（坐席）**：封号被当掉线反复重连是最大痛点；要「接手感」（新号继续聊自动带出
  历史/备注/上次聊到哪）；批量但不失控（排好序的清单+每日安全额度）；老板要回收率报表。
- **UI/UX**：状态色板缺「封禁」语义档（最严重状态反而没表达）；「历史」ghost 样式像垃圾箱
  不像保险箱；405px 桌面壳窄屏是一等公民；全部走 `--tk-*` token 双主题；危险色克制
  （红只给徽章和横幅边，不整屏泛红）。

## 5. 迁移包 Schema v1（P0 契约，向导的输入）

zip 流式下载，命名 `chatx-migration_{platform}_{account}_{yyyymmdd-HHMM}.zip`（对齐既有
`chatx-history_*`）。结构：

```
manifest.json          # schema_version:1, generated_at, platform/account_id/label,
                       # ban{reason,banned_at}(取 registry meta), counts{conversations,
                       # messages,contacts,media_files,media_bytes,media_missing},
                       # integrity{各文件 sha256}, generator{app 版本}
contacts.jsonl         # 「人」清单，三源合并（见下）
contacts.csv           # 运营友好投影（UTF-8 BOM，Excel 直开）
conversations.jsonl    # 逐字复用 export-history schema=1 白名单（_CONV_FIELDS/_MSG_FIELDS）
media/                 # 可选（默认不打包，勾选才捞）
media_index.jsonl      # message_id → 包内相对路径/size/sha256/missing
README.txt             # 人话说明书 zh/en
```

contacts.jsonl 每行：并集基表（`chat_key/display_name(通讯录备注名优先)/notify_name/
in_book/has_conversation/never_spoke/last_ts/unread`）+ conversations 身份列（`username/
phone/avatar_url/first_seen`）+ CRM best-effort（`contact_id/funnel_stage/intimacy_score/
tags/notes/follow_up_at`，contacts 子系统未启用则留空）+ 派生 `reachability`
（both/username/phone/none——「可加回覆盖率」唯一口径）。

端点 `GET /api/accounts/{p}/{id}/export-migration`：权限与 export-history 同闸
（`_require_account_manager`），审计 `ops_events: account_export_migration`（只记行数）。
counts 与逐行数据必须对账一致（导出完整率指标的数据源）。

## 6. 迁移向导数据与交互规格

**数据模型**（新库 `config/migration.db`，服务层跨库组装、不 SQL attach）：
`migration_tasks(task_id, src_platform, src_account_id, dst_account_id, status:
draft→inventory→ready→running→paused→done/cancelled, policy_json, counts_json,
created_by, ts…)` + `migration_items(item_id, task_id, chat_key, contact_id?, reachability,
value_score, batch_no, state: pending→staged→invited→reconnected|failed|skipped|
unreachable, attempts, last_err, reconnected_cid, ts…)`。同 src 同时只许一个非终态任务
（重复发起 409）；items 幂等按 chat_key。

**自动认领**：新号入站首条 → `phone 精确 > username 精确 > name+语言+时区模糊` 三级，
前两级直接 reconnected + CRM 挂接（复用 MergeService/link-channel），模糊级进
`merge_review_queue`；命中推事件流+收件箱 toast。契约测试：非清单渠道回来不误挂、
reconnected 不重复计数。

**边界情况**（每条进门禁）：新号中途被封→任务 paused+告警+可换 dst 续跑；每日额度耗尽→
批次顺延不弹错；客户新号已有会话→盘点即标 reconnected 跳过邀请；旧号解封→可 cancel、
双 identity 保留合法；跨平台迁移 v1 不支持（UI 置灰指路既有 handoff 引流）；句柄失效→
重试 3 次转 unreachable 如实入统计；迁移中导出允许（只读）。

**API 面**：`POST /api/migrations`、`GET /api/migrations[/{id}]`、`POST .../inventory`、
`PATCH .../{id}`、`POST .../start|pause|cancel`、`POST .../items/{item}/mark`；前端轮询；
权限 `_require_account_manager`；动作全进 `ops_events`（`migration_*` 家族）。

  HTTP 验接线）。

**四条设计红线**（改之前先读模块 docstring，那里有完整版）：
1. `manifest` **最后写**，`counts` 是真正写进包的行数，同时保留 `store_counts`
   预估——两个数并列摆着即「导出完整率」的原料，刻意不做取较小值之类的抹平；
2. **零 `store.py` 改动**（多线共享热文件），身份列走只读 URI 连接自取；
3. **双层路径防线**：zip 成员名净化（zip-slip）+ 磁盘侧对**双**媒体根做
   `commonpath` 容纳校验（只用主根会把旧根命中误判成穿越）；
4. 字段白名单与 `export-history` 两处**各自持有**（不 import 那个巨型路由模块），
   用静态源码比对当防漂移门禁。

**顺带修掉的一个真缺陷（这条最重要）**：**WhatsApp 的 `chat_key` 就是手机号**
（协议层用号码寻址）。生产实测 47 条 WA 私聊只有 11 条填了 `phone` 身份列，而
47 条 chat_key 全是裸号码 ⇒ 该平台「可加回覆盖率」被低报到 6%，而真实接近 100%，
且 WhatsApp 是本机联系人最多的平台（234 条）。修法是**平台白名单硬门控**的派生
（`derive_handles`，白名单只有 `whatsapp`）：**绝不能按形态猜**——Telegram 的
`chat_key` 是 10 位数字**用户 id**（`8506426282`），形态与手机号无从区分，按形态
派生会把 155 条 TG 会话全标成「有手机号可加回」，运营照单去加会全部加不上，比少报
坏得多。LINE 的 44 字 MID / Messenger 的 16 位 FB id 都不能用来重新加好友，如实
留 0。派生结果带 `handle_source` 留痕，manifest 里写 `reachability_rule` 自描述。
**效果：全机群覆盖率 22.2% → 69.0%（345/500）。**

✅ **该遗留已于同日闭环**（见 §9-B）：卡片与迁移包现在共用同一条规则、同一个人群。

**配套：`ops_events` 分级保留期**（`src/ops/ops_events.py`）。原本所有 kind 一律
90 天裁剪，而资产台账是「资产保全」承诺的唯一证据面 ⇒ 数据主权类 kind
（`_CUSTODY_KINDS`＝导出/清除/迁移/快照）改 730 天，其余不变（整表放宽会让高频的
风控/限速事件无界增长）。门禁 `tests/test_ops_events_retention.py`，其中一条钉住
「台账 API 的默认 kind 集 ≡ 保留期豁免集」——漂了就会出现「看板展示一个注定被裁剪
掉的类型」。

**测试与验证**：新增 53 + 保留期 6 + 路由契约 346 + `gate_sweep` ALL GREEN 1071 +
`restart_preflight` app 装配 4/4。**上线前**先用只读探针在真库上验过（sqlite backup
API 快照到临时文件——`InboxStore.__init__` 会跑 DDL+ALTER 属写操作，绝不能指向活库）：
16/16 账号产出结构完整的包，sha256、行数对账、zip 越界扫描全过。**上线后** `--live`
真 HTTP 11/11 PASS（鉴权闸 / 注册表 label+ban 注入 / manifest 与预览同口径 / 审计
落账且不含联系人内容 / 服务端临时包已清理）。

**两个被实测否决的「刻意不做」**（别再重做这两轮分析）：
- **导出不改异步任务**：最大账号实测不带媒体 1.2s/0.30MB、带媒体 4.0s/24.85MB
  （419 个媒体文件）。重新评估的触发条件＝单账号媒体 >~500MB 或耗时稳定 >30s。
- **不打包时不为媒体算 sha256**：会把最常用的 1.2s 路径拖成 2~3s，换一个极少用的
  字段；`size`+`missing` 已是弱完整性信号。

## 9-B. 资产中心 P0 体验批 + 可加回口径统一（2026-08-28 完工，已上线并真机验证）

承接工单 2 的同一天，接手了**停摆的** Asset Center P0 车道（原 owner 从意向板消失，
`workspace_assets.html` / `asset_center_page.py` 全干净，只在 `asset_center_routes.py`
留下两个**无消费方**的常量 `_PURGE_HINT_STATUSES` / `_NO_HANDLE_PLATFORMS`——
本批给了它们真实消费方，没有删）。

### A. 老板报障的三条

1. **「一些号码是很长的字串，看不懂」**——那是平台自己的账号标识（LINE 的 44 字
   MID / Messenger 的 FB 数字 id / WhatsApp 的手机号），不是乱码。根因是回落链
   只有一层：`label` 为空就直接显示 `account_id`，副行再打印一遍，同一串出现两次。
   修法＝接上收件箱早就在用的**四级回落**（别名 > 平台昵称 > @用户名 > 脱敏 id）
   + 渐变字首头像 + 手机号脱敏（`639****480`，防截图外泄）+ 复制完整 ID 按钮 +
   未命名账号出「起个名字」。昵称数据**本来就在** registry `meta.self_*`
   （登录时 `account_self_profile.enrich_from_fields` 写入），这一页只是没读。
   实测效果：`UBStXHv7S2b57EbwB4QJqBI-…` → **vic001**、`61584070255403` →
   **Calixa Lopez**、`6834964252` → **智聊支持**。
   ⚠ 后端 `label` 现在**只表示「运营起过的别名」**，不再回落成 account_id——
   回落发生在前端；后端塞 id 进 label 会让前端分不出「有没有起过名」。
2. **「每个账号应该有删除功能」**——端点自 2026-08-17 就齐了
   （remove / restore / purge-history / label），此前**唯一入口**是收件箱账号抽屉的
   三级溢出菜单。本批把它们接到卡片的 ⋯ 菜单：重命名 / 恢复（仅 removed）/
   彻底删除（仅历史态，危险色 + 分隔线）。删除走「GET 预估体量 → 影响预览 →
   两步确认（第二步提醒先导出备份）」，`purgeable=false` 在弹框**之前**就诚实拦下。
3. **「每个账号还应该有更多功能」**——工单 2 的迁移包 CTA 随端点上线自动点亮
   （`features.export_migration` 探测），无需前端改动。

⚠ 全部动作走**事件委托 + `data-act`，零内联 onclick**：本页脚本是 IIFE，内联
handler 必须挂 window 才可达（本仓一天内两次实锤的死按钮根因）；委托模式从根上
绕开那个陷阱，动态生成的行零接线自动生效。

### B. 可加回口径统一（本批最重要的修复）

发现**两层**不一致，第二层比第一层严重得多：

1. **规则**：卡片直接读 `conversations.phone` 列，而 WhatsApp 的 chat_key 就是
   手机号、`phone` 列只有 11/47 条填上 → 低报。
2. **人群（真 bug）**：卡片一侧显示「165 联系人」（并集口径），紧挨着显示
   「可加回覆盖 100%」，而那个百分比按**私聊会话行**（9 条）算——两个数字并排
   摆着、看起来后者是前者的比例，实际分母差 156 人。全机群：会话分母
   100/217=46.1% vs 并集分母 345/500=69.0%。

修法＝新增 `migration_export.reachability_over_union()`：**人群**复用
`store._contacts_base_from(include_chats=True)`（那个 UNION 在本仓刻意只写一处），
**规则**复用同模块的 `derived_phone_sql()`，卡片与迁移包从此同源。旧的
`_reachability_map`（按会话聚合）**已删除**，并在原地留了「别加回来」的说明。

原先排除通讯录-only 联系人的理由是「它们没身份列，计入会误报无句柄」（§1）——
该理由已被派生规则**部分推翻**：WA 通讯录联系人的 chat_key 就是号码，是实实在在
可加回的 229 人，排除掉才是误报；TG 的通讯录-only 确实没句柄 → 如实计入 `none`
（偏低但为真，永远优于偏高的假数字）。

⚠ **实施中踩到并修掉的一个 SQL NULL 陷阱**（写这类聚合前必读）：并集基表是
`LEFT JOIN conversations v`，通讯录-only 联系人根本没有 `v` 行 → `TRIM(v.username)`
是 **NULL**，而 `NULL = ''` 求值为 NULL（不是真）⇒ 四个桶的 CASE 全落 ELSE 0，
**那些人整行从分母里静默消失**（首版实测并集应 12 人、实得 9）。身份列必须
`COALESCE(…, '')`。这个 bug 是被「人群必须含通讯录-only」那条门禁当场抓到的——
而门禁的首版夹具（每人恰好一条会话）曾把人群差异完全藏住，后来刻意加了通讯录-only
样本才有鉴别力。
