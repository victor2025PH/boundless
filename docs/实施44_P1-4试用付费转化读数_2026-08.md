# 实施 44：P1-4 试用→付费转化读数（2026-08-18）

> 三视角复盘 P1 清单末件：「试用→付费 ≥30%」（规格周排期第 9-12 周验收）
> 此前无读数面。原设想=厂商侧独立周报 CLI join 三个数据源。

## 先确认已开发面（结论把方案砍掉了一大半）

| 原设想要建的 | 实况 |
|---|---|
| 试用签发台账 | ✅ 已有：`website/lib/trial-claim-store`（指纹幂等 + 联系方式） |
| 激活链路读数 | ✅ **已被另一条线建成**（P1-⑧，2026-08-10 事故沉淀）：五段激活漏斗（装机→领试用→派凭据→首账号→首出站）+ `/console/funnel` 页 + 48h 同期群 + 挽回名单；客户端 1.0.20 起带里程碑信标、还有 usage-beacon 用量回流 |
| 付费真相 | ✅ 已有：集团库 `group-ledger.db`（orders.paid_at / licenses / **identities 身份归并表**，kind 含 fingerprint——join 键像是为这次预留的） |
| **缺口** | ❌ 仅剩「商业段」：漏斗止步 first_reply，试用→付费无 join、无展示 |

**方案改向**：不建独立 CLI（数据与眼睛都在 console，另起 CLI=第二套口径），
改为给既有漏斗补**付费段**——新 lib + API 字段 + console 两张卡。

## 落地物

- `website/lib/trial-paid-funnel.ts`：cohort 口径（窗口内领试用 × 转化看截至
  现在——转化天然滞后于领取，按窗口截转化会系统性低估）；**付费真相=
  orders.paid_at**（真金白银；**licenses 表刻意不当付费证据**——它收录一切
  签发含试用，会虚高，只经 identities 参与身份归并）；三级 join 每 claim 只计
  一次（fingerprint 直配 → contact 归一直配（小写/去@/trim）→ identities 归并到
  customer 后看其名下有无已付订单），matched 分桶回传（join 质量可观测）。
- `/api/console/funnel` 增 `trial_paid`（7/30 双窗）；`/console/funnel` 页增
  两张「💰 试用→付费」卡（≥30% 达标变绿、matched 分桶小字、空样本/集团库
  不可读各有显式态）。
- 冒烟 `npx tsx lib/trial-paid-funnel.test.ts`：空库诚实零（营收前常态，
  `getLedgerDb` 自带 mkdir 自愈——「文件缺席」在网站侧不构成真实状态，首版
  想测它被实况纠正）/ 三路 join 各中一条 / 未付订单不算 / 窗口语义 / FK 完整
  （identities 需先建 customer）。`activation-funnel.test.ts` 回归照跑不受影响；
  `tsc --noEmit` 零错。

## 深想记录

- **「已开发确认」这步砍掉了 2/3 的原方案**：激活漏斗、用量回流、身份归并表
  全部已存在——P1-4 从「建三源 join 的周报系统」缩成「补一段 + 两张卡」。
- 转化率的分母语义选 cohort（领取窗）而非活跃窗：老板问的是「上月领试用的人
  里多少付了钱」，不是「本窗恰好同时活跃的」。
- 付费证据面从严：宁可漏计（identity 表没归并到的付费客户）不虚高（licenses
  表混试用签发）。matched 分桶暴露 join 覆盖度，归并率低会自己显形。
