# 实施 46：群成员提取多平台化 · 四视角深度分析与优化方案

**日期**：2026-08-19
**性质**：方案（深度分析 + 架构设计 + 分期路线图；**本轮不改代码，只出方案**）
**跨仓库范围**：`engines/chengjie`（Telegram / WhatsApp / LINE / Messenger）+ `engines/huoke`（Facebook / TikTok）
**触发**：运营诉求——「群成员提取现在只有 Telegram 群组可用吗？如何让 WhatsApp / TikTok / LINE / Messenger 都能用」
**决策已拍板**：全套多平台（含 huoke 跨仓库的 Messenger/TikTok、LINE 全套并接受其技术局限）；先做 P0 触达闭环 + 抽象层；同步做 UI/UX 重构美化；WhatsApp 为重点。

---

## 一、现状定位（先回答核心问题）

**群成员提取现在是 Telegram 独家能力，而且是「半条命」——提取做了，触达没接。**

它只存在于 `chengjie` 仓库、只对 Telegram 可用：后端 `src/companion/group_member_extract.py` 直接调 Pyrogram 的 `get_chat_members` / `get_chat_history`，入库到 `group_members.db`（表 `tg_group_members` / `tg_extract_jobs`，见 `src/companion/group_members_store.py`），前端是独立页 `/tools/tg-members`（`src/web/templates/tg_members.html`，约 635 行），唯一出口是**导出 CSV**。提取出来的成员表预留了 `outreach_state` 字段，但**没有任何自动触达接线**——这是整个功能价值只兑现约 30% 的根因。

### 1.1 现状链路

| 角色 | 路径 | 说明 |
|---|---|---|
| 提取编排 | `chengjie/src/companion/group_member_extract.py` | Pyrogram `get_chat_members`/`get_chat_history`，多号分片 `user_id % num_shards` |
| 持久层 | `chengjie/src/companion/group_members_store.py` | `tg_group_members`(主键 group_id+user_id) / `tg_extract_jobs`；DB=`config/group_members.db` |
| HTTP 路由 | `chengjie/src/web/routes/group_members_routes.py` | `/api/tg-members/*` + `/tools/tg-members` |
| 前端页 | `chengjie/src/web/templates/tg_members.html` | 独立自包含页，**不继承 base.html**，内联 zh/en（不走 i18n pack） |
| i18n pack | `chengjie/src/web/i18n_packs/group_members.py` | 仅 ops 卡/收件箱入口/错误键 |
| 副驾组件 | `chengjie/shared/copilot/components/cp-tg-members.js` | 当前群一键拉 + 配额 + 导出 |
| 显隐闸 | `chengjie/src/web/ui_visibility.py` → `group_extract` | |
| 总开关 | `companion.group_members.enabled`（默认 false） | |

### 1.2 一个关键事实：你的系统横跨两个仓库、两套架构

运营诉求里的五个平台，分属两个技术栈完全不同的仓库。这不是「加个功能」，是「要不要建跨仓库统一提取层」的架构决策。

| 仓库 | 平台 | 底层机制 | 群成员提取现状 |
|---|---|---|---|
| `chengjie` | Telegram | MTProto / Pyrogram（**协议级**） | ✅ 已实现（本功能） |
| `chengjie` | WhatsApp | Baileys（Node，**协议级**） | 仅 @提及实时名单（不入库） |
| `chengjie` | LINE | line_rpa（**UI 自动化**） | ❌ |
| `chengjie` | Messenger | messenger-web（**网页自动化**） | ❌ |
| `huoke` | Facebook | uiautomator2（**安卓真机**） | ✅ 但是 FB Group，另一套 `extract_group_members` |
| `huoke` | TikTok | uiautomator2（**安卓真机**） | 只有粉丝列表筛选，无「群」概念 |

> `huoke/src/app_automation/facebook.py::extract_group_members` 已是成熟实现（进群→Members/contributors/feed authors 列表→翻页抓名→写 `LeadsStore`→给 campaign 的 `add_friends`/`send_greeting` 消费），但它是**安卓真机 UI 自动化**，产能低、有封号红线，且在**另一个仓库**。

### 1.3 多平台可行性矩阵（整个方案的地基）

能不能做，取决于底层协议给不给「枚举成员」的能力。差异是天壤之别，必须诚实建模，否则会做出「LINE 提了一堆无法使用的显示名」这类事故。

| 平台 | 可行性 | 机制 | 能拿到 | 能去重 | 能触达 | 硬限制 / 风险 |
|---|---|---|---|---|---|---|
| **Telegram** | ⭐⭐⭐⭐⭐ 已有 | Pyrogram 协议 | user_id / 用户名 / 发言 / 管理员 | ✅ user_id | ✅ | 大群 GetParticipants 上限 1 万；FloodWait（已处理） |
| **WhatsApp** | ⭐⭐⭐⭐ 高 | Baileys `groupMetadata` | 手机号 JID / 是否管理员 | ✅ 手机号 | ✅ 可发陌生号 | **无显示名**（需从消息补 pushname）；**手机号=强隐私（GDPR）**；群上限 1024；发陌生号封号风险高 |
| **Messenger/FB** | ⭐⭐⭐ 中 | huoke 安卓 UI | 显示名 / 主页（可导 id） | 部分 | ✅ 加好友后 | **跨仓库**；真机产能低、脆；FB 封号红线严；需 huoke 排产 |
| **TikTok** | ⭐⭐ 中（语义变了） | huoke 安卓 UI | 用户名 / 主页 | 部分 | 有限（需关注/开 DM） | **无「群」概念**——只能提粉丝/评论者/话题受众；跨仓库 |
| **LINE** | ⭐ 低 | line_rpa UI 抓取 | **只有显示名** | ❌ 显示名会撞 | ❌ 拿不到 mid | LINE 不暴露 user_id；反自动化严；**提了也无法去重/触达** |

**两条贯穿全案的结论：**
1. **WhatsApp 是多平台里 ROI 最高的一块**（协议级、全在 chengjie 内、市场最大、可触达）。
2. **所有平台共同的最大短板不是「提取」，是「提取完没有触达闭环」**——这才是价值只发挥 30% 的真因，也是单点投入产出比最高的改造。

## 二、四视角深度分析

### 视角 A · 开发工程师（架构 / 可维护性 / 集成）

**A1. 现状工程问题**

1. **全 Telegram 硬编码，零平台抽象**：模块直接调 Pyrogram；表名带 `tg_` 前缀；路由带 `/api/tg-members/`；前端页甚至不继承 `base.html`、不用 i18n pack（内联 zh/en）。这是刻意自包含的「工具箱」，不是可扩展架构。
2. **跨仓库鸿沟**：TikTok/Facebook 的深度能力在 `huoke`（安卓真机），chengjie 要用只能经 huoke 的 task 队列跨服务调用。这是最大的架构分叉点，方案必须显式处理，不能假装两仓是一个进程。
3. **能力差异没有被建模**：Telegram 有干净的 user_id，WhatsApp 是手机号，LINE 根本没有稳定 id。当前代码假设「成员 = 有 user_id 的行」，直接套到别的平台会产生无法去重、无法触达的脏数据。
4. **配额/合规口径单一**：现在只有「每号每日 cap」。但 WhatsApp 读 `groupMetadata` 是零风险本地操作、LINE UI 抓取是高风险、huoke 真机有 ComplianceGuard 硬限制——三者不能共用一套配额模型。
5. **触达闭环断线**：`outreach_state` 字段预留了却没接。chengjie 的主动触达链路（`proactive_topic`）与收件箱草稿队列**都已存在**，只差把提取表连上去。

**A2. 工程优化方向（本方案建议）**

1. **抽象出 `MemberExtractor` provider 接口**（解耦核心）：
   ```
   class MemberExtractor(Protocol):
       platform: str
       capabilities: ExtractorCapabilities  # 声明能力，见 A3
       async def list_targets(account) -> [Target]      # 列可提取的群/受众源
       async def extract(account, target, filter, cap) -> [Member]
   ```
   现有 Telegram 逻辑迁入 `TelegramExtractor`，行为不变。新增 `WhatsAppExtractor` / `MessengerExtractor` / `TikTokExtractor` / `LineExtractor`。
2. **数据模型泛化**（见 §三.D）：`tg_group_members` → 通用 `audience_members`，加 `platform` 列；`member_id` 通用主键（tg=user_id / wa=手机号 JID / line=无 id 只存显示名 + 稳定 hash）。
3. **能力声明驱动前端**：每个 provider 声明 `capabilities`（`can_enumerate_all` / `can_scan_speakers` / `has_stable_id` / `can_dedupe` / `can_reach`），前端据此渲染，不支持的功能**置灰 + 一句人话解释**。
4. **配额 per-platform**：配额模型带 `platform` 维度，风险等级不同则默认 cap 不同（WA 可高、LINE 应极低甚至只读）。
5. **触达闭环接线**（工程量不大、价值最大）：成员表 `outreach_state` → `proactive_topic` 候选 / 收件箱草稿队列。复用现成链路。

**A3. 能力声明表（provider capabilities，前端渲染依据）**

| 平台 | can_enumerate_all | can_scan_speakers | has_stable_id | can_dedupe | can_reach | 触达通道 |
|---|---|---|---|---|---|---|
| Telegram | ✅ | ✅ | ✅ user_id | ✅ | ✅ | 已是好友/可私聊 |
| WhatsApp | ✅ | ⚠️ 需扫消息 | ✅ 手机号 | ✅ | ✅ | 直接发号（限速+合规） |
| Messenger | ⚠️ UI 翻页 | ❌ | ⚠️ 主页 | 部分 | ✅ | 加好友后 |
| TikTok | ⚠️ 粉丝/评论 | ❌ | ⚠️ 用户名 | 部分 | ⚠️ | DM（需关注/开放） |
| LINE | ⚠️ UI 翻页 | ❌ | ❌ | ❌ | ❌ | 无 |

**A4. 工程侧风险提示**

- huoke 是安卓真机 uiautomator2，产能低（FB extract 默认每号每日 20 人）、脆、有封号红线。当「提取后端」用要先定 SLA 与排产，不能给市场「和 Telegram 一样快」的预期。
- 现有 `tg_group_members` 有生产数据，泛化表结构要 `ALTER` + backfill `platform='telegram'`，需在重启窗口内谨慎操作（见 §三.D）。
- 跨仓库调用（huoke task 队列）会引入异步、失败重试、状态回传的复杂度——比 chengjie 内的协议级调用重一个数量级。

### 视角 B · 市场经理（获客漏斗 / ROI / 合规=品牌）

**B1. 现状营销问题**

1. **获客漏斗断在第一环**：从竞品群/行业群/兴趣群提取潜客 → 触达 → 转化，是增长引擎的核心。现在只有 Telegram 且提完只能导 CSV，**价值只兑现约 30%**。
2. **没有 ROI 读数**：每个群/每平台提取多少、触达多少、回多少、转多少、成本（封号/额度）多少——全无。市场无法判断哪个群/平台值得投。
3. **多平台缺口 = 市场覆盖缺口**：WhatsApp（东南亚/中东/拉美/印度）、LINE（日/泰/台）、Messenger/FB（欧美+东南亚）、TikTok（年轻内容流量）——每个缺口都是一块拿不到的市场。

**B2. 营销优化方向（按 ROI × 可行性排优先级）**

| 优先级 | 平台/能力 | 市场理由 |
|---|---|---|
| **P0** | Telegram 触达闭环 | 零新平台成本，直接把 30%→80%，盘活现有资产 |
| **P0/P1** | WhatsApp | 大市场 + 协议级可行 + 可触达，ROI 最高 |
| **P1** | Messenger/FB Group | 欧美+东南亚巨大获客池，huoke 有现成实现 |
| **P2** | TikTok 受众 | 年轻内容流量，但需重定义为「粉丝/评论者/话题受众」 |
| **P3** | LINE | 日/泰/台主力，但技术受限到「能看不能用」，**必须管理老板预期** |

**B3. 获客漏斗看板（市场核心诉求）**

跨平台一张漏斗：**提取 N → 可聊/可达 M → 已触达 K → 已回 J → 转化 C**，按平台/按群/按时间维度切。数据源可复用现有 `outreach_log`（触达真发落账）+ 提取表计数。这是市场判断投放的唯一依据。

**B4. 合规 = 品牌风险（必须写进方案而不是回避）**

- 批量提取手机号（WhatsApp）涉 GDPR/隐私法；发陌生号封号风险高；LINE/FB 抓取违反平台条款可致封号。
- 市场要的是「可持续获客」，不是「一波流封号」。方案必须内建：触达限速、opt-out 词表（chengjie 已有 `proactive_optout`）、合规话术、每平台风险分级配额。
- 与 `docs/智聊合规能力说明_EUAIAct50_SB243_NY1700_2026-08.md` 的对外合规定位保持一致。

### 视角 C · 用户（坐席 / 运营）

**C1. 现状用户痛点（从页面直接可见）**

1. **发现性差**：`/tools/tg-members` 是孤岛，不在主导航，要知道 URL 或从收件箱一张卡进。运营根本不知道有这功能。
2. **「死胡同」体验（最大挫败点）**：辛苦拉了 500 个可聊的人，然后只能导 CSV 到 Excel 手动一个个加。用户要的是「提取 → 勾选 → 一键 AI 打招呼」回到收件箱闭环。
3. **看不全**：表格固定 `limit=500` 无翻页控件；导出上限 5000。
4. **信息错位**：表格第一列是 `user_id`（对运营无意义），而运营真正判断「值不值得聊」需要的**最近发言内容、活跃时段、头像**都没有。
5. **多平台是用户原始诉求**：本方案的触发就是运营问「我 WhatsApp/LINE 群的人呢？」

**C2. 现状做得好、重构必须保留的**

- 任务进度条 + 客户端估算 ETA + FloodWait「限速等待中」提示（`tg_members.html` L471-483）。
- 多号选择 → 自动列群（并集）→ 覆盖度提示「所选 N 号中 M 个在此群；不在的会空拉」（L401-417）。
- 每号今日配额 mini bar + 全机群合计（L305-333）。

这几处交互扎实，重构时别丢。

**C3. 用户理想体验**

一个页面，顶部平台 tab（TG / WA / Messenger / TikTok / LINE），切换即切数据源；每个平台明确告诉我「能做什么、不能做什么」；提取 → 勾人 → 一键「加入触达队列 / 生成打招呼草稿」→ 回收件箱看回复；成员行带头像、最近发言、活跃度、可聊度、是否已联系过。

### 视角 D · UI/UX 设计师（视觉体系 / 信息层级 / 响应式）

**D1. 现状（视觉基础不差，但与主产品割裂）**

优点（保留）：深色模式适配、CSS 变量、圆角卡片、账号卡带头像+在线点、可聊度色块、进度条——设计语言干净。

问题：
1. **不继承 base.html**，主题色 `--accent:#1e8cf2` 是本页私有 token 而非产品统一 brand → 看起来像「另一个 App」；字体、间距各写一套（`tg_members.html` L16-90）。
2. **信息层级平铺**：①②③三张卡等权重堆叠，无引导动线。
3. **表格朴素**：无头像、无斑马纹/hover、无行多选、无空态、无骨架屏。
4. **无翻页/虚拟滚动**：500 行一次性渲染，大群卡顿。
5. **窄屏溢出**：6 列表格在桌面壳 405px 下会挤压/横向溢出（违反你们的窄屏密度纪律）。
6. **无批量操作栏**：勾选多成员做批量动作缺失。
7. **反馈全纯文字**：错误/空态无图标/插画引导。

**D2. 美化方向（见 §三.C 具体线框）**

统一到 base.html 主题 token 并进主 nav；平台 tab 用产品统一分段控件；成员表升级为「富表格」；顶部加获客漏斗条；主从布局；补空态、骨架屏、批量操作栏、窄屏响应式。

## 三、优化 + 美化落地方案

### A. 架构重构：平台无关的「受众/线索提取」框架

把「群成员提取」从 Telegram 专用工具箱，升级为平台无关的 **Audience Extraction** 框架。命名建议从「群成员提取」放宽为「**受众/线索提取**」——因为 TikTok 根本没有「群」，FB 是「群+主页粉丝+互动者」，统一叫「受众」才准确。

```
统一前端页（平台 tab）
  → /api/audience/*  (平台无关路由，旧 /api/tg-members/* 保留别名兼容)
     → ExtractorRegistry
        ├─ TelegramExtractor  (现有逻辑迁入，协议级)
        ├─ WhatsAppExtractor  (Baileys groupMetadata，chengjie 内)
        ├─ MessengerExtractor (桥接 huoke task 队列)
        ├─ TikTokExtractor    (桥接 huoke，语义=受众)
        └─ LineExtractor      (line_rpa，能力受限/只读)
     → audience_members 表 (加 platform 列)
     → 触达闭环 → proactive_topic / 收件箱草稿队列
```

每个 provider 声明 `capabilities`（§二.A3），前端按能力渲染，不支持的功能诚实置灰。

### B. 触达闭环（单点价值最高，建议第一个做）

把提取表 `outreach_state` 接到 chengjie 现成链路：
- 成员表「勾选 → 加入触达队列」→ 写 `proactive_topic` 候选 → AI 按人设自动打招呼 → 回复回流收件箱；或
- 「勾选 → 批量生成草稿」→ 进收件箱草稿队列，坐席人审后发。

复用现成的主动触达/草稿链路 + `proactive_optout`（opt-out 保护）+ 出站限速。**这条链路 chengjie 已全有，只差把提取表连上去。**

### E. 跨仓库桥接（huoke → Messenger / TikTok）

huoke 的能力在另一个仓库、另一套架构（安卓真机 task 队列）。桥接设计：
- chengjie 的 `MessengerExtractor`/`TikTokExtractor` **不直接实现抓取**，而是向 huoke 的 host web / executor 投递 task（`facebook_extract_members` / TikTok 受众任务），轮询/回调取结果，落 chengjie 的 `audience_members`。
- 契约参照 `huoke/docs/INTEGRATION_CONTRACT.md`（task_type 命名空间、频控）。
- **明确 SLA 预期**：真机产能低（FB 默认每号每日 20），前端要展示「排队中/真机执行中」而非假装秒回。

### F. 各平台适配器设计（逐平台）

- **Telegram**（迁移现有）：逻辑不变，迁入 `TelegramExtractor`。
- **WhatsApp**（chengjie 内，重点）：调 Baileys `groupMetadata(jid).participants` 拿手机号+管理员；显示名从消息历史 pushname 补；「发言人」筛选扫 Baileys 消息 store。合规：手机号入库要脱敏展示 + opt-out + 触达限速。
- **Messenger**（桥接 huoke）：复用 `extract_group_members`（FB Group）+ Messenger 群聊成员 UI。
- **TikTok**（桥接 huoke，语义重定义）：受众源 = 粉丝 / 关注 / 视频评论者 / 话题参与者（复用 huoke `tiktok.py` 粉丝列表能力）。UI 上明示「TikTok 无群，这里是受众提取」。
- **LINE**（能力受限，诚实标注）：line_rpa UI 翻成员页抓**显示名**。**明确局限**：无稳定 id → 无法去重、无法自动触达；产物仅作「人工参考名单」，触达按钮对 LINE 置灰。老板选了「全套」= 接受此局限，方案如实落到 UI 文案。

## 五、风险 / 合规 / 刻意的取舍

- **LINE 全功能的诚实边界**：老板选了「全套」，但物理上拿不到稳定 id → 无法去重、无法自动触达。方案交付的是「显示名只读名单」，触达能力对 LINE **必须置灰并写明原因**，避免运营误以为能一键触达。
- **WhatsApp 手机号隐私**：批量存手机号涉 GDPR/隐私法；发陌生号封号风险高。需合规话术 + 触达限速 + opt-out，且手机号在 UI 脱敏展示。不能一波流。
- **跨仓库（huoke）复杂度**：Messenger/TikTok 走安卓真机，产能低、脆、封号红线严；桥接引入异步/重试/状态回传复杂度。不能给「和 Telegram 一样快」的预期。
- **数据迁移**：现有 `tg_group_members` 有生产数据，`ALTER`+backfill 需在重启窗口内谨慎操作。
- **两个仓库的 owner 边界**：改 huoke 属另一条线的职责范围（见 `huoke/CLAUDE.md` 硬边界），跨仓库改动要走对方 review。
