## 〇 四段根因（只读核对后）

- **A 采用草稿不消费（CV4E22 / RU89S6 / 8FSXX2）**：前端早有 `_cdraftResolveAdopted()`（发送成功后 fire-and-forget `POST /api/drafts/{id}/resolve {action:cancel, by:composer_adopt}`），但它**不 await 就立刻 `_refreshComposerDraft()`** → GET pending 先于 POST 落库返回，同一条旧稿（`inbox:<cid>` 单行复用）被重新顶回草稿条 → 坐席每次发完都得再点一次「忽略」。服务端 `/api/unified-inbox/send` 完全不认草稿（AGENTS.md 已记）。
- **B 定时下点浅色/深色无反应（N9JQ3M / 4KEJ63 / NVFCZB）**：`appearance.js` 快捷面板夜间四档 chip 的 click handler **直写 `state.night.mode` 绕过 `setNightMode()`** → 不 `releasePin()`；桌面壳 webview 带 `?theme=dark` 钉，`eff()` 钉优先 → cp_theme 写了、高亮动了、`data-cp-theme` 不动。且钉释放标记在 sessionStorage（窗口级）→ 重开壳即回钉，用户的选择不持久。
- **C Telegram `_migrate` closed DB（13:32 栈）**：`_advance` 进 DC 迁移时另一路（cancel / TTL 清理 / 换码）已 `disconnect()` → pyrogram `storage.close()`；`_migrate._do` 再 `storage.dc_id()` / `session.start()` 撞 `sqlite3.ProgrammingError: Cannot operate on a closed database`，且 `_advance` 的「首试失败自动重试一次」对同一具尸体再撞一次（两份栈）。
- **D 帮助语料 295 条（22KVXF / B3PT5D / 32PTMK）**：代码事实＝帮助语料**早就**在小智独立库 `assistant_help.db`（`src/assistant/help_kb.py`，表 `help_entries`），从未写过 `kb_entries`；用户从启动日志「帮助语料自动播种完成：upsert 295 条」误读为播进用户 KB。真正缺的是：日志不说去向 + KB 页没有「按来源 dry-run 后清除预置」的统一入口（现有 vendor 一键清空不 dry-run；legacy-seeds 有 dry-run 但无 UI）。
