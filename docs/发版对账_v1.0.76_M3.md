## 一句话结论（改写了 GAJ5T2 的三层根因）

**四个平台所有 >2MB 的媒体从工作台就没发出去过——不是大文件堵服务、不是 .MOV 格式、不是网络。** `admin.py` 的全局请求体闸 `body_size_limit_middleware`（P25-A，2026-07-15 起在）默认 **2MB**，只给 translate-* 四个端点写了覆写，`send-media`（2026-07-29 才有）从没进过豁免/覆写表。于是：任何 >2MB 的上传在**路由跑起来之前**就被中间件 `413 + Connection: close`；浏览器此刻还在推 body，连接被掐，XHR 只见 `onerror`（没有状态码）→ 前端按「无响应」显「结果未知」；后端因为没进路由，`[send-media]` 零记录。本机真 uvicorn 复现：98MB 上传 `ConnectionAbortedError(10053)` 10ms 内、5MB 上传拿到 413 后 `ConnectionResetError(10054)`。对照证据全部吻合：98MB `product_mv`（#227）、5MB `IMG_7312.MOV` 三平台全灭（#229 #231）、今日成功的视频**全是 <2MB 的 .MP4**（TG `IMG_2854.MP4` 1.4MB）。J-3 C 把 LINE 上限放到 100MB 的那一轮是用 `probe_line_media.py` 直打 worker 验的，没经过这道闸，所以没发现。

被推翻的两条：① 「大文件把 Web 服务堵 20–30s」——Starlette 0.41 + python-multipart 0.0.20 解析 98MB 只要 0.25s（`tmp/m3_bench_multipart.py` 实测），事件循环最大间隙 0.05s；两个 `Failed to fetch` 窗口更像是 98MB 请求被中途 RST 之后 Chromium 网络栈的连带反应，修掉早关连接后不再有 RST 来源，但机制本身未能在本机复现，落点表如实记「推断」。② 「.MOV 被前端白名单静默拦」——前端此前**根本没有**格式白名单，`_stageMedia` 只查大小；renderer 报告里「零 fetch 错误」也不能证明请求没发出：`zl_collect` 的 renderer 过滤词是 `error/failed`，此前的 `[send-media] no-response …` 一行两个词都不含，值守根本看不到。本批所有前端拦截/重试日志都带 `error=` 字样。

- **B**：GAJ5T2 从「后端零请求 + renderer 零 fetch 错误」推出「请求未离开前端」，漏了两件事：XHR 的 onerror 不产生 `Failed to fetch`，且此前唯一的前端无响应日志行不含过滤词。
- **C**：`_mediaQueue` 设计时（08-17 多文件队列）就是模块级变量，切会话逻辑只交换了文字草稿。
- **D**：J-4 C / L-1 D 两轮只修「无响应」这一类的措辞，415/413/明确失败仍共用红字兜底。
