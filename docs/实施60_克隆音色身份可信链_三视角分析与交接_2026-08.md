### 1.2 根因：日志记的是「路」，不是「人」

`provider=hub_fish` 是**路由名**（走 AvatarHub 这条路），不是引擎名。
hub 的 `/api/tts_only` 响应信封里**根本没有引擎字段**。于是：

- hub 的 voice_route 是 **prefer 语义**：质量轨引擎（IndexTTS-2）不可用时**静默回落 fish_speech**，响应不带任何标记；
- 客户端拿到一段合法音频，长度、耗时、HTTP 200 全部正常 → 记一行「ok」；
- **整条链路里没有任何一处知道刚才是谁在说话。**

唯一可判别的物证是**采样率指纹**：IndexTTS-2 = 22050 / MOSS = 24000 / fish = 44100。
这就是为什么「老板的耳朵」比所有监控都早——**监控测的是「有没有声音」，老板听的是「是不是她」**。

### 1.3 为什么 strict 没挡住

`voice_consistency: strict` 的判据是「**hub 说自己不可用**」。08-20 两次正确触发即证明它工作正常。
但 08-22 的形态是「**hub 说可用，然后换了个人发声**」——从任何一个客户端可见的信号看都没有异常，
strict 无从下手。**这不是 strict 失效，是 strict 的输入信号本身不覆盖这个失败面。**

### 1.4 唱歌是不是元凶？——不是，但它是同一块 GPU 上的邻居

hub 引擎目录实测拓扑（gateway 在 176:9000，但真身分散）：

| 引擎 | 真身地址 | 角色 |
|---|---|---|
| `index_tts2` | **192.168.0.173:7865**（5090） | 克隆声质量轨＝人设本人的声音 |
| `fish_speech` | 176 本机 `127.0.0.1:7855` | 静默回落目标＝那个「怪异的声音」 |
| `yingmusic_svc`（唱歌） | 176 本机 `127.0.0.1:7853` | 翻唱/清唱 |

结论要说准：

- **唱歌不直接抢 IndexTTS-2 的卡**（一个在 173，一个在 176），所以「开发唱歌导致音色变了」这个因果**不成立**；
- 但唱歌与 fish、**以及 hub 网关本身**同在 176。176 被压满时，受影响的是**网关响应与回落链**——
  即「主路不可用 → 回落也慢/也抖」的复合态。所以唱歌是**相邻压力源**，不是元凶，
  上线前该有闸门（§4 P2）。

## 2. 三视角分析

### 2.1 开发工程师视角：我们监控了「有没有」，没监控「是不是」

- `true_probe` 判绿的口径是「合成出了一段有效音频」。fish 冒名顶替 index_tts 时，这个断言**为真**。
  探针不是坏了，是**断言写窄了**——它证明了服务活着，没证明身份对。
- 同类盲区在本仓有前科：`.cursor/rules/media-artifact-validation.mdc` 里
  「HTTP 200 + 文件 KB 数 = 零鉴别力」是同一个病的另一种形态。**内容层面的验证必须验内容特征，
  不能验外形。**
- 另一处结构性缺口：WhatsApp / Messenger 的 RPA 语音链**从未进 voice_outage 台账**
  （全局台账被任何一条健康链路掩盖 → 24/24 OK）。这条已由并行线补上（§4）。
- 工程结论：**凡是「多引擎 + 静默回落」的服务，客户端必须有独立于服务自述的归属判据。**
  这里的判据是采样率；换成别的领域就是别的指纹，但「不能只信服务端自述」是通例。

### 2.2 市场经理视角：音色是人设资产，换声＝换人

- 卖点不是「有语音」，是「**是她的声音**」。克隆音色是人设人格的一部分，与头像、说话方式同级。
  一次静默换声，对客户是「这号换人运营了」级别的破绽——比不发语音伤害大得多。
- 因此**「宁可不发，也不用别人的声音顶班」是正确的产品默认**（strict 的存在是对的），
  需要补的只是让它**看得见**：客户端有回落时必须显式告知坐席「这是标准音色，非人设克隆声」，
  而不是灰字黑话。
- 内测群里「克隆音色不能用」的反馈**要分两类回**，混在一起答会失信（§3.3）。

### 2.3 用户（坐席 / 终端客户）视角

- 坐席侧：坐席无法分辨「hub 换了引擎」，只能听出「怪」。他们需要的不是引擎名，是一句人话：
  **「当前发出的是标准音色，不是这个人设的克隆声」**。
- 终端客户侧：客户不会报障，只会**降低信任**——不投诉的静默流失，比投诉更贵。
- 内测群用户侧：报「克隆音色不能用」的人，看到的是**报障群里客服号不发语音**，
  容易理解成「你们自己都用不了」。这是刻意设计（§3.3），但**没解释过**，
  于是防线本身变成了新的负面证据。

## 5. 复发防线清单（回答「怎么让以后不会再发生」）

1. **服务自述不可信，验内容特征**——多引擎静默回落的服务，客户端必须有独立归属判据（此处＝采样率指纹）。
2. **探针断言要贴业务语义**——「有音频」不等于「是她的声音」。探针要断言**身份**，不只断言**存活**。
3. **fail-closed 优先于 fail-soft**——音色属人格资产，宁可不发。strict 的方向一直是对的，
   要补的是它的输入信号覆盖面。
4. **台账要按来源布防**——全局聚合会被任一健康链路掩盖（WA 语音全挂而台账 24/24 OK 是实锤）。
5. **日志要记「谁」不只记「哪条路」**——`provider=hub_fish` 说明不了发声人；归属结论必须落日志。
6. **抑制类防线要配对外说明**——`voice_suppressed` 是好设计，但沉默的防线会被当成故障。

既有两道闸此时都不响（目录预检看 available 为真；指纹闸永远拿不到音频），故补第三道：

`response_format: ogg`，而指纹靠 WAV 头采样率——`engine_attribution` 对非 wav 明确
返回 `unknown` 放行（hub 转 opus 恒 48k 会抹掉指纹）。但三道闸是互补的：
**目录预检不依赖 wav**（ogg 直出同样有效）且报的是根因（目标引擎离线），
**熔断也不依赖 wav**。指纹只是最后一道正面反证。故 ogg 路径仍有两道闸覆盖。
