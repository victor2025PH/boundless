## 3. A —— 每拍可追溯（P1）

- 目标详情（`goal_routes` 新 `GET /api/goals/{id}/beats`）列出每一拍：第 N 拍 / 时间 / 会话 / 发送内容摘要 / 相位（sprint:pN / daily / care）/ 状态（已发 / 拦下 + 原因 / 预览待确认），可跳转到该消息（`platform_msg_id`）。数据源：`gstore` `beat_sent` 事件补 `conversation_id` / `message_id` / `text_head` 字段（`record_*_beat_sent` 两处写入）。
- 目标卡「已推进 N 拍」变成可点，展开上面的清单；**看门狗的 `sent_24h` 与卡片的 N 必须同一口径**（都读 gstore 事件）。

## 4. B —— 注入不断档 + 日志无死角（P1）

- `[goal-inject]` **每一稿一行**（自动链 / 手动链 / 主动链同口径），`disabled` 与 `no_goal` 都 INFO（去掉 10 分钟节流或把节流值降到 60s），带 goal_id / status / 早退原因；目标 `expired` 时明确 `reason=goal_expired`。
- **被动注入（客户来消息时带方向）不受拍数上限限制**（拍数上限只管主动出手）——落点表写清 `effective_beat_cap` 在 inject 路径的读取点与改法。
- 目标状态变更（创建 / 重置 / 阶段推进 / 延期 / 到期 / 完成）每次一行 `[goal-state]` INFO 并写 gstore 事件；卡片「当前：起步 / 深化」读同一事件流，不再出现「深化→起步」说不清是谁改的。

## 5. C —— 到期结算不静默（P1）

- 目标到期 / 失败当刻生成**结算摘要**：计划 X 拍 / 实际 Y 拍 / 被拦 Z 次及原因 / 客户回应 N 条 / 未执行的主因一句话；推到工作台通知中心 + 目标卡上留「已到期 · 查看结算」7 天，**不经 3 条 / 24h 聚合门槛**（`notify.py` L544 已有「3 小时目标失败趁热复盘」的例外，扩到所有到期）。
- 重建目标时若前一个同会话目标刚到期，卡片提示「上一个目标 X 拍 / Y 完成，已结算」，避免用户以为引擎重置。

## 6. D —— 卡片说真话（P1）

- 「自动推进中」只在**过去 24h 内有 ≥1 条 `beat_sent`** 或 **当前有排期在 24h 内**时显示；否则按真相三选一：「今日已达上限，明日 HH:MM 继续」/「等待首拍（预计 HH:MM）」/「被 X 拦住（原因）」；新建目标 24h 内无可见动作 → 卡片不得显「自动推进」。
- 单目标粒度 stalled：`liveness.py` 增 `goal_stall_verdict(goal)`（有排期但 24h 零 `beat_sent` → stalled），看门狗告警带 goal_id 与会话，卡片同步红字。
- 卡片文案与 `engine-status` 的 `sprint_blockers` 对齐（J-2 A2 已有点名闸），不再出现「自动推进⚠」却不说 ⚠ 是什么。
