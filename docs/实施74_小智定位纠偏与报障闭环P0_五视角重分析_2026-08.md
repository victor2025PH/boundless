## 3. 五视角问题清单（按正确定位）

完整版见对话记录；此处只留**指向实施项**的条目。

- **开发工程师**：发布了没订阅（静默）／三入口三套存储无统一工单 ID／前后端状态机

  没映射）／截图存了但**无任何读取端点**／howto 靠人工 seed 且无门禁／anchor 仅 3 条／
  小智问答无评测集／报障不带账号与应用版本。
- **市场经理**：报障是交付前唯一能验证的价值通道而它断路／32 条 howto 撑不起 41 页产品／
  "做帮助而非代操作"是**正确且克制**的技术选择（2026 年长任务 agent 完成率仅 20.6%）
  但没讲出去／入口叫"替我做"造成预期错配／修好了用户不知道更新。
- **用户**：多数页面问不出答案／报了障没人联系我／不知道工单进展／教学模式认不出控件／
  66 个设置只能帮改 16 个／客服说能远程协助但找不到入口。
- **美术设计**：报障与"对话"平级未体现地位／截图标注是最有价值的细节却无视觉突出／
  6 个工单状态无颜色语言／空态无设计／帮助三类内容混排不分层。
- **UI/UX**：入口语义错配／报障在 IA 里被低估／提交后零预期管理／答不上来无优雅降级
  （应转报障）／教学与帮助是同一件事却两个入口／设置协助无能力清单。

## 5.4 P2：小智问答检索评测（2026-08-27 13:49-14:35）

语料两批扩到 57 条 how-to 之后，「补进去的条目能不能被真实问法检索到」**零数据**
——关键词是人按经验写的，写偏了就是「补了等于没补」，而这种失败**完全静默**
（用户只看到一句「不知道」）。小智问答也是全仓最后一个没有离线评测的 AI 能力。

### 新增 `src/eval/assistant_qa_eval.py` + 常驻门禁

- **只评检索不评措辞**：BM25 确定性、无网络无模型 → 可做**常驻门禁**（LLM 答得
  好不好属另一层，需 `EVAL_LLM` opt-in）。检索捞不到，再好的模型也只能拒答。
- **语料从代码构建**（`build_all_entries()`）而非读线上库：评的是随包发货、
  客户新装机首启拿到的那份，也避免被某台实例手工灌过的数据污染。
- **40 条金标，问句刻意不照抄标题**——照抄必然命中，是零鉴别力的同义反复。
  全部按「用户真会怎么打字」写（口语、别名、错位说法、场景描述）。
- CLI：`python -m scripts.run_eval --assistant-qa [--json]`；
  门禁 `tests/test_assistant_qa_eval.py`（6 例）。

### 三个靠直觉抓不到的发现

1. **补关键词有交叉影响。** 给 `escalation-config` 补了「人工客服」之后，它把
   「怎么新增一个客服人员」从 `add-agent-user` 手里抢走了。改任一条都可能误伤
   别的条目——已把这条写进 `add-agent-user` 的代码注释，并要求改关键词后复跑评测。
2. **`min_score=1.6` 这道拒答闸门形同虚设。** 实测 BM25 分数落在 **28~120** 区间，
   所有金标问句的最高分都远超 1.6——**它从来没拦下过任何东西**。这解释了线上
   qa_log 的怪现象：`answered=1` 却答非所问（2026-08-20 那 7 条真实提问里至少 3 条
   跑题，却同样被记成「答上了」）。已用

## 5.5 P3：`min_score` 重新校准——让「诚实拒答」真正生效（14:17-14:50）

§5.4 发现 `min_score=1.6` 形同虚设后，本批把它校准掉。

### 先建负样本（没有负样本就无从校准）

评测此前只有正样本，只测「该答的答没答上」。只测正面会得出「阈值越低越好」
的错误结论。新增 `NEGATIVE` 15 条**应该被拒答**的问题，分三类：
`chat`（闲聊）/ `common`（常识）/ **`product`（产品形状但语料没覆盖）**/
`garbage`（乱码）。product 一类是刻意分出来的——后面会看到它是唯一拦不住的。

### 实测：正负分布重叠，只能选代价点

| 阈值 | 误拒正样本 | 拦住负样本 | 备注 |
|---|---|---|---|
| **1.6（原值）** | 0/40 | **1/15** | 只拦得住纯乱码 |
| 35 | 0/40 | **7/15** | **取这个**，离最低正样本 41.2 留 6.2 余量 |
| 40 | 0/40 | 8/15 | 只多拦 1 条，余量却只剩 1.2，太脆 |
| 50 | 3/40 | 8/15 | 开始误拒真问题 |

正样本最低 41.2、负样本最高 109.8——**重叠**，单一 BM25 阈值不可能干净分开。

### 一个只改 example.yaml 会踩空的坑

实例配置（`config.local.yaml` / `config.yaml`）里**根本没有 `assistant.query`
段**，线上跑的是 `assistant_routes` 里硬编码的回落值。所以：
**只改 `config.example.yaml` 对生产毫无作用**——必须同改路由默认值。两处都已改。

### 改动

| 文件 | 改动 |
|---|---|
| `src/web/routes/assistant_routes.py` | 硬编码回落 `1.6` → **`35.0`**（附完整校准表注释） |
| `config/config.example.yaml` | `min_score: 1.6` → `35` + 依据说明 |
| `src/eval/assistant_qa_eval.py` | `DEFAULT_MIN_SCORE` 同步；新增 `NEGATIVE` 15 条 + `refusal_rate` / `refusal_by_kind` / `margin` 三个口径；报告增「校准余量」「诚实拒答」「仍会硬答」三段 |
| `tests/test_assistant_qa_eval.py` | 旧的「闸门形同虚设」断言已过时，换成 4 条真校准守卫 |

新门禁四条各守一个决定：**零误拒**（抬阈值最不能踩的红线）、**余量 ≥3 分**
（守住「不为多拦 1 条把链路搞脆」这个取舍）、**拒答率 ≥45%**（防阈值被悄悄调回）、
**product 类仍是已知缺口**（把限制钉成可见事实；等语义核对上线它会红，红了
就该改成正向断言）。

### 校准后读数

```
可作答 40/40 (100%)      ← 零误拒
校准余量 正样本最低 41.18（离阈值 +6.18）
诚实拒答 7/15 (47%)      ← 原来是 1/15
   chat 1/3 · common 3/3 · garbage 1/1 · product 2/8
仍会硬答 8 条（分数天然高，需语义核对才拦得住）
```

### 诚实的局限

`product` 类只拦住 2/8。「怎么导出所有客户的手机号」（96 分）、「怎么把数据
迁移到别的服务器」（110 分）这类**用产品词汇提问、但语料里没有答案**的问题，
分数落在正样本分布中间，抬阈值只会先误拒真问题。**这是本次校准解决不了的
那一半**，需要出站前的语义核对，已列为下一阶段第一优先。

### 验证

- 门禁 62 passed；assistant + 评测相关全量 **220 passed**。

## 5.6 P4：「没依据」哨兵——补上分数拦不住的那一半（19:17-20:00）

§5.5 校准完 `min_score` 后仍有 8/15 负样本被硬答（product 类，用产品词汇提问、
分数天然高）。本批补上这一半。

### 先否决了自己上一轮提的方案

上一轮建议「出站前加语义核对」，参照仓里 `confidence_switch.semantic` 的先例
用嵌入余弦。**实测把它否了**：

| | 正样本 | 危险的 product 类负样本 |
|---|---|---|
| query↔命中条目 余弦 | **最低 0.455** | 0.608 / 0.602 / 0.586 / 0.564 |

**负样本全部落在正样本区间内**，任何余弦阈值都不可能分开。原因很实在：
「能不能自动打电话给客户」与「出站自动翻译」在嵌入空间本就近（都是「AI 自动
对客户做某事」）——**余弦量的是话题相关性，不是「这段文档能否回答这个问题」**。
先量后建，省下了一个注定无效的子系统。

### 采用的方案：让答题的 LLM 自己声明

关键观察：**正在答题的那个 LLM 本来就同时看着问题和参考条目**，它就是最合适的
裁判。再调一次 LLM 当裁判要多一个往返、给每条问答加延迟；让它自己声明是零成本。

真正的断点也不是「LLM 不肯拒答」——提示词里一直写着「覆盖不到时诚实说明」——
而是**缺一个机器可读的信号**：路由无从判断它是答了还是拒了，于是
`qa_log` 恒记 `answered=True`（自答率虚高）、`report_hint` 不亮（用户没有出路）、
ops「未答清单」看不见缺口。

| 改动 | 说明 |
|---|---|
| 提示词（中英） | 教 LLM：答不了就把 `NO_BASIS` 原样放在最开头，别的什么都不写 |
| `_is_no_basis()` | 哨兵**必须在开头**才算数——正文中间提到这个词不得误伤 |
| 流式首段缓冲 | 攒够哨兵长度才决定放行；命中则停流，**用户一个字都看不到**（先吐半句再撤回比不撤更糟）。代价只是首 8 字节的等待 |
| 非流式回落 | 同样先判后吐 |
| 命中处置 | 与「零命中」同一出口：`asb.a.no_hit` 诚实文案 + `answered=False` + `done.answered=false` |
| `assistant-ball.js` | 报障入口新增第二个来源 `done.answered === false`——只看 `meta.report_hint` 会漏掉「答不上来」这个最该给出路的时刻（VER `20260827c`） |

### 门禁 `tests/test_assistant_no_basis.py`（20 例）

三条不变量：命中时零输出、`answered` 记真话、哨兵在正文中间不误伤。
含**端到端真跑路由两例**（假 LLM 返回 `NO_BASIS` → 断言用户拿到的是诚实说明
且响应里绝不出现哨兵；正常回答一字不改）——比模拟流硬得多。

### 顺带补上一个更大的缺口：门禁没进 sweep

发现本线此前几批的门禁**一个都不在 `gate_sweep.ps1` 的清单里**——意味着别的线
收口时跑不到，改语料/改路由的回归只有本线自己跑才发现。已把五个文件登记进去
（`test_assistant_beacons` / `test_bug_report_loop` / `test_howto_coverage` /
`test_assistant_qa_eval` / `test_assistant_no_basis`），并按该文件惯例逐条写明
「它守什么」。全是静态或纯确定性（BM25/无网络无模型），秒级完成。

**清单 61 → 66 个文件，sweep 939 → 991 passed。**

### 验证

- 广域 `gate_sweep`：**ALL GREEN**（66 文件 / 991 passed，首轮零红）。

## 5.7 P5：拒答分型可观测（19:50-20:10）

哨兵是**依赖模型行为**的机制（LLM 得肯输出约定词）。它不工作时不会报错，
只会退回「把沾边条目硬凑成答案」——在别处完全看不出来。所以必须可观测。

### 开工即发现并行线已做了一半

`src/assistant/qa_log.py` 19:39 被**另一条线**改过（不是本线），他们读了本批的
哨兵代码，顺手在 `stats()` 里加了拒答分型：`miss_no_hit` / `miss_no_basis` /
`no_basis_share`。设计很聪明——**零迁移**，靠既有 `top_score` 列推导
（零命中分支不传该参数默认 0，哨兵分支必传 `strong[0]["score"]` 必 >0），
所以对历史数据同样成立。

但 grep 显示**零消费方**：数算出来了，没有任何界面展示，意向板上也无人认领。
所以本批的活是**补消费面 + 补契约门禁**，不是重写。

### 做了什么

| 事项 | 说明 |
|---|---|
| ops「🤖 小智」卡新增拒答分型行 | 零命中 N（补语料） · 有条目但答不了 N（哨兵，占比%）；**零拒答不占版面** |

数据链无需改动：`/api/assistant/health` 的 `qa_7d` 直接回 `stats()`，字段本就在。

### 门禁守住那个零迁移方案唯一的脆弱点

零迁移的代价是**语义隐含在两个 `record()` 调用点的参数差异里**：谁给零命中

- `test_ops_card_surfaces_the_breakdown` —— 算出来没人看等于没做，含「零触发亮黄」；
- `test_refusal_i18n_keys_are_bilingual`。

`tests/test_assistant_no_basis.py` 20 → **30 例**。
