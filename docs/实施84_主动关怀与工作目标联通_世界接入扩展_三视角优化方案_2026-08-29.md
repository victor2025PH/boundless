# 实施84：主动关怀 × 工作目标联通 + 真实世界接入扩展 —— 三视角分析与优先级方案

> 日期：2026-08-29 ｜ 性质：**纯方案文档，本轮不改任何代码**
> 依据：当日对 care / goals / 世界接入三个子系统的代码勘察（文件:行号均为实况）+ zhiliao 实例配置核对 + 2026-08 业界调研。
> 老板原话：「现在发送的内容和运行的逻辑与我希望的不一致，他应该与工作计划功能相通……加入更多（世界）接入，让聊天更加真实。」

## 0. 一页结论

老板的三个感受，各自对应一个**可证实**的根因，没有一个是错觉：

| # | 感受 | 根因（代码实况） |
|---|------|----------------|
| 1 | 「发送的内容和运行的逻辑与我希望的不一致」 | **关怀页展示的和客户真正收到的是两套系统。** 主动关怀（care）至今 `dry_run: true` 只拟稿不发（overlay :664）；真正发出去的主动消息来自沉默回访管线 proactive_topic（真发中），其文案逻辑（问候/接旧话/生活分享/新闻天气）与关怀页承诺的「记住约定、到点关心」不是一回事。截图里那条「旅行怎么样啦」是 8/10 的**试运行拟稿样本**，不是实发。 |
| 2 | 「应该与工作计划功能相通」 | **确实不相通。** 工作目标（goals）在 zhiliao 已全量开启（auto_create/订单回流/留存/winback，overlay :781-809），被动回复链也已消费目标（`_goal_block` 注入 prompt）；但 care 代码对 goal **零引用**（全树 rg 无命中），而「目标搭主动开场」的桥 `companion.goals.bridge` 虽然代码已就绪（`goals/bridge.py`、`proactive_topic.py:1616,2486`），**默认关、实例也没开**。结果：AI 被动聊天时懂目标，主动出击时不懂。 |
| 3 | 「加入更多世界接入」 | 现有真实外部源只有两个：天气（Open-Meteo，`weather_state.py`）与新闻（RSS，`daily_topics.py`），且无统一接入框架，注入点散装在 skill_manager。节日/场景/衣着/饮食全是本地模拟（这部分是对的，不该联网）。可低成本扩 6+ 个免费源，并把「世界事件」升级为第四种触达时机。 |

**方案主轴一句话**：把六条各自为政的主动出话管线收敛成「**一个联系人一份计划、一个出口一本账**」——目标（goal）定方向，关怀（care）与世界事件（world feed）定时机，统一预算与来源标注定分寸。

**优先级总览**（详见 §5）：

| 级别 | 主题 | 性质 | 预估节奏 |
|------|------|------|---------|
| P0 | 把「看到的=发出的」修直 + 目标桥开闸 + 拟稿上下文补齐 | 多数是配置与小改 | 本周 |
| P1 | care×goal 双向数据流 + 全管线统一打扰账本 | 结构打通 | 1–2 周 |
| P2 | WorldFeed 统一框架 + 新增 6 类接入 + 事件锚触达 | 增强 | 2–4 周 |
| P3 | 回复率/推进率反哺 + 变现联动 + 周报叙事 | 数据驱动 | 数据攒够后 |

## 1. 现状梳理：六条主动管线与四本账

### 1.1 管线盘点（客户视角只有一个「TA」，系统视角是六条线）

| 管线 | 触发 | 文案上下文 | 冷却/账本 | 投递 | zhiliao 现状 |
|------|------|-----------|----------|------|-------------|
| **proactive_care** 约定关怀 | 捕获的约定到点（事件日 20:00 / 道贺 09:00，`care_commitment.py:26-28`） | 最近 8 条原文 + 约定原话；**无人设、无长期记忆、无目标**（`build_care_prompt`，`care_dispatcher.py:124-159`） | `care_schedule.db` + 真发写 `outreach_log` | deferred 队列 | enabled + **dry_run**（只拟稿） |
| **proactive_topic** 沉默回访 | 沉默 ≥24h、冷却 48h | 记忆事实 / 生活素材 / 新闻 / 天气 + 人设风格 | `companion_proactive_cooldown.json` + `outreach_log` | 编排器直发 | **真发中**（telegram） |
| **daily_ritual** 早晚安 | 晨 7-10 / 晚 21-24 个性化择时 | ritual opener（可附灵签/天气行） | `companion_ritual_cooldown.json` | 直发 | 真发中 |
| **milestone_ritual** 纪念日 | 认识 N 天 / 生日 / 节日 | milestone opener | 同 ritual json | 直发 | 真发中 |
| **reactivation** 漏斗召回 | contacts journey 阶段 + 沉默天数 | 强制 episodic 记忆 | `journey_events`（**不写 outreach_log**） | deferred | config.yaml dry_run，且依赖 messenger_rpa |
| **goals.bridge** 目标搭车 | 搭 topic 顺风车（不自建队列） | goal 今日意图 → 开场 directive | — | 随 topic | **默认关、未开** |

### 1.2 「与期望不一致」的七个根因（每条有代码依据）

- **R1 页面与现实脱节**：关怀页只展示 care 一路，而 care 在 dry_run；客户收到的主动消息几乎全部来自 topic/ritual。坐席在页面上「过目」的话术与实发内容无关 → 感知必然是「发的和我看到的不一样」。
- **R2 捕获面窄**：正则抽取**必须有未来时间锚**（明天/周五/3月5日…，`care_commitment.py:90-195`），「下次给你看照片」「等我忙完这阵」这类无锚承诺全漏；无词库主题置信 0.5 < 入库阈值 0.6，也进不了库（`care_commitment.py:238-243` + `care_schedule.py:116`）→ 「近 24h 捕获 0」的直接原因。LLM 抽取只在影子模式（对照日志不入库，overlay `llm_extract.shadow: true`）。
- **R3 拟稿上下文薄**：`build_care_prompt` 只注入约定原话 + 最近 8 条消息拼接，人设口吻、episodic 记忆、工作目标全都不进 → 产出「诶，你之前说的旅行怎么样啦？玩得开心不」这类无个性、无推进方向的泛泛话术。
- **R4 与工作目标零联动**：goal 的「今日拍」（`goal_actions`：今日意图 + 力度）已被 A/B 线被动回复消费（`skill_manager.py:1489,3158` → `_goal_block`），但主动侧：care 零引用；bridge 未开。**坐席设了计划，AI 主动出击时却自说自话。**
- **R5 dry_run 语义陷阱**：试运行拟稿后 `mark_sent(note="dry_run")`（`care_dispatcher.py:482`）——**待办被消费掉**。试运行期间「演习」过的约定，切真发后不会再发；坐席以为 dry 只是预览，实际是消耗。
- **R6 账本分裂**：冷却/触达账本至少 4 本（outreach_log、topic 冷却 json、ritual 冷却 json、journey_events）；reactivation 真发不写 outreach_log → 不受每联系人预算（contact_budget）约束。客户同一天可能收到「约定关怀 + 早安 + 沉默问候」三连。
- **R7 细节缺陷**：`already_discussed`（近期已聊过就别再打卡）参数存在但启动未注入（`background_tasks.py` 未传）；👎 黑名单在进程内存、重启即丢（`metrics_store.py:114-116`）；care 的 due/安静时段用服务器本地钟，无用户时区（对比 ritual 已有 `user_clock`）。

### 1.3 工作目标侧：已建资产比想象厚，只差「主动」最后一公里

goals 子系统（`src/companion/goals/`，独立库 `marketing_goals.db`）已具备：
- 模板体系（摸底/转化/关系/唤回/自定义，`templates.py:50-462`）+ 两步建目标向导（cp-goal.js）
- **每日拍**：`refresh_goal` settle-on-read 规划当日 `goal_actions`（今日意图 + push_level + 情绪/沉默 hold）
- 被动注入：`_goal_block` 进 A/B 线 prompt（含【今日意图】【推进纪律】）
- 自动化：sweep 补结算、完成通知、auto_create（su_wan 获客）、订单回流（bd2026.cc order_hook/order_pull）、留存/winback——**zhiliao 全开**
- 观测：goal-report 报表、ops 🎯 卡、周报 CLI

**唯一断点**：主动触达不消费它。bridge 是现成的接口（开关即用），care 则需要新建联动。

### 1.4 世界接入现状

| 接入 | 数据源 | 新鲜度 | 注入点 | zhiliao |
|------|--------|--------|--------|---------|
| 天气 | Open-Meteo（免 key） | 30min 鲜 / 3h 陈旧可用 | 聊天事实块、weather_hook 开场、晨安行、生图场景过滤 | 开 |
| 新闻 | RSS（Google News zh + BBC + 娱乐/体育分区） | 6h 后台刷新 | `_daily_topics_hint` 回复提示、news_share 开场 | 开（新闻优先于生活分享） |
| 节假日 | 本地规则表 + lunar_python（农历/节气） | 本地计算 | 用户侧节日问候、人设侧生活纹理 | 开 |
| 客户时区 | 推断（自述/国码/行为），零 HTTP | 6h 缓存 | 时钟行、触达择时 | 开 |
| 场景/衣着/饮食/生活线 | 本地确定性模拟 + 人设静态素材 | 同日恒定 | 状态块、生图 | 开 |

**结构问题**：无统一 Provider 抽象——天气是同步 TTL 缓存、新闻是后台 daemon + 文件缓存，各写各的；新增一个源就要再发明一次轮子。**内容问题**：新闻/天气是「人人一样的世界」，没有按客户兴趣路由（客户没提过球赛也可能收到体育新闻话头）。

## 2. 业界对照（2026-08 调研要点）

**架构共识**：会话 LLM 与「何时说/说什么」的策略模块分离。
- 学界（ProChatIP，arXiv 2604.11077）：客服主动探询用独立 conversation strategy 模块（SFT+RL 双奖励：主动收益 vs 等待价值），核心结论是**时机错了用户直接拒绝**——11.6% 失败案例源于「突兀切入」。
- 工程界（LangChain ambient agents）：事件流驱动 + 人审三档 **notify / question / review** + 「agent inbox」（等人过目的队列）。我们的 dry-run 样本审核页就是 agent inbox 的雏形，方向踩对了，缺的是把六条管线的产出汇进同一个 inbox。
- 开源实践（AstrBot proactive 插件等）：连续未回封顶（max_unanswered 停止重排）、随机间隔、安静时段——我们 Phase19 的退避/变体/安静时段与之同构且更精细。

**产品共识**：contextual triggers > 定时推送。PopVid 的招牌场景「你提到面试，晚上它来问结果」**正是我们 care 的设计目标**；HeyWaii 把 rituals（晨安/睡前）列为留存锚——我们有 daily_ritual。差距不在机制缺失，在**捕获率低（R2）+ 文案薄（R3）+ 没和商业目标挂钩（R4）**。

**市场数据**（支撑投入决策）：
- AI 陪伴市场 2026 约 $9B（2024 $4.3B → 2025 $6.8B），**2027 年预测的头号增长驱动就是 proactive engagement + 深度个性化**。
- 行业 R30 约 43%，头部 53%；带持久记忆的用户留存显著高于无记忆（JMIR Ebb 案例：改记忆架构后 R30 33%→53%）。「记住约定并守约」是可量化的留存杠杆。
- 反面警示：被 FTC 视为 dark pattern 的是「为重开率优化措辞和时机」的操纵式推送——**诚实与分寸是长期资产**，我们的 opt-out/预算/退避护栏要作为卖点保留而非阉割。

**接入趋势**：MCP 工具化成为外部数据标准形态（Perigon news MCP、Open-Meteo/Stooq/API-Football 组合的开源范例）。本方案接入层按「provider 可平移为 MCP tool」的形状设计，但现阶段先内置（见刻意不做 §6-6）。

## 3. 三视角分析

### 3.1 开发工程师视角

**优势资产**（不要重造）：
- 触达纪律工具箱业界领先：未回退避（3^n 封顶月频）、变体守卫（防复读机）、回复率反哺、mode 门控、opt-out、每联系人预算、安静时段、危机豁免——全部有门禁钉住。
- goal 子系统数据模型完整，`conversation_id` 三元组与 care/outreach 同构，打通无需迁移。
- dry-run→人审→真发的灰度范式成熟（care/reactivation/proactive 三处同构）。

**架构债**（按修复收益排序）：
1. 账本分裂（R6）——「客户今天被打扰几次」没有单一口径，这是所有打通工作的地基。
2. dry_run 消费待办（R5）——转真发前必须修，否则试运行期间的约定全部作废。
3. 拟稿上下文装配无统一入口（R3）——care/topic/ritual 各拼各的 prompt，goal 块、记忆、人设的注入要逐处重复接线；值得抽一个 `build_touch_prompt` 共用装配器。
4. 世界接入无抽象（§1.4）——每加一个源重复 fetch/cache/fail-open/观测四件套。

**改动面评估**：P0 大头是配置（bridge 开闸零代码）+ 单文件小改（`care_dispatcher.py` / `background_tasks.py`）；P1 涉及 goals service 与 care store 互调，注意 `skill_manager.py` 是热区（共享树协议：动工前 agent_probe）；P2 新增文件为主，风险低。全程复用「新子系统默认 enabled:false + overlay 开」约定。

**风险**：① 双推——care 与 bridge 同时推进同一目标时需让路规则（§5 P1-3 显式优先级）；② 平台风控——主动私聊频次已有 pacing 管着，新增事件锚必须进同一预算，绝不另开口子；③ 测试面——每个 P 项配套门禁清单已在各项中列出。

### 3.2 市场经理视角

**卖点重构**：从「AI 自动回复」升级为「**AI 自动跟进**」。竞品（客服 SaaS 与陪聊 App）的主动能力普遍停留在定时群发/模板 push；我们能讲的故事是三层：
1. **会记事**：聊天里的约定自动记下（care 捕获）；
2. **会守约**：到点用对方的语言、人设的口吻自然回访（care 派发 + 人设/记忆注入）；
3. **有目的**：每一次主动开口都在推进坐席设定的工作目标（goal 联动），而且推进有报表（goal-report 归因）。

**差异化证据链**：演示场景直接用真实工作流——坐席早上建一个「转化解锁」目标 → 当天 AI 在客户提到「周五发工资」时自动记下 → 周五晚 20:00 用人设口吻问候并自然带到产品 → goal-report 显示这条触达推进了里程碑。这一条链没有竞品能完整演示。

**变现联动**（复用已有 monetization gate）：目标托管数（active goals 上限）、每日主动触达配额、高级世界接入（赛事/行情/热搜）都可进付费档位。行业基准：头部免费转付费 15-20%、付费月流失 4-6%——「记忆+守约」正是拉开这两个数的功能。

**风险与合规**：主动消息的骚扰投诉是品类第一杀手。我们的立场应是「**分寸即卖点**」：opt-out 词表、未回退避、每日上限全部保留并写进产品文案（「AI 知道什么时候该闭嘴」）。避免任何「为重开率优化」的暗黑话术——2026-2028 是该品类监管收紧窗口（调研 §2）。

### 3.3 用户视角（两层用户）

**坐席（直接用户）**：
- 现状痛点：关怀页、目标面板、收件箱三处叙事互不引用；主动消息发出后坐席**说不清「这条为什么发、是谁发的」**；dry/真发语义靠猜。
- 期望形态：「**设定计划即托管**」——建一个目标，之后 AI 的每次主动开口都能在目标卡里看到出处与效果；关怀页变成「AI 替我盯着的所有事」的统一视图（约定/纪念日/目标节点/世界事件），每条可预览、可改期、可跳过（正是现有 UI 承诺的「每条都可预览、改期、跳过」，把它做实到全部管线）。
- 信任建设：来源标注 + 一键解释（「因为客户 8/10 提到旅行，且目标『提升亲密度』处于第 2 里程碑」）。

**终端客户（被触达者）**：
- 要「被记住」的真实感：回访要引用**具体的事**（记忆 bullets）而不是「最近怎么样」；世界事实（TA 城市的天气、TA 提过的球队）让开口理由天然成立。
- 要不被打扰：全管线合计的频次上限（单一账本）、TA 的时区、TA 的作息（user_clock 已有推断）。
- 要不穿帮：世界事实必须真数据注入（禁 LLM 编造比分/日期）；「你之前说的旅行」必须真的说过（care 捕获有 source_text 兜底）。

## 4. 目标架构：联系人计划中枢（Contact Plan Hub）

```
┌─ 战略层  goal（这个客户我要什么）           ← 坐席建目标 / auto_create
│    └─ 每日拍 goal_actions（今天做什么、多用力、要不要 hold）
├─ 时机层  「什么时刻开口最自然」＝四种锚
│    ├─ 时间锚  care 约定（客户说过的事到点）      ← 现有
│    ├─ 日历锚  ritual / milestone（晨晚/节日/纪念日）← 现有
│    ├─ 沉默锚  proactive_topic（多久没聊）        ← 现有
│    └─ 事件锚  world feed（TA 城市暴雨/球队赢球/…）← P2 新增
├─ 生成层  build_touch_prompt 统一装配
│    人设口吻 + episodic 记忆 + goal 块(今日意图/推进纪律) + 世界事实 + 负样本(👎/最近已发)
├─ 调度层  统一打扰预算（outreach_log 单一账本）
│    优先级：危机 > 约定 > 纪念日 > 目标推进 > 沉默问候 > 画像采集
│    共用：安静时段(用户时区) / 未回退避 / 变体守卫 / opt-out / 每日上限
├─ 出口    单一 outbox + 来源标注（坐席可解释每一条）
└─ 反馈层  回复率 by 来源 / goal 推进归因 / 👎黑名单 → 反哺时机与文案
```

核心论点：**care 不是一个独立功能，是「计划的时机引擎」；goal 不是一块看板，是「触达的方向盘」。** 六条管线不必合并成一个引擎，但必须共享同一个方向盘（goal 上下文）、同一本账（打扰预算）、同一个出口叙事（来源标注）。

## 5. 按优先级排序的实施方案

### P0 —— 把「看到的=发出的」修直 + 最小打通（本周；配置为主、小改为辅）

## 6. 刻意不做（与做什么同等重要）

1. **不推倒六管线重写成单一大引擎**。现有退避/变体/预算/观测机制成熟且有数百门禁钉住；收敛「账本、方向盘、出口」三个共享点即可，管线各自的触发逻辑保留。
2. **不做无兴趣路由的全员新闻/赛事推送**。骚扰感是品类第一留存杀手（§2 调研）；没有画像证据的客户宁可不发。
3. **不动 A/B 线被动回复的 goal 注入**。它已在工作，本方案只补主动侧。
4. **不在影子数据不达标时强开 LLM 捕获**。切主判据（正确率 ≥80%、样本 ≥20）既定，尊重它——先跑 `care_shadow_report` 看数。
5. **不做高频实时行情推送**（websocket 盯盘类）。TTL 快照 + 事件检测足够，高频轮询的成本与账号风控风险不对称。
6. **不马上把接入层 MCP 化**。MCP 是行业外呈形态（§2），我们按「provider 可平移为 MCP tool」的形状设计接口，但先内置跑通——避免为架构而架构。
7. **不新建第二套「补一条关怀」类人工入口**。现有 `/api/care/schedule` 手动排期保留为唯一人工写入口。
