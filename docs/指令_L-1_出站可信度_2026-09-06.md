## 2. A —— 拆条止血（#210，P1）

**现象**：skuio 机 `inbox.reply_style.bubbles.enabled=true / per_sentence=true / max_parts=2`（`tmp_diag\88MP86\config\config.local.yaml` L15–23），Sceya 00:39 回复被拆两条、条间 6–15s；客户随即指出「TG 和 WA 打字方式差别很大」。

**根因落点**：
- `src/inbox/reply_split.py` `parse_bubbles_cfg`（L215–244）：`per_sentence` 开 → 逐句成条；`min_total_chars=24` 太低，两句英文短回复也拆。
- `src/inbox/reply_pacing_settings.py` L257–300：bubbles 字段默认与 `parse_bubbles_cfg` 缺省需一致（门禁钉住）。
- 谁把他机器上的 `enabled` 打开了无记录——`reply_settings.html` 保存不落审计。

**修法**：
1. 默认值：`enabled` 保持 False（出厂关）；**`per_sentence` 默认 False**；新增 `explicit_newline_only=True`（只在草稿含显式空行/换行时才拆，算法切句只当兜底且默认关）；`min_total_chars` 抬到 80（CJK 计权后英文 ≈ 320 字符），短回复永不拆。`reply_pacing_settings.FIELDS` 同步默认 + 门禁测试更新。
2. 跨平台一致：同一人设的 bubbles / pacing 以人设为键（已有 `按人设覆写节奏` 表），平台覆写只允许调**延迟**不允许改**条数**（`max_parts` 不进平台覆写）。
3. `reply_settings.html` 「消息分条节奏」卡：开关旁加一句风险提示「拆条会形成固定节奏，客户可能据此识别 AI；建议关闭」；保存落 `audit_store.log("reply_settings_save", diff)`（谁/何时改了什么）。
4. **存量热修**：给 `config_manager` 加一次性迁移——若 `bubbles.per_sentence=true` 且用户未显式写 `explicit_newline_only`，迁移为关（写日志「拆条已按 1.0.75 默认收紧」）。skuio 机不用等他手动关。

**验收**：`tests/test_reply_split.py` 增例：两句英文 60 字符不拆、显式空行拆、`per_sentence` 默认 False；skuio 机装 1.0.75 后 Sceya 会话新出站单条。

## 3. B —— 工作台按实际发出条数显示（#210 后半）

**现象**：手机 2 条、工作台 1 条；`_send_bubbles`（`unified_inbox_send_routes.py` L505–580）逐条发送但镜像只记原稿一行。

**修法**：`_send_bubbles` 成功后按实际 parts 落镜像行（每条独立 `platform_msg_id`，`source.bubble_group_id` 关联），或至少在原稿行 `source.bubbles_sent=N` 并在气泡右下角显示「已拆 N 条发出」。前者更真；如 `store.py` 禁改导致落多行困难，走后者（`unified_inbox.html` 渲染层读 `source.bubbles_sent`）。自动链（`autosend_helpers.py` L1903–1944）同口径。

**验收**：拆条发送后工作台条数 == 手机条数，或气泡有「已拆 N 条」标。

## 4. C —— 问候不编事实 + greeting 分类收紧（#208，P2）

**现象**：steven→cinderella 15:03 greeting → 15:04 「Just got back from a walk, the rain's light here」；档案无雨、无天气源、KB 跳过、记忆 0 条（FTK6S7 全链）；编造进 `_conversation_history` 后被当事实反复提。同号「I want to buy vitamins」「Send me the receipt」也标 greeting。

**根因落点**：`src/skills/skill_manager.py` `GreetingSkill`（注册 L678 / L695；L2036 强制走 AI「避免复读机」）——prompt 要求「自然带一句今日近况」，模型无来源即编；意图分类 L174 把 `greeting/small_talk/direct_chat` 一锅端。

**修法**：
1. `GreetingSkill` prompt 硬约束：「不得编造天气、地点、行程、正在做的事；只能引用人设档案写明的日常或本会话/记忆里客户说过的事；没有就只问候不叙事」。
2. 与 J-1 A 的 `media_promise_guard` / B 的 `persona_guard.service_frame` 同层加 **`fabrication_guard`**：出站含天气/地点/行程类陈述（词表 + 简单模式）且来源不在（档案 / 记忆 / 本会话入站）→ 重写为无陈述版本；命中落 `[fabrication_guard]` INFO。
3. 已发出的编造不得当事实：`_conversation_history` 注入时对本方历史句带 `origin=ai` 标，prompt 说明「你之前说的近况不是事实，不要延续」。
4. 分类收紧：含交易/收据/购买/媒体请求关键词 → 不走 greeting（复用 `greeting_lexicon.is_greeting_message` 的否定表）。

**验收**：`tests/test_greeting_no_fabrication.py`：档案无天气 → 问候输出不含 rain/sunny/walk 类；「Send me the receipt」分类 ≠ greeting。

## 5. D —— 无响应文案与双提示合一（#194，P2）

**现象**：发视频无响应时附件条「后台刚重启，结果未知…」+ 右下 toast「后台重启中，媒体发送结果未知…」同时出现；后台并没在重启。

**修法**：`_doSendMedia`（`unified_inbox.html`，J-4 C 改过的 `res==null` 分支）：① 只留一处提示——附件条内联状态，toast 不再重复；② 文案按真相分两句：`__wsRestartCool` 真在重启冷却 → 「后台重启中，结果未知」；否则 → 「没拿到发送结果（可能是网络或文件较大超时），已自动核对，确认没发出再重试」；i18n 新键 `inbox.media.send_result_unknown` zh/en；`sticker-panel.js` 同口径。

**验收**：`tests/test_media_send_unknown_toast.py` 增例：无响应且非重启窗 → 文案不含「重启」；只出现一处提示。
