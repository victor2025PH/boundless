## 四之二、173 深挖：那 29.9 GB 里有一半在为不存在的并发预留

第一版盘点把 173 记成「一张 5090 只跑一个模型、利用率 0%」，当时看不出还能不能挖。
进 WSL 拿到启动参数后，结论变了——**它是全集群可释放空间最大的一台**。

### 实测到的真实配置

```
/root/vllmenv/bin/python -m vllm.entrypoints.openai.api_server
  --model /root/models/qwen36-27b-abl-awq  --served-model-name chatx
  --max-model-len 24576  --gpu-memory-utilization 0.93  --max-num-seqs 32
```

部署形态：**Windows 主机 + WSL2 Ubuntu-24.04**（所以 Windows 侧 `nvidia-smi --query-compute-apps`
看不到它的进程名，只看得到显存被占——第一版盘点在这里差点误判）。

### 账怎么算

- `--gpu-memory-utilization 0.93` ⇒ vLLM 向显卡要走 32607 × 0.93 = **30324 MiB**（实测 29937，吻合）
- 27B AWQ 4bit 权重 + 激活 ≈ **15–16 GB**
- ⇒ **剩下约 14–15 GB 全部是 KV cache 池**，而它是按 `--max-num-seqs 32`（32 路并发）
  × 24K 上下文的规模预留的

**但 173 的角色是「云端挂了才用」的兜底**：GPU 利用率实测 **0%**，热态单次推理 **224 ms**。
为一个平时零流量、真用起来也就 2–4 路并发的兜底模型，预留 32 路满长 KV——
**这是全集群最大的一块空转显存**。

### 可释放量

把 `--gpu-memory-utilization` 降到 **0.65**、`--max-num-seqs` 降到 **8**：

| 项 | 现在 | 调整后 |
|---|---|---|
| vLLM 总占用 | 30.3 GB | ~21.2 GB |
| 权重 | ~15.5 GB | ~15.5 GB（不变） |
| KV cache 池 | ~14.8 GB | ~5.7 GB（够 1 路满长 24K 或 4–6 路常规会话） |
| **释放** | — | **约 9 GB** |

兜底能力**实质不变**（并发从 32 降到 8，而实际并发从来没超过个位数），
换来一张 5090 上多出 9 GB 可用空间。

### 上机执行后的实况修正（2026-08-28 23:00–23:15，**上面那笔「释放 9 GB」不成立**）

真去动它才发现，173 的显存账里有一项上面完全没算：**Windows 桌面自己常驻占 8029 MiB**
（`nvidia-smi --query-compute-apps` 全是 `[N/A]`：dwm / explorer / WindowsTerminal /
SearchHost / ShellHost / CrossDeviceResume）。这台机器同时是坐席机（有 `ChatXFirstRunView`
/ `ChatXFix173` 计划任务），会话不能注销去抢那 8 GB。

于是真实可用空间只有 **23.6 GB**，而配置要 0.93 × 31.84 = **29.6 GB**：

- vLLM 在 **20:57 停掉**（原因未查明，日志尾部是正常 HTTP 请求、无 traceback）；
- 一停，桌面立刻把释放出来的显存扩张吃掉（Windows 桌面会用尽可用显存）；
- 此后 `Restart=on-failure` 每 20 秒重试一次，**每次都因显存不足必败**，且每轮先白等
  240 秒 `ExecStartPre`（`vllm_drain_wait.sh` 等显存降到 3000 MiB 以下——这台机器
  永远等不到）。**服务从 20:57 到 23:10 整整 2 小时不可用**，LAN 翻译兜底期间为零。

**⇒ 「降 KV 腾 9 GB 给 ComfyUI」这条路被桌面占用堵死**：即使降到 0.70，
vLLM 21.6 GB + 桌面 8.0 GB = 29.6 GB / 31.84 GB，**只剩 2.5 GB**，装不下 ComfyUI
（SDXL/FLUX 推理要 8–10 GB）。出图零备胎的解法**不在 173**，得另找（见文末修订）。

### 已落地的修复（可逆）

drop-in `/etc/systemd/system/vllm.service.d/99-vram-fit.conf`：`utilization 0.93 → 0.70`
（21.6 GB，装得进 23.6 GB 空闲）；`max-model-len 24576` / `max-num-seqs 32` **均未动**
（保持业务契约不变）。`vllm_drain_wait.sh` 阈值 `3000 → 12000`（承认桌面那 8 GB 是常驻的，
否则每次启动白等 4 分钟）。桌面显存被回收后删掉该 drop-in 即恢复 0.93。

验证：`/v1/models` 外部可达（`model=chatx max_len=24576`）、真实翻译请求
`finish=stop` 译文正确、真探针 `translate OK 0.4s` 内容断言通过、GPU 29626 MiB（符合预期）。

### 这台机器的存活机制：`VLLM_Keepalive`（**曾被禁用两周**）

`vllm.service` 单靠 systemd **活不下来**，因为 **WSL2 的 VM 在最后一个 wsl.exe 客户端退出后
会空闲回收**，回收时 systemd 干净地停掉所有服务。维持它的是 Windows 计划任务
`VLLM_Keepalive` → `C:\models\vllm_keepalive.ps1`，做四件事：

1. `Start-Process wsl.exe -- sleep infinity`：**pin 住 VM**（这是核心，没有它一切白费）；
2. `systemctl start vllm`；
3. `netsh interface portproxy add 8001 → <WSL IP>:8001`：**外部访问 8001 全靠这条转发**；
4. 每分钟健康探测 + 服务重启检测 + **一次 JIT warmup**（vLLM 0.27 首次长生成要编译 kernel，
   冷 7 tok/s vs 热 56–60 tok/s）。

该任务**处于「已禁用」状态，日志最后一条是 08-14 23:36**。vLLM 之后两周还活着，
是靠那次留下的 pin 会话残留；今晚一断就再没有任何机制拉它回来。已重新启用并运行，
23:09:44 pin + portproxy、23:10:48 health recovered、23:10:52 warmup 4.1s，闭环完整。
**「服务 enabled 而它的存活前提被 disabled」这个组合本身就是坏的**，怀疑是临时禁用后忘了恢复。

### 我在这轮里犯的三个错（都属于会重复踩的类型）

1. **读错了配置文件就断言文档全错**。`/root/start_vllm_nohup.sh`（qwen2.5 / 8192 /
   0.9）是 **08-15 换模型时就废弃的手动应急脚本**，真正生效的是 `vllm.service`
   （qwen3.6-27B / 24576 / 0.93 / max-num-seqs 32）——**与本文档原记录完全一致**。
   我据旧脚本宣布「权重 18.56 GB、KV 9.72 GB、文档算式全错」，还照它启动了**错误的模型**
   （幸好显存不足而失败）。**教训：systemd 托管的服务，唯一事实源是 `systemctl cat`，
   不是同目录下看起来像启动脚本的那个文件。**
2. **`wsl --shutdown` 打断了 GPU 直通**。为「回收残留显存」执行它，结果显存一分未减
   （那 8 GB 本就是 Windows 桌面的），却让 WSL 的 GPU 接口进入不稳定态
   （`dmesg`: `misc dxg: dxgkio_query_adapter_info: Ioctl failed: -22`），紧接着的启动
   因此失败。`vllm_drain_wait.sh` 的注释早就写明了这个坑（"WDDM/WSL defers freeing;
   starting too early re-poisons KV-cache profiling"）——**注释在文件里，我读了却没当真**。
3. **把自己制造的现象当成外部事件**。我看到 `vllm_drain_wait` 在跑，判断「有另一条 agent 线
   在动 173」并据此上报。真相是：**我每次 ssh 连上都会冷启 WSL VM → systemd 自动拉起
   vllm → drain_wait 开始跑 → 我的 ssh 命令一结束，VM 空闲回收就 SIGTERM 掉它**
   （日志里一排 `Control process exited, code=killed, status=15/TERM`）。那个「2 小时循环」
   的每一轮，都是被我的查询触发又被我的断连掐死的。**教训：在 WSL 机器上，"我只是看一眼"
   不是只读操作——每次连接都在启停整个 VM。**

## 四之三、实施中挖出的两个「配置说的不是真的」陷阱（**通用教训，不止本次**）

执行 198 那一步时连撞两个陷阱，都属于「按配置文件推断行为」会推错的类型，值得单独记。

### 陷阱一：Ollama 的 GUI 设置库覆盖环境变量

198 的 `HKCU\Environment` 写着 `OLLAMA_CONTEXT_LENGTH=8192`，`ollama_serve.bat` 里写着别的值，
而**实际在跑的 server 用的是 262144**。真值只在一个地方看得到——
`%LOCALAPPDATA%\Ollama\server.log` 的 `"server config"` 行：

```
OLLAMA_MODELS:D:\models  OLLAMA_CONTEXT_LENGTH:262144  OLLAMA_KEEP_ALIVE:2562047h47m16s
```

来源是 Ollama 0.33 的 GUI 设置库 `%LOCALAPPDATA%\Ollama\db.sqlite`，它**优先于环境变量**。
顺带这一行还揭穿了模型目录：bat 写 `D:\ollama_models`（旧遗留库，只有 qwen3:4b/8b），
实跑的是 `D:\models`（MyVisionQwen 与 qwen3-vl 都在那儿）。

⇒ **查 Ollama 的真实配置，只认 `server.log` 的 `server config` 行**，不要看注册表/bat/文档。

### 陷阱二：`/v1` 兼容层不用服务端 `CONTEXT_LENGTH`，用模型自带的原生上下文

这一条更隐蔽，也是本次卡住最久的地方。同一台机、同一个模型、同一时刻：

| 调用口 | 加载后 size | 冷载+识图 |
|---|---|---|
| `/api/generate`（原生口） | **5.13 GB** ← 用服务端 `CONTEXT_LENGTH=4096` | 5.2s |
| `/v1/chat/completions`（OpenAI 兼容口） | **26.59 GB** ← 用模型 Modelfile 的 262144 | 36.8s |

而我方识图的单图路径**正是走 `/v1`**（`vision_client` 注释写明「/v1 兼容层不认 options.num_ctx」）。
所以「把服务端 ctx 调小」这个方案对识图**根本无效**——它只影响原生口。

一度以为是 SYSTEM 身份的问题（SYSTEM 下确实还有另一套 profile：
`C:\WINDOWS\system32\config\systemprofile\.ollama\`，日志有 `Couldn't find ...id_ed25519` 为证），
换回用户身份后仍是 26.59 GB，才定位到是**调用口差异**而非身份差异。

**解法：把 `num_ctx` 钉进模型定义本身**，这样无论走哪个口都一致：

```
FROM qwen3-vl:8b-instruct
PARAMETER num_ctx 4096
```
```cmd
ollama create qwen3-vl:8b-instruct -f qwen3vl_4k.Modelfile   :: 覆盖同名，复用已有 blob
```

**效果**：`/v1` 加载 size 26.59 GB → **5.13 GB**，冷载 36.8s → 15.1s，热态 **0.11–0.30s**。
且模型名不变 ⇒ **生产配置一行都不用改**。

### 6.4 执行中发现的机制根源：`OLLAMA_KEEP_ALIVE=-1`（**推翻本文档此前的归因**）

撤 198 的钉之后模型 **2 分钟就回来了**，查服务端配置才找到真因：

```
198:  OLLAMA_KEEP_ALIVE=-1   OLLAMA_CONTEXT_LENGTH=8192   OLLAMA_KV_CACHE_TYPE=q8_0
140:  OLLAMA_KEEP_ALIVE=-1   OLLAMA_CONTEXT_LENGTH=4096   OLLAMA_KV_CACHE_TYPE=q8_0
```

**① `KEEP_ALIVE=-1` ⇒ 显存只增不减。** 任何模型**被调用过一次就永久驻留、永不释放**。
所以「撤钉」根本不是解法——本机随便一次调用即可让它回来。
今天 140 的 `hy-mt2`（18:05 撤、40 分钟后回）和 198 的 `qwen3:8b`（19:28 撤、19:30 回）
是同一个机制。

> **更正**：此前 4.2 节与给中枢的补充 F 把这归因为「中枢 keepwarm 主动恢复」，**那个说法是错的**。
> 不是有人去拉，是服务端配置让模型永远不卸。

**② 各机 `CONTEXT_LENGTH` 不一致 ⇒ 同模型显存占用差 5 倍。**
`qwen3-vl:8b-instruct` 在 140（ctx 4096）是 **5.55 GB**，在 198（ctx 8192 + q8_0 KV）
实测加载后报 **26.59 GB**，12 GB 的 4070 直接溢出到 CPU，首答 23.6 秒。

#### ⇒ 比本文档全部方案都更根本的一条建议

**把各机 `OLLAMA_KEEP_ALIVE` 从 `-1` 改成有限值（如 `30m`），只对真正需要常驻的模型显式打钉。**

一个环境变量，可能解决大半显存问题：不用的模型 30 分钟后自动让位，
热路径上的模型因持续被调用永远不会被卸。配套把各机 `OLLAMA_CONTEXT_LENGTH` 对齐（识图/翻译 4096 足够）。

**这条应该排在第五章所有方案之前**——在 `KEEP_ALIVE=-1` 还生效的前提下，
撤任何钉都只是争取几十分钟。

第 2 条的「停 keepwarm」是硬要求：老板 18:05 授权撤 140 的 hy-mt2 后空闲回到 4791 MiB、
ASR 备胎当场复活，但 **40 分钟后它又被自动钉回来、空闲掉回 400 MiB**。
不停 keepwarm，这一步做多少次都会被还原。
