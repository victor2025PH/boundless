## 3. E3 —— AI 说起其他人设推荐的产品并贬低（#145③）

报障人的定性是「AI 犯了很大的错误」。这是**跨人设串味**：A 人设的产品 / 话术
出现在 B 人设的回复里，而且还贬低了 —— 对客户来说这是「换人了」级别的破绽。

### 查两处

1. `src/companion/goals/site_catalog.py` / `offers.py` 的目录解析**是否按当前会话人设过滤**
2. prompt 注入链**是否把全局目录整份喂进去**（大概率是这个）

### 修（两层，都要）

- **注入层**：产品 / 报价类注入**必须按会话生效人设过滤**，非本人设的产品**一条都不进 prompt**。
  没进 prompt 的东西 LLM 编不出来 —— 这是根治。
- **出站守卫**：加一条守卫，AI 稿里提到「未绑定给本人设的产品名」就拦下重写。
  与既有的 `persona_guard` 同族，**复用它的模式**（先 Grep `persona_guard` 看现有写法，
  不要另造一套守卫机制）。

两层都要的理由：注入层管住 95%，但产品名可能从对话历史里被 LLM 捡回来，
出站守卫是最后一道。

### 验收

1. 人设 A 的会话，注入块里**零 B 人设产品**
2. 金标（构造一份含他人设产品名的 AI 稿）**被拦下**

## 4. E4 —— 手机端删除消息不同步（#32② / #145⑤）

### 产品选择已明确（报障人拍过板，别再问）

> **同步删除（显得专业）；AI 可以有记忆，但不要主动提删掉的信息。**

### 现状

`src/inbox/store.py` **已有 `conversation_tombstones`** —— 基建有一半了。
但 **store.py 你不能改**：用它已有的接口，或者新建一个消费模块。

```
Select-String -Path engines/chengjie/src/inbox/store.py -Pattern "conversation_tombstones|tombstone" -Context 3,3
```

### 修

平台的删除事件 → ① 工作台移除该条；② 记忆侧**保留但标「已撤回，不得主动引用」**。

「保留但不主动引用」而不是「一起删掉」的理由：上下文会因为凭空少一条而错位
（AI 会答得莫名其妙）；而且客户删掉的信息往往正是关键信息，AI 应该"知道但装作没看见"，
这也是报障人「AI 可以有记忆」那半句的意思。

### 验收

1. 手机删一条 → 工作台该条**消失**
2. AI 后续回复**不主动提及被删内容**（给金标：被删内容是「我下周去日本」，
   之后 5 轮 AI 都不该主动提日本）
3. **上下文不因删除而错位**（AI 回复仍然接得上）

## 5. E1 —— LINE 收发图片 / 语音 / 视频仍不行（#145②，钧「验证未过」）

报障人在 #63 下明确写过「LINE 还是不能收发图片语音视频」。

### 先定层，**别靠读代码猜**

本仓有现成的真机探针：
```
python tools/probe_line_media.py            # 默认只读
python tools/probe_line_media.py --confirm  # 真发，且只发给自己
```
先跑只读版拿第一现场。涉及层：`src/integrations/line_rpa/**` 的媒体收发链
+ 平台会话健康（`platform_session_health`）。

⚠ 媒体产物验证纪律（2026-08-13 事故沉淀）：**落盘后必验 magic bytes 才许报 OK**
（WAV=`RIFF`、OGG=`OggS`、PNG=`\x89PNG`、JPEG=`0xFFD8`）。
HTTP 200 + 文件 KB 数**不构成内容验证** —— 那次事故里 18 个「.wav」全是 JSON 信封，
比真音频还大 1/3，「验证」全过。

### 验收

1. 探针四类媒体（图 / 语音 / 视频 / 贴纸）**双向各一次通过**，且产物过 magic bytes 校验
2. 失败路径有**明确红字原因**，不是静默失败
