# 发版对账 v1.0.94（2026-09-20）

一句话：**「移除旧版」整步收归新安装包，旧版自带的卸载程序不再运行**——于是「从旧版升上来」这一跳也不再弹「智聊 无法关闭」，且结果不再取决于有没有文件被杀软按住。

这是同一个症状的第四轮。前三轮（1.0.92 / 1.0.93 的 C9 / 被否掉的 C10）都写在下面，因为**中间那次失败的尝试本身就是这一版的立论依据**。

---

## 1. 为什么 1.0.93 之后还有人弹窗（1.0.93 说明里已如实预告）

弹窗有两个不同的出处，1.0.93 只关掉了第一个：

| 出处 | 触发 | 1.0.93 的处置 |
|---|---|---|
| `allowOnlyOneInstallerInstance.nsh::_CHECK_APP_RUNNING` | 关闭旧版只给约 6.3 秒，智聊按设计要 8 秒以上 | **已接管**（`customCheckAppRunning` 自己做「先请求关闭→轮询确认→强制→再确认」） |
| `installUtil.nsh::uninstallOldVersion` 的 `UninstallLoop` | 旧卸载器 `un.atomicRMDir` 改名 9429 个文件，任一失败即整树回滚 + `Abort(2)`，框架重试 5 次后 `MessageBox appCannotBeClosed` | **修在我们发出去的卸载器里（C9），只保下一跳** |

C9 住在「我们发出去的」卸载器里，而**执行本跳移除的是旧版自带的卸载器**——修复进不去那里。这就是 1.0.93 说明里那句「从 1.0.92 升到 1.0.93 的过程本身仍可能提示一次」的由来。

关键位置（`node_modules/app-builder-lib/templates/nsis/include/installUtil.nsh`）：

```nsis
UninstallLoop:
  IntOp $R5 $R5 + 1
  ${if} $R5 > 5
    MessageBox MB_RETRYCANCEL|MB_ICONEXCLAMATION "$(appCannotBeClosed)" /SD IDCANCEL IDRETRY OneMoreAttempt
    Return
  ${endIf}
```

注意它在 `handleUninstallResult` **之前**——所以我们自己的 `customUnInstallCheck` 无论怎么写都拦不到这个窗口。

---

## 2. C10（被否）：缩小暴露面不管用

思路（Devin 实现，[PR #23](https://github.com/victor2025PH/boundless/pull/23)）：旧卸载器开跑前，先由新安装包把 `$INSTDIR` 非原子清空、只留旧卸载器 exe，这样它的原子改名只剩几个文件，随机瞬时占用撞上的概率降四个数量级。

隔离测试用户里两组对照（各自从 1.0.92 起跳，锁同一个文件、锁法相同：`FileShare.Read` 打开 = 无 `SHARE_DELETE`，与杀软扫描持有方式一致）：

| 组 | 升级用的包 | exit | 耗时 | `old-uninstall-failed` | preclean |
|---|---|---|---|---|---|
| A 对照 | 1.0.93（无 C10） | 0 | 418s | **1** | — |
| B 实验 | 带 C10 | 0 | 342s | **1** | 9429 → leftovers=2 |

机制确实生效了，但没用：

```
[preclean] start INSTDIR=<INSTDIR> files=9429
[preclean] sweep done, top-level entries left: 1
[preclean] done leftovers=2
  left LOCKED <INSTDIR>\resources\services\messenger-web\node_modules\playwright-core\...\privacy-sandbox-attestations.dat
[2026-09-20T19:41:06] old-uninstall-failed
```

**被锁的那一个文件，预清空同样删不掉**——它作为残留留在原地，旧卸载器照样撞上、照样回滚、照样 `Abort`。缩小候选集只对「随机扫到」有概率收益，对现场真实症状「某个文件在升级期间一直被按住」为零收益。

沉淀：**这类「降低概率」的修法，验收必须用确定性场景（把那个文件按住），否则拿 9429→2 的漂亮数字就能骗过自己。**

## 3. C11（本版）：让框架压根不运行旧卸载器

同一份模板里有条确定性的早退路径：

```nsis
!insertmacro readReg $uninstallString "$rootKey" "${UNINSTALL_REGISTRY_KEY}" UninstallString
${if} $uninstallString == ""
  ...
  ClearErrors
  Return          ; $R0 早已 Push 0 / Pop $R0 → handleUninstallResult 视为成功
${endif}
```

即**注册表里查不到旧卸载入口 → 这一步按成功跳过**，既不进那个重试循环，也不弹窗。运维侧早就在走这条路：173 那批 robocopy 旁路装出的机器没有卸载器，下次升级就是直接覆盖（见 `chatx-desktop-install.mdc`）。

所以 `customCheckAppRunning` 末尾（家族已收割、`uninstallOldVersion` 之前，仅安装器单元）做两件事，每个根键各一遍（模板自己就为 `SHELL_CONTEXT` 与 `HKEY_CURRENT_USER` 各跑一次）：

1. 按注册表 `InstallLocation` 取旧安装目录（**不是 `$INSTDIR`**，这样自选过安装目录的用户也覆盖到），非原子清扫：`Delete` / `RMDir /r`，忽略错误，删不掉的留成残留——新版本随后覆盖写进同一目录，`extractAppPackage` 的覆盖写就是为这个准备的；
2. `DeleteRegKey` 掉该根键下的卸载注册项。这正是成功卸载本该做的事（`uninstaller.nsh` 自己就 `DeleteRegKey SHELL_CONTEXT "${UNINSTALL_REGISTRY_KEY}"`），新版安装尾声会重写回来。

安全命门与边界：

- **只清「自证是我们的」目录**：必须先确认该目录下存在我们的卸载器 exe 才清。损坏/外来的 `InstallLocation`（想象 `C:\`）永不进 `RMDir /r`，这是本宏全部的安全性所在。
- **清不干净且又不是本次目标目录时保留注册项**：否则会孤立一棵旧树且再也无法卸载。
- 不碰 `--updated`（压根不跑旧卸载器，数据保全不再依赖它的判据）、不看 `%APPDATA%`、不往 `REBOOTOK`/`RunOnce` 排任何东西（新版本马上装进这个目录，排了就是删新装的）。
- **代价（已写进官网发版说明）**：移除旧版这步不可回滚。安装若在此之后失败，旧版程序文件已清空（数据与登录状态不受影响，重跑安装包即可）。模板自己的 `atomicRMDir` 成功路径也是同样后果——它把整棵树搬走。

## 4. 实弹验收

全部在隔离本地用户里跑，绝不碰本机现装的智聊。

| 验证项 | 方法 | 结果 |
|---|---|---|
| 锁文件 A/B（决定性） | 两个独立用户各从 1.0.92 起跳，锁同一文件全程不放 | A（无 C11）`old-uninstall-failed=1` / 609s；**B（C11）=0 / 283s**，且该文件全程 `LOCKED` |
| 全新安装 | 干净用户直接装 1.0.94 | exit=0，程序就位（C11 早退，无任何删除） |
| 自升级带锁 | 1.0.94 → 1.0.94，锁同一文件 | exit=0 / 279s / `old-uninstall-failed=0`（C11 + C9 同时在场） |
| 可卸载性 | 升级后跑随包卸载器 `/S` | exit=0，注册项随之消失 |
| 注册表回写（回归命门） | 1.0.92 → 1.0.94 后以该用户身份读 HKCU | 正好 1 条，`DisplayVersion=1.0.94`，`UninstallString` 指向真实存在的 exe |
| 用户数据 | 升级前在两个数据目录各放标记文件 | 2/2 存活（A/B 两组都是） |
| 发布产物本身 | 对最终 `ChatX-Setup-1.0.94.exe` 再跑一次锁文件升级 | 见「产物核对」 |
| 静态门禁 | `node test/uninstall-nsh-invariants.test.js` | 399 断言通过 |

耗时 609s → 283s 的 326 秒差额，就是旧卸载器 5 轮原子改名 + 回滚烧掉的时间。

探针（`%TEMP%\cxprobe\`）：`probe_c10ab.ps1`（两组对照）、`probe_c11_reg2.ps1`（注册表回写）、`probe_c11_reg.ps1`（全新装/自升级/可卸载）、`smoke_1094.ps1`（产物冒烟）。

> 探针踩过的坑：`Start-Process -Credential -RedirectStandardOutput` 读 `reg query` 输出会被截断（`reg2` 那轮因此误报 `BROKEN`，连全新安装都误报，而全新安装 C11 根本没执行删除——这正是它是探针 bug 而不是产品 bug 的判据）。改成让测试用户自己跑 PowerShell 落盘后为真。

## 6. 沉淀

1. **「降低概率」的修法要用确定性场景验收。** C10 把 9429 缩到 2，数字很漂亮，实测收益为零——因为现场症状不是随机碰撞。
2. **弹窗有多个出处，先定位是哪一个再动手。** 同一句「智聊 无法关闭」在 1.0.92、1.0.93、1.0.94 三轮里分别来自库存检查、`UninstallLoop`、以及（本版之后）不再出现；看它在进度条的哪个位置弹就能分辨。
3. **别只在自己的代码里找修法，先读框架模板的早退路径。** `uninstallOldVersion` 的 `$uninstallString == "" → Return` 两轮前就在那儿摆着。
4. **动注册表要连带验「反面」**：删了卸载入口，就必须验证新装回写、且机器仍可卸载，否则会发出「装上却卸不掉」的机器。
