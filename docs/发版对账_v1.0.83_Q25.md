## §〇 先答一问：Y39D8U 的「AI work」是怎么进画像的？

工单 Y39D8U（`tmp_diag/Y39D8U/…report.md`，Telegram 7543790794 Enrique）：AI 自己问「inspection work 做多久」，客户只答「Not so long dear been a couple months.」，右栏职业=「AI work」来源=AI 推断。日志窗（20:32–22:02）里该会话每轮 `[extract] … facts=0 slots=0 llm=0/1`、**没有** `[profile] … slot=occupation` 写入行，`[goal-inject] state=…occupation:mentioned…` 从 21:18 起已是 mentioned——写入发生在日志窗之前，且不是走 Q-19 的 `profile_fill.apply` 三闸。三条线索对应指令要核的三点：

1. **锚定用了 token 部分匹配**：目标引擎旧 LLM 回填轨 `profile_llm.run_llm_capture`（`goals/service.py` L1972 `schedule_llm_capture` 触发）只过 `ground_extracted` = `memory_grounding.fact_grounded_in_user_msg`（任一内容 token 重叠即接地）——值 `AI work` 的 `{ai, work}` 只要 `work` 撞上客户历史里任何一个 `work` 就过；Q-19 只给它补了 `slot_validate`（形态），没补锚定。
2. **「AI 问 → 客户答」被当回填**：`profile_slots.slot_state` 的 `mentioned:answered`（我方问过该槽 + 客户接了 ≥2 字）让「couple months」把 occupation 标成 mentioned（无值）——这本身正确（只标线索），但卡片把「无值 mentioned」渲染成「已提及（未确认）」+ 可点确认，坐席看到的就是「已提取未确认」。
3. **AI 问句实体成候选**：旧轨提示词只给客户当条消息，但接地判据对「值里含 AI 问句里的词」零抵抗——只要客户任何一条历史消息含 `work`，`AI work` / `inspection work` 都能过。

**修法**：抽一道共享 `src/companion/fact_gate.check(value, slot_or_kind=, evidence=, inbound_texts=, customer_lang=)`——类型尺子（复用 `slot_validate`）+ 来源守卫（只认 `direction=in`）+ 原句锚定（evidence 逐字在**同一条**客户入站）+ **值每个核心 token 整词在 evidence 里**（禁部分匹配）+ 语种守卫 + `kind=fact` 主体守卫；画像 `profile_fill.apply`、目标回填 `profile_llm.run_llm_capture`、记忆 `episodic.add_fact` 三链都从这道门过；客户只答时长 / 是 / 数字 → 不进 LLM 回填，只留 mentioned 线索；卡片「无值 mentioned」改显「AI 有线索，待补值」不可确认。

| 闸 | 规则 | 不过 → |
|---|---|---|

| 兜底 | 门自身异常 → `(False, "gate_error")`，**不放行** | `gate_error` |
