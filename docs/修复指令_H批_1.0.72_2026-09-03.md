## H1（P1）#154 会话「发→X」铆定被程序清空 → AI 整段切成对方语言直发客户

**证据**：`D:\boundless\tmp_diag\YQJMZ7\backend.log`：13:11:09 sendpoint「出站语言已按铆定修正（#106）pin=en」正常 → 14:50:35 / 14:50:45 / 14:58:15 / 14:58:24 A 线『已回复消息』直发日语（うん、ちゃんと休むよ。/ 風は任せて… / おやすみ、また明日ね🌙），14:50 后 sendpoint **零日志** = `outbound_lang_pin()` 返回空；会话 `telegram:7331682688:8852939166`。报障人确认未动语言选择器（群 mid=1140）。守卫判定逻辑本地直测正常（`pin_script_conflict(日语,'en')=True`），问题只在 pin 消失。

**根因（已定位，三处合力）**：
1. 前端 `src/web/templates/unified_inbox.html` L18805 `_loadXlateForConv`：`_xlateOut=(convEntry&&convEntry.out)||bd.out||''` —— **只从 localStorage 灌值，从不读服务端** `GET /api/unified-inbox/conv-xlate-out`。
2. 同文件 L19026 `_persistXlatePrefs` → L19041 `_syncConvXlateOutSrv`：**任何**翻译偏好变动（改「收→」、预览开关 `_onXlatePreviewToggle`、回译 `xl-back-chk`、语气段）都走它，把当前 `_xlateOut`（可能为空）POST 到服务端；去抖只看本会话期内是否已发过同值。
3. 服务端 `src/web/routes/unified_inbox_translate_routes.py` L614-646 `POST /api/unified-inbox/conv-xlate-out`：`lang=""` → `src/inbox/store.py` L4624 `set_outbound_lang` L4632-4637 **直接 DELETE 行**，无审计无日志。

合起来：只要本地没有该会话的 out（换窗口/清缓存/多账号机切号/另一台机器，或 `bd.out` 全局默认为空），用户随手改一次「收→」或预览开关，服务端铆定就被删；反向：`bd.out='en'` 时改别的会话的「收→」会把那个会话**悄悄钉成英文**。

**修向**：
- a) 服务端：删除必须显式（body `clear:true`），空串 `lang=""` 视为 no-op 并 200 返回当前值；`set_outbound_lang` 加变更审计表 `conversation_outbound_lang_log(conversation_id, prev, new, source, ts)`，source ∈ `ui_select|ui_prefsync|api|import|clear`，每次清除打 WARNING。
- b) 前端：`_syncConvXlateOutSrv` **只**在 `_onXlateChange` 且 `#xlate-out` 真被用户改动时发送（带 source=ui_select），其他偏好变动一律不发；`_loadXlateForConv` 先 GET 服务端值 hydrate（服务端非空优先于 localStorage，并回写 localStorage 该会话项）；`bd.out` 不再作为其他会话的隐式 pin（只作 UI 预选，不同步服务端）。
- c) 兜底：`src/ai/sendpoint_guard.py` L235 `outbound_lang_pin` 为空时，按会话历史我方出站主语种（最近 N 条）保守回落，不允许因对方一条外语就整段切语言。
- d) #154 上午形态一并收：坐席侧出站译文（✎ 行）语言跟随对方最新入站漂移 → `outbound_translations` 的 target_lang 取会话「收→」设置。

**验收**：① 单元：POST `lang=""` 不删行；`clear:true` 删行且审计有 prev/new/source；② 前端：会话 A 设「发→英」→ 切到 B 改「收→」→ 回 A，服务端 A 仍 `en`，选择器显示 en；清 localStorage 重开 A 仍显示 en；③ 金标：四条日语原文在 pin=en 下全部被改写为英文（`tests/` 新增）；④ `test_sendpoint*`、`test_tg_gap_probe*` 不红。

## H3（P1）#160 全自动放行策略重定义：闸从「客户说了什么」挪到「AI 要说什么」+ 分类器修复 + 挂起可见

**证据**：包 `GRECHC`/`JTU34M` + 报障人文档 `protocol_media/telegram/6834964252_1148.md`（conv `whatsapp:447742959746:447717717796`）：19:45/19:46/20:04 三稿 L2 秒发；20:08 客户原文 `"Yes you did because I was happy chatting with you i didn't want to stop"` → `src/ai/chat_assistant_service.py` L246-249 `_detect_intent` `any(k in t for k in ("stop", ...))` 子串命中 `stop` → intent=停止联系 → `_detect_risk` L278 → `reasons=["stop_contact"]` → high → L4 → AI 稿 `"Aww, that's really sweet…"`（完全干净）被扣到 21:04。现状机制：`src/inbox/drafts.py` L1014-1020 `risk=max(quick_analyze(入站).risk, keyword_risk_level(入站))`，L1192 `risk_to_autopilot(high,*)=L4 / (medium,*)=L3` 无条件；L1211 `is_autosend_allowed` 只放 L2；`autosend_worker.py` L1544 只捞 L2；`holding_reply.py`（L3 缓冲话术，为 2744 分钟挂起事故而建）`inbox.l2_autosend.holding.enabled` **默认关**且 levels 默认只 `["L3"]`。

**A. 放行矩阵（auto_ai 会话）**——新模块 `src/inbox/autosend_policy.py`（纯函数 `decide(peer_risk, peer_reasons, reply_risk, reply_reasons, account_policy) -> (level, hold_reason)`，drafts.py 的 `auto_generate_draft`/`enrich_draft` 与 worker 都只认它）：
- 出站稿 `reply_risk=low` 且入站任意 low/medium/high-提及类 → **L2 自动发**（入站风险只作上下文信号：写进 draft `peer_risk`/`peer_reasons` 字段供卡片与日志显示，并给人设产线注入一条守卫提示「对方提到 xx，回复不得报价/不得给账号或付款信息/不得越界」）。
- **硬底线（任何模式都挂起，`hard_floor` 配置可增删，默认四条）**：
  1. `stop_contact`（真·停止联系，见 B 收紧后的判定）→ 不发任何内容（含缓冲话术）+ 会话标 `do_not_contact` + 待处理带原因；

  4. `credential_or_payment_request`（客户**索要**转账/卡号/密码/验证码/地址，模式：`(send|give|share|tell) me (your )?(bank|card|account|password|otp|address)|转(给|到)|把.*(卡号|密码|验证码|地址).*(发|给)`，与「提及」区分）→ 挂起。
