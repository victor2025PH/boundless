## 2. A —— backfill 二次观察（正文双写 + 假 verified 放大器）

### 实锤
- 工单 #166/#167/#168 正文每句出现两遍：`[skuio 花无缺] …`（实时链，reporter_name 全名）与 `[skuio] …`（回放，`first_name`）。
- app.log：`00:25:39` 实时链把钧「已经可以了，看是否可以修复，稳定一点的」判 verify_yes → #142；`00:29:24 [bug_backfill] 补登记 2 条（水位 1180→1183）` 又观察一次同一句 → `pending_verify_ticket` 取下一张 → #140 也翻 verified。`00:14:23 补登记 5 条（1171→1176）` 同秒 #138 被翻（那 5 条库内原文都不含确认词，触发文本无法复原——说明回放拿到的文本/归属可能与镜像不同，一并核）。
```
Select-String -Path D:\chengjie-instances\zhiliao\data\logs\app.log -Pattern 'bug_backfill' | Select-Object -Last 10
```
- 机制：`bug_intake_backfill.py` L183 `plan_replay(rows, last_id)` 只用自己的 `last_msg_id` 水位差集；实时链处理过的消息没有任何标记可查 → 每条都被回放一次。

### 修
1. 共享「已观察 mid 集」：实时链 `observe_group_message`（或 `trigger_verdict`）成功处理一条群消息时登记 `(chat_id, msg_id)`——`note_group_msg_seq`（序号哨兵）已在收 mid，复用它的存储加一个 `seen` 语义（进程内 + 落 `bug_intake_backfill.state.json` 同目录，重启不丢）；backfill 回放前 `if seen(chat_id, mid): continue`。
2. `observe_group_message` 增可选参数 `msg_id`，实时链与回放链都传（telegram_client 调用点在他线文件里——**回放链在你文件内先传**；实时链的 msg_id 透传若需改 `telegram_client.py`，写进结束报告交值守，先用「同 reporter + 同文本 + 60s 内」作近似去重兜底）。
3. 回放链 `reporter_name` 取 `first_name` 与实时链取全名不一致 → 统一（回放取 `first_name + last_name`）。

### 验收
- 单测：同一条消息实时观察后再回放 → 不产生第二条事件/正文；verify_yes 不重复触发。
- 门禁 `tests/test_bug_intake_backfill*.py` 绿。

## 3. B —— verify 归属（决策 D5）

### 实锤
`detect_verify_intent`（`bug_intake.py` L287）子串命中「可以了」→ `pending_verify_ticket`（L678）取该报障人最新一张 fixed+notified 单。钧那句说的是 WhatsApp 登录，却翻了总闸单 #142；同一报障人回访后有几十张单同时待验时，任何一句「还是不行」打到 id 最大那张（I-6 结论 B）。

### 修
1. 命中确认/否认词 **且** 文中有 `#N`（N 属该报障人 fixed+notified 集）→ 归属 N；
2. 无 `#N` 时，只有当这条消息是**对支持号回访消息的回复**（`reply_to` 指向 notify_msg_id）才归属该单；
3. 其余情况不翻状态，只记 `verify_ambiguous` 事件（值守可见）。短句「可以了/好了」在群闲聊里出现概率太高，不能再单独触发。
4. `pending_verify_ticket` 保留但改名语义 `candidate_verify_tickets`（返回列表供值守面板挑选）。

### 验收
- 单测：「#142 好了」→ #142 verified；「已经可以了」无 #N 无 reply_to → 不翻，记 ambiguous；reply_to 回访消息 → 归属该单。

## 4. C —— 限频只管回复不管登记（决策 D4）

### 实锤
`trigger_verdict` L1111：`_rate_ok(u:<chat>:<user>, max_replies_per_user_hour=4)` 不过 → `_note_capped_report`（只记 `rate_capped_report` 事件，**不立单**）→ return False。且 `observe_group_message` L1208 对**每条**消息 `_rate_mark`，闲聊也计数。当夜 skuio 22:55 / 00:58 / 01:11 三条真报障被拍扁。AI 在报障群 08-21 起全静默（`ai_silent`），限频现在只剩「丢登记」这一个效果。

### 修
- `ai_silent` 为真（或独立开关 `bug_intake.rate_limit_registration: false` 默认 false）时：限频**不影响** `observe_group_message` 的立单/补录路径，只影响「要不要回复」；`_note_capped_report` 里 `_report_like` 的消息走正常 `record_bug_ticket` / 收集窗补录。
- 保留 `rate_capped_report` 事件作观测但语义改为「已登记、未回复」。
- 防刷屏门禁（现有 test）若钉的是「超额不回复」，语义不变；若钉「超额不立单」，按新语义改测试并在 commit 里说明。

### 验收
- 单测：同一用户一小时第 5-8 条报障 → 全部立单/补录；bot 不回复（ai_silent）。
