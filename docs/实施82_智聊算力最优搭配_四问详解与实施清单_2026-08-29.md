## 问一：换 TTS 引擎会不会「降智」？

### 结论：不会。TTS 完全不参与内容生成。

智聊的语音链是**三段分离**的，文字在进 TTS 之前就已经定稿：

```
① 内容生成    云端 DeepSeek 主链（老板锁 cloud）→ 决定「说什么」
                     ↓ 文字定稿
② 口语化改写  173:8001 vLLM chatx（qwen3.6-27B）→ 书面语改口语（不改语义）
                     ↓ 口语稿定稿
③ 语音合成    IndexTTS / CosyVoice / Fish → 只决定「怎么念出来」
```

代码上钉死了这个顺序（`src/ai/tts_pipeline.py:2328`）：

```
# 口语化必须在 hub / 本地合成之前（2026-07-24 读稿音根因）
# 旧序：hub_fish 先命中 → 直接用 rv.text 书面稿 → IndexTTS「念稿感」。
# 新序：先口语化（LLM vivid / 规则档）→ hub 与 7852 共用同一口语送稿
```

**两条 TTS 路径拿到的是同一份口语稿**。换引擎影响的只有音色像不像、情绪够不够、多久能出声——**一个字都不会变**。

唯一会改文字的是第 ② 层（`avatar_voice.colloquial.mode: llm`，打 173:8001），而它已有三道枷锁（问句主导跳过 LLM 档 / 语义地板 0.84 / 校验不过 fail-closed 拒用改写稿），与选哪个 TTS 引擎正交。

### 但「换引擎」有另一个真实代价，比降智更该担心

回执 §2.2 给了一个决定性数据——**campplus 声纹克隆相似度**：

| 引擎 | 克隆相似度 | 判读 |
|---|---|---|
| Fish-Speech 1.5 | **0.37** | 灾难级漂移。本仓刻度：<0.70 warn、<0.60 critical |
| Qwen3-TTS | 0.76 | 及格 |
| CosyVoice3（140:7852） | 0.78–0.86（本仓 8 样本实测） | 良好 |
| IndexTTS-2 | 音色天花板，且**情感与音色解耦** | 最优 |

**所以「对话改 Fish」这条建议不能照搬。** 回执是从**延迟**角度给的（Fish 首块 200–300ms vs IndexTTS 8–10s），但对智聊，人设声音是核心资产：0.37 的相似度意味着客户听到的**不是同一个人**，这比慢几秒严重得多。

### 三引擎对智聊的真实定位

| | IndexTTS-2（现主力） | CosyVoice3（现回落） | Fish-Speech |
|---|---|---|---|
| 真身 | 176:7865（经 Hub 9000） | 140:7852 直连 | 176:7855 |
| 音色相似 | 最高 | 0.78–0.86 | **0.37 ✗** |
| 情绪 | **8 维向量，情感不吃音色税** | emotion/instruct 标签 | instruct |
| 延迟 | 8–10s/轮 | 中等 | 200–300ms 首块 |
| 许可 | 商用需授权 | **Apache-2.0** | CC-BY-NC-SA（不能公开卖） |
| 智聊定位 | **人设语音主力** | **快速回落 + 方言 instruct** | **不适合做人设声音** |

**注意许可**：Fish 是 CC-BY-NC-SA，对外卖的产品不能用；CosyVoice 是 Apache-2.0 可商用。这一条单独就足以否掉 Fish 进人设语音链。

### 现有配置其实已经是对的

```yaml
hub_fish: {enabled: true, base_url: 176:9000, tts_engine: index_tts}   # 主
base_url: http://192.168.0.140:7852                                     # 回落
voice_consistency: strict                                               # 音色事实源锁定
policy.no_edge_fallback: true                                           # 宁缺毋滥
```

`tts_pipeline.py:2511` —— **hub IndexTTS-2 优先，失败贯穿回落本地 CosyVoice3**。这正是「音色优先 + 有快速回落」的组合。

**唯一值得动的是按场景分流**（可选，非必须）：首包敏感的短对话走 140 Cosy（相似度够、更快），情绪戏/长口播走 IndexTTS。但这要改代码加路由逻辑，且当前 `voice_consistency: strict` 会把「换引擎」判成音色源变更。**建议先不动**，等有真实延迟投诉再说。

## 问二：人设声音是不是本机没接？要从哪复制？

### 结论：本机接好了，而且是自给自足的。176 那套是另一种封装，不是缺的东西。

智聊的克隆声**完全本地自持**：

```yaml
# profiles_runtime.yaml（林小雨为例）
voice_profile:
  backend: avatar_clone
  reference_audio_path: config/voice_refs/lin_xiaoyu.wav
  instruct_style: 俏皮
  emotion: playful
```

`config/voice_refs/` 下 **12 个人设各有参考音 + 逐字稿 sidecar**（1.6–2.1 MB wav）：

```
warm_companion(小灵) / professional_support(小界) / lin_xiaoyu(林小雨)
chen_meiling(陈美玲) / haruko_traveler(晴子) / marcus_wei(韦明远)
zhao_laoshi(赵老师) / zhang_jingguang(张景光) / lin_jiaxin(林佳欣)
chen_mo(陈默) / mizuki(美月) / su_wan(苏婉)
另有 liu_dehua 六个版本（ref / v2-v5 / sad_ref + 11MB 原始素材）
```

合成时把参考音送给 CosyVoice3 或 Hub 做**零样本克隆**。逐字稿 sidecar 是关键——有它才能走 `inference_zero_shot` 全条件路径（保音色保韵律），没有会掉进 instruct2 导致音色漂移。

### 176 的 53 个角色库是什么关系

那是 AvatarHub 的**角色库**（脸+声+档案，SQLite `avatar_profiles.db`），其中 8 个带 `-智聊` 后缀：

```
张景光-智聊  晴子-智聊  林佳欣-智聊  林小雨-智聊
美月-智聊    赵明德-智聊  陈美玲-智聊  魏卡斯-智聊
```

**名字与本地参考音高度重合** ⇒ 大概率是同一批声音在服务端的注册副本。调用方式不同：

| | 本地方式（现用） | 176 角色库 |
|---|---|---|
| 调用 | 送参考音 wav + 逐字稿 | `POST /api/tts_only {"profile":"林小雨-智聊"}` |
| 音色管理 | 智聊自己掌控文件 | 服务端管理 |
| 换声 | 换 wav 即可，有指纹生命周期守卫 | 要在 176 侧重新注册 |
| 断链影响 | 参考音在本地，永远在 | 176 挂 = 音色源没了 |

**建议：维持本地方式为准。** 理由是资产自持——参考音在自己手里，换声、审计、迁移都不依赖别人的机器。176 角色库可作为**已注册的等价副本**（Hub 路径合成时本就用它，`_try_hub_fish` 以人设 id 作 hub 声纹档名，1:1 对应）。

**唯一要补的是对齐检查**：确认那 8 个 `-智聊` 用的参考音与本地 `voice_refs/` 是同一份。如果 176 侧是旧版本，Hub 路径和本地回落路径会发出**两种音色**——这正是 `voice_consistency: strict` 要防的事。

## 问三：aitr_asr 是什么模型，起什么作用？

### 它是我们自己 07-11 部署在 176 上的 GPU 语音服务，一个进程干两件事

```
C:\aitr_asr\asr_server.py  →  176:8765
  ├─ ASR：faster-whisper large-v3-turbo (CUDA)   热态 0.3–0.4s
  └─ SER：emotion2vec_plus_large (CUDA)          warm ~44ms
```

智聊配置里两处都指着它：

```yaml
voice_recognition:  176:8765/v1/audio/transcriptions   # 主 ASR
speech_emotion.remote.base_url: 176:8765/v1            # 主 SER
```

**它在业务里干什么**：客户发来语音消息 → ASR 转成文字喂给 LLM（否则 AI 根本不知道客户说了什么）；同时 SER 从声音里读情绪（急躁/低落/开心）→ 影响回复策略和主动关怀的抑制判断。

### 它和 140:7854 的重叠是真的，但不能整个撤

| | 176:8765 aitr_asr | 140:7854 Hub STT |
|---|---|---|
| ASR 模型 | large-v3-turbo | **完全同一个** |
| 情绪识别 | **有**（emotion2vec） | 无 |
| 归属 | 智聊自有 | 中枢 `SVC_STT` |
| 占卡 | 176 的 5090 | 140 的 4070 |

**回执点名它是 176 识图超时的贡献者之一** —— 那台机器上 11 个服务抢 CPU/IO，而 ASR 这份和 140 完全重复。

**可行的减负方案**：ASR 主路改打 140:7854（同模型同质量，本来就是我们的备点），176 只保留 SER。代价是 SER 仍要占 176 的卡（emotion2vec 没有第二个落点），收益是砍掉一份 Whisper 的显存和 IO 争抢。

**但这不是今晚该做的** —— 需要先量清楚 aitr_asr 到底占多少显存、砍掉后 176 的识图超时是否真的缓解。盲改会把一条正常工作的主链换成未验证的路径。

## 问四：198 的 Ollama 有没有冲突？

### 有，是编制与实际用途的冲突，而且智聊这边的用法是对的

| | 中枢编制（SSOT） | 我 08-28 改成的 | 谁在用 |
|---|---|---|---|
| 模型 | `qwen3:8b` 9.7 GB | `qwen3-vl:8b-instruct` 5.5 GB | — |
| 用途 | 口语化备点 | 识图备点 | — |
| 智聊引用 | **无** | **有**（`vision_backup1`） | 探针 0.4s 实测在顶班 |

**冲突点**：198 只有 12 GB，两个装不下（9.7 + 5.5 = 15.2 GB）。

**关键事实**：智聊的口语化改写打的是 **173:8001 vLLM**，配置里写得很清楚：

```yaml
colloquial.llm_endpoints:
  - base_url: http://192.168.0.173:8001/v1   # 唯一一条 LAN
    model: chatx
```

配置注释还记着 08-28 中枢执行单摘掉了 173:11434 那条互备。**所以 `qwen3:8b` 这个「口语化备点」对智聊是零引用的** —— 智聊从来不打 198 要口语化。

反过来，`qwen3-vl` 在 198 上**确实在干活**：今晚 176 的识图主点超时，198 用 0.4 秒顶上（比主点快 15 倍）。

**结论：保留 qwen3-vl，编制该改的是 SSOT 而不是这台机器。** 如果中枢有别的消费方需要 qwen3:8b，那需要另找落点——但至少不是智聊在用。
