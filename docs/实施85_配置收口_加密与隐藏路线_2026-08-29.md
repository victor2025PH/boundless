# 实施85：配置收口——后台设置化、加密与隐藏路线（2026-08-29）

> 触发：2026-08-29 07:19 老板指令（报障群实录截图）。值守把「调防轰炸额度」
> 答成了 YAML 教程（打开数据目录 config 下的 local 覆盖层、找键、加行、重启）。
> 老板三条裁决：**① 群内容不得给用户修改配置文件的方法；② 配置文件以后要做
> 加密和隐藏；③ 所需要的设置要在后台管理中进行设置。**
> 本文档＝③②的路线图与已落地部分的台账；①的机器闸门见
> `docs/实施81_…md` §3.7（support_reply_guard + duty_reply 硬拦）。

## 0. 一句话

用户永远不该知道「配置文件」的存在：能调的进后台设置页，调不了的对用户
不可见；配置文件本体对用户隐藏、敏感值加密——分四期做，P0 本批已落地。

## 1. 现状盘点（为什么用户今天能摸到配置文件）

| 面 | 现状 | 暴露 |
|---|---|---|
| 坐席/客户机（ChatX 桌面包） | 数据目录明文 `config\config.yaml`（种子）+ `config.local.yaml`（覆盖层），记事本可开可改 | **高**——支持只要一句「打开数据目录」用户就进来了（本次事故走的正是这条） |
| 壳配置 | `%APPDATA%\telegram-ai-desktop\config.json` 明文（含 `backend.spawn` 等危险开关，2026-08-15 曾被单方面翻过一次酿成双后端事故） | 高 |
| 117 生产（智聊实例） | 引擎树 + 实例数据根 overlay，多 agent 线/运维日常手改，git 可 diff | 内部面，**不在加密范围**（见 §4 边界） |
| 后台设置页 | 大部分高频旋钮已收口（回复档位/节奏/班表/额度守卫/分条…）；本批把**防轰炸额度**（companion_send_gate 七键 + 白名单）也收进 `/reply-settings` | 每收一组键，「教改文件」的借口就少一个 |

## 2. 分期路线

### P0（本批已落地，2026-08-29）

1. **companion_send_gate 全键进设置页**：`/reply-settings` 新卡
   「🚦 账号发送额度（防轰炸）」——enabled / target_cap / warmup_start_cap /
   warmup_ramp_days / block_on_red / reserve_for_manual / exempt_peers
   （白名单全表管理，与收件箱横幅「白名单此客户」按钮同一张表）。
   全键 hot（消费方逐次发送现读 config），保存即生效零重启；
   起步>目标 保存拦截；target_cap 下限 1（0=全停脚枪不进 UI）。
   门禁：`tests/test_reply_settings.py`（缺省值与闸门代码签名对拍）。
2. **对外答复机器闸门**：`src/ops/support_reply_guard.py` +
   `tools/duty_reply.py` 发送前硬拦（详见实施81 §3.7）。
3. 待办移交：`POST /api/admin/bug-intake/{id}/reply` 同款接线
   （bug-tickets 线，.ops 便签已留）。

### P1：隐藏（桌面包侧，低风险先行）

- 安装/首启把数据目录下 `config\` 打上 **hidden+system 属性**；壳与后端
  读写不受影响，资源管理器默认不可见。
- 盘点并收掉 UI 里所有「打开数据目录」类入口对 `config\` 的直达
  （日志目录可保留入口，config 不给）。
- 支持话术同步：需要现场排障时走「导出诊断包」而不是让用户开目录。
- 落点：`desktop/build/installer.nsh` 或首启引导（`ensure_seed` 一侧加
  attrib 步骤）；坐席机存量经下一次整包/热补丁的 apply 脚本补打属性。
- 风险：几乎为零（属性不改变路径与权限）；防的是「顺手好奇+被教程引导」，
  不防有意的高级用户——那是 P2/P3 的事。

### P2：敏感值加密（DPAPI，机器作用域）

- 范围：**只加密值，不加密结构**——`api_key` / `auth_token` / `token` /
  `secret` / `password` 族键的值写成 `ENC[DPAPI:<base64>]` 信封；
  `config_manager.load()` 读到信封即解密（Windows DPAPI machine scope，
  零额外密钥管理），写路径（save_overlay_patch / set_overlay_flag /
  save_channel_credentials）对白名单键自动封箱。
- 只在**打包态**启用（flavor 探测：`build-info.json` 存在才开），
  117/开发树永远明文——运维 diff、多 agent 协作、git 全依赖可读文本。
- 已知代价（写进验收）：DPAPI machine 绑定本机 → 数据目录整体拷到另一台
  机器时信封解不开——`restore_chatx_accounts` 的跨机恢复场景要么剥信封
  重录，要么接受「换机重登」。**这是选 DPAPI 的自觉代价**，比自管密钥
  （密钥放哪？又是一个明文文件）诚实。
- 风险中等：改的是 config 读写热路径，必须带「信封损坏→按缺键处理+告警」
  的软失败，绝不能让坏信封把实例启动搞死。

### P3：整文件封存（客户 flavor 终态）

- 客户包 config 整体落加密容器（结构+值），后台管理页成为**唯一**写入口；
  YAML 逃生门只在内测/坐席包保留。
- 前置：设置页覆盖率——只要还有「必须手改 YAML 才能用」的功能，封存就会
  逼出更糟的民间解法（截图教程、发压缩包替换）。先按 §3 的缺口清单收完
  再动 P3。
- 明确不承诺日期：P1/P2 数据攒够（支持工单里「让用户改文件」归零）才立项。

## 4. 边界（刻意不做）

- **117 生产实例不加密不隐藏**：多 agent 共享树的全部协作纪律（agent_probe
  / 脏树闸门 / overlay 保注释 round-trip / git diff 审计）都建立在配置可读
  可 diff 之上；对内加密＝自断观测。老板指令的对象是**用户面**。
- **不做自管密钥**：密钥文件放数据目录＝把锁和钥匙钉在同一扇门上，只有
  仪式感没有安全性；用平台能力（DPAPI）或不做。
- **不靠加密防支持自己**：支持乱教的治理靠答复闸门（实施81 §3.7）+ 设置页
  覆盖率，不靠把文件藏起来（藏起来他会教注册表）。

## 5. 验收

- P2：客户包 `config.local.yaml` 里 grep 不到任何明文 key/token；坏信封
  实例照常起（对应功能降级+告警）；117 树 grep 行为不变。
- 长期：支持工单/值守台账中「建议改配置文件」出现次数 → 0
  （support_reply_guard 拦截计数即读数）。
