## 2. A —— #172 LINE 入站视频 4 分钟就判「已过期」，重试无效

### 原话
> 「分析对方发送视频类消息为什么无法查看」（图 1170：Kevin 会话，气泡「[视频] 该视频已过期（LINE 服务器不再保留），如需查看请让客户重发」「拉取失败，点击重试」）
> Cursor 报告 MWX6QN：「180 分钟内该会话文字往来正常、00:51 手动发图 delivered=True，但入站视频拉取记录为 0……点击重试亦无后端记录」（agent 说的「重启 4 次」是把 09-03/04 的 session 行读进窗口了，09-05 只重启 1 次——**别被它带偏**）

### 证据（已核）
- 88MP86：`22:48:26` 与 `22:48:46` 两条 `[line_media] 入站媒体已过期（OBS 404，对象已被 LINE 回收，重试/回填都救不回）kind=video id=630323359523275215 acct=UIq2koGB…`。视频气泡时间 22:44。**4 分钟内 404**——不是保留期问题。
- `line_media.py` L88-89 `_OBS_SERVICE="talk"` / `_OBS_SID="m"`，L546 `api.obs.download_object(_OBS_SERVICE, _OBS_SID, msg_id)`——**图/语音/视频/文件全走同一路径**；L556 `status==404 → break` 直接判 `MISS_EXPIRED`（L569）。图片能拉说明路径对图片成立；视频未验过。
```
Select-String -Path D:\boundless\tmp_diag\88MP86\logs\app\backend.log -Pattern 'line_media' | Select-Object -First 10
rg -n "download_object|MISS_EXPIRED|_OBS_SID|def _download" engines/chengjie/src/integrations/line_media.py
```

### 修
1. **先真机定层**（最便宜，先做）：117 LINE 号从手机发一段 10 秒视频 + 一条语音 + 一张贴纸给自己 → 跑 `tools/probe_line_media.py`（先扩它支持 video/voice/sticker 入站拉取，输出每类的 HTTP 状态 + 落盘 magic）。目标是回答：视频对象是不是在 `talk/m/<id>` 之外（例如需要不同 sid、`?oid=`、预览/原件两个对象、或 okline 的 `obs.download_object` 对大对象的分块接口）。
2. **404 不再等于「已过期」**：在 `_download`/判定处加消息龄：`age < 1h` 的 404 记 `MISS_NOT_FOUND`（文案「拉取失败（服务端 404），点击重试」）并**允许重试**；只有 `age ≥ 保留期阈值`（配置，默认 24h，待真机核实 LINE 实际保留期）才标 `MISS_EXPIRED`。`expired_media_text` 只给真过期。
3. **收到即预取**：入站媒体事件到达时立即下载落盘（不等坐席点开），失败进回填队列（现有 `media-refetch` 链）；重试点击写一行 INFO（kind/id/status/age）。
4. 视频/语音真机跑通后，`docs/平台能力矩阵.md` 由 `python -m scripts.platform_matrix --out docs/平台能力矩阵.md` 重生成（**勿手改**）。

### 验收
- 真机：手机发 10s 视频 → 工作台 60s 内可播，产物过 `ftyp` 校验；语音过 `OggS`/`ID3`；贴纸有图。
- 单测：404 + age 3min → NOT_FOUND 可重试；404 + age 30h → EXPIRED。
- 落点表写清 LINE 视频对象的真实路径结论（哪怕结论是「同路径但需 X 头」）。

## 3. B —— #180 LINE 号语音发送 501「该账号不支持从收件箱发送语音（需 protocol 多开且在线）」+ 媒体按钮灰

### 原话（钧，图 1187 / 1188）
> 「文字转语音克隆成功了，不能发送」「媒体这里发不了任何东西了，图标空的」

### 证据（已核）
- 红字 = `unified_inbox_send_routes.py` L1349-1352：`orch.owns_media(platform, account_id)` False → `HTTPException(501, tr(request, "err.inbox.voice_unsupported"))`；L1117 媒体同款 `err.inbox.media_unsupported`。`owns_media`（`account_orchestrator.py` L394-400）= worker 存在 **且 `state == "running"`** 且有 `send_media`。
- 3PZ95W（钧机）：同一 LINE 账号 `09-03 12:06` `[orchestrator] send_media dispatch line:UJ3WxT2K… worker=LineProtocolWorker type=voice … delivered=True` **成功过两次** ⇒ 能力存在；00:48 那一刻 worker 不在 running。同日志 `09-03 19:55–20:02` LINE receiver 对 `line-chrome-gw.line-apps.com/api/operation/receive` **连败 6 次 → 「放弃并交编排器重启」** 循环多轮——重启期能力全灰。
- 文案「需 protocol 多开且在线」是通用措辞（`errors_stock.py` L77/L87），对 LINE 号是误导。
- 00:48 的 worker 状态要等钧机新包 `dr-mtnarhxg-o8apf7`（到 `tmp_diag/` 后 `Select-String -Pattern 'line-worker|owns_media' `）——**不要等，先修状态机与文案**。

### 修
1. 501 分因：`owns_media` False 时区分 `no_worker`（账号未托管/该平台不支持）与 `worker_not_running`（state 值），文案两套：前者「该平台账号暂不支持从工作台发送语音」，后者「{platform} 通道正在重连（{state}），稍后再试」——`errors_stock.py` 新键 zh+en（i18n 单源规则：进 pack 不进单体）。
2. 返回体带 `reason` 与 `state`，前端媒体按钮灰态 tooltip 同源（落点 `unified_inbox.html` → 写进结束报告交 J-4）。
3. LINE receiver 断连：`account_orchestrator` line-worker 段——连败即重启的循环加**退避**（当前 6 次约 2 分钟即重启，重启后又立刻连败），并在重启期把账号在线态置 `reconnecting` 而不是静默；观测计数进 `/api/workspace/metrics`（`line_receiver_restarts_total`）。**根因（为什么 gw receive 连败）单列观测，不猜修**。

### 验收
- 单测：`owns_media` False 两种原因 → 两种 501 文案；返回体含 `state`。
- 3PZ95W 里 19:55-20:02 的日志模式在新逻辑下应表现为 `reconnecting` + 退避日志。

## 4. C —— #169 LINE 发视频 >25MB 被拦

### 原话 / 证据
> 「line 发送视频超过 25mb 的视频无法发送」；Cursor AMKK5Z/WQYPPX：40 分钟零 send_media，前端预检拦；红字「文件超过该平台上限（25 MB）」。
- 上限来自 `unified_inbox_send_routes.py` L177-195 `_media_cap_mb`：`inbox.media.limits_mb.{platform}` → `.default` → **25**；LINE 未单配；前端经 `send-caps.media_max_mb` 拿同一数字。

### 修
- `_media_cap_mb` 加平台内建默认表（在 `limits_mb` 缺省时生效）：`line` 按 A 步真机实测 LineProtocolWorker 上传上限定（LINE 官方客户端视频上限 200MB；先实测 30MB / 60MB / 100MB 三档，取稳定通过的上一档），`telegram` 200、`whatsapp` 64；`default` 仍 25。红字带实际大小与差值（`inbox.media.too_large` 文案加 `{size}/{cap}` 参数，两语）。

### 验收
- 30MB 视频 LINE 发送成功且对方能播；100MB 若不通给出明确上限文案。
