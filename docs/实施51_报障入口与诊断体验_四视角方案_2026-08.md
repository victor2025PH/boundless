## 一句话诊断

不是功能缺失，是**入口埋没 + 文案误导**：诊断链路早已闭环（一键上传 → 官网收包
→ **自动推送客服 TG**），但 ①全站没有一个常驻可见入口（坐席端埋在头像下拉、
后台壳帮助球退役后只剩 Ctrl+K 暗门）；②面板文案还在教用户「把 6 位码念给客服」
——那一步**本来就是多余的**（官网收包即推送），纯粹给用户加不存在的负担。

## 四视角要点（详版分析在执行对话，此处只记结论）

- **开发**：全部地基已在（_support.html 双壳共享面板 / /api/support/diag-upload /
  官网 diag-upload 自动 notifyAdmins / check_remote_diag 远程拉取）。要做的是摆位与
  接线，不是新功能。唯一机制缺口=远程拉取时延（每小时轮询）。
- **市场**：「报障 3 分钟响应」是官网卖点，支持入口本身就是可信度展示位；内测→
  付费窗口里一次报障无门=卸载级情绪。指标：报障附包率、入口点击→上传转化、首响时长。
- **用户**：心智模型=「出问题→按一个明显的按钮→完事」。机器码/回执号全是管道细节。
  原四步流程（找暗门→上传→抄码→切群贴码）应压成一步。
- **UI/UX**：面板信息层级颠倒（关于页优先、报障藏在说明里）→ 翻转为报障优先；
  成功态是情绪峰值，回执号用验证码式排版；入口用两壳既有控件族（药丸/topbar 按钮），
  不复活悬浮球（当日刚退役）、不加首启 coachmark（首启线已实证弹层疲劳）。

## 第二阶段（同日 13:00-13:30 已实施）

1. **「已查看」回执回显——深想后砍掉**（对原 P2-1 的否决，比做出来更重要的决定）：
   核实官网收包路由后发现**诊断包在上传当刻就以文件形式 sendDocument 进客服 TG**，
   `/diag 码` 只是推送失败的兜底——正常路径根本没有「取包」动作可当已读信号；
   若改成靠客服在 TG 手点「已读」按钮，信号可靠性取决于人手纪律，**漏点时界面
   显示「未查看」反而制造焦虑，比没有更糟**。改做诚实且零依赖的替代：
2. **持久回执**（`_support.html`，热更已生效）：上次报障的回执号/时间落
   localStorage（48h TTL），重开面板即见「上次报障：回执号 X · 已送达客服 · 时间」
   ——用户关掉面板后心里没底再打开，不再是一片空白。
3. **`sup_` 埋点全链**（热更已生效，零后端改动——ui-event 端点无白名单）：
   `sup_open_<入口>`（hdr/menu/toast/banner/cmdk 分桶）+ `sup_send_ok|fail|off`。
   读数：`GET /api/admin/ui-event-trend?prefix=sup_`（zhiliao 已开 ops.ui_event_trend，
   按日落库重启不清零）。**两周后（≈09-04）按「入口点击→上传转化」裁决要不要做
   主动 nudge**——先给常驻入口一个证明自己的机会，别急着叠弹层。
4. **教育物料已成稿**（见下方附录，值守线可直接取用）。

门禁：模板 JS 语法 22 文件 0 失败 + support/i18n/emoji/哑按钮家族 110 绿。
