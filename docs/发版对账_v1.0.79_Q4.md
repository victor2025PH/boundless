## §〇 先答一问：为什么 1.0.78 把美英客户的下午关掉了？

**答：D④ `2ddbb3ec` 把 `inbox.work_schedule.enabled=true + 08:20–01:00` 升成 A 类基线，注释写着「timezone 空＝本机钟（桌面机就是运营者时区）」——这个假设在客户机上是错的，而基线机制把错误假设复制到了每一台升级机。** 三层：

1. **时区归属错**：`work_hours_gate._resolve_tz("")` 回落服务器本机钟。运营者在上海、客户在纽约 / 伦敦：上海 01:00–08:00 ＝ 纽约 13:00–20:00 / 伦敦 18:00–01:00——正是客户最活跃的下午和晚上。KYHGSZ：Mike 01:46（上海）来信、01:47 稿已生成 `risk=low`，被 worker 班表闸**静默**留 pending 到 08:00+，无一行日志（worker 扣留分支只 `total_skipped_off_hours++`）。
2. **机制放大**：`_ensure_baseline` 的三态语义（缺键才补）本身没错，但它只回答「用户表过态没有」，不回答「这个默认在客户机上对不对」。skuio 机原本**没有** work_schedule 块（§四 D④ 当时已写「落待老板知会」）→ 首启补成上海时区班表；额度闸门 `companion_send_gate` 也走种子显式 `enabled:true 300/100/3`，各号折算 114–129 条，且 `gate_decision` 对 `origin=manual` 仍比 `recommended_cap` → 人工也拦（CSTCJT「自动 ok / 人工 ok」两列）。
3. **决策层缺红线**：拆条（D-L3 `82BF95`）已经吃过一次「会改变发送行为的开关默认开」的亏并降 B，但没有沉淀成机器可判的规则，两天后班表 / 额度又以 A 类进了基线。

**修法 = 三条红线钉进 `feature_registry`（docstring + `_validate` fail-fast + 测试），班表 / 额度降 B 出厂关，存量只回滚「基线原样形态」，并给升级加回读日志。** 见下表。
