## 2. A —— 上传不阻塞本地 Web 服务 + 访问日志 + 上限同源（#227，P1）

**事实**（MKYD7D / SPRZKS / 8YNDKE）：98MB `product_mv_16x9` 前端预检过（声明 100MB），上传阶段后端零记录、renderer 15:16:35–15:17:01 与 15:20:22–15:20:50 两窗口对 `127.0.0.1:18799` 全部 `Failed to fetch`，同会话 1.4MB `.MP4` 1.4s 送达；工具箱语音也标 25MB。**结论：单个大上传把本地 Web 服务堵住 20–30s，期间所有请求（含上传本身）失败无痕。**

**修法**（D-M5）：
1. 先找到堵点：`send-media` 处理里哪一步在事件循环上同步跑（落盘 / sniff / hash / 转封装 / 平台 worker 同步等待）——用 98MB 文件本机复现，`py-spy dump` 或 `[send-media]` 分段计时日志钉住；把 CPU / IO 重活移到线程池（`run_in_threadpool`），上传改流式落盘（分块读已在 L1254，确认没有二次全量 `read()`）。
2. Web 层访问日志：路径 / 大小 / 耗时 / 状态码一行（`[http] POST send-media 98MB 23.4s 200`），被拒也落（文件名 / 大小 / 原因）。
3. 上限同源：前端预检读 `media_max_mb`（L2071 已下发）而非本地常量；**流式落地前把视频上限临时压到 50MB**（D-M5），落地并过 12 次矩阵后再放回平台表；超限提示「文件 X MB 超过上限 Y MB」。
4. 上传期间前端若 `Failed to fetch` → 附件条显「后台暂时无响应，正在自动重试」，不再是「结果未知」。

## 3. B —— .MOV 选文件即判（#229 #231，P1）

**事实**（DR2QWV / GAJ5T2）：5MB `IMG_7312.MOV` 在 LINE / WhatsApp / Messenger 三处点发送均「结果未知」，后端零 `[send-media]` request、renderer 零 fetch 错误——请求未离开前端；成功的视频全是 `.MP4`。后端 `_OUT_VIDEO_EXT` 其实含 `.mov`，拦的是前端（MIME `video/quicktime` 或 `send-caps` 白名单）。

**修法**（D-M4）：找到前端拦截点（`_mediaQueue` 入队校验 / `send-caps.video_mimes`），改为**选文件时**即按平台白名单判：不支持 → 当场拒绝「该平台暂不支持 .MOV，请转成 MP4」，绝不进入队列复用「结果未知」；若随包有 ffmpeg → 后台转码 MOV→MP4 后再入队并提示「已自动转为 MP4」；前端拦截落 `console.warn('[media] rejected ext/mime …')` 进 renderer 日志。

## 4. C —— 附件按会话隔离（#228，P1）

**事实**（V9DZ5S）：LINE 会话发送失败的附件切到 WhatsApp Nori→Nell 会话仍挂在输入框——`_pendingMedia` / `_mediaQueue` 是全局变量。

**修法**：媒体队列改按 `conversation_id` 键存（切走保留、切回恢复）；附件条明示「发往 LINE · Kevin」；`_doSendMedia` 发送前校验附件所属会话 == 当前会话，不等则拒绝并提示；失败附件可一键清除；顺带核查文字草稿框是否同为全局（落点表写结论）。
