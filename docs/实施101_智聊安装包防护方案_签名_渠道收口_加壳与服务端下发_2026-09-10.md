## 0. 一页结论

| | 判断 |
|---|---|
| 能不能被反编译 | **能**。`app.asar` 用 `npx asar extract` 一条命令解开（明文 JS）；后端 `backend.exe` 是 PyInstaller onedir，`pyinstxtractor` 一步解出全部 `.pyc`——后端用 **Python 3.13**，成熟反编译器（decompyle3/uncompyle6）尚不支持、`pycdc` 只能部分还原，但 `dis` 反汇编 + 字符串提取足以读出全部提示词与业务分支；而 `--add-data` 随包的 i18n `.py`、模板、YAML 种子本来就是**明文**。无代码签名、无混淆、无完整性校验。 |
| 拆开能拿到什么 | 提示词工程、人设/陪伴/危机/翻译整套业务逻辑、Web 后台全部模板、i18n；**内测包还带生产机人设/参考音/相册/KB 种子**（`stage_internal_assets.py` 把它们打进 `resources/seed-data`）。 |
| 拆开拿不到什么 | DeepSeek key / 网关密钥（只在 VPS）、授权签发私钥（.117 仓外）、坐席账号会话（包外）。云侧账单**不会**因为拆包被盗刷。 |
| 真正的风险排序 | ① 内测包＝生产数据种子，正躺在公开 URL 上 ② 无签名 → 任何人可改包重发「智聊」，用户和 SmartScreen 都分不出真假 ③ 热补丁通道只靠 HTTPS+sha256，服务器被端＝远程执行 ④ 提示词/人设逻辑明文 ⑤ 试用/授权是「诚实客户模型」，改一行即绕过 |
| 这份方案要做什么 | **不追求「不可反编译」**（做不到，追这个只会买到杀软误报和启动变慢）。目标改为四件可达的事：**发布真伪可验**、**内测资产不外流**、**改包客户端拿不到云服务**、**核心资产逐步不落地**。 |
| 需要老板拍板的 | 代码签名证书（要公司主体材料 + 年费）；提示词服务端化（联网依赖）；PyArmor 商业授权（可选）。其余是工程内部事，不用等。 |

## 1. 威胁模型：谁在拆、图什么、能做到什么

| 角色 | 证据 | 动机 | 能做到 | 我们真在乎的 |
|---|---|---|---|---|
| **同行/仿品团队** | 三件全拿的 VPN 出口；机房 IP 长期自动更新 | 抄产品：提示词、人设体系、渠道接入方式、UI | 完整还原源码；套皮改名上架 | 提示词与人设工程；渠道自动化 know-how |
| **蹭内测的人** | TG 群公开链接 → 帕拉纳克移动用户下 1.0.79 | 白用、看看 | 拿到**内测包里的生产人设/参考音/相册/KB** | **这是数据泄露，不是软件泄露** |
| **破解/去授权** | 暂无证据 | 绕过试用额度、白用云 AI | 删 `local_trial.json` 重置试用；patch `license_manager` 让 `feature_enabled` 恒真 | 云 AI 网关有 claim+HMAC 设备令牌，白用云 AI**做不到**；本地功能能白用 |
| **冒名分发/投毒** | 无签名 → 任何时候都可能 | 挂马、钓鱼、收钱卖「破解版」 | 改包重打 `ChatX-Setup-x.exe`，用户无法分辨 | 品牌与客户机器安全；出事算我们的 |
| **供应链** | 热补丁 manifest 无签名 | 端掉 VPS 即可全量下发任意 JS/exe | 一次推送全体客户端执行任意代码 | 最坏情况，概率低、后果最大 |

**能力现实**：三类人里没有一个需要「高手」。asar 与 PyInstaller 的还原都是公开教程级别。
所以防护的收益不在「拦住拆」，而在**拆了也白拆**（资产不在包里 / 改了包就失去服务）和
**拆了也别想冒充我们**（签名）。

## 3. 目标分级：保什么、放弃什么

```
                        成本 →
  收益 ↑   ┌─────────────────────┬─────────────────────┐
           │ P0 立刻做            │ P2 产品决策后做       │
           │ · 内测渠道收口        │ · 提示词/人设服务端下发│
           │ · 代码签名            │ · 授权与网关绑定       │
           │ · 热补丁签名          │ · 官方构建指纹白名单   │
           │ · 包内杂物清理        │                      │
           ├─────────────────────┼─────────────────────┤
           │ P1 顺手做            │ 不做                  │
           │ · Electron fuses     │ · VMProtect/Themida   │
           │ · main.js 字节码     │ · 反调试/反虚拟机      │
           │ · 构建指纹上报        │ · 模板/静态资源混淆    │
           │ · PyArmor 试点        │ · 纯离线 DRM          │
           └─────────────────────┴─────────────────────┘
```

**明确放弃**（写下来省得以后反复争论）：

- 「让 asar / PyInstaller 拆不开」——不可能；加壳只是把半小时变成一天，代价是杀软误报、
  启动变慢、每次 Electron/Python 升级都要重验兼容。
- 混淆 Web 后台模板/JS——它们本来就会原样送到浏览器，混淆等于自欺。
- 纯离线 DRM——坐席机（173/198/104/140）与私有化客户需要离线可用，任何「必须联网才启动」
  都与产品形态冲突。联网只能作为**增值服务的前提**（见 P2），不能作为启动前提。

## 4. 分期落地清单

### P0 · 本周（全部工程内部可做，零产品变更）

#### P0-1 内测渠道彻底离开公开路径（最高优先，这是数据泄露口）

现状：`https://bd2026.cc/downloads/internal/ChatX-Setup-x.exe` 与 `latest-internal.yml` 任何人可下，
包里是生产人设、参考音、相册、KB。

做法（服务端 + 客户端各一处，`website/` 与 `desktop/` 分别改）：

1. **内测源改为鉴权路径**：`/downloads/internal/*`（含 `.yml`）一律进 `/dl/` 门（扩展
   `next.config.mjs` 的 `rewrites.beforeFiles` 把 `.yml/.json` 也纳入），`/dl/` 路由对
   `internal/` 前缀要求请求头 `x-chatx-channel-key` 与 `.env.local: INTERNAL_CHANNEL_KEY`
   一致，缺失/不符 → 404（**不是 401**，不要告诉外界这里有东西）。
2. **内测壳自带该头**：`desktop/main.js` 的 `autoUpdater.requestHeaders = {"x-chatx-channel-key": <key>}`，
   key 由 `write-build-info.js` 在内测构建时写入 `build-info.json`（公开/lite 构建不写）。
   key 泄露即在 `.env.local` 换一个并重发内测包——**可轮换是设计要求**。
3. **首次安装的分发**：`/download/chatx` 页面不再出现内测入口；内测安装包改为
   `/dl/internal/<一次性签名 URL>`（`console` 里生成，含到期时间 + HMAC，台账记「发给谁」）。
   TG 群里只贴**签名 URL**，24h 过期。
4. **R2 侧**：`rclone` 发布脚本 `publish_chatx.ps1 -Channel internal` 不再同步到公开桶前缀
   `downloads/internal/`，改推私有前缀由 `/dl/` 代理流出（或直接只留 VPS 本地不推 R2；
   内测流量小，VPS 直出够用）。
5. **既有泄露处置**：现在 R2 上的 `downloads/internal/*` 全部下架（对象删除）；台账里
   `channel=internal` 且非办公室/非已知测试机指纹的 IP 列出来，逐个判断。

验收：匿名 `curl -I https://bd2026.cc/downloads/internal/latest-internal.yml` → 404；内测机
（钧 / 花无缺）自动更新仍正常；`/console/downloads` 里 internal 行只剩带 key 的请求。

#### P0-2 代码签名（Authenticode）

作用：① 用户与 Windows SmartScreen 能分辨「真智聊」与「改包」 ② electron-updater 在
Windows 上校验更新包签名与运行中程序**同发布者**（`verifyUpdateCodeSignature` 默认开，
但**只有已签名的 app 才会校验**）——这一条把「服务器被端就能推毒更新」的敞口关掉一大半
③ 装机时不再出现「未知发布者」黄条，这本身就是转化率。

选型（三选一，按省事程度）：

| 方案 | 费用 | 门槛 | 备注 |
|---|---|---|---|
| **Azure Trusted Signing**（推荐） | ≈ $10/月 | 需公司主体（无界科技 BOUNDLESS）验证，3 年以上主体秒过，否则要材料 | 云端签名无实体 U 盾；electron-builder **25+** 原生 `win.azureSignOptions`，本仓是 24.13 需升级 |
| OV 证书（SSL.com / Sectigo） | ≈ $200–400/年 | 主体验证；2023 起私钥必须在硬件（U 盾或云 HSM） | SmartScreen 信誉要累积 |
| EV 证书 | ≈ $400–700/年 | 更严主体审核 | SmartScreen 即时信誉 |

落地：
- `desktop/package.json`：升级 electron-builder → 25.x；`win.signtoolOptions` 或 `azureSignOptions`；
  `nsis` 安装器与卸载器一并签（electron-builder 默认会签）。
- `publish_chatx.ps1` 发布前加一步 `signtool verify /pa /v ChatX-Setup-*.exe`，不通过不上传。
- `package-layout.test.js` 增门禁：发布产物必须有有效 Authenticode 签名（CI 无证书时 SKIP）。
- **证书私钥/Azure 凭据只在打包机**，绝不进仓；`.env.local` 同款纪律。

验收：`Get-AuthenticodeSignature ChatX-Setup-x.exe` → Valid；从未签名 1.0.7x 升到签名版正常；
篡改后的 exe 被 updater 拒绝（日志 `[updater] New version … is not signed by the application owner`）。

#### P0-3 热补丁 manifest 签名（Ed25519）

现状是「同源 + sha256」，信任锚只有 TLS 和 VPS 本身。补一把离线私钥：

- 打包机 `hotpatch` 构建脚本对 manifest 的规范化 JSON（排序键、去空白）做 Ed25519 签名，写入
  `hotpatch.json.sig`（或 manifest 内 `signature` 字段，签名覆盖除该字段外的全部内容）。
- 客户端 `hotpatch-stage.js` 新增 `verifyManifestSignature(rawJson, sigB64, pubKeyHex)`——Node
  原生 `crypto.verify(null, buf, keyObject, sig)` 即可，零依赖；公钥常量随壳内置。
  **验签失败 = 整份拒绝**（与现有 `manifestTampered` 同哲学：不套半份）。
- 私钥与授权私钥**分开**（一把管授权、一把管代码下发；泄一把不连坐），同样 .117 仓外保管。
- 门禁：`desktop/test/hotpatch-apply.test.js` 加正/反例（篡改一字节必拒）。

#### P0-4 包内杂物与明文清理

- `desktop/package.json` `files` 追加 `!_notes_*.txt`、`!UTF8`、`!README.md`、`!*.md`。
- `build_backend.py` 的 `--add-data`：i18n packs 与 config 种子里凡「非运行时必需的注释/
  内部主机名/人名」，构建时走已有 `refresh_backend_datas.py` 暂存路径**剥注释**（YAML/PY
  注释里的内网 IP、坐席名、事故记录是最容易被忽略的泄露面）。`after-pack.js` 已禁内网地址，
  扩到 `.py` 注释与 `.txt`。
- 检查 `../shared/inject/*.js`（随包注入脚本）与三个 Node 边车目录：`!**/*.md`、`!**/.env*`、
  `!**/sessions/**` 已排，补 `!**/*.log`、`!**/test/**`。

#### P0-5 台账告警接进 ops 群

`download-ledger` 已打 `sweep`/`ratelimit`/`bot` 标记，但没人盯就是空转。
`engines/chengjie/tools/send_ops_group_report.py` 已有 ops 群投递能力：加一条
`GET /api/console/downloads?days=1&all=1` 摘要——`sweep` 出口、机房/VPN ASN 的 internal 下载、
非办公室的 internal 命中，每日一条；`sweep` 命中即时一条。规则：**只报 internal 与 sweep**，
public 渠道的正常用户不报（否则又是告警噪音）。

### P1 · 两到三周（提高改包成本，不改产品形态）

#### P1-1 Electron fuses + asar 完整性

`@electron/fuses` 在 afterPack 阶段翻转：

| Fuse | 设为 | 效果 |
|---|---|---|
| `RunAsNode` | off | 不能拿 `ChatX.exe` 当 node 跑任意脚本 |
| `EnableNodeOptionsEnvironmentVariable` | off | 堵 `NODE_OPTIONS=--require evil.js` |
| `EnableNodeCliInspectArguments` | off | 堵 `--inspect` 挂调试器 |
| `EnableEmbeddedAsarIntegrityValidation` | on | asar 被改 → 启动即拒（Windows/mac 均支持） |
| `OnlyLoadAppFromAsar` | on | 不能塞个 `app/` 目录替代 asar |

注意：热补丁替换整份 `app.asar` 是合法路径，完整性哈希随新 asar 一起由 electron-builder 写进
exe 资源——**所以热补丁换 asar 时也必须换 exe 头**，或者把热补丁范围收缩到 `resources/`
下非 asar 文件（backend、shared/inject、边车）。这是 P1-1 与 P0-3 的接口，做前先在
`hotpatch-apply.test.js` 定契约。开发态 `npm start` 不受影响（fuses 只翻在打包产物上）。

#### P1-2 main.js / preload / hotpatch-*.js 编译成 V8 字节码

`bytenode` 在打包机用**同版本 Electron** 把 `main.js`、`preload.js`、`backend-launcher.js`、
`hotpatch-*.js` 编成 `.jsc`，asar 内只留一个 3 行的 loader。字节码可逆向但没有现成一键工具，
把「解开就是源码」变成「要人肉读 V8 字节码」。风险：Electron 大版本升级时必须重编（构建流程
内含，不额外增加人工）；`hotpatch-apply.test.js` 等 Node 直跑门禁继续跑源码，不受影响。

#### P1-3 后端提高门槛（三档，按需选一）

| 档 | 做法 | 成本 | 效果 |
|---|---|---|---|
| a. 零成本 | 确保 PYZ 只带 `.pyc` 不带 `.py`（默认如此，别开 `--noarchive`）；`--add-data` 随包的 i18n `.py` 改为预编译 `.pyc`（`refresh_backend_datas.py` 暂存阶段 `compileall`）；**钉住 Python 3.13**（`build_backend.py` 加版本断言，别为省事退回 3.11） | 半天 | 3.13 字节码目前无成熟反编译器，只剩反汇编读法；随包 `.py` 明文这一层直接消失 |
| b. **PyArmor**（推荐试点） | 商业授权（Basic ≈ $52 一次性/机器）；对 `src/` 做 RFT/BCC 模式混淆后再喂 PyInstaller | 2–3 天含兼容验证 | 反编译出的是被改名/被编成 C 的壳，FastAPI/pydantic 路径需逐模块验证（已知坑：动态 import、`inspect` 依赖） |
| c. Nuitka | 整体编成 C 再打包 | 一周+，构建时间 30 分钟级 | 最硬，但 `platform/` 动态包与 lunar_python 等需逐个排；每次发版慢 |

建议：**a 立刻做，b 试点在 `src/ai/`、`src/companion/`、`src/licensing/`（价值最高的三个包）**，
c 暂不做。无论哪档，先跑 `desktop/build/smoke_backend.py` + `smoke_clean.py` + `smoke_internal.py`
三个冒烟，再看首启时间是否劣化 >20%。

#### P1-4 构建指纹上报（为 P2-3 铺路，本身就有观测价值）

- `write-build-info.js` 写 `build_sha`（= asar sha256 + backend 目录 sha256 的组合）。
- 客户端已有 beacon（`client-logs.jsonl`，带 ip + fp + version）：多带 `build_sha`。
- `publish_chatx.ps1` 发布时把官方 `build_sha` 登记到 VPS `~/hualing-leads/official-builds.json`。
- `/console` 新增一行：**「非官方指纹」客户端数**——改包客户端一上线就现形。

### P2 · 需要老板拍板的产品决策

#### P2-1 提示词 / 人设逻辑服务端下发

最值钱的资产是提示词工程与人设编排，不是 FastAPI 胶水。方案：把 `src/ai/prompts/*`、
人设模板、危机/翻译指令模板改成**按版本从网关拉取**（`/api/ai-gateway/prompt-pack?ver=`，
复用设备令牌 claim），本地只缓存加密副本（AES-GCM，密钥由设备令牌派生）。

- 代价：未 claim 或断网的客户端**只能用内置的精简提示词包**（能聊，但没有完整人设体系）。
- 这恰好与「云 AI 是增值服务、本地是基础功能」的商业口径一致：**买了云 AI 才有完整智聊**。
- 坐席机与私有化客户：走 `licensing` 的站点授权（`machine: "*"`）签发**离线提示词包**，
  用授权私钥签名、按客户加密——泄露可定位到客户。

#### P2-2 授权与网关绑定

现在离线 license 与网关 claim 是两套。合并成一个语义：**设备令牌签发时校验 license 状态**
（plan / seats / exp），付费功能（L4、白标、多坐席）的判定放在**网关侧**而不是客户端
`feature_enabled`。客户端 patch 掉 `feature_gate` 只会得到本地假绿灯，真正的云能力仍按网关口径。

#### P2-3 官方构建指纹白名单

在 P1-4 基础上：网关 `device-token` 签发时校验 beacon 上报的 `build_sha ∈ official-builds`；
不在名单 → 拒发令牌（改包客户端**没有云 AI**）。这是整套方案里性价比最高的一刀：
零 DRM、零加壳、不影响正版用户，但让「拆包改包再用」失去意义。要配一个逃生门：
`official-builds.json` 支持 `allow_unknown_until`（发版后 24h 宽限，防发布脚本漏登记把全体用户断服）。

#### P2-4 内测包按测试人水印

`stage_internal_assets.py` 打种子时，对每位测试人生成不同包：人设 YAML 里塞一条不可见的
`_wm: <hmac(tester)>`、参考音尾部 0.3s 静音里嵌 LSB 水印。内测包再外流，24h 内知道是谁传的。
（前提是 P0-1 做完——先把门关上，再谈追责。）

### P3 · 法务与运营配套（不排期，随手做）

- 安装器已有 `license_zh_CN.rtf / license_en_US.rtf`（安装前须知）：补「禁止反编译、逆向、
  去除技术保护措施」条款与管辖地，让日后的下架投诉有依据。
- 所有发布产物随附 `SHA256SUMS` + 签名（P0-2 之后可直接用 Authenticode，`SHA256SUMS` 供 mac/其他）。
- 建立「发现仿品」处置流程：Telegram 群/网盘链接 → 台账比对 build_sha → 平台投诉模板。

## 6. 验收总表（做完后一次过）

1. 匿名下载：`downloads/internal/*` 全 404；public/lite 正常；台账 internal 行全带 key。
2. 签名：`signtool verify /pa` 通过；篡改 exe 后自动更新被拒；SmartScreen 无「未知发布者」。
3. 热补丁：篡改 manifest 一字节 → 客户端日志 `manifest signature invalid`，不落地。
4. asar：手改 `app.asar` 一字节 → 启动失败（fuses 生效）；正常包启动时间无劣化。
5. 后端：`pyinstxtractor` 解出目录里无 `.py`；PyArmor 试点包 `smoke_*` 三冒烟全绿，首启 ≤ 基线 +20%。
6. 指纹：`/console` 出现「非官方指纹」计数；用改包客户端申请设备令牌 → 拒（P2-3 后）。
7. 门禁：`cd desktop && npm test` 全绿（新增签名/热补丁验签/杂物排除用例）；`package-layout.test.js` 对签名的断言在无证书环境 SKIP 不红。

## 8. 不在本方案内、但顺带发现的

- `desktop/package.json` `appId` 仍是 `com.telegram-mtproto-ai.desktop`——签名后 appId 与
  发布者名会一起出现在系统「应用和功能」里，建议换成 `cc.bd2026.chatx` 之类；**换 appId 会让
  旧版无法原地升级**（NSIS 按 appId 找卸载项），要与 P0-2 同一版处理并写升级说明。
- `AvatarHub_SignWorker` 计划任务仍在两台办公机每 20s 打不存在的 `/api/console/sign/pull`
  （401）——属 176 线，未动；建议那条线停掉。
- 内测种子里的**参考音**是真人声音样本，属个人生物特征数据；P0-1 之外还应有「内测协议里
  写明不得二次传播」的合规条款（P3）。
