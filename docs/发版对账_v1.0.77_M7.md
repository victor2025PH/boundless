### 问 2 ｜ `sent_24h=4` 的 4 拍发到了哪？

- 口径：看门狗 `liveness.collect_send_liveness` 数的是**所有** active auto 目标（当时 `auto=7`）的 `goal_events`，`SENT_KINDS=("care_sent","beat_sent")`；而 `background_tasks._care_sent_hook` 每次真发**同时**写 `beat_sent`（`record_*_beat_sent`）和 `care_sent` 两条 → **一次真发计 2**。13:56 stalled → 14:01 recovered `sent_24h=4` ＝ 大概率 **2 次**真发，分布在 7 个目标里。
- 「真发」的定义：`care_dispatcher` L933 在 **入 deferred 队列成功**时调 `sent_hook`（`mark_sent` 在其后），`item` 只有 care 行字段，**无正文、无 deferred row_id、无消息 id** → `beat_sent` 事件天然不可追溯（detail 只有 `sprint:pN` / `daily:auto`）。
- 卡片「已推进 2 拍」＝`goal_routes._attach_beats` 数 **goal_actions** 表 `status∈{consumed,sent}` 且 `push_level!=none` 的行：`consumed`＝回复链把方向织进拟稿（被动），`sent`＝主动发出。与看门狗**不同表、不同口径**。
- BABY BEAR（WhatsApp，3+1 天＝natural 档）能否拿到主动拍：`due_daily` 要求 `natural_silence_min_sec=6h` 内客户**没开口**；该会话夜里 3h 59 条入站，白天同样活跃 → 每 tick `not_due`（ticker 只在 `last_skips` 内存计数，不落事件）。**结论：4（=2）拍发给了其他沉默会话；BABY BEAR 的「2 拍」是两次被动注入的 `consumed` 行**——用户在会话里看不到「目标驱动内容」，因为那是被织进普通回复的方向，不是独立的一条消息；而 `[goal-inject] injected` 那两行又被问 1 吞掉。
- 无法从本机反查 skuio 的 gstore（诊断包不含 `marketing_goals.db`）；上述为代码路径推断，A 项落地后下一次复报可直接从 `/beats` 端点读到答案。

### 问 3 ｜ 09-07 到期时发生了什么？

- 到期判定只有 settle-on-read（`refresh_goal` → `settle_goal`）：`companion.goals.sweep.enabled` **不在 A 类基线**（默认 False）→ `notify.scan_tick` 里 `settle_sweep` 不跑；靳靠下一次入站（inject）或卡片刷新（`for-conversation` → `_refreshed_view`）把 status 翻成 `expired`。BABY BEAR 消息密集，翻状态本身不成问题。
- 翻成 expired 后：`scan_sprint_miss`（即时单条）只收 `pace∈{today,session}`，自然档**不进**；`scan_miss_digest` 需 `len(rows)>=3` **或** 最老一条 `>=24h` → 1 条、未满 24h → `return`（静默）。24h 后即便出账，`goal_miss_alert` 只被 `webhook_notifier.py` 消费；`unified_inbox_realtime_routes._SSE_EVENT_TYPES/_NOTIF_EVENT_TYPES/_NOTIF_TYPE_I18N` 与 `workspace_base.html` 通知中心只登记了 `goal_completed_alert`，**没有任何 miss/expired 类型** → 工作台永远看不到。
- 卡片侧：`for-conversation` 无活跃目标时返回 `last`（最近一条终态）——用户 02:2x 重建新目标后 `goal` 非空、`last=None`，上一目标的结局从卡上消失。**结论：到期结算在工作台层面是结构性静默，不是门槛没到。**

### 问 4 ｜「白天 2/1 拍」超额后被动注入是否也停？

- **是，而且拍数上限从来只拦被动注入。** `effective_beat_cap` 全仓只有两处读：`service.refresh_goal` L489–495（`cap and n_existing>=cap → hold="pace_cap" → build_block_for_chat L1343 return None`，不带方向）和 `goal_routes._attach_beats`（显示）。冲刺 ticker（`run_once`）与 care 派发**不读 cap**——主动拍靠相位点（≤3）/ 每日一拍自限。
- 但对 BABY BEAR 不成立：3+1 天＝natural，`effective_beat_cap(natural)=0` → `pace_cap` 不会触发；natural 日槽 `consumed` 后同日再入站直接复用当日拍继续注入（L484 取到既有 action → 组块）。V76EPK 的「动作 2/1 拍」是 1.0.74 的 1 天目标（`cap=total_days=1`，`used=2` 含 z:/s: 槽），是显示口径不是限流。
- 改法（B）：`refresh_goal` 增 `inbound_turn` 分支——客户来消息（reply/draft 链）时 cap 不再 hold，只在主动链/系统调用上生效；`pace_cap` 达到时改记 `beat_blocked(pace_cap)` 事件（仅主动侧）。
