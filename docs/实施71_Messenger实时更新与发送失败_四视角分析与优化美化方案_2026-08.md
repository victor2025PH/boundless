另有一个诚实性问题：**断线期间的消息补收进来时，时间戳记的是补收时刻（02:12）而不是客户真实发送时刻**——所以时间线从 8/18 直接跳到 8/27 02:12，既像「老信息」又像「刚发的」，两头失真。

### Q2：「发送失败」是什么时候的信息？为什么失败？

**就是今晚（2026-08-27）02:12:35 的消息，AI 全自动模式对「柴犬」入站生成的回复；失败原因不是网络、不是掉线，是被自家「账号防封安全额度」闸门拦下的**（同批 02:12:32 Micah Bindo 会话那条也被拦，`app.log` 原话：`send_gate:daily_cap, origin=auto`）。02:12:33 已向 ops TG 推过一条 ⚠ 告警。

拦截的算术链（每个数字都已实测）：

```
今晚 02:11:34 登录成功 → 注册表为该号「重建」账号行（created_at = 02:11:34）
  ↓  账号在闸门眼里 = 0 天新号（尽管库里它 8/16 就有聊天记录！）
预热起步额度 recommended_cap = warmup_start_cap = 15
  ↓  减去人工预留 reserve_for_manual = 20
自动链可用额度 auto_cap = max(0, 15 - 20) = 0
  ↓  已发 0 条 ≥ 0 → 拦截，reason = daily_cap
```

即：**AI 一条都没发过，但它的可用额度本来就是 0**。蓝色横幅（「AI 已发 0 / 今日上限 15」却说已达上限）其实就是在报这件事，但没把「预留 20 給人工」这步算术亮出来，读起来自相矛盾。

暴露出的三个真缺陷：

1. **重登＝年龄清零**：账号 8/16 就存在（inbox 库有它 8/16-8/18 的完整聊天），今晚重登后注册表行被重建，预热闸门把老号当 0 天新号管。
2. **配置自噬**：`reserve_for_manual(20) > warmup_start_cap(15)` ⇒ 任何新号/重登号头 ~6 小时自动额度**恒为 0**（爬坡到 >20 需 0.26 天），而系统没有任何校验提醒这个组合。
3. **失败不自解释**：气泡上只有「发送失败」四个红字，原因（防封让路）在另一条蓝横幅里、算术又对不上——老板只能来问人。

> 附带一个需要现场核对的疑点：02:12:04 入站的柴犬文本与 8/18 08:24 本账号**发出**的那条逐字相同。若是对面（Calixa 号持有者）今晚照脚本重发的测试消息则无事；若是 e2ee 线程重登后回填时**方向判反**（把自己的旧出站当成对方新入站），则是数据级 bug。核对法：从 Calixa 侧发一条**全新文本**，看 15 秒内是否入站、方向是否正确。

## 2. 四视角深度分析

### 2.1 开发工程师视角——「机制都在，真相分了三层各说各话」

本页面同屏存在**三个互相矛盾的真相面**：顶部红条说「messenger 离线 65 小时」（数据源＝全账号聚合里的僵尸行）；账号 dock 的 Wisley 头像是在线绿点（数据源＝当前账号状态）；聊天区在正常收发（数据源＝会话消息流）。每一层单看都「对」，拼在一起就是事故现场。工程病根五条：

1. **账号生命周期缺「退役」态**：注册表里 messenger 有 3 行——在用 1（Wisley online）、僵尸 1（Calixa offline 自 8/24）、已移除 1。offline 行无限期驱动 channel 级红条；`platform_session_health` 的 unhealthy 聚合不区分「在用账号掉线」（真事故）与「废弃账号躺尸」（噪音）。
2. **预热身份记忆断裂**：闸门的「账龄」读注册表 `created_at`，而重登路径重建了行 → 年龄清零。事实上 inbox 库里该号 `first_seen`/最早消息在 8/16——**年龄的真相源应当取「注册表 created_at 与库内最早消息 ts 的最小值」**，或重登 upsert 必须保留旧 created_at。这是所有「重登见效前先被闸门憋死几小时」类事故的共同根。
3. **配置无 lint**：`reserve_for_manual ≥ warmup_start_cap` 是一个数学上必然把新号自动链锁死的组合，但配置层不校验、ops 卡不亮灯、日志不提示。闸门参数之间存在隐式约束（reserve < start_cap < target_cap），应当有一处启动期一致性检查（同类先例：实施34 的配置体检卡）。
4. **失败原因没有落库**：autosend 拦截时 reason 只进了 WARNING 日志与 ops 告警，消息行只写 `status=failed`——前端永远无法就地解释。数据在链路上**产生过**却在最后一米被丢弃，这与实施69「需人工标签无溯源」是同一个病：**状态无出处**。
5. **补收消息时戳失真**：回填统一 `ts=ingested_at`，原始发送时刻丢失且不打「补收」标——时间线完整性受损（排序幻觉、断档幻觉），还会污染回复时延 SLO 与「入站 burst」判定（reply_latency 按首条入站计等待——补收 21 条会被当成 02:12 的瞬时爆发）。

另有一条**正面确认**：这次事故里真正的自愈链（worker 计划任务拉活、code_stale 自报、PIN 输入窗、ops 告警推送、send_gate 预判横幅）全部按设计工作了——坏的不是链路，是**表达与身份**。

### 2.2 市场经理视角——「防封保护做成了『发送失败』，卖点演成了事故」

内测老板在凌晨两点半亲自测试，看到的是：红条喊离线 + 消息发不出去 + 一句冷冰冰的「发送失败」。他嘴里传出去会是**「Messenger 修好了但还是发不出消息」**——而事实是「系统为保护你刚救活的账号，主动把 AI 发言权让给了人工」。同一件事，两种叙事，天壤之别：

| 页面现状 | 客户脑补 | 实际语义 | 应有叙事 |
|---|---|---|---|
| 红条「已离线 3920 分钟」挂着不走 | 「修了半天还是断的」 | 废弃账号的僵尸告警 | 「当前账号在线；有 1 个历史账号已停用（可归档）」 |
| 气泡「发送失败」 | 「产品不稳定」 | 防封额度主动让路 | 「已为账号安全暂缓自动发送，点此人工发出」 |
| 蓝横幅「AI 已发 0/上限 15，已达上限」 | 「连数都算不对」 | 15 条全预留给了人工 | 「新号保护期：今日 AI 0 条 / 人工 15 条」 |
| 恢复后无任何庆祝 | 「到底修好没有」 | 已补收 3 会话 21 条 | 「已恢复收发，补收 21 条，AI 拟好 2 条草稿待你过目」 |

三个市场侧动作：

1. **把「新号保护期」做成显性产品概念**（对标手机「电池保养充电」的用户教育）：账号卡/会话头出「保护期第 1 天：AI 今日 X 条、人工不限、Y 天后全速」——竞品普遍只有冷冰冰的限流，可解释的防封是差异化卖点，也顺手消化掉「0/15 却触顶」的沟通事故。
2. **恢复时刻＝价值时刻**：断线→重登→补收的闭环数字（掉线时长、补收条数、AI 代拟草稿数）直接进「AI 价值周报」与恢复横幅——把一次事故变成一次「系统兜住了」的证明。
3. **告警的信噪比就是口碑**：僵尸账号驱动的常驻红条属于「狼来了」训练器，会让真离线被无视。红条必须只为「在用资产的真故障」响。

### 2.3 用户（坐席/老板）视角——逐断点走查

每个断点问两问：「我知道发生了什么吗？我知道下一步做什么吗？」

1. **看到红条「离线 3920 分钟」但聊天明明在动**：两问全不及格——不知道离线的是哪个号（Calixa 是谁？我正聊的这个吗？）、不知道该做什么（点「重新登录」会登谁？）。期望：红条写人话「历史账号 Calixa Lopez 已停用 65 小时（当前账号 Wisley 正常）」+「归档该账号」按钮。
2. **看到「发送失败」**：不知道为什么失败（第一反应网络/掉线，真相是额度）、不知道下一步（重发？等？换人工？）。期望：气泡上原因词 +「人工发出」一键（人工额度还有 15 条，点了就能立刻回客户——**今晚这两条其实现在就可以人工补发**）。
3. **恢复后突然涌进一批 02:12 的消息**：不知道客户到底什么时候说的（回错语境风险：客户 8/25 说的「明天见」今天回「好呀明天见」＝穿帮）。期望：线程内「断线补收」分隔线 + 补收标注。
4. **不知道 AI 曾试图回复**：AI 拦截记录藏在右栏「全自动进行中…失败 1」小字里，离聊天区十万八千里。期望：线程内系统备注「02:12 AI 已拟回复，因新号保护期暂缓 → [查看草稿] [人工发出]」。
5. **凌晨密集测试的情绪负荷**：同屏红条+蓝横幅+红失败+徽标数字，全在喊，分不清主次。期望：一次只喊一件事，其余收进状态托盘。

### 2.4 美术 / UI-UX 工程师视角——「状态色系超载，缺一条『情绪弧线』」

对照截图逐区走查：

1. **横幅带（页面咽喉）**：红色渐变常驻条 + 蓝色额度条同屏堆叠，加上会话内蓝色系统横幅，纵向吃掉 ~90px 且**红色被廉价消耗**——真急停出现时已无更高优先级的视觉词汇。缺「横幅栈治理」：同刻至多 1 条常驻横幅，按 严重度×新鲜度 竞争上岗，其余折叠进右上状态托盘计数（铃铛体系已在，缺的是收纳规则）。色彩语义需立法：红＝需要人立刻行动的真故障；琥珀＝受控降级；蓝＝纯信息；绿＝恢复确认（驻留 10s 自动退场）。
2. **失败气泡解剖**：现状是时间行拼红字「✕ 发送失败」，孤立无援。应升级为**失败 chip**：`⛔ 防封额度 · 转人工发送`——图标+原因词+动作词三件套，hover 展开完整解释（何时/为何/谁拦的），红色只染 chip 不染整行。同型规范可复用到语音失败、媒体失败（与 cp-voice 的错误态设计语言对齐）。
3. **额度横幅从「散文」到「仪表」**：三个数字（AI 已用/AI 可用/人工余量）用一条双色分段计量条表达，预留段用人工色显式画出来——「0/15 却触顶」的悖论在图形上一眼自洽。CTA 就地给：「白名单此客户」（接口已有）/「调整额度」（有权限者）。
4. **恢复编排（情绪弧线）**：断线→恢复目前没有任何视觉过渡，红条只是「下次轮询时消失」。应设计：登录成功事件即时把红条**变形**为绿色「已恢复，补收中… ▓▓░ 21 条」，完成后驻留 10 秒自动收起。用户对系统可靠性的记忆点恰恰在这几秒。
5. **线程时间诚实**：「—— 8/18 08:24 ~ 8/27 02:11 通道断线，以下 14 条为补收（时间为入库时刻）——」细分隔线；补收消息时间戳加虚线下划线样式以示「非原始时刻」。
6. **右栏信息架构**：业务助手（网页版/客户关系/工具箱）+ 翻译工具 + 会话 + 全自动卡 + 语音克隆/发送 + 人设绑定，一屏塞不下、重要性混排。建议顶部固定一张**「本会话状态摘要」卡**（自动化档位 · 额度计量条 · 本账号通道健康三元组），其余分区默认折叠记忆展开态——坐席 90% 的疑问（能不能发/AI 在不在管/通道通不通）应在不滚动的第一屏得到答案。
7. **暗色主题一致性收口**：红/蓝横幅用的饱和渐变与主题 token 体系（`--th-bg-red9` 等已存在）不完全一致；系统横幅内 emoji（📢/⚠/🛡）与 uiIcon SVG 混用，视觉噪点。美化批统一：横幅左缘 3px 色带 + 低饱和底 + token 化色值；图标一律 uiIcon；圆角/间距对齐 `--tk-radius-sm` 节奏；徽标数字字号/字重统一。
