## 2. 设计决策（实施中优化过的点）

### 2.1 flag 传导：provider 而非参数穿透（实施中改道）

原案给 `format_persona_block` 加 `honest_identity` 参数——但其调用点散在
skill_manager 等热区文件，一个布尔要穿透十几个签名、且每个调用点都得拿 config。
改为 `src/compliance/runtime.py` 进程级 provider：`create_app` 注册一行
`set_config_provider(lambda: config_manager.config)`（天然跟随 overlay 热重载），
persona_manager 消费点惰性读取，provider 未注册（单测/legacy 装配）恒 False。
**代价自知**：这是仓库「注入而非全局导入」惯例的一次显式松动——用一个模块级
provider 换掉 N 个热区签名改动；provider 只读、失败恒 False，破坏面有界。

### 2.2 「身份类」判定复用一套正则（防第二套漂移）

人设模板普遍带 `forbidden_phrases: ["作为AI", "我是语言模型"]`——只折算 `deny_ai`
不豁免这些禁语，诚实回答照样被剥。豁免判类**复用** `_AI_SELF_ID_PATTERNS`
（`_matches_ai_self_id(phrase)`），与出站检测同一口径；全局规则条目判类另用
「已知 id（anti_bot_response）+ 保守内容模式」双轨——出厂规则实测只有
anti_bot_response 属身份规避类（「不要自称AI」在实例覆盖层数据里，内容模式负责
接住运营自写条目；门禁断言出厂 12 条**只剔这一条**，误剔即红）。

### 2.3 剔除必须成对追加（只删会失控）

诚实模式对全局规则不是纯剔除：剔掉「被质疑时不认账」却不给「怎么如实说」，
模型行为不可控。`filter_constraints_for_honesty` 在剔除的同一注入面**追加**
`compliance_honest_identity` 条目（如实+简短+人工可接入+不冒充人类+跟客户语言），
幂等不重复。

### 2.4 正交锁必须幸存（实施中被测试抓到的边界）

persona_manager 里有**两个**「身份硬锁」家族：名字锁（防幻觉改名，David Lin
事故防线）与 AI 否认锁。诚实模式只折算后者；首版门禁断言过宽（`"身份硬锁" not in`）
被名字锁教育——现门禁把「名字锁幸存」写成正向对照断言。

### 2.5 披露防重不落 conversation_meta（对规格原案的显式偏离）

规格写「落 conversation_meta 防重」。实施改为合规包自带 JSON 标记库：
① `store.py` 正被 msg-ops 线活跃编辑（schema 迁移碰撞面）；② A 线（telegram
协议链）拿 store 句柄不如 B 线顺手，独立标记库两条链同键（`platform:acct:chat`）
零耦合；③ 标记失败仍前置披露（宁重复不遗漏——重复披露合规无害）。
探索报告证实 InboxStore 无通用 KV，原案本就要加列迁移。

### 2.6 计数器持久层：日桶 JSON 而非 sqlite/审计行

年报要区间合计 → 日桶是最小充分粒度；危机事件稀疏 → JSON+锁+原子写足够；
ops_events / store 均在他线活跃编辑中，独立文件零碰撞。CrisisEventStore
（A 线专用审计）保持不动——计数与审计正交，rider 里计数点覆盖 A+B 两线。
