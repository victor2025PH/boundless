# 实施68：Messenger E2EE PIN 二次输入窗口 + 收发恢复 —— 三视角分析与优化方案

（报障原话：「messenger 在登录后输入 PIN 的时间太短，需要有二次打开可以输入 PIN
的窗口，然后 messenger 不能收发消息」。本文档=先分析后施工的存档件；与实施67
P1-9（B70 PIN 闭环，已落码随 1.0.55 待装）是同一条线的延续——B70 修了「托管代填」
半边，本批补「窗口生命周期 + 人工逃生门」半边。撰写：117 执行线，2026-08-24 晚。）

---

## 第一部分：代码级根因实锤（先于视角分析，全部读码验证）

### 1.1 「PIN 输入时间太短」——根因＝登录成功后 12 秒无条件 auto-hide（现役包）

**背景**：FB 已把 Messenger 私聊全面转端到端加密（E2EE），网页版登录成功后会弹
「输入 PIN 恢复加密聊天」浮层；不输 PIN → 加密线程全部是占位符，**读不到也发不进**。

**确定性证据链**（`services/messenger-web/server.js`）：

1. `HIDE_AFTER_LOGIN_DELAY_MS` 默认 **12000ms**（:119，env 可调但从未调过）；
   `maybeAutoHideAfterLogin`（:2589）在登录 promote 成功后注入「登录成功」横幅、
   12 秒后关 headed 窗换 headless——**现役坐席包（≤1.0.54）无任何 PIN 避让**，
   PIN 浮层与横幅、12 秒倒计时正面竞态。用户体感「输 PIN 的时间太短」逐字吻合。
2. B70（实施67 P1-9，已落码未装）加了 auto-hide 前**一次性**核对：浮层在场→
   有托管 PIN 先代填，未愈→本轮不隐藏+摘横幅（:2603-2620）。但它是
   **单点检查**：PIN 浮层晚于 12 秒出现（FB 常在收件箱骨架加载完几秒后才弹）
   或 `detectPinPrompt` 漏检（文案/DOM 变体）→ 窗口照关，回到旧病。
3. deferred（不隐藏）分支**无收尾**：人工输完 PIN 后窗口永久保持 headed 可见，
   没有「解锁→自动收回无头」的闭环；也没有复检循环再给代填第二次机会。

### 1.2 「需要二次打开 PIN 窗口」——根因＝「缺 PIN」被折叠进「重新登录」这个更重的动作

现状唯一人工入口＝`POST /accounts/:id/relogin`（:3539）：关旧 context → 同 profile
headed **30 分钟完整交互登录窗**。语义错位三连：

1. **重**：cookie 明明还活着（`c_user`/`xs` 在），只缺 E2EE 密钥恢复这一步，却要
   把人扔回「账密/2FA/checkpoint」全流程的登录窗；每多一次完整登录都是一次
   FB 风控暴露面。
2. **窄**：秒 promote 后又进 1.1 的 auto-hide 竞态——「重新登录再抢一次 12 秒」
   是现状用户唯一的自救法，循环踩坑。
3. **忘记 PIN 无出路**：FB 官方重置流程（浮层里点「忘记 PIN？」→ 重置加密数据 /
   用另一台在登设备恢复）**只能人工在真窗口里点**，托管代填永远救不了这个场景；
   收件箱 PIN 弹窗的「忘记了？」按钮（`inbox.pinm.forgot`）目前只展示帮助文字，
   没有任何可执行动作。

### 1.3 「不能收发消息」——原因链（读码坐实）

```text
E2EE 密钥未恢复
  → 读：线程全是加密占位（_convStats 占位比高）/ readThreadTail 失败 → 收不到
  → 发：composer 被 PIN 浮层挡 → classifyComposerBlock=e2ee_pin_prompt → 发不出
  → 半死心跳（/inbox-health）报 stall → hint=e2ee_pin_required / e2ee_relogin
  → 若另推 needs_login/expired → platform_session_health 标不健康 → 自动发直接短路
```

PIN 恢复后 `tryAutoE2eePin` 已做读窗清零（`_readWin`/`_convStats`，:1474），但
**不主动重扫**——要等下一拍轮询/心跳才恢复+上报，用户看到的是「输完 PIN 还要
再等一会儿才动」，容易误判「没修好」。

### 1.4 B70 已修面（勿重复施工）

- 托管即重放：`/accounts/:id/e2ee-pin` 落盘后异步 `driveE2eePinReplay`（当前页
  在场就地填；不在场导航首条 `/e2ee/t/` 线程钓浮层，试完回原页）。
- 立即验证：`/accounts/:id/e2ee-pin/verify`（浮层在场才真验，「所存即所验」）。
- 收件箱必答弹窗：`e2ee_pin_required` hint → 自动弹模态（解释+输入+当场验证回执，
  `inbox.pinm.*`），PIN 经主站 `/api/unified-inbox/messenger/e2ee-pin` 转边车。
- auto-hide 前一次性避让 + 成功横幅避让 PIN 页。
- 代填安全护栏：预算 2 次/轮 + 10min 冷却（`autoPinGate` 纯函数）、登录表单在场
  绝不碰、PIN 明文绝不入日志。

**本批缺口＝三个**：① 一次性检查 → 要「守到解锁」；② 无专用二次 PIN 窗口；
③ 解锁后无主动重扫/正反馈。

## 第二部分：三视角深度分析

### 视角一：用户（坐席/老板）

**用户契约：「登录成功」=「能收能发」。** 现实是登录成功后还藏着一道他看不懂的
门（E2EE PIN）：窗口弹出 12 秒就消失，很多人根本没看清那是什么；然后整个
Messenger 静默停摆——收不到、发不出，界面不解释为什么，唯一按钮「重新登录」
又把他扔回完整登录流程再赌一次 12 秒。**用户不怕多输一次 PIN，怕的是错过一次
就永远错过。**

用户不知道也不该需要知道什么是端到端加密。他要的朴素闭环是四句话：
**输 PIN 的机会永远在**（错过了随时能再开）、**输错了当场知道**（不是石沉大海）、
**输对了立刻能用**（消息流当场动起来）、**忘了有出路**（指路官方重置而不是死循环）。

「不能收发」在用户眼里比「窗口太快」严重一个量级——前者是业务停摆，后者只是
操作不便。修复叙事必须以「收发恢复」为主轴：PIN 窗口是手段，不是目的。验收也
要按用户动线验：输完 PIN 的下一眼，消息流必须肉眼可见地恢复。

### 视角二：开发工程师

**根因分层**（四层，每层独立成立）：

1. **时序竞态**：浮层出现时机（页面加载后不定点弹出）vs 一次性 12 秒检查点——
   用定时器赌事件，赌输就关窗。修法＝事件驱动替代定时赌：**守到解锁**（复检循环
   + 解锁事件触发收窗），把「检查一次」变成「窗口生命周期状态机」。
2. **恢复动作缺分级**：现状只有「重新登录」一档核弹。正确梯度＝
   **托管代填（零人工）< 二次 PIN 窗口（人工输一次）< 完整重登（cookie 死了才用）**，
   逐级升级，每级语义清晰、成本递增。缺的是中间档。
3. **状态机不闭环**：deferred 后窗口无收尾（永久 headed）；解锁后无主动重扫
   （等下一拍）；这些「差一步」让已修的链路在用户观感上仍像没修。
4. **检测单点**：`detectPinPrompt` 靠文案正则+输入框选择器，FB 改版/换语言即漏检，
   漏检＝直接回旧病。已有间接信号（占位比≥0.6 / 读窗全败，`maybeAutoPinSelfHeal`
   的 suspicious 判据）**必须进守护循环当兜底**——探不到浮层但间接信号响，也不许关窗。

**风险控制**（施工红线）：headed 窗口开关=浏览器指纹变化，有 FB 风控暴露面 →
同 profile 复用（绝不新建 loginId）+ 二次窗口频控（同账号 10min 一次）；自动代填
预算（2 次/10min）**不放宽**——错 PIN 连打是锁定加密数据的高危动作；PIN 明文
不入日志纪律保持；守护/开窗全程 best-effort，任何异常回落现状行为，绝不把
登录链变得比现在更脆。

**实现经济性**：二次窗口的「headless→headed 换壳」与 auto-hide 的「headed→headless」
是同一机制的反向（关 context → 同 profile `startLogin`），代码可复用；钓浮层导航
复用 `driveE2eePinReplay` 既有逻辑；状态机抽纯函数进 `msg_ops.js` 可单测。净新增
面很小，主要工作是把散落的动作串成生命周期。

### 视角三：市场经理

**Messenger 是获客主战场，「装好了但不能收发」是交付现场的死刑级观感。** 客户
不会区分「Facebook 强推加密的限制」和「你的产品坏了」——停摆一天，结论就是
后者。且这个坑是**每个新登录账号必踩**（FB 全量 E2EE 化后 PIN 是必经步骤），
不是边缘场景：新客户开箱第一小时就会撞上，正好撞在信任最脆弱的时点。

**竞品叙事机会**：同类网页自动化工具在 FB 全量 E2EE 后大面积瘫痪或干脆放弃
Messenger。把 PIN 处理做成能力页一句话卖点：「Facebook 强推端到端加密后，我们
做到**输一次 PIN 全自动恢复**；错过了一键再开窗口，忘了 PIN 也有官方重置引导
——Messenger 照常收发」。这句话竞品今天说不出来。

**支持成本账**：PIN 类工单每单都是远程指导 10 分钟起（「你点重新登录…看到窗口
没…没了？再来一次」），且高复发（每次重登都可能再弹 PIN）。自助闭环（弹窗输
PIN 当场回执 / 一键开窗）把这类工单归零，值守从「教操作」退到「看板确认」。

**验收即营销素材**：修复设计成用户可自验的形态——输完 PIN 立刻看到「已验证，
加密消息已解锁」回执 + 消息流当场恢复。值守回访时给报障用户走一遍，让他从
报障人变成修复见证人；录屏即能力页素材。

## 第三部分：优化方案（逐项：修法/涉改/验收/门禁）

### P0-A：PIN 窗口生命周期——「一次性检查」升级「守到解锁」（边车）

**修法**（`server.js` + `msg_ops.js`）：

1. `maybeAutoHideAfterLogin` 的 12 秒定时器改为**守护循环**（每 3-5s 一拍）：
   - 浮层不在场且**连续 2 拍干净** + 无间接半死信号 → 隐藏（防浮层晚到竞态）；
   - 浮层在场 + 有托管 PIN → 代填（预算/冷却走既有 `autoPinGate`）；成功 → 隐藏；
   - 浮层在场 + 无 PIN/代填失败 → 保持可见 + `bringToFront` 一次，继续守；
   - 守护期内浮层消失（人工输入成功）→ 读窗清零 + **自动收回 headless**
     （修 deferred 无收尾）+ 触发 P1 主动重扫；
   - 守护上限 `MSG_PIN_WAIT_MS`（默认 10min）超时 → 照常隐藏（不永久占屏），
     hint 链（`e2ee_pin_required`）继续引导托管/二次窗口。
2. **间接信号兜底**：`detectPinPrompt` 探不到但 suspicious（占位比≥0.6 / 读窗
   全败，复用 `maybeAutoPinSelfHeal` 判据）→ 本拍不隐藏（漏检不回旧病）。
3. 状态机抽纯函数 `msg_ops.pinGuardStep(state, signals) → {action, next}`
   （keep/front/fill/hide/timeout），`msg_ops.test.js` 门禁全路径。

**验收**：登录后浮层晚弹（>12s）窗口不关；无托管 PIN 人工慢慢输不被打断；
输完自动收窗；10min 不管它自动收窗且 hint 在。

### P0-B：专用「打开 PIN 输入窗口」（二次窗口；边车+主站+前端）

**修法**：

1. 边车新端点 `POST /accounts/:id/pin-window`（id 兼容 login_id/account_id，
   与 relogin/e2ee-pin 同款双解析）：
   - 在线 headless 会话 → `_intentionalClose` + 关 context + **同 profile** headed
     重启（auto-hide swap 的反向，复用其代码路径）；cookie 活着秒 promote；
   - promote 后钓浮层：当前页探 → 不在场导航首条 `/e2ee/t/` 线程（复用
     `driveE2eePinReplay` 导航法）→ `bringToFront`；
   - 随即进入 P0-A 守护模式（守到解锁，解锁自动收回 headless）；
   - 会话不在线/未授权 → 409 + `reason:"needs_relogin"` 明确指路重新登录
     （不静默降级成完整重登——语义要分明）；
   - **频控**：同账号 10min 内一次（防连点反复开关窗惊动风控），429 回执带剩余秒。
2. 主站薄代理 `POST /api/unified-inbox/messenger/pin-window`（复用 e2ee-pin 路由的
   账号解析+鉴权+超时），登记 `test_admin_route_inventory` 路由清单。
3. 前端入口三处（i18n zh+en，`inbox_workspace.py` pinm 族扩展）：
   - 收件箱 PIN 必答弹窗：第三按钮「🪟 打开输入窗口」；「忘记了？」帮助文案改为
     **可执行**——点击=开二次窗口+提示「在窗口里点『忘记 PIN？』走官方重置」；
   - 账号行/半死横幅 `pinCase` 分支：「输入 PIN」旁加「打开窗口」；
   - ops 卡平台会话行（运营侧）：不健康 messenger 行在「重新登录」旁加
     「PIN 窗口」（P1 批，可后置）。

**验收**：headless 运行态一键开窗 → 浮层在场且置顶 → 人工输入 → 自动收窗 →
收发恢复；连点被频控拦；cookie 已死时明确提示走重新登录。

### P0-C：现役机队止血（零代码，立即）

1. **117 边车**：`start.ps1` 加 `MSG_HIDE_AFTER_LOGIN_DELAY_MS=120000`（2 分钟），
   重启边车即生效——P0-A 到位前把 12 秒竞态窗拉宽 10 倍。
2. **坐席机（≤1.0.54）**：值守口径统一为「登录后立刻输 PIN（12 秒内）；错过 →
   点『重新登录』再来一轮，窗口出来先输 PIN 再干别的」；若壳侧可下发边车 env
   （待核：壳拉起 sidecar 的 env 注入通道），同步下发 delay=120000。
3. 1.0.55 若尚未发版（实施67 装包验收未勾），P0-A/B 争取**并入同一班车**省一次
   发版；赶不上进 1.0.56。发版班车决策交值守。

### P1：收发恢复闭环（解锁的下一眼必须看到效果）

1. **解锁即重扫**：`tryAutoE2eePin` 成功 / 守护模式检测到浮层消失 → 主动触发一轮
   侧栏扫描 + 变更线程 `readThreadTail` + **即时** `/inbox-health` 心跳上报
   （现状读窗清零后要等下一拍才重报）——把「输完 PIN 到消息流恢复」从分钟级
   压到秒级。
2. **发送失败精确文案核对**：`classifyComposerBlock=e2ee_pin_prompt` 的 500 回执，
   核对前端消费链是否译成人话+直达「输 PIN/开窗口」按钮（现状待核，缺则补）。
3. **解锁正反馈**：hint 从 `e2ee_pin_required` 翻绿时收件箱 toast
   「加密消息已解锁，正在补收历史消息」——用户的「修好了」确认点。

### P2：观测与防回归

1. `pinHealBump` 扩计数：`window_opened / manual_ok / wait_timeout`（守护模式
   出口分布）→ `/accounts` 心跳出网 → ops 卡 PIN 行——「二次窗口有没有人用、
   守护模式多少次守到解锁」看板可见。
2. `msg_ops.test.js`：`pinGuardStep` 状态机全路径 + 频控判定纯函数门禁；node
   全量保持绿。
3. 文档收口:边车 README 补「E2EE PIN 生命周期」章节（现状几乎不提 PIN）；
   `chatx-desktop-install.mdc` 装机验收清单加一行「Messenger 登录后 PIN 走查
   （输入→回执→收发恢复）」。
