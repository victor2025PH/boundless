# 值守分析：运维群链接打不开 · AI 回复「重复 / 太笨」是不是兜底与网络 —— 2026-09-09 08:5x

## 一、运维群最底部的链接

**是哪条**：运维群 = 通知端点 `tg-ywqz`（09-09 07:58 新加的第二个 Telegram 端点，与 `tg-ops` 同规则；`data/config/notify_webhooks.json`，`base_url=https://katie.bd2026.cc`）。08:04–08:07 连发三条告警（语音引擎 / LAN GPU / 机器人对方），最底部 08:07 `bot_peer_alert` 卡片末行：`打开收件箱: https://katie.bd2026.cc/workspace/inbox`（模板在 `src/inbox/webhook_notifier.py` L1355，相对链接经 `_plainify(base_url)` 拼成绝对地址）。

**服务端核对（08:3x）**：DNS `katie.bd2026.cc → 165.154.233.121` 正常；证书 Let's Encrypt 有效期到 11-05；`https://katie.bd2026.cc/workspace/inbox` → 303 `/login?next=…` → 登录页 200（从办公室网络可开）；VPS nginx `prod-katie.conf` 只有 443 → `proxy_pass http://127.0.0.1:18799`，而 VPS 的 `127.0.0.1:18799` 是 **sshd 反向隧道**回到办公室 zhiliao 实例。

**关键事实：今天 nginx 访问日志里没有任何一次来自手机 / 浏览器对 `/workspace/inbox` 或 `/login` 的请求**（只有每 10 分钟一次的健康探测 `Python-urllib` 和我 08:32 的测试）。老板点击的那一下**根本没有到达服务器** → 不是后端的问题，是点击设备到 VPS 之间不通：Telegram 内置浏览器 / 手机所在网络无法访问 165.154.233.121（Telegram 自身走代理不代表浏览器也走），或 DNS 解析失败。同机验证方法：同一部手机打开 `https://bd2026.cc`（同一台 VPS）——打不开即网络问题。

**顺手发现的三处真缺陷**（即使网络通也会遇到）：
1. katie 没有 80 端口 server 块：`http://katie.bd2026.cc/...` 被默认站 301 到别的域名再 404（实测 `GET /workspace/inbox` → 301 → 404）。任何以 http 打开的链接都死。修：加 `listen 80; server_name katie.bd2026.cc; return 301 https://$host$request_uri;`（一行，低风险）。
2. 链接落在**登录页**：手机上没有管理令牌，等于死链。运维告警的链接应改为：卡片正文自带足够信息（现在已基本做到）+ 链接指向免登录只读状态页，或带 10 分钟一次性令牌的 magic link；`base_url` 若填办公室内网地址更会全员死链（现在填的是公网域名，正确）。
3. katie 走 SSH 隧道到办公室实例：**每次 zhiliao 重启就是一个 502 窗**（今天 05:23:08 nginx error.log 记了一次 `upstream prematurely closed`；昨天到今天重启了 6 次）。隧道应由 autossh 独立守护、不随实例重启断开；或告警链接不依赖办公室实例。

## 二、AI 回复「重复」和「太笨」是不是兜底回复和网络波动？

**结论：绝大多数不是。** 兜底句早已移除、系统话术兜底在他机器上全部停用；网络超时的后果是「这一轮不回」，不是「回得笨」。「重复」有四种各不相同的机制，「太笨」有六种，都在提示词 / 记忆 / 目标引擎 / 守卫层，已分别进了 O / P / Q 批。

### 2.1 兜底回复：现在的产品里几乎不存在「罐头兜底」

- `src/ai/ai_client.py` L2466 `_fallback_reply`：**2026-08-15 起罐头占位句已移除**，「全链失败（主链 / 备用池 / 本地兜底都没出话）→ 返回 None = 本轮不回复」（运营裁决「可以不回复，不能乱回复」；8/13 那次 173 宕机导致三平台批量罐头刷屏后改的）。
- 知识库「系统话术 · 直接」（全局兜底 / 问候 / 闲聊 / 投诉处理 / 测试回复）：skuio 机器 1.0.77 / 1.0.78 逐条核对**全部已停用、用 0 次**（32PTMK / 22KVXF）；GXP 支付话术 1.0.77 已清。
- 人审缓冲话术「稍等我看看哈~」（`_maybe_holding_after_enrich`，仅全自动会话落到 L3 需人审时）：3 小时零次（E8CYS9）。
- 人设补全失败的「兜底放行」（`autodraft_helpers.py` L797）只是把未补全的稿放进**人审**，不自动发。
- 所以报告里那些「太笨」的句子（「I hear you… Take care」「better get back to work」「here's that view I promised you」「Saturday noon sounds lovely」）**都是模型真生成的**，不是兜底模板。

### 2.2 网络波动：真实存在，但后果是沉默

- 内测机的 AI 生成走官网托管网关 `https://bd2026.cc/api/ai/v1/chat/completions`（`src/ai/hosted_gateway.py`：桌面端不配云 Key，向官网换设备令牌；真 Key 只在官网进程）。VPS nginx 近两天该接口约 **3300 次调用，200 约 97.6%**；**499（客户端等不到响应先断开）约 78 次 ≈ 2.4%**，5xx 7 次全部在 09-08 19h（R78 官网部署窗 19:23–19:45）。
- 客户端 `ai.timeout=30` 秒（`config.desktop.min.yaml`）、`max_retries=0`：生成超过 30 秒即放弃 → 降级链「重试 → 备用池 → 本地兜底 → None」——干净安装没有备用 Key、本地兜底是内网地址打不通 → **None = 这一轮不回**。客户看到的是「AI 没回」，不是「回得笨」。
- 超时集中在 09-08 15h（19/474 ≈ 4%）和 **23h–00h（23/520 ≈ 4.4%，正是 23:16 升到 1.0.78 之后）**：1.0.78 把系统提示词从 1868 字换成 3940 字、加了目标注入 / 引用 / 拟人节奏，prompt 更长 → DeepSeek 峰时更慢 → 更多 30 秒超时。
- 我方 zhiliao 实例的「AI 启动探针：云端连接测试失败」（09-08 18:13、09-09 05:23）是我们自己实例的云端 Key 探针，不影响内测机（他们走官网网关）。

### 2.3 「重复」——四种机制，都不是网络

| 现象 | 机制 | 位置 / 去向 |
|---|---|---|
| 同一问题问到第 20 次（K24YJ2 / AEMAMJ） | 目标引擎只判「问了没」不判「知道没」，抽取关着槽位永空，missed 无界重试 | `goals/service.py` `decide_probe_target` → **Q-1** |
| 采用草稿发出后同一草稿又显示（CV4E22 / RU89S6） | 发送没把草稿置 consumed，面板重渲染旧稿；**不是重发** | `unified_inbox_send_routes` → **Q-10** |
| 第二句照片文案与第一句相近仍放行（6SRA2B `near_duplicate 跨轮相近放行`） | 近重复守卫只比对文本相似度，不看「本轮有没有图」 | `autosend_helpers` → **P-3 / Q-6** |
| 客户连发几条、AI 各回一条同义双发（FW78ZP） | 每条入站各自起草 | `inbound_merge` 8–15s 合并，**1.0.78 已修**（9NWYRW 已验） |
| 值守回执 12 条幻影行（32PTMK） | 我们的值守工具在 502 假失败上重试，send 路由失败仍写 out 行 | **P-5 已修**，随 1.0.79 |

### 2.4 「太笨」——六种机制

| 现象 | 机制 | 去向 |
|---|---|---|
| 客服腔（I hear you / Take care / 我的助理会联系您） | 陪伴人设跑在 1868 字销售 / 客服底稿上 | O-1 C，**1.0.78 已换 3940 字私人聊天底稿**（口吻待实聊验） |
| 忘事、否认有女儿、再问一遍 | 记忆抽取白名单空（1.0.78 已修）、画像 AI 抽取关（`profile_llm`）、人工出站不入记忆（1.0.78 已修） | **Q-5** |
| 纯接话、无话就退场 | 没挂目标的会话零推进意图；软注入永远让位；`proactive_topic` 关 | **Q-8** |
| 编造（徒步路线 / 被工作埋了 / 加载慢再发一次） | 无事实锚点校验；文字与发图两套决策 | P-1 B `claim_guard`、P-3 / **Q-6** |
| 被质问后「自责 + 再承诺」；答应见面 | 模型对现实动作无可行性概念，无政策 | **Q-2** |
| 中文直投外国客户（8DVDVC） | 翻译链 `target_lang_mismatch` 校验失败后放行原文 | M-1，**1.0.76 已修** |

### 2.5 网络与兜底真正该改的四件小事（建议并入 Q-4 或另立 Q-14）

1. `ai.timeout` 30 → 60 秒 + 1 次重试（或流式），并把 prompt 预算做上限（系统提示 + 注入 + few-shot 合计 token 上限，超了先裁 few-shot）。
2. 超时 / 失败**对坐席可见**：会话里一条灰标「AI 本轮未生成（超时 / 网关不可达）」+ 日志 `[ai] fail reason=timeout latency=…`，不再无声。
3. 官网网关记录耗时 p50 / p95、按模型；慢于阈值自动切备用 Key / 模型；官网部署改零停机（蓝绿或先起新进程再切）。
4. katie 三件：80 → 301；隧道 autossh 独立守护；告警链接免登录只读页或 magic link。
