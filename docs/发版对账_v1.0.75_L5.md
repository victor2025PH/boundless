## 1. A —— 出厂默认进基础配置（D-L1 半边）

### 1.1 为什么单改 `config/config.yaml` 到不了客户机（改前核实的机制链）

`src/utils/config_manager.py`：
- 桌面态（`AITR_DESKTOP_MODE=1`）首启 `_ensure_seeded` 把 **`config.desktop.min.yaml`**（不是 `config.yaml`、不是 example）拷成用户的 `config.yaml`（L226–250）；
- `load()` → `_merge_overlay`（`config.local.yaml`）→ **`_ensure_baseline`**（`feature_registry.baseline_patch`：A 类键在合并视图里**缺失**才补，写进 overlay；显式 true/false 都尊重）→ `_ensure_deploy_profile`（`cloud_light.yaml` **只在本次全新播种**时套）；
- `_ensure_seeded_extras`：只有 `resources/seed-data` 存在（smart 包）才把 `config.local.internal.yaml` 播进 overlay。

所以 D1/D7 此前写在 `cloud_light.yaml`（只惠及全新安装）和 `config.desktop.internal.yaml`（只惠及 smart 包）里，**两台内测机 = clean 包 + 升级安装，两条路都不经过** → 1.0.74 启动 `goals.sprint.enabled=False`（QF3A66）、危机留痕关（C6EFRS）。仓库 `config/config.yaml` **不在 git 里**（本机私有），只影响开发态。

**结论**：能到存量 clean 升级机的唯一无代码载体 = `feature_registry` A 类基线（指令里「`_ensure_baseline` 三态语义」指的就是它）。

## 2. B —— 内测渠道（D-L1 另半边）：**B1 独立渠道**

### 2.1 设计（为什么是「烘进包」而不是壳按 flavor 选 feed）

electron-updater `generic` provider 运行时只认随包 `resources/app-update.yml`（electron-builder 由 `publish` 配置生成）。把 `publish.channel=latest-internal` + `publish.url=https://bd2026.cc/downloads/internal/` 只加给 smart 构建：
- electron-builder 在 Windows 上生成 **`latest-internal.yml`**（不再生成 `latest.yml`）；装出来的 app 查 `…/downloads/internal/latest-internal.yml`；
- 装过一次 channel 包的机器永远跟内测渠道（每个后续 smart 包都带同样的 app-update.yml），装 clean 包的机器只跟对外渠道；**零壳代码、零坐席机配置**，`main.js` 未动；
- 两种包 exe 同名（`ChatX-Setup-<v>.exe`）→ 用 `internal/` 子目录隔离；Next.js `public/downloads/` 递归静态服务、`/dl/<path>` 路由与 R2 桶同布局，托管层零改动（已验证 `/downloads/internal/…` 与 `/dl/downloads/internal/…` 均通，见 §3）。
- 已核实 electron-builder 24.13.3 `mergePublish`：CLI `--config.publish.*` 会 `Object.assign` 到 package.json `publish[0]` 上（不会整段替换）。**踩坑**：多个 `-c.x=y` 短旗标 yargs 解析错误（第三个被当成配置文件路径），必须用长形式 `--config.x.y=z`。
