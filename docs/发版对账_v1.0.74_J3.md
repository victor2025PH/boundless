## A 真机定层结论（视频对象的真实路径）

**结论：4 分钟就 404 的不是保留期，是 Letter Sealing（e2ee-next）媒体的对象定位 + 加密两层都缺。**

## C 真机三档实测（#169，2026-09-05 05:1x–05:4x，117 号 → 自己的 Keep memo）

文件：ffmpeg testsrc2 1280x720 CBR 8Mbps + AAC 64k（`%TEMP%\line169\line169_{30,60,100}mb.mp4`），发送走生产 `send_line_media`（`--max-mb 120` 只放开 worker 局部上限以探真上限）。

| 源文件 | 结果 | 上传耗时 | 服务端转码后（回读 `object_info`） | 落盘 magic |
|---|---|---|---|---|
| 30.3 MB | delivered `630365460638466083` | 18.5s（修前）/ ~20s | `encodeStatus: succ`，8.4 MB | `ftyp` OK |
| 59.8 MB | **修前**：`obs_upload_failed`——`('Connection aborted.', TimeoutError('The write operation timed out'))` ×3 重试，91.2s 后失败；**修后**：delivered `630365523116818586` | 40.2s | succ，16.6 MB | `ftyp` OK |
| 98.9 MB | delivered `630365612505825383` | 60.5s | succ，27.5 MB | `ftyp` OK |

- 结论：LINE OBS 对 ~100MB 视频**不拒**（官方客户端上限 200MB），三档全部稳定通过 → 内建 `line: 100`。60MB 档修前失败的根因**不是服务端上限**，是 okline `LineConfig.timeout=30s` 是 socket 级写超时（`ObsClient.upload_message_object` 单 POST 整体、不接 timeout 形参）——坐席机上行 ~1.5MB/s 下 60MB 写不完 30s；`max_retries=2` 让整条链 91s 才报错。修法＝上传期临时把 transport 超时按体积放宽（30s + size/256KB/s，60MB→270s、100MB→430s、封顶 900s），退出恢复原值；receiver 长轮询自带显式超时不受影响。
- **入站侧发现（不在 #169 范围，未改）**：LINE 服务端会把视频转码再分发，收件人拿到的是转码件（100MB 源 → 27.5 MB）。我们 `DEFAULT_INBOUND_MAX_BYTES` 仍是 20MB，收 skuio/钧机发来的长视频时 ≥20MB 的转码件会 `too_large_actual` 拒下（本次回读 100MB 档首轮即撞此拒绝，加 `--max-mb 120` 后才拿到 magic）。建议 J-4 或后续评估把入站缺省提到 32~40MB（`platform_login.line.media.inbound_max_bytes` 可现场配）。
- 前端：`unified_inbox.html::_mediaCapMb` 已消费 `send-caps.media_max_mb`（同源），LINE 会话下自动从 25 变 100，**零模板改动**（J-4 热区未碰）。

**给 J-6 的线索**（本条不改）：
1. `services/whatsapp-baileys/close-policy.js::decideCloseAction` 只把 `401 loggedOut` 当终态；`403 forbidden`（风控封）与 428 一样走 `reconnect` → 曾配对账号（accountId 非空）被封后**永久 6 次/15min 循环**，日志被它刷满、真问题被淹。建议 403 也判终态（`postStatus("forbidden")` 给坐席「账号被 WhatsApp 限制，需换号/申诉」），或至少连续 N 轮 403 后停止慢重试。
2. `408 ENOTFOUND` 属 DNS：退避重连本身对；可在 close 日志里对 `ENOTFOUND` 单独计数并在 `/health` 暴露，让 ops 卡分得清「网络断」还是「被封」——现在两者都叫「connection closed unexpectedly」。
3. Bad MAC 已有 app-state resync 自愈；要确认的是 resync 后同一对端是否还刷（报告尾每份 5–6 次、跨 3 小时都在，疑似 resync 没修好该对端会话，可能需要删该对端 session 文件让 libsignal 重建）。
