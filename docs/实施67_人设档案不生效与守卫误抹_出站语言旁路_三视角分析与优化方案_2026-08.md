## 第一部分：代码级根因实锤（先于视角分析，全部读码验证）

### 1.1 B75「人设档案全程不进对话」——根因＝交付档 compact 档位静默丢弃 70% 档案字段

**确定性证据链**（全部读码核实，非推测）：

1. 客户包交付档 `config/config.desktop.internal.yaml:369` = `persona_block_detail: compact`
   （两位测试者 skuio/钧机的 internal flavor 世代都在此档）。
2. `persona_manager._format_persona_compact`（compact 编译器）只输出：
   名字/role/身份硬锁/年龄/性别/禁忌短语/emoji 档/回复长度/deny_ai/避谈话题/
   退役设定/通话/发图边界/联系方式约束——**共约 1/3 的字段面**。
3. 工作室人设编辑器（personas.html `pe-pf-*` 表单）可填 20+ 档案字段，其中
   **背景故事（background）/ 家人含父母职业（context.family）/ 英文名（names.english）/
   西文全名 / 爱好 / 喜欢·不喜欢·观点（tastes）/ 专属记忆 / 外貌 / 作息 / 口头禅 /
   幽默感 / 性情**——全部只在 `_format_persona_instructions`（full 档）编译，
   **compact 档一概静默丢弃**。
4. 用户填的「职业/父母职业」落在 background 与 context.family（`_FAMILY_LABELS`
   含 father/mother 职业标签），「英文名」落 names.english——三者全在被丢弃面。
   ⇒「AI 即兴自编商业咨询」「父母职业全错」「英文名不知道」完全吻合。

**为什么一直没被发现**：117 引擎内部部署 `config.yaml=full`（zhiliao overlay 虽为
compact，但绑定的出厂人设靠 A 线长期调教掩盖）；客户包=internal flavor=compact
+ 用户自建人设——两个条件恰好在公开发行后首次组合，1.0.51+ 自建人设用户批量踩中。

**排查点①（派单点名）的结论**：`_inject_known_profile` 硬注入块与人设块**无预算
冲突**——主链（云端/hosted 网关）在引擎侧无任何截断机制；`_trim_messages_to_budget`
只挂本地 fallback 链且从 system **尾部**砍（头部人设优先保留）。硬注入块在
context prompt（user 段），与 system 段人设块是并集不是挤占。**真凶不是昨夜记忆
三件套，是 compact 档位与自建档案的组合盲区**（0823 夜批只是让用户开始密集考题
验证，暴露了存在已久的丢弃）。

### 1.2 B74「叫我。」名字被抹——真凶＝sanitize_self_name 的 hard 档② + inline 抹名兜底（不是呼格守卫）

**派单根因嫌疑修正**：`strip_vocative_self_name` 的两个呼格模式都要求**逗号形态**
（句尾「…, Name」/ 句首「Name, …」），「叫我X」无逗号根本不命中呼格——值守按行为
反推的嫌疑对象错了。真实机制（读码坐实）：

1. `skill_manager._enforce_persona_consistency` 里 `sanitize_self_name` 在呼格守卫
   **之前**跑；其 hard 档②＝「我叫/叫我/我的名字是 + **非白名单** CJK 名」→ 剥除。
2. 剥除策略：先按句剥；**整段剥光时走 inline 抹名兜底**（`re.sub` 把名字串抹空）。
   「叫我浩然，朋友都这么喊我。」是单句（逗号不切句）→ 按句剥=剥光 → inline 抹名
   → **「叫我，朋友都这么喊我。」**——与 `_352` 实录逐字吻合。
3. 名字为何不在白名单：白名单=守卫处 `get_persona(chat_id, account_persona_id)`
   解析的人设 + 全局 ai_name。当会话人设解析与生成时不一致（绑定断链/试聊链不带
   绑定/历史学名），AI 顺对话历史自报的名字就成了「陌生 CJK 名」→ 必杀。
   **B74 是 B75 的下游症状**：档案/绑定断链让白名单失去人设名，守卫把正当自报
   家门当身份泄漏砍。
4. 设计缺陷独立成立：**自介句里剥名字必产残句**（「叫我。」），比误放行穿帮
   100 倍——inline 抹名兜底对自介引导句是反向优化。

### 1.3 B67 出站语言旁路——根因＝「发→X」设置只存前端 localStorage，自动链根本看不见

**读码坐实的三层断链**：

1. 收件箱「发→英」（`xlate-out` 控件）的持久化=`_persistXlatePrefs()` **只写
   localStorage**（unified_inbox.html:18115）；手动发送时前端把值放进 send 请求体
   `target_lang` ——**这个设置从未到达服务端**。
2. A 线（TG 原生即时应答）：发送前**无出站翻译闸**——语言正确性完全依赖生成层
   lang_policy 按客户语言生成；lang_policy 判定翻车（短消息/证据污染）时无兜底。
   `_337` 实锤「即时应答三条中文回英文客户」即此。
3. B 线 autosend / proactive 的 `translate_outbound_text` 由**全局配置**
   `inbox.l2_autosend.translate.enabled` 控制，与会话级「发→X」是互不知晓的两套系统。

⇒ 用户视角「我开了发→英」≠ 系统视角「只有手动发送译」。这是**意图存储位置错误**
（应为服务端会话级），不只是某条链漏接。

## 第二部分：三视角深度分析

### 视角一：用户（付费客户/内测测试者）

**B75 是信任级事故，不是功能 bug。**用户完成了产品要求的全部动作（建人设→填档案
→保存→应用→甚至重启 3 次自证），系统每一步都回「成功」，然后 AI 当着他的面即兴
编造。用户直问「核心逻辑是否被改」——这句话的含义是**他已经开始怀疑产品在骗他**。
比「功能坏了」严重一个量级：功能坏了用户等修，被骗了用户走人。

用户的朴素契约：**「保存成功」=「AI 从此知道」**。系统真实契约：「保存成功=数据
落库；进不进对话取决于一个用户永远看不见的配置档位」。这个落差没有任何界面提示。
修复必须回到朴素契约：**填了就算数；确实不进对话的字段，编辑器上明说**。

B74 在用户眼里与 B75 是同一件事（「连名字都说不出来」）——他不知道这是两个机制，
也不该需要知道。B67 同理：「发→英」开着=所有发出去的都是英文，没有「手动才译、
AI 自动不译」的心智模型。**用户以开关的字面语义为契约，系统按实现边界执行**——
三个案子是同一类病：意图声明与执行面脱节。

B73/B70 的共性：**系统状态变化时用户没有出口**。「已安全拦下」不给原因不给按钮、
PIN 输了之后永远「等下次」——用户不怕出问题，怕的是出了问题只能干等。

### 视角二：开发工程师

**根因分层**：三个 P1 案子共享同一个架构病——**「配置/意图」与「执行」之间缺
契约门禁**：
- B75：编辑器字段集与 prompt 编译面之间没有「字段防丢弃」契约（编辑器加字段、
  编译器不消费=静默丢）；档位（full/compact）语义与绑定 tier（用户显式意志 vs
  域默认）没有联动。
- B74：守卫白名单与生成时 prompt 锁定名之间没有同源契约（各自解析、时序分叉）；
  「自介句剥名必残句」缺形态判断。
- B67：会话级意图（发→X）存储位置错误（前端 localStorage），服务端自动链在
  意图可见性之外。

**修法原则**（与仓内既有哲学对齐）：
1. **单一事实源**：出站目标语言=会话级服务端持久化，所有出站路径读同一处；
   守卫白名单补「生成时 resolved name」直传，消解析分叉。
2. **契约门禁**：编辑器可填字段 ⊆ full 编译面（AST/schema 级测试钉死，字段加了
   没编译=CI 红）；守卫金标双向（_352 自介必放行 + _236 呼格必拦）。
3. **宁可漏拦不误伤**（persona_guard 全模块既有哲学的回归）：自介句无法安全剥离
   时保留原文——错放一个陌生名的伤害 < 「叫我。」残句的必然穿帮。
4. **不加新开关**：档位跟随 tier 是语义修复不是新特性；「发→X」升服务端是存储
   位置修复。全部走既有配置/存储基建。

**token 成本权衡**（compact 存在的理由）：full 档全量编译对**出厂人设**（背景故事
1500 字级）每轮多耗约 1-2k token。但**用户显式绑定人设的会话**本来就是产品核心
场景，档案就是拿来用的；未绑定的域默认会话（生产大多数）维持 compact 不动。
即：**成本只加在用户明确要求人格化的会话上**——这正是该花的地方。

### 视角三：市场经理

**自建人设是付费转化的第一卖点**（人设池/自定义人格/克隆声三件套）。B75 的市场
伤害路径：内测用户在群里晒「填了档案 AI 不认」→ 潜在买家结论「自定义是假的」→
转化漏斗最贵的一环（已装包待付费）漏水。**用户那句「核心逻辑是否被改」如果不被
正面回应，会变成群里的定性结论。**

修复的市场化表达（修完值守可直接用）：
- 「**档案即人格：填了就算数**」——绑定人设的会话档案全量生效，工作室验收考题
  可自证（问职业答职业、问父母答父母、问英文名答英文名）。
- 「**发→英=全链路英文**」——手动/AI 即时/AI 主动三路出站同一语言闸。
- B73 横幅升级后的表达：「宁可不回也不发错话，**且每次拦下都告诉你为什么、
  在哪放行**」——把无兜底纪律从「AI 坏了」的观感扭成可信赖卖点。

**验收即营销素材**：本批每项修复都设计成「用户可自验」的形态（考题/开关/横幅
点击），值守回访时直接给验证脚本，让报障用户变成修复见证人——内测期口碑管理
比新功能更值钱。

## 第三部分：优化方案（逐项：修法/涉改/验收/门禁）

### P1-11a（B75 主修）：档案进对话——档位跟随绑定 tier + 字段防丢弃契约

**修法**：
1. `persona_manager.format_persona_block` 增加 tier 感知：解析 tier ∈
   {conv_override, chat_binding, account_profile}（用户显式绑定）时，
   **detail=compact 自动升 full**（`none` 尊重不动——那是显式全关）。
   域/默认 tier 维持配置档位。实现在 format_persona_block 单点（消费方零改动）。
2. **compact 档补齐「小而硬的事实字段」**（即使未升 full 也不该丢的）：英文名/
   西文名（names.*，被问外文名答不上=穿帮面）——一行紧凑注入。
   背景故事/记忆/好恶等长文维持 full-only（compact 的省 token 语义保留）。
3. **字段防丢弃契约门禁**（新测试 `tests/test_persona_profile_field_coverage.py`）：
   工作室编辑器落库的档案键清单（name/names.*/age/gender/background/appearance/
   context.family/context.hobbies/context.specific_memories/context.emotional_triggers/
   tastes.*/personality.*/speaking.*/boundaries.*）逐键断言「full 编译输出包含该键
   内容」——以后编辑器加字段没接编译=CI 红。
4. 交付档修正：`config.desktop.internal.yaml` 的 `persona_block_detail` 保持
   compact（tier 升档后自建人设已全量生效；域默认会话继续省 token），**加注释
   说明升档语义**防后人误判。

**验收**：本地复现派单场景——新建自定义人设（张浩然：职业/父母职业/英文名）→
绑会话 → 逐项问档案题 → 全对。pytest 门禁全绿。

### P1-11b（B74）：自报姓名守卫加固——自介句禁残剥 + 白名单同源

**修法**（`persona_guard.py` + `skill_manager.py`）：
1. `sanitize_self_name` 剥除策略修正：hard 命中的名字若处于**自介引导语境**
   （我叫/叫我/我的名字是/我是/call me/I'm/my name is 紧邻其前）→ 该句**禁用
   inline 抹名**（残句「叫我。」必穿帮）；多句时整句剥仍可；剥光→保留原文
   （宁可漏拦，与模块既有哲学一致）。
2. 白名单同源：`_enforce_persona_consistency` 增加 `resolved_name` 形参，A/B 两链
   把生成时 `context["_resolved_persona_name"]`（prompt 身份硬锁用的名字）直传进
   白名单 extra——**AI 按 prompt 指令自报的名字绝不该被抹**（消「守卫解析 vs
   生成解析」时序分叉）。
3. 金标：`_352`（「叫我X，朋友都这么喊我」X∉白名单 → 原文保留不残剥；X∈白名单
   → 不命中）+ B42 `_236`（"you're not that old, Steven" 呼格必拦）回归不回退
   + David Lin 事故金标（借对方名缝合必拦）不回退。

### P1-8（B67）：出站语言统一闸——「发→X」升服务端会话级 + 全路径守卫

**修法**：
1. **服务端持久化**：新端点 `GET/POST /api/unified-inbox/conv-xlate-out`
   （会话三元组 → outbound_lang；存 conversations meta，复用既有 meta 基建）。
   前端 `_persistXlatePrefs` 在写 localStorage 同时 best-effort POST（特性探测
   fail-soft，与 agent-lang 同款模式；旧后端 404 静默=行为不变）。
2. **统一出站语言守卫** `src/inbox/outbound_lang_guard.py`（纯函数核心）：
   `resolve_outbound_target(conv_meta, conv_language, cfg)`（优先级：会话级发→X
   显式设置 > l2_autosend.translate 全局闸的客户语言语义）+
   `needs_language_fix(text, target)`（复用 `cjk_substantial`/`lang_is_cjk` 口径：
   文本实质 CJK 且目标非 CJK → 需处理）。
3. **接线**（施工中修订）：目标解析升级做在 `translate_outbound_text` 单点——
   B 线 autosend 投递、proactive/care deferred 共用该函数**自动获益**；客户包的
   「即时应答」走 B 线 autosend（l2_autosend.deliver=true + auto_ai），`_337` 在
   覆盖面内。**A 线刻意不另接**：A 线由生成层 lang_policy 按客户语言生成管辖，
   且客户包事故链不经 A 线；翻译不可用 → 沿用既有 HOLD 语义
   （delivery_block translate 域，绝不中文裸发）。
4. **流水实证**：装载后调 `_328`（19:49 三条）/`_337` 会话的生成投递记录，确认
   旁路点与修后行为。

**验收**：「发→英」开启的英文会话——手动发中文→出英文；AI 即时应答→英文；
AI 主动跟进→英文。普通中文会话回归不回退（无设置+客户中文=不动）。

### P1-9（B70）：Messenger E2EE PIN 闭环（边车+壳，随 1.0.55 包）

**修法**（services/messenger-web/server.js + relay 前端）：
1. **托管即重放**：PIN 保存端点在落 sidecar 后**立即触发**既有 e2ee 自愈函数

2. **浮层避让**：relay「登录成功」浮层渲染前查分类器当前段——checkpoint/e2ee_pin
   段不渲染成功浮层（或渲染为可关闭小条，默认避让）。
3. **文案对齐**：「发送不受影响」→ 按实况分流（PIN 未恢复期间发送会失败排队，
   恢复后自动继续）。zh+en。

**验收**：skuio 机 Roselyn 账号走通 PIN 恢复、发送恢复（装包回访）。

### P1-10（B73）：delivblock 横幅可诊断化（引擎+前端，热更）

**修法**：
1. 横幅数据源（既有轮询接口的 delivery_block 段）增加 `top_reason`（by_reason
