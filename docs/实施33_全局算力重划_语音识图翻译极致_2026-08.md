# 实施33 v2：全局算力重划——无备机 · 无兜底 · 失败必弹窗（2026-08-17 03:49 老板拍板版）

> v1（03:36）的「二线/备机/回落链」全部作废。老板 03:49 拍板三原则：
> ① 不要备机，所有算力全部投入把功能做到极致；
> ② 不要兜底，宁愿不回消息也不发替代品——兜底掩盖错误、制造聊天事故；
> ③ 出问题必须弹窗提示，方便维护。
> 依据：8/15-8/17 连环事故（canned 句、垫场句、旧识图串台、fish 冒充 index、
> CPU torch 假活、全天语音断档零告警）——每一起的放大器都是某层兜底。

## 〇、总则：单轨制

每个功能只有**一条指定链路、一个实例**。链路失败＝**不发消息** + 弹窗 + 待办入工作台。
没有第二音源、第二引擎、第二端点、备用 key、垫场话术。

**「兜底」的判定线（防止执行走样）**：

- ❌ **禁止＝静默替代品**：换一个声音顶班、换一个引擎冒充、换 canned/垫场句、
  翻译失败发原文、识图失败装作没有图接着聊、云 key 挂了换池内备 key。
- ✅ **保留＝诚实行为**：AI 亲口说「这会儿发不了照片」（真话不是替代品）；
  口语化改写失败就用**原稿**直念（原稿是真内容，跳过的是可选润色——但必须计数上报）；
  watchdog 自动重启**服务本身**（这是修机器不是换内容，且每次动作必须弹窗留痕）。
- 每个「保留」项都要可观测：跳过润色/自愈动作全部进计数 + 告警面，不许无声。

## 一、新全局算力规则（十条，v2）

1. **聊天大脑＝云端 DeepSeek，单 key 单链**。key_pool 备用池、173 本地回落、
   canned 全部拆除。云端挂＝不回消息 + 弹窗（熔断只用于快速失败，不用于换路）。
2. **一功能一实例**：TTS 质量轨只在 176 index；ASR 只在 140；翻译只在 173 FP8；
   识图只在 173 30B-A3B；嵌入只在 140 bge-m3。跨机重复部署一律拆除。
3. **一人设一音色一引擎**：聊天链合成**显式钉 tts_engine**（禁止 hub prefer 隐式路由
   ——8/13 fish 冒充事故的机制化收口）；旧音色预渲染库存停用；hub 内部的
   cosy/xtts 回退层对我方调用关闭。合成失败＝该回复转工作台待发 + 弹窗，
   不自动改发文字。
4. **翻译失败不发原文**：出站翻译/图片翻译任何一环失败＝拦下不发 + 弹窗
   （现行「异常回落发原文」逻辑拆除）。
5. **识图失败不装懂**：图片消息识图失败＝不自动回复该消息（防「看不见图硬聊」
   的串台事故复发）+ 弹窗；坐席可在工作台看原图手工处理。
6. **显存预算 ≤ 卡容量 − 余量**（32G 卡留 5G、12G 卡留 2.5G）；引擎装载串行。
7. **gpu 服务启动自证 CUDA**，自证失败拒绝上线 + 弹窗（CPU torch 事故收口）。
8. **真活探针制**：每个 GPU 服务 5 分钟一次「真干活」探针（真合成/真识图/真翻译/
   真转写），连续 2 次失败＝弹窗 + tg-ops；health 200 不构成「活着」。
9. **弹窗三端**：117 运维桌面 Windows 弹窗（host_alert 已有该能力）+ tg-ops webhook
   + 工作台红条（带会话直链）；每域 10 分钟去抖，恢复也弹绿窗。
10. **watchdog 只修服务不换内容**：自动重启保留（含新增的「真活探针失败→重启引擎」），
    每次动作必弹窗；修不好就保持故障态让人来，绝不降级出货。

## 三、失败面与弹窗设计

| 故障 | 用户侧表现 | 系统动作 |
|---|---|---|
| 云端聊天挂 | 不回消息 | 弹窗「主链断」+ 回复内容不生成；恢复自动续答（轮询兜底重拾机制保留——它是重试不是替代品） |
| TTS 挂/慢超 30s | 不发语音也不发替代文字 | 回复转工作台「待发」+ 弹窗；修好后坐席一键发出 |
| ASR 挂 | 该语音不被自动回复 | 镜像 [语音] 行 + 原音归档可人工听 + 弹窗 |
| 翻译挂 | 不发出站消息 | 拦截 + 待发队列 + 弹窗 |
| 识图挂 | 图片消息不自动回 | 工作台见原图 + 弹窗 |
| 嵌入挂（语义闸门失明） | 依赖闸门的链路拦下 | 弹窗（检验器也是链路的一环，检验不了＝不出货） |
| CUDA 自证失败 | 服务拒绝上线 | 弹窗 + 引擎不注册 |

弹窗实现：复用 `host_alert.py`（Windows 弹窗 + EventBus + webhook 三出口已建），
新增事件类 `delivery_blocked`（带 platform/会话/域/原因），10 分钟去抖 + 恢复绿窗；
工作台红条给会话直链。**未送出的回复一律落工作台待发队列**——内容不丢，
修好即人工放行，这是「宁可不回」与「不丢工作成果」的兼容点。

## 四、三视角复核（v2 变化）

- **工程师**：删掉的代码比新写的多——回落链、双活探测、冷却降权、池排序整族退役；
  系统从「哪条路通走哪条」变成「一条路 + 一盏灯」，故障定位从跨机排查变成看弹窗。
  新增工作量集中在：拦截点改造（发→拦+入队+告警，约 6 处）、真活探针（4 域）、
  delivery_blocked 事件与弹窗去抖。风险=单点故障期间该功能全停——这正是老板要的
  （可见性换覆盖率），MTTR 靠弹窗+watchdog 自愈压短。
- **市场**：卖点从「永不掉线」换成「**出手必是最高标准**」——音色永不换人、
  译文要么对要么不出、识图要么真懂要么不装懂。对陪伴/跨境客服客群，
  「一次穿帮」的伤害远大于「晚回十分钟」，这个取舍成立。
- **用户**：不再收到垫场句、换声语音、看不懂的原文、答非所问的串台回复；
  代价是故障窗内 AI 静默（坐席人工可顶——工作台待发队列让人接管有抓手）。
